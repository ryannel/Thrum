# Thrum build plan

Updated 4 November 2026. This is the current status page. Git history retains prior detailed plans and experiments. [C4 contracts](design/CONTRACTS.md) own shared invariants; [the maturity ledger](design/maturity.json) separates implementation, correctness, visuals and device measurements.

## Goal

Thrum is a modern engine that is exceptionally fast because it uses the hardware each device actually has. A capability registry selects a frame recipe per GPU family (Apple tile, Android tile, desktop high, portable), accelerated CPU, IO and network paths, and optional providers (reconstruction, ray tracing, frame interpolation, ML) through one frame contract. A quality governor holds frame, thermal and latency budgets. Portable runs everywhere as the reference and fallback; dedicated paths are promoted only by a measured win on their own hardware. [Hardware-native decision](design/decisions/HARDWARE-NATIVE-ENGINE.md).

## V1 milestone

One reusable engine powers one test game (`examples/v1-game`) on macOS and a physical iPhone, qualified against their budgets. Chrome WebGPU runs the same game at a declared reduced tier for a smoke check, with no V1 frame budget. The game has 10,000 entities with 1,000–2,000 moving; registered game components and systems; serial and parallel execution; snapshot restore; cooked meshes and textures; dynamic camera, lights, clustered forward and cascaded shadows; GPU-driven culling with indirect draws; the Apple tile recipe with memoryless attachments and MetalFX reconstruction to native output resolution; EDR output; hot reload; a named CPU/GPU profiler; display-link interpolation and a quality governor. Then four peers run **the same game** over real QUIC transport on macOS and iPhone through a 100 ms RTT, 20 ms jitter, 2% loss conditioner, with prediction and reconciliation at no more than 64 kbit/s per client including transport overhead. The first game uses 60 fixed ticks/s; this is not an engine ceiling. WebTransport follows behind the same link trait after V1.

A gate passes only when the capability runs in this game on a named target, `./dev check` is green, the independent review finds no blocking defect, and the [ledger](design/maturity.json) records the actual evidence. Repository checks alone establish no visual, device or performance claim. `./dev check` is the landing gate; CI remains manual-only by the owner's 4 November decision.

- [x] **G1 — one identity and publication spine.** The world owns dense generation-checked slots and publishes one immutable complete page plus per-component dirty sets each tick. The V1 game renders the page; its optional ordered projection outbox copies the same page and reports gaps requiring a baseline. The short ring retains adjacent endpoints. Zero steady-tick allocations were observed after warmup, including actions; the native Metal path and two 600-frame window runs were measured, with pacing and V1 budgets still open. [G1 evidence](evidence/integration/G1-PUBLICATION-2026-11-04.md).
- [ ] **G2 — generic simulation.** Game-owned components, systems, rules, inputs and wire schema; engine-owned registered storage and enforced accesses. The 10k/100k mover/static comparison selected private hecs storage-order `PreparedQuery` for generic integration, with integrated profiling as a reopen gate. Add serial and Rayon executors with equal-result test, restore/replay for prediction, and move fixture content from engine crates into the game. [Decision](design/decisions/G2-STORAGE-SELECTION.md).
- [ ] **G3 — executing renderer.** Before implementation, review a design of at most two pages covering record closures, transient pool, derived load/store, culling, automatic timestamps, compute passes, 3D/cube/array textures, epoch-skipped and time-sliced passes. Implement mesh arena, material table, texture arrays and per-frame `ViewPacket`; move `FrameHost` to an engine crate. Run cooked content in the game. Build the capability registry, the portable and Apple tile recipes, frame-contract fields (jitter, motion vectors, reversed-Z Depth32Float, reactive mask, history reset), executor-derived memoryless/transient attachments, persisted pipeline caches and GPU frustum/occlusion culling with indirect draws. Meet the ray-tracing readiness constraints, support the sea and cloud consumers (compute-before-fragment, texture arrays with mips, 3D noise, ping-pong and wrapping histories, async-compute-eligible passes) and decide the shading library. The graph design gets an independent cross-module review.
- [ ] **G4 — presentation clock.** Drive presentation from the display link; interpolate local and remote entities; fold tone mapping into present with EDR/HDR output; reconstruct to native output resolution with MetalFX on Apple and own TAAU on portable; close the quality governor over GPU time, thermal state and missed presents. Measure input-to-photon latency and qualify visible game pacing on a named target.
- [ ] **G5 — content loop.** File content-addressed store with atomic manifest and stat cache; glTF meshlets via meshoptimizer and KTX2 (ASTC on iPhone, BC7 on desktop); BLAKE3 hashing and memory-mapped zero-copy products; watcher and barrier publication; dev cook server for browser and phone. Run edit-to-visible and save/restore through the game.
- [ ] **G6 — sessions and real transport.** `ServerSession` and `ClientSession` behind a link trait, one conditioner; Quinn on macOS and iPhone with GSO/GRO offload; QoS-classed network and simulation threads. WebTransport follows later as a web-tier adapter. Compact header with piggybacked ACKs, residual encoding, priority, byte budget and non-aborting recovery. Resume ACK/rebase/retry/reconnect/lane hardening here, over real transport.
- [ ] **G7 — four rendered peers.** Run and measure the same game on macOS and a physical iPhone under the specified conditioner, plus a Chrome reduced-tier smoke run. Record tick, encode, named GPU pass, bandwidth, frame pacing, latency, allocations, retained bytes, thermal state after ten minutes and visible quality separately, for the Apple tile recipe and for portable on the same device.

Hardware leads capability design. Every pass declares its required capabilities; the registry selects the recipe and prepares the portable fallback at pipeline closure, before the first draw. Stay on wgpu with native-only features and one isolated raw-backend module per backend for platform wins such as tile memory and MetalFX. A direct native backend requires measured evidence that the escape hatch dominates. The browser runs the portable recipe and never weakens a native recipe; designing to the lowest common denominator is a defect.

The game is an external engine consumer. It uses only public engine APIs; engine crates never depend on it and engine tests/benches use minimal private fixtures. Each gate reports game line count and engine-side references to game types, with a target of zero. No new standalone fixture binary lands on main. New dependencies require a reuse record and architecture registration. The game gets an unused-dependency and Wasm compile check.

## Current baseline and limits

- The fixed-step clock, checked identity/handle semantics, validate-then-apply edits, pipeline closure and temporal-history contract are retained.
- G1's 10k/1.5k-moving incremental tick plus page measured 76.16 µs median in isolation; the first full-copy page measured 119.5 µs and was replaced. Four world pages reserve 10,001,488 bytes on this 64-bit build; the optional warmed game projection outbox reserved 4,073,984 bytes. Two macOS Metal window runs showed tick CPU p50/p95 104.625/193.167 and 103.666/129.833 µs, with variable scene GPU and optional-view tails. These are diagnostics, not V1 budget qualification. [Evidence](evidence/integration/G1-PUBLICATION-2026-11-04.md).
- A private hecs backend and serial A1 simulation ran a 10k/1.5k local fixture at 51.83 µs median. The G2 split-archetype comparison measured hecs versus fixed SoA at 10k (2.42–2.50 vs 1.65 µs) and 100k (26.74–27.62 vs 19.08–19.24 µs). It selects hecs for the generic path; these isolated kernels do not qualify the whole-game 100k path. [Evidence](evidence/v1-workload/G2-STORAGE-COMPARISON-2026-11-04.md).
- The V1 diagnostic rendered 10k synthetic cubes with local lights and two synthetic cascades. Chrome WebGPU and macOS offscreen/window diagnostics exist; the scene still has no running cooked mesh/texture loop, and the graph is declarative. [Chrome evidence](evidence/render/V1-CHROME-WEBGPU-2026-11-04.md); 4 November independent review (`tmp/code-review-2026-11-04/THRUM-REVIEW.md`).
- Historical conditioned four-peer headless and test-only cook paths never fed the displayed game. The conditioned program is now retired from the active tree; cooked content remains a test-only path. No real transport or physical-iPhone game qualification exists.

## After V1: hardware track

Each item lands as an optional provider or recipe, promoted by measurement on named devices: Android tile (Adreno, Mali, ADPF); desktop high (NVIDIA, AMD, Intel) with visibility buffer, mesh shaders, async compute and Reflex/Anti-Lag; DLSS, FSR and XeSS reconstruction and frame generation; hardware ray query for shadows, AO and reflections with a radiance cache and denoising; VRS and rasterisation rate maps; tensor/neural-accelerator inference; MTLIO and DirectStorage readers.

## Decision and review gates

Use [engine-contributor](../.agents/skills/engine-contributor/SKILL.md) for every code change and [engine-architecture](../.agents/skills/engine-architecture/SKILL.md) for contract changes. Authority and saves refuse atomically; wire data is dropped/counted/repaired without aborting; presentation clamps and counts; authored content validates with tolerances. Every gate gets a read-only defect-first review, including cross-module identity, time, coordinate and engine/game seams. Keep evidence to one page per slice and bulk outputs out of Git. Commit only after `./dev check` is green; publish only with exact-push authorization.
