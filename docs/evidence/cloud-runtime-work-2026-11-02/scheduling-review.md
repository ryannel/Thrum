# Source-only preview scheduling review

2 November 2026. Bounded read-only delta review after checkpoint `b12fef6`, limited to source-only scheduling, observer labels and pause/reset consistency. No GPU run, motion inspection, performance certification or broader cloud acceptance.

## Sound structural changes

`WorldClock` remains outside render admission. At normal 1×, `sourceOnly` is false. At 16×/64×, a source-only graph advances every admitted fixed source step while omitting light, view and display passes between preview presentations; the source time, last submitted graph and last presentation graph are tracked separately. `uiDirty` and a final advance/pause flush normally request a current image. The source preflights weather-history availability before mutating its driver or q bookkeeping. A failed render cancels an active benchmark and attempts an aborted receipt, so a failed run is not silently reported as a normal 10-second result. The mask comparison now requires the ordinary play toggle to be paused. These are code-path observations, not proof that host presentation deadlines or visible motion pass.

## Consequential remaining issues

1. **Weather command buttons do not force a prompt preview.** `front` and `storm` handlers enqueue commands and update text, but do not set `uiDirty`. The storm handler's programmatic slider `.value` assignments do not dispatch DOM input/change events. At 16×/64×, the next source graphs can remain `sourceOnly` until the 50/200 ms preview interval expires, after the command has committed and materially changed q. This contradicts the receipt's claim that control edits request immediate presentation. Mark the command path dirty at the commit or handler, then verify a midlife front/storm command yields the next available presentation graph with the new source time even when the normal preview interval has not elapsed. A failed GPU deadline should remain explicit.
2. **“Displayed” and presentation rate are submission observations.** `Scene.lastPresentation` is assigned immediately after `g.submit`; `presentedFrames`, `presentationHz` and the HUD's `Displayed` time count submitted image graphs. Neither GPU completion nor an observed canvas display is established there. Rename them to submitted presentation graph/time/rate unless an actual display signal is captured. Retain requested/source/submitted/completed/displayed clocks separately in evidence, especially when the GPU queue stalls. The preview cadence is a maximum request policy, not an observed 5/20 Hz display guarantee.
3. **Accelerated GPU totals omit source-only graphs.** Timestamp sampling is disabled when `ui.sourceOnly`; the 10-second GPU sample list therefore observes only the less frequent presentation graphs. `sourceSteps` includes source-only updates, but `wholeP95`, `sourceP95` and similar fields cannot describe all accelerated GPU work or queue demand. Instrument source-only graphs separately or label these statistics as presentation-graph samples and leave aggregate accelerated GPU work unqualified. The normal 1× path is not affected by this omission.

## Smaller consistency checks

- `mask-tests` rejects `playing=true`, but allows `playing=false` while `advanceTarget` is still active. During its async GPU comparison, `busy` stops scene rendering while the deterministic advance can keep moving CPU weather. Require `advanceTarget===null` for a genuinely stationary world/source observation, or record the frozen source time and advancing world time explicitly.
- `Scene.reset` does not clear `lastPresentation`. Until the first new image graph, the HUD can pair the new optical epoch with the previous epoch's submitted image time. Clear or epoch-tag that field at reset; the existing `uiDirty` request then fills it with the first new image. Capture itself submits a fresh image under its own metadata.
- An aborted benchmark receipt is attempted asynchronously from `fail`; if that POST fails, `.catch(console.error)` reports to console but leaves no durable aborted record. Do not treat absence of a measurement file as a successful run. This is a bounded evidence limitation, not a source scheduling defect.
