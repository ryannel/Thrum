# Cloud programme: independent proof and done review

## Acceptance derived before reading the current cloud plan

The user's target is a beautiful modern cloud and atmospheric system whose behaviour remains convincing in an actual running scene. Five named families—Cu, Cb, Sc, St and Ci—must be seen growing, renewing and breaking up. A timed opacity fade, sprite swap or advected static texture does not by itself demonstrate those processes. Wind, weather, air, fog, illumination, cloud shadows, surface ambient response and independent reflections must respond coherently to shared physical causes. The evaluator must inspect actual images and motion at native 1× time and at an accelerated rate, including transitions; a numerical or still-frame pass cannot stand in for observed motion. The programme may replace substantial previous work when evidence calls for it.

Proof should progress from isolated risky couplings to a challenging full scene. Each proof needs a declared prerequisite state, exact visible setup and camera, controls, reference target, negative control, capture period and evidence artifact. A gate passes only if the intended behaviour is visible, its mechanism is distinguishable from a cheap substitute, interaction consequences are demonstrated, and its measurements are reported honestly. An absent browser/video observation is *unrun*, not passed.

At the specified 720p M2 WebGPU target, the eventual cloud workload must fit 5 ms GPU within a 16 ms whole-frame GPU budget and 512 MiB for the whole browser. Native 3/10 is unqualified in the commission, so the plan must identify what those numbers measure before using them as a quality or speed gate. Cost proof must include representative cloud/weather complexity and time evolution, not only a sparse still view. Intermediate stages need measured budgets or explicit cost predictions and a path to the final target; a scaled-down proof cannot claim full-scene viability.

Keep four independent statuses per stage: implemented; functional/contract proof; witnessed visual and motion quality; measured device cost. The acceptance bar belongs to the full experience and is not automatically satisfied by passing component tests. Failures should halt dependent promotion and revise the owning model or contract before adding more layers.

## Plan review

### Scope and verdict

I read `AGENTS.md`, the repo-local module-design/review/performance guidance, `docs/BUILD-PLAN.md`, `CLOUD-MIGRATION.md`, `CLOUD-CAPABILITIES.md`, the canonical `CLOUDS.md` scenario/cost sections, and the prior migration POC review/disposition. This is an independent *second battery of planning checks* in the limited sense that the opening criteria above were saved before the plan was read. I did not run a build, inspect a new GPU image or watch any retained video. Existing D1 review has already corrected the largest order error by placing the spatial P4a sentinel before Cb, full LUTs, production rendering and history; those corrections should stand.

**The queue is broadly practical if a POC is a bounded falsification exercise.** Its present wording can still turn P0/P3a/P3b into a general renderer and infrastructure campaign before the first visual result. More importantly, several boxes could be marked green from a report that contains the right *kinds* of evidence but misses the user's requested appearance, growth or complete cost. The amendments below tighten those decisions without expanding the required product scope.

**One governing completion rule:** use the existing separate statuses, but require every checked P stage to link a short signed proof packet with (a) exact source/build and immutable fixture, (b) executable launch/replay path, (c) reference and camera/exposure comparability limits, (d) the specific cue and observable rejection, (e) native images plus *what interval was actually watched continuously* at 1× and accelerated rate, where motion is relevant, (f) mechanism/consumer counterexample, (g) numeric/reference result, (h) actual measured cost and memory scope, and (i) an explicit pass/fail/unrun by capability ID. A screen recording's existence is not a witnessed motion judgment. Record sampled frames as samples. One reviewer should write what they personally watched at what playback speed and for how long. A numerical-only stage may pass *numerical scope* while its visible quality remains unrun; do not let that checkbox imply a complete POC.

The packet should use the same fixed source time, world point, camera and exposure across comparison toggles; include a held reference that was not used to author or tune the candidate. Preserve a visibly failed negative control at the same settings where feasible. For morphology, log persistent IDs and local occupancy/connectivity/height or layer amount at tagged world regions. These traces establish that changing *source support* caused the image change; they do not alone establish beauty. Overlaying a prefigured shape with opacity, rigid translation, a sprite swap, noise scroll or preset crossfade must visibly fail the appropriate control, even when its aggregate coverage curve looks similar.

### Cross-stage blockers and practical limits

1. **Checkbox semantics can overclaim.** `CLOUD-MIGRATION.md` lines 15–17 says a checked stage's stated gate passed, while P2a can pass numerical reference and P4a can proceed without the target device. Keep a matrix in the status row for *mechanism, visible result, watched motion, consumer correctness, cost, device admission*. Use `passed <scope>` literally; a stage may advance dependencies on a scoped pass, but do not call that stage fully done when a required quality or device dimension is unrun.
2. **Visual references need a decision, not just a board.** P0 names comparators, yet later checkboxes do not consistently say which exact native view or motion span each reference can falsify. Freeze reference identity and controlled exposure/FOV/time caveats in each packet; reserve at least one held-out comparator per family/weather story. Do not require photographic pixel matching where weather geometry is stochastic; judge named silhouette, light, scale, pace and topology cues separately.
3. **The P4a hard gate still has an escape hatch.** “Viable bounded reduction path / representation revision / unavailable target measurement” is three different outcomes. A quantified route may justify P1b, an unqualified device limits claims, and a structural overrun requires rework. None alone is a `P4a passed` cost result. P3a/P3b stress screens also need a stated maximum admitted population/domain and a full-cover lower bound so the programme cannot migrate an unscalable prototype by calling the broad case a future optimization.
4. **Performance and beauty must be tested on the same graph.** P5's family cost receipts should include all retained consumers, not just source/render. P7 should benchmark the exact visual settings used for FS acceptance, then separately profile diagnostic/reference paths. A quality reduction that saves time needs its own moving visual re-acceptance; lower resolution or temporal reuse is not inherently equivalent during births/64×.
5. **Keep the harness narrow.** P0 needs only enough world/source/pass ownership to falsify stale publication. P3a far transfer may be rejected without implementing a universal far renderer; P3b makes a selected production path once its stress evidence warrants one. Stop an experiment when its candidate is disproved, write the consequence, and revise the canonical design before dependent production. This avoids turning a POC sequence into a speculative framework while preserving the challenging P7/P8 endpoints.
