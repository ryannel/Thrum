# Second-battery performance review — cloud migration

2 November 2026. Design/code audit only; no build, browser run, GPU benchmark, or device admission. This review is independent in its **initial cost derivation**, then reconciles the written migration plan, source map, existing prototype and retained evidence. The browser M2/WebGPU 1280×720 cloud ≤5 ms, whole GPU ≤16 ms and whole-browser ≤512 MiB are **objectives**, not predictions; native 3/10 ms remains unqualified. The old one-source local graph's ~12.976/17.075 ms p50/p95 is an adverse observation in a narrower fixture, not a full-sky scaling coefficient.

## Cost model derived before reading the plan

The critical multiplicity is `views × fresh pixels × occupied ray steps × (density lookups + light/source lookups)`, plus source preparation, Sun columns, ambient directions, environment rays, filtering and reconstruction. Main, independent reflection, environment/probe, shadow and CPU semantic consumers can each remain active when another is hidden. A 320×180 primary view at 64 occupied steps is 3.6864 million visits; 640×360 is 14.7456 million before secondary light work. A 16× or 64× physical-time advance does not multiply frame count, but can cause endpoint-cache misses, swept support changes, almost-global light invalidation and fresh history pixels in the **same display deadline**. Low Sun widens the influence of one changed source; overcast removes the empty-space advantage. This is a graph critical-path and bandwidth problem, not solely a ray-march kernel problem.

CPU costs likely concentrate in persistent event/front traversal, source-to-cell/column/region dependency building, cache-key construction, dirty-set union, F4 decode, queue bookkeeping and WebGPU API object creation. These are frequent cheap operations that may allocate or provoke GC even when GPU kernels are optimized. Memory must distinguish unique encoded master bytes, CPU decoded cache, GPU encoded bytes, physical atlas/mip/guard bytes, light products, histories, staging, in-flight generations and browser/driver process residency. A logical texture sum is neither committed physical memory nor the peak during seek, quality switch or device recovery. Working-set locality matters: two endpoint samples per occupied step can add random brick/atlas loads even while removing a full per-age field rebuild.

## Executable performance worklist for the build queue

1. **P0:** implement a deterministic scenario/pass manifest, immutable loaded-artifact identity, nonblocking timing ring, bounded counters and queue/deadline receipts. Use a reference CPU traversal and a compact production-shaped event/region layout; record allocation/GC and disabled/all-off costs. Pass means no authority/input GPU wait and truthful display versus completion clocks; this is harness correctness, not target performance.
2. **P1a:** with one accepted Cu, compare endpoint-on-demand versus pooled current blend at identical optical times and all consumers. Record two-fetch sample work, unique endpoint misses, decode/upload, cache churn, CPU query cost and simultaneous physical bytes for steady, seek and 64×. Select a bounded resident/paging policy or revise the cook before P3. Do not treat one clip as the full library memory proof.
3. **P3a:** run the 1/2/16/64 independent-age, sparse/full-cover, low-Sun, offscreen and far-gap stress matrix with counters from PF1/PF5. Fit count-to-time slopes and tile/index tradeoffs on the available host; name the target device if it is M2. A structural overrun triggers representation revision before P1b/P3b, even when imagery is still a conformance fixture.
4. **P4a:** assemble current-generation source→shadow→ambient/env→main/reflection spatial graph. Measure graph critical path, CPU p99, latency/backlog, physical memory and cadence under birth/seek/low-Sun motion; compare with the old graph only under pinned matched fixture limits. Record viable bounded reduction path, structural revision or device-unavailable status. Never award 5 ms from individual kernels or a held displayed frame.
5. **P3b/P4b:** populate the required FAIR/BROKEN/OVERCAST/STORM steady and burst worksheet before choosing expensive caches, then qualify reconstruction and any slower radiance cadence against fresh spatial references. Repeat the combined graph, not a sum of isolated wins; include CPU/index/upload and old+new peaks.
6. **P7/P8:** admission on actual M2 browser and actual native host, separately, using exclusive matched runs and observed beauty/motion. Include cold shader/source load, sustained operation, cut/seek, 64×, all-off, device recovery and full browser/process peak. Pass only if required lifecycle/consumer quality survives **and** the declared device objectives hold; an unavailable device or counter remains unqualified.

## Review conclusion

The revised plan has the right top-level cost semantics and several early gates. The consequential remaining design risk is that conservative exact coherence may turn many-source changes into large source-index, light and environment work, while endpoint sharing moves cost into random reads and cache residency. PF1–PF5 make that risk falsifiable before broad content production. Historical code is a source of oracles and adverse timing lessons, not a production performance baseline. No new hard budget or speedup is asserted here.
