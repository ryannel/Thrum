# First live-cloud proof: bounded code review

2 November 2026. Read `src/weather.js`, `src/gpu.js`, `src/scene.js`, `src/bench.js`, `index.html`, the shader paths they bind, and the current P0/P1a proof cards and `CLOUD-PROVIDERS.md`. Ran `node tests/weather.test.mjs` successfully. I did not inspect moving output, execute WebGPU, measure a host or assess family appearance. This is a dense standalone pilot, not Thrum engine/provider implementation or P0/P1a acceptance.

## Findings, ordered by contract consequence

1. **Weather authority is still driven by optical frames.** `scene.js::render` calls `weather.advanceTo(this.time+.25)` only in the source-tick loop. `bench.js::frame` sets source ticks to zero for shadow/clear providers, pause and skipped/over-capacity graphs. A GPU bottleneck, hidden visual source or selected shadow-only profile therefore stops E1 weather/front time and any semantic cause development. `Weather.snapshot(time)` also accepts a caller-supplied time that can be ahead of its actual 1-second `weather.tick`, so a source/control receipt can appear current without a committed cause at that time. Move Weather stepping/command admission to one bounded host/world schedule independent of views/provider. Have source updates consume the committed WeatherFrame with explicit tick/revision and report optical age when GPU work lags. P0 should hide/remove optics and show weather/wind/cause time continuing; P1a should perturb forcing while GPU presentation is backlogged.
2. **The provider/main switches do not prove the F2 off-cost or replacement contract.** `weather.js::validateProvider` checks only the `full` recipe; `validateProvider('shadow','clear')` succeeds although the shadow-only recipe requires actual cloud attenuation. `bench.js::provider.onchange` increments an epoch and changes a uniform, but does not validate full versus shadow-only dependency closure or prepare/retire resource ownership. `scene.js::render` continues its voxel-light dispatch, view pass and display pass for shadow/clear; q, scratch, rest, light and view textures stay allocated. `main=false` changes the fragment condition while still rendering a full optical view/light graph. These are diagnostic toggles, not actual provider registration, replacement or retirement. P0 can use a small finite adapter, but it needs a real independent 2D attenuation producer/consumer, an invalid combination rejected before activation, and counted stopped passes/pages/leases for each off mode. Do not require a second full-sky renderer.
3. **Reset and recovery do not yet implement the selected optical-epoch policy.** `bench.js::reset` constructs a new `Weather`, reapplies UI defaults and sets scene time to zero; the button labelled “Recreate optical epoch” calls that path. This discards CPU weather progress/event identity, whereas `reset-optics` preserves them and reinitializes q from *current* controls under a new optical epoch. `Scene.reset` can return false at capacity after weather is already replaced, leaving weather and q from different runs; the caller ignores the return. There is no current-state checkpoint/forcing recovery for `continuous-optics`, which is fine to defer, but the UI must not imply it exists. Root is already correcting the pending-3 reset; the same fix should make weather/source reset a single admitted transition and distinguish a fresh seeded world from optical-only recovery. A simulated device loss should show unavailable/current-weather retention, not a new weather world.
4. **The frame/capture identity is not yet evidence-safe.** `bench.js::capture` ignores `Scene.render(...,0) === false`, waits for already queued work, then saves the canvas under `scene.time`, `scene.epoch`, current controls and `weather.snapshot(scene.time)`; the image may be the previous submitted frame. `identity` is fetched once before shader/source fetches and is a hash of files currently on disk, not verified bytes of the modules actually loaded; an edit during load or capture can make the build hash misleading. POST responses for `/capture` and `/receipt` are not checked. Bind each submitted frame to actual source tick, WeatherFrame revision, optical epoch, provider/profile and loaded-code identity; capture only after that frame is known to have rendered, or report unavailable. Reject failed saves and retain exact submitted-frame metadata rather than current UI values. This is a proof validity issue, not a demand for new media tooling.
5. **The displayed 16×/64× controls currently cannot establish requested-rate source evolution.** `bench.js::frame` clamps the accumulator to two seconds and submits at most two 0.25-second source steps per callback. At 60 callbacks/s this tops out near 30 source seconds per wall second even before GPU stalls; a 64× request silently discards accumulated demand at the cap. The HUD reports delivered rate, which is useful, but the benchmark stores requested rate without a cumulative requested-versus-admitted-versus-dropped source-time ledger. Keep bounded work and responsive input, but report the unmet time obligation and do not mark the P1a 64× witness passed from a short accelerated clip or rate selector. The fixed-step state may deliberately lag and seek/reset under an explicit policy; it cannot relabel stale q as requested time.
6. **Forcing replay and command semantics are incomplete for the P1a driver witness.** `Weather.command` mutates `target` immediately, records a bounded 256-command array and silently evicts oldest entries; `sendFront` changes `frontX/front` immediately but records no command. The source can see the new dry front at its next 0.25-second step while wind/moisture targets change via the next 1-second weather step. Thus the perturbations have different commit boundaries, and the front cannot be reconstructed from `commands`. Use identified, ordered pre-tick commands with one effective tick, validate ranges/units (the current validator only checks known finite keys), and either checkpoint/retain sufficient forcing or declare replay unavailable after the ring horizon. The chosen small art-directed model is fine; a scientific weather solver is not required.
7. **Cost receipts are narrower than the card's claims.** `Gpu.bytes` sums requested texture/buffer sizes at creation and never subtracts retired resources; it omits bind groups, pipeline/driver scope and physical allocation effects. `Timings` samples every twelfth frame even outside the named 10-second benchmark, so an observer-off/A-A noise floor is not yet measured. CPU timing wraps `Scene.render` encoding and weather updates, but not presentation, input/HUD or save; `callbackFps` is callbacks that submitted a graph, not displayed FPS. The asynchronous timestamp/readback path avoids a per-frame blocking wait, a good start. Label current receipts “logical created bytes” and “submitted graph samples”; add actual current/peak/fenced/old-new inventories, queue age/deadline and observer-on/off scopes before claiming P0 bounded-work or P1a all-state/scratch cost. The planned M2/full-sky budget remains entirely unqualified.

## Current positive scope and missing witnesses

The code has one CPU Weather object, finite ordered GPU graph submission, a three-graph cap, asynchronous timestamp collection, a deterministic seeded dense q update, an explicit source reaction/transport shader and a source probe. The small CPU weather/reaction/provider tests pass. The mirror path traces an independent reflected ray; the main-off shader can retain a reflected cloud sample. These are useful local mechanisms, subject to running image/optical checks.

P0 is not closed by the current controls: no actual independent shadow-only provider lifecycle/off-cost, no proved late-work generation rejection, no verified loaded-build/capture binding, and no demonstrated no-consumer weather continuity. P1a is not closed by a family selector or source probe: the review did not watch normal/accelerated local birth, mature replacement, ragged breakup and midlife changed-driver response; sparse-support birth/halo, source/world identity, source-time coherence, recoverable recipe/forcing and all source/scratch costs need their specified witnesses. The current single dense field and analytic light/mirror are properly labelled a pilot; they establish no five-family, complete-air, environment, device or engine pass.
