## Closure of the two prior critical findings

- **Causal weather sampling: closed in code for the tested interval contract.** `Weather.step` integrates the preceding held interval before committing queued commands. `sample(t)` uses the latest snapshot at or before `t` and analytically advances only its held wind/front position within the half-open interval. The regression confirms samples at 0, 0.25, 0.5 and 0.75 are unchanged after a command commits at tick 1, and tests compare delayed versus live sampling. `Scene.render` now gives each source step the left-endpoint weather sample. This fixes the prior retroactive-forcing counterexample. Longer-run/source GPU behavior remains unobserved.
- **Observation versus configuration race: closed for the reviewed handlers.** `configure()` marks a pending request and returns while `busy`; probe, capture, reference checks and reset keep `busy` through their awaited work and queue configuration afterward. Capture requires a submitted graph, clones that frame's metadata, waits for completion, and checks image/receipt POST status. This prevents the previous old-probe/new-scene mix and false “saved” success in the ordinary handler paths. Async GPU/device failure behavior remains untested.

## Remaining lifecycle defect

**Rapid configuration changes can rebuild the final provider twice.** When `configure()` is already running, a second UI change increments `configurationVersion`, sets `configurationPending=true` and returns. The running `while` loop observes the new version and eventually applies it. The flag is never cleared inside that loop, so `finally` queues another `configure()`, which increments the version again and fully disposes/recreates the same selected provider. This is unnecessary GPU device/pipeline churn and distorts P0 transition/off-cost receipts. Clear the pending flag when the running loop consumes the latest request, or have the deferred drain process the existing version without creating a new request. Verify a rapid full→shadow→clear or optical-off sequence produces exactly one final activation and one retirement per superseded active generation.

## Checkpoint and evidence precision

- The pilot implements the **default reset-optics** behavior only: a new optical epoch seeds q at current CPU weather while preserving the world; it does not have a durable q/carrier checkpoint, 60-second forcing replay closure or `continuous-optics` recovery. This is a valid P0 limit. Captures and status must not call the optical reset a continuous material restore, and P6's checkpoint receipts remain open.
- `Scene.lastSubmission` is now useful immutable frame evidence: visible and committed source times, world time, optical epoch, family, controls and a weather input are recorded. For a frame containing several 0.25-second catch-up steps, that one `weatherInput` describes the displayed sample, not every source-step input. A future checkpoint/replay or exact lineage claim needs the source-step range and committed WeatherFrame revisions/forcing closure used to reach q, rather than inferring them from the final display sample.
- The receipt's `identity` still comes from `/identity.json` before `Scene.create()` fetches and compiles shader bytes. A file change between those requests can make the build hash differ from the loaded program. Pin/check the actual fetched JS/WGSL bytes, or reject a manifest mismatch, before treating image and numerical receipts as exact loaded-build evidence. No external asset or new framework is needed.
- Current `logicalCreatedBytes`, submitted callback rate and guarded cross-pass timestamps are scoped pilot diagnostics. They are not physical peak memory, displayed FPS or an accepted GPU total. Keeping unordered totals null is correct. P0/P1a visual, latency, cost and provider transition witnesses remain unqualified until actually run.
