# RENDER-2D M1 evidence

The game selects the sprite scene with `THRUM_SCENE=sprites` on the Mac or
`?scene=sprites&scale=2` in Chrome. The game supplies the card as one frame row
from an embedded pixel sheet. The host owns the drawable extent, graph, submission,
timing and device replacement. Frame rows are in the game's supplied painter order.

## Metal correctness

- **M1.1** compares every submitted SDR pixel with CPU placement of the asymmetric
  3-by-2 source sheet. The test places the rows across all four edges at 64×46 and
  65×47, at scales 1, 2, 3, 4 and 6 on both native recipes. [Metal test output](M1/metal-tests.log)
- **M1.2** compares the complete scene and capture pass lists. It counts every
  live HAL buffer, texture and query set before and after preparation, after
  retiring one-off uploads on both sides. The five textures are the sheet and the
  two targets per slot. The nine buffers are the frame table, the two sprite
  inputs per slot and the two timing buffers per slot. The creation ledger counts
  exactly three render pipelines. The same test prepares a clustered, shadowed
  atmosphere scene with stars and TAAU, then checks its graph, storage,
  selected reconstructor, creations and completed timing. [Metal test output](M1/metal-tests.log)
- **M1.3** refuses temporal sampling, each explicit camera culling mode, TAAU,
  Reference, shadow, opaque and after-opaque. Each refusal has its own expected
  name and an unchanged graph and submitted image. The accepted upload/simulate
  contribution clears a real GPU buffer, dispatches a named compute pass, and
  records submission after those callbacks. The native and web launch boundaries
  carry named reconstruction requests to preparation.
  [Admission test](../../../crates/thrum-render/tests/scene_2d.rs)
- **M1.4** compares Metal pass names and execution order, attachment-storage
  decisions, and transient assignments on both recipes. The engine fixture covers
  64 combinations of 3D graph choices, capture source, copy and recipe. The
  game-level control separately prepares the actual V1 grid, temporal input,
  cloud shade and sky, field cubes and meshes, cooked valley variants, and cooked
  exit recipes with the surface consumer attached. Both starting records came
  from an archive of `4392b652fb63994e6ca9090e9b5d20602777337d`. Only the
  snapshot drivers were added to that archive to emit these records.
  [Engine fixture record](../../../crates/thrum-render/tests/support/scene-3d-starting.txt) ·
  [V1 fixture record](../../../examples/v1-game/tests/support/scene-3d-starting.txt)
- **M1.5** reads the ordinary submitted SDR and scene-linear checkpoints on both
  recipes. All 256 grey codes and seven saturated colours match exactly. The
  blend uses the one-code allowance and the bright test reads 2.0 in scene-linear
  red before SDR clips it. The shared sRGB encoder has the same arithmetic and
  the 3D shader retains both tone operators and dither.
  [Colour test](../../../crates/thrum-render/tests/sprite_colour.rs)
- **M1.6** compares against a fresh scene after resizing, doubling backing
  density, discarding an encoded frame, refusing a surface, submitting an
  endpoint capture and publishing a different Metal device. It also checks that
  a pending capture of the retired device is refused. [Metal test output](M1/metal-tests.log)

## Chrome correctness

**M1.7** runs the V1 page and compares the submitted bytes with a JavaScript
rasterizer using the game's authored sheet. It checks the whole pass list and
matches scales 1, 2, 3, 4 and 6. At scale 4 it refits to an odd 1121×657 canvas,
destroys the live WebGPU device and uses the game's Restore graphics button.
The Wasm receipt identifies the loaded build. [Chrome record](M1/chrome-sprites.json)

## Fixed Metal inspection

**M1.8** uses the game binary in a release build, the portable Metal recipe, and
T2's submitted-image tap in `fixed` mode. The stills are entire frames and the
detail images preserve source pixel size. The registration marks are asymmetric.
The upper-left gold corner and lower-right aqua corner locate the card's
orientation. The ramps preserve their authored colour and the vertical and
horizontal lines maintain their whole-number widths. The background is black.

```sh
cargo build --locked --offline --release -p v1-game --bin v1-game
THRUM_SCENE=sprites THRUM_SPRITE_SCALE=2 python3 scripts/capture_v1_runtime.py \
  --binary target/release/v1-game --case checkpoint --mode fixed --recipe portable \
  --extent 1280 720 --output tmp/sprite-card-1280x720-scale2
```

## Costs and exact baselines

**M1.9 and M1.10** retain the separate release runs, machine load, CPU times,
named GPU times and prepared target bytes. Both targets use 1920×1080 and
3456×2234 backing pixels. Chrome records the limits admitted by the runtime's
capability record. The valley pairing uses the fixed moving route, portable
Metal, the same cooked store and release build settings on both sides, and pairs
the same ticks and culling modes. The checked command reports tripwires from
the samples and returns a result from record completeness. The paired Metal
valley medians changed by +2.0%, +0.5% and +0.6% for Direct, Frustum and
Occlusion, respectively. Chrome reported 16 sampled textures, 256 array
layers and eight storage buffers per stage. Both Chrome takes flag the
sprite pass's size comparison. Its median moved from zero recorded
nanoseconds at 1080p to a single 65,536 ns step at full backing size.
The measurement cannot resolve a ratio across that step.
