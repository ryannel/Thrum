# RENDER-2D M1 review

## Verdict and findings

**Fail.** Eight items pass. M1.3, M1.9 and M1.10 fail. There is also a defect in the shared contribution interface. The automatic checks passed on the files at `de59644d67b6`. I built the native game and captured the submitted SDR output at review commit `5dd82c28ed3d`.

1. **M1.3 · Must Fix · verified on Metal.** A sprite launch silently accepts a traced-geometry view. I ran the fixed checkpoint with `THRUM_SCENE=sprites THRUM_TRACED_VIEW=on` at 1280×720. The game prepared `TwoD`, submitted the card and exited successfully. Its PNG matched the ordinary scale-2 frame byte for byte. The launch parser sets `DisplayOverlay::TracedGeometry` in `examples/v1-game/src/content.rs:183`. The sprite branch at `examples/v1-game/src/host.rs:655` checks other 3D settings and forwards only the temporal overlay. This option explicitly requests the opaque geometry seen by camera rays. Preparation should return an error naming the traced view. The engine-level refusal tests bypass this launch path. I reproduced this on the native launch path. [Capture receipts](M1-review/capture-record.json)
2. **Contribution frame interface · Must Fix outside the items · verified in source.** A sprite contribution receives the origin for a displaced camera. `ContributionFrame::camera` promises the declared world-space camera position in `crates/thrum-render/src/contribution.rs:300`. The sprite uploader subtracts the supplied view centre from row positions, then returns a scale-only projection. The frame passed to upload and simulate hard-codes the camera to zero in `crates/thrum-render/src/runtime/sprites.rs:237`. For a view centred at (10, 5), a sprite at (10, 5) lands in the middle while a contribution using the reported camera observes (0, 0). The existing callback test records callback order and ignores camera values. I traced both producers and the callback interface in code. **Proposed item:** For a non-origin 2D view, an attached upload/simulate contribution observes the game's world-space view centre and maps a known world point to the same output pixel as the sprite pass.
3. **M1.9 · Must Fix · verified with a negative control.** The Metal cost verifier accepts a record missing every target byte count. In an in-memory copy of the retained gzip JSON I deleted `build` and removed `scene_bytes_per_slot`, `sdr_bytes_per_slot` and `present_bytes` from all four storage records. `scripts/render2d.py:179` accepted each remaining `{"slots": 2}` object, and `validate(record, "mac-metal")` returned successfully. The `costs` command uses that validator. Require the sizes the item names and their build provenance. The existing measurements can be retained.
4. **M1.10 · Must Fix · verified with a negative control.** The Chrome cost verifier accepts two runs with no machine-load observation. In a copy of the Chrome record I removed `build` and set every row's load to `{"before": null, "after": null}`. The same validator returned successfully with both takes and all timings intact. Check that the load observations and build details actually exist. Both cost probes changed only in-memory copies, and neither used a timing threshold.
