## Must Fix

**MF3 · M5.11 · Partly resolved, verified.** The revised digest catches the earlier example of a changed Mac frame driver. It still omits the launcher and capture scripts that determine how the measured program runs. There is a counterexample in project history. Commit `4ffb33052` changed two JavaScript files so Chrome's exit receiver could accept 1,800 records. Its parent refused ordinal 1,024, short of the exit flythrough. I compared the Git trees on both sides. Every path in the proposed digest was identical. A successful record taken with the higher limit would therefore still pass the specified digest comparison after reverting the limit. [Timing record design](../../plans/SHOWCASE/DESIGN.md#motion-on-a-shared-machine) · [Browser capture driver](../../../scripts/capture_v1_browser.mjs) · [Receiver limit](../../../scripts/browser_capture_receiver.mjs)

Listing the driver in `reads` makes the script run the checker again, but the checker would compare the same digest with the old record. A change confined to the receiver can also reuse the cached pass because the receiver is absent from `reads`. This matters to timing as well as completeness. The retained M5 runs saw export omissions and different submission gaps as the capture path changed. Make the record identity and the check's reuse decision cover the same inputs that select, drive and observe the six arms, including their capture helpers. A change to the receiver limit or to the route selected by the launcher must invalidate the old record, even when the game binary is identical. This can remain a cheap check of the saved record.
