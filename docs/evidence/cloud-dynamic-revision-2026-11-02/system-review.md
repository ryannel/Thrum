# Runtime atmosphere and weather: independent scope derivation and cloud-plan audit

2 November 2026. Written design review only; no runtime or visual qualification. This review was exposed to the existing cloud capability table and governing design before its own inventory was saved, so the derivation below is an independent *reasoning pass*, not a blind review. Basis: the new user direction (runtime evolving weather, pluggable approach, no Houdini or baked lifecycle), the [five-family commission](../cloud-sky-design-2026-11-01/COMMISSION.md), [C04/C08/C09](../../design/CONTRACTS.md), and [E1 architecture](../../design/modules/ENVIRONMENT.md). Current canonical choices are audited only after this first section.

## 1. Capability and interaction checklist derived from the requested experience

The required experience is a changing, spatially coherent sky whose visible structure and environmental effects agree across time, cameras and consumers. It does not imply a scientific forecast, a universal fluid solver, or every weather phenomenon. In the list, **D** means this commission must design and prove it, **S** means the commission must define a typed seam but another module may implement the effect, and **X** means a selectable future extension.

| ID | Observable result and authority/interaction question | Scope |
| --- | --- | --- |
| A01 | Fair Cu, developing Cu/Cb with towers and anvil, broken Sc, connected St/overcast and fibrous Ci each have recognizable shape, scale, altitude, nonclone variation, local birth/renewal/loss and persistence. A runtime update changes structure and connectivity; moving noise or fading a premade volume is insufficient. | D |
| A02 | At normal and accelerated time, clear-to-scattered, rising cover, overcast and storm development/approach preserve surviving identities. New cloud, wind shear, cover and phase transitions affect source, optical shadow and reflection at the same world time. | D |
| A03 | A selected **weather cause authority** advances once per world step or declared lower cadence and publishes spatial/time fields/events. Its controls, seed, external forcing, revision, replay/save semantics and discontinuities are separate from a particular cloud-density implementation. A cloud source consumes the admitted causes and publishes optical matter/coverage; it does not become the weather authority by drawing sky. | D |
| A04 | Wind has one spatial/altitude/time source. Cloud transport/deformation and rain drift, water and vegetation sample that source with their own response operators. If an optical provider cannot respond to a changed wind in its declared latency/domain, F2 rejects that combination rather than silently retaining old motion. | D for cloud/wind relation; S for other responses |
| A05 | Cloud optical queries cover view, Sun/Moon, shadow receiver, sky/environment capture and independent reflected rays, including offscreen casters. Query domain states position/segment, direction, time, footprint, support, units, error/quality, source identity and validity; zero extinction is distinguishable from unavailable. One condensate contributes once across parts, LOD and near/far paths. | D |
| A06 | Clear air gives a sky/horizon and aerial transmittance/scattering over the admitted camera/cloud/planet domain. Local fog/haze has an identified source and overlap policy. Air, cloud and fog enter one C08 transport order; separate screen blends cannot claim exact overlap. | D for optical contract and representative coupled proof; S for independently owned fog/weather aerosol generation |
| A07 | Celestial and environment inputs have one Sun/Moon/time/geometry and irradiance convention. A visible sky, night/Moon regime, cloud shadows, surface diffuse light and environment/reflection products are distinct consumers; optional Moon must be explicitly admitted or rejected. V3 owns lighting/transport, V4 display. The cloud provider supplies attenuation/scattering, not a rival light registry or exposure. | D for specified Sun/sky conditions and admitted Moon; S for general celestial/night system |
| A08 | Receiver shadows, cloud self-shadow, aerial shafts, reflection and environment use the same current cloud support/light. Surface water, wetness and materials consume derived light and weather without feeding GPU pixels back into physical authority. | D for cloud effects; S for water/surface implementation |
| A09 | Rain/lightning causes have stable IDs, location/support, units, occurrence time and relation to storm state; visible streaks, flashes, thunder, wetness deposition, water forcing, audio and gameplay are independently selectable consumers. Cloud visibility/offscreen culling cannot erase required causes. | D for causes and seams; S for effect/response implementations |
| A10 | Source, optics and presentation can be selected separately by profile: clear, attenuation-only, reflected/environment-only, visible and headless; a game may replace a cloud source at load with another conforming provider. Disabled capabilities release avoidable source update, GPU graph, histories, cache and content leases after readers/fences; retained consumers keep their minimum source. | D |
| A11 | V2 temporal correspondence tracks actual retained prior sample and material/feature survival; births, holes, cuts, seeks, LOD, provider replacement and device loss invalidate affected histories. F4 and V1 own immutable content and GPU lifetime; no stale async publication or in-flight overwrite. | D |
| A12 | Authoring exposes meaningful runtime weather controls and source parameters, reproducible seeds/traces and cause inspection, plus family-specific shape controls. It can still use offline tools to make *static reusable material/shape resources*, but required lifecycle/weather evolution is runtime state. Content revision and provider version are pinned for replay and troubleshooting. | D |
| A13 | Complete FAIR/BROKEN/OVERCAST/STORM skies demonstrate coverage, distribution, layer depth, horizon, local development, nonrepetition and all retained consumers at common quality. Work, copies, memory/lease overlap, IO, update/ray costs and latency are measured as a combined workload; choose the cheaper viable approach only after matched visual/behavioural quality. | D |
| A14 | Scientific thermodynamics, conservation, all genera, arbitrary planetary travel, tornadoes, full volumetric rain/lightning implementation and seamless live conversion between unrelated cloud models are optional. Unsupported domains and transitions are typed and visible. | X |

**Required causal walk.** A front changes the weather authority's local forcing; committed wind/moisture/instability/coverage/precipitation potential (or explicitly authored equivalents) feeds a runtime cloud source. Existing cells advect and locally grow/erode while new cells form. The source exposes optical coefficients/support and stable identities. V3 integrates air/fog/cloud, generates Sun attenuation and sky/environment lighting; independent main and reflected views observe it. Precipitation/lightning causes and physical surface/water/audio/gameplay consumers take the same committed cause event. V2/V4 only reconstruct/display versions compatible with that source time. Pausing/culling either view does not advance or erase the world. A provider switch at load validates the same required semantics and starts a new run/epoch; live migration is a separate optional promise.

**Selection rule before implementation.** Compare at least a shipped dynamic weather-map/shape-field family, a runtime field/volume evolution family, and a simpler layered/coverage alternative against the *same* five-family lifecycle, weather and consumer scenes. Use public production accounts for visual cues and known operating limits, then derive which source variables/operators can reproduce them. A title or paper proves neither its private algorithm nor suitability for Thrum. Reject an approach that needs a baked animation to supply the required lifecycle. First find approaches meeting the visible and behavioural bar; compare complete CPU/GPU/IO/memory and authoring cost within that set. Equal quality makes lower total cost decisive. Record any reduced-profile substitution as a declared quality/semantic envelope, not a silent replacement of the target.

The current five-family, weather and full-sky *outcome* ledger already covers most A01/A02/A13 cues. CL01/05/07–17/20–24/29 and C04/C08/C09 provide useful constraints for A05–A11. Their status is mostly partial/unproven, which is honest. The issue is the selected causal producer, composition proof and boundary detail, not an absent demand for extra phenomena. [Epic's current cloud documentation](https://dev.epicgames.com/documentation/unreal-engine/volumetric-cloud-component-in-unreal-engine) is a primary production precedent for real-time volume materials integrated with sky atmosphere, lighting, cloud shadows and sky capture; its documented BSM versus secondary-ray tradeoff is useful, but it does not prove one source algorithm for Thrum. Guerrilla's [Nubis³ production account](https://www.guerrilla-games.com/read/nubis-cubed) supports judging prepared cloud morphology and efficient evaluation, not a requirement to bake lifecycle. The selection must compare *watched motion and coupled complete skies*, not just cited methods.

### Proposed public composition contract (design target, not an implemented API)

The composition root registers a **weather cause provider** and zero or one cloud optical-source provider for each nonoverlapping world/domain key; any regional overlaps require an explicit selector/combiner. A separate clear-air provider, local-fog providers and celestial/light inputs register through their own capabilities. The cloud provider declares `requires` (weather fields/events, wind, celestial/source facts, spatial frame and clock), `provides` (cloud matter/coverage, optical coefficient query, optional visibility/attenuation, identity/correspondence and cause outputs if it owns them), supported scale/altitude/angles/time rates/families, source and query error, deterministic/replay level, platform features, persistent-state codec if needed, and resource budget. F2 validates a finite selected recipe; it does not discover a law from installed providers. A static game module may register directly; optional packages use the same declarations. No new universal plugin framework or binary hot loading is needed.

E1's weather authority publishes one committed `WeatherFrame(world, epoch, tick/sample_time, revision, domain)` with declared causal fields (for example wind in m/s, moisture/instability/coverage controls with named units or normalized authored meaning, precipitation flux/potential, storm/lightning event IDs). A provider must distinguish modeled quantities from artistic controls. Its transition operator specifies state, inputs, source/sink/transport or authored-control law, spatial and temporal support, interpolation and boundary behaviour. It may be a small designed procedural model rather than scientific meteorology. The cloud-source provider updates from one such frame plus its prior owned state at a declared schedule and publishes a coherent immutable cloud sample. It may maintain high-frequency derived visual detail, but that detail cannot invent a second weather or wind authority. If source update lags the weather frame, publish source time/age and an admitted error/latency limit; do not relabel stale matter as current.

The optical query takes a **world-space bounded ray/segment or point, direction, source/light identity where relevant, source time, footprint/quality, and requested accuracy**. It returns nonnegative extinction/scattering coefficients (m⁻¹) and liquid/ice/phase or equivalent typed medium parameters over support, plus source/sample identity, validity/error and a conservative bound; for a specified light path it may return optical depth or dimensionless transmittance. It does not return a camera composited sky colour as physical authority. Exact point/segment coefficients are needed where V3 jointly integrates overlapping air/fog/cloud; a preintegrated `(T,S)` is admissible only under C08's disjoint or jointly owned conditions. Directional shadow fields may be approximations with stated light-angle, altitude, footprint and freshness domains. A visual-only provider cannot satisfy a retained physical shadow query. Clear is `sigma=0`, `T=1`; unavailable/stale/outside-domain is a typed error, not clear. Two render LODs of one condensate substitute/partition, never add. V3 owns integration and light accounting; V4 owns exposure/display.

The selected provider's state and content are pinned by build/profile/provider/schema version. W1/F1 owns the world tick; a view never advances weather/cloud state. The provider publishes immutable snapshot/product handles, and extraction obtains C02 snapshot plus CPU/product leases. F4 retains exact admitted source/config and recoverable products; V1 owns GPU pages, graph and fences; V2 owns view demand, bounds and prior sample mapping; V3 derives cloud shadow/environment/reflection products and their validity; V4 histories carry provider/source/view/device epochs. A job begun for an old epoch may finish, but may not publish into a newer generation. No render readback drives headless thermal, precipitation or gameplay authority.

**Replacement and removal.** The baseline promise is compile/build exclusion and load-time provider choice. To replace a running gameplay/weather source, stop and start a new world with validated source/config/save compatibility, or reject the save; no automatic cross-provider state migration. An explicitly supported visual-tier change can prepare old/new products under peak reservation, commit at an extraction barrier, invalidate affected histories and retire the old generation after leases and GPU fences. A live weather-law switch needs a separately designed state transfer and game consent. Turning off visible cloud drawing releases its passes and per-view histories but retains cloud update/attenuation/environment products demanded by other consumers. With all cloud optical consumers off, cloud GPU products and recurring optical preparation retire; E1 weather, wind and rain causes remain if their own consumers need them. With no cloud attenuation, V3 receives the explicit clear value. Headless weather creates no GPU device. Track released work and physical memory rather than assuming a hidden flag saves cost.

### Responsibility boundary for this commission

| Concern | This revised commission delivers | Other owner/dependency |
| --- | --- | --- |
| Runtime weather and cloud state | Weather-provider contract, selected bounded runtime cause model, cloud-source operating model, five families and four changing-weather stories, authoritative sample/version/identity and rain/lightning cause seams | E1/W1/F1 own final engine publication/order; game policy chooses forcing |
| Clear optical air and fog/haze | Admitted clear-air SKY-G optical domain and representative local fog overlap with cloud, one C08 transport closure | E1 air/fog source may be separate provider; V3 owns joint integration |
| Sun, Moon, sky, night | Shared source/light contract and the required Sun/sky test matrix; Moon/night either an explicitly selected supported profile with independent proof or typed unsupported configuration | E1 celestial drivers and V3 lighting; no promise of every astronomical/night effect from cloud source |
| Shadows, illumination, environment, reflection | Same-time cloud attenuation, self/receiver/air shadow, clouded ambient/surface irradiance, independent reflected rays and environment capture including offscreen sources | V2 view demand, V3 transport, V1 GPU graph, V4 display/history; rough water at actual engine integration |
| Wind, rain, lightning | Cloud response to shared runtime wind, typed precipitation/lightning causes and alignment proof with offscreen cloud | E1 wind/weather; V5 particles/flash, audio thunder/rain, surface deposition, water forcing and gameplay responses are separate implementations |
| Wetness, water, audio, gameplay | Stable flux/event/time/location seams and a coupled stub proving IDs and units through the graph | Surface state/P7, water E1 provider, audio A1, game/P6 and network N1 own their state and effects |

This boundary still requires a convincing coupled sky: dependency modules need not be fully built before a standalone proof uses typed stubs, but their source facts, units, order and absence behavior must be real enough to reject a false cloud/weather coupling. The actual Thrum API/platform proof remains gated by I1/I2/I3 construction.

### Revised decision and proof sequence

1. **Reopen D2 source selection.** Keep the five-family acceptance inventory and optical algebra. Derive candidate runtime state variables and operators per family and front/storm interaction. Compare dynamic field/shape systems and hybrid layer/volume systems using shipped production quality as the visual reference, then reject candidates unable to create local growth, renewal, breakup and anvil development *at runtime*. Select only after cost modeling of full sky, shadow, reflection, ambient and cross-view work. The exact density/LOD format follows this decision.
2. **Contract sentinel before content scale.** In a small world, two persistent cells (one developing Cu→Cb) and a low deck respond to a changing front and height wind. Drive clear→scattered→greater cover→storm from a runtime weather provider. Include Sun, clear air, one fog overlap, ground receiver, main-off shadow, independent reflected ray, semantic rain/lightning events and a paused second view. Trace same-point/time IDs and optical depth. A prerecorded VDB clip or sky alpha can pass a still; require watched normal and accelerated structural motion and a perturbation (change forcing/wind at runtime) that alters the future source without recooking.
3. **Provider substitution sentinel.** Bind the full runtime source and a genuinely separate shadow-only/low-cost provider through F2 setup. Verify admission rejection for unsupported close/ice/self-shadow regimes, clear fallback where permitted, headless cause continuity, load-time replacement/restart and all-off retirement. Measure released CPU/GPU jobs, pages and leases. This need not prove arbitrary hot swap.
4. **Five isolated families, then mixed weather and four skies.** Reuse current CF/CW/FS cue gates, adverse Sun/angle, native appearance and personally observed normal/accelerated motion. Add the runtime perturbation/replay witness, area/time response and source-to-shadow/reflection/environment consistency to each relevant gate. The first complete-sky workload must retain all consumers and expected horizon/LOD.
5. **Cost and engine admission.** Retain the current conservative CPU/GPU/IO/memory ledger, but replace frame-window bake terms with the selected runtime update, state residency, dirty propagation, generated detail and persistent/checkpoint bytes. Charge weather update once per world, cloud update once per source step, then per-light/per-view/ray costs and invalidated caches. Compare provider candidates at matched accepted quality and full retained workload; rank lower total cost only inside the visual pass set. P7 fixture and P8 actual engine/device admissions remain distinct. A failed 5 ms cloud allocation or unavailable device is an open measured gate, not a reason to drop required behaviour.

**Disposition.** The current selected Houdini/episode design is superseded by the user's new requirement; its visual references, bounded Q1/Q2/Q3 transport tests, C08 composition, clear-air analysis, controls, rejection witnesses and adverse cost receipts remain useful inputs. The new runtime source/authority mechanism and provider conformance are unfinished design work. No claim of independent blind review, implemented runtime, watched revised visuals, performance pass or user acceptance follows from this document.
