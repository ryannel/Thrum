# Bounded completed history and peer progress

1 November 2026. A charged authority now reserves the requested storage for each peer's completed history **before** accepting a new sequence. The required count is completed entries plus pending entries plus the candidate. The vector grows geometrically to at most 256 entries, with old and new requested buffers charged concurrently while values move. A failed growth returns `PublicationCapacity` without consuming the sequence. A resolved input moves from the already admitted pending count into one completed slot, so the tick needs no history-buffer allocation. Reconnect clears entries and reuses the charged capacity. Acknowledgement releases retained values and their separately charged payloads; the vector's reserved storage remains available for later actions until the peer retires.

The old completion-order `VecDeque` is replaced with a private `Vec`. Completion order still differs from sequence order when a timed action resolves after a later immediate action, so duplicate lookup and acknowledgement search by sequence. The previous `BTreeSet` of out-of-order sequence numbers is replaced with four inline `u64` words. The bit offset is `sequence - resolved_through - 1`, including offset 255. This is bounded because every admitted sequence above the contiguous watermark remains pending or completed, acknowledgements cannot pass the watermark, and admission caps those entries at 256. An ordinary next-in-order result with no gap advances the watermark directly; a gap uses the fixed word window. Reconnect resets the window. The subsequent [peer registry proof](PEER-REGISTRY.md) replaces the tree with charged sorted storage.

The [unit proof](../../../crates/thrum-core/src/authority.rs) resolves sequences 2 through 256 before sequence 1, then checks that the watermark reaches 256 and every window bit clears. It also fills the pool during a one-to-two-slot history growth, confirms that both the old charge and failed new request preserve the pool count, retries after release, and checks reconnect reuse and final release. The [integration fixture](../../../crates/thrum-core/tests/i1_game.rs) now refuses a second new sequence while the pool is full, then reconnects and accepts a new sequence using its retained history slot. Its charged-output test compares pool usage after history admission with usage after rejection acknowledgement and reader release, so the payload lifetime proof remains exact despite the retained buffer. Delayed-gap, duplicate, acknowledgement and two-peer outcomes remain the same. `RUSTC_WRAPPER= ./dev check` passes.

The [two-peer release fixture](../../../crates/thrum-core/examples/i1_two_peer_cost.rs) was run on local macOS/aarch64 against the previous tree at `586401e` and the new source, with 1,000 warmup and 10,000 measured ticks per run. It submits two accepted actions, steps the authority, admits one in-memory replica group and acknowledges both results per tick. Paired sessions varied substantially:

| p50 nanoseconds per tick | Previous tree, three runs | New source, two runs |
| --- | ---: | ---: |
| Authority step | 416 / 541 / 417 | 375 / 583 |
| Both admissions through replica and acknowledgement | 708 / 917 / 709 | 667 / 1,041 |

These ranges overlap, so they do not establish a throughput improvement or a stable regression bound. The new representation removes the tree allocation on out-of-order result tracking and gives a checked, finite history buffer; it pays a one-time buffer growth cost at admission boundaries. The fixture does not measure a long sequence gap, allocator counts, devices, sustained load or future output byte credits. The whole-process memory gate stays open.
