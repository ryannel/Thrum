# Local I1 protected-path allocation audit

2 November 2026. **Diagnostic, not a hard memory cap.** The [standalone example](../../../crates/thrum-core/examples/i1_allocation_audit.rs) installs a narrowly scoped `GlobalAlloc` forwarding wrapper. It counts successful Rust global-allocator requests and requested bytes, plus API-boundary live requested bytes. The wrapper forwards allocation, zeroed allocation, reallocation and deallocation to `System` with their original contracts; its hooks use only static atomics and do not allocate, log, panic or unwind. Only this example binary installs it. The workspace core and app allocator paths are unchanged.

The same `Increment` rule runs under standalone and two-peer match authorities. Each run uses a closed scalar state/action/event profile, one four-byte `RuleContext` scratch allocation per action from a reusable charged buffer, a sealed `HeadlessHost` with required charged replica, eight inputs per peer due at the next tick, an old snapshot reader and a competing pool user occupying every unreserved logical byte before the callback. The callback commits exactly once; the replica sees eight or 16 increments and events, results are acknowledged, and final pool usage returns to zero. A third two-peer run deliberately allocates a private 257-byte `Vec` inside each of the 16 game decisions. It changes neither the rule result nor pool admission; it tests whether the allocator observer detects work outside `RuleContext`.

Three serial runs of the release example on local macOS arm64 with pinned Rust 1.99.1 and locked offline dependencies produced the same request counts and sizes:

| Run | Admission requests / bytes | Callback requests / bytes | API-boundary peak above pre-admission live bytes | Pool before / after admission / after callback, excluding competitor |
| --- | ---: | ---: | ---: | ---: |
| Standalone, 8 inputs | 4 / 2,520 B | 15 / 1,608 B | 2,952 B | 4,609 / 43,009 / 7,161 B |
| Match, two peers and 16 inputs | 8 / 5,040 B | 15 / 2,456 B | 5,144 B | 5,713 / 82,769 / 10,457 B |
| Same match with game-private allocation | 8 / 5,040 B | 31 / 6,568 B | 5,144 B | 5,713 / 82,769 / 10,457 B |

The positive control adds exactly 16 successful allocator requests and 4,112 requested bytes (`16 × 257`) during the callback while every reported pool value remains identical. Its short-lived allocations do not raise this run's peak requested-live counter because the ordinary callback already has a larger simultaneous peak. Pool reservations include unused future credits, so an allocator count below `pool.used_bytes()` would not prove coverage. The wrapper cannot see allocator-internal reallocation overlap, C/OS allocations, GPU allocations or Rust allocations elided by the optimizer; a global allocator also does not intercept all standard-library activity. These numbers are observed requests in this build, not a proof that the game can never allocate privately.

`/usr/bin/time -l` around the **whole three-run-mode binary**, separately from the allocator phases, reported maximum resident set sizes of 1,867,776, 1,884,160 and 1,900,544 bytes and peak memory footprints of 1,114,424, 1,130,808 and 1,147,192 bytes across three serial invocations. These process values include startup, all three modes and reporting, and do not isolate one callback. They are neither an admitted owner-byte limit nor named-device qualification. Binary SHA-256: `4056877f4367d41256078b353d5d7c62b165f73162d95a562c0a0d7dc27555d1`.

Commands: `RUSTC_WRAPPER= rustup run 1.99.1 cargo build --release --locked --offline -p thrum-core --example i1_allocation_audit`, then `/usr/bin/time -l target/release/examples/i1_allocation_audit` three times, serially. `RUSTC_WRAPPER= ./dev check` also passed, including Clippy and the existing core, clock, mobile and game suites. Xcode Allocations was considered, but its 30-second recording limit was not honored for the large repeated fixture; that interrupted trace was discarded. No allocation-stack attribution or comparison to device behavior is claimed.

This demonstrates a concrete blind spot of the current protected profile without weakening C02. The [scope analysis](PROCESS-MEMORY-SCOPE.md) keeps whole-process admission open. The next game-work proof needs typed closed-value projections and a finite mechanism for game-private work; remote queues, allocator/RSS margins and physical devices remain separate.
