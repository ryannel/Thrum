# I1 qualified group owner selection

1 November 2026. This is a selected representation and proof queue, not an implemented byte gate.

The current `StateGroup` owns four public `Vec` columns and derives `Clone`, so copying a group deep-copies its changed records, results, events and peer watermarks. Authority also retains result/event copies in duplicate history; `baseline` clones all snapshot records and retained outcomes. `Replica::apply` moves group states into its object map after validation, but copies its progress map for non-idle groups. The host retains a vector of callback publications. These are separate live owners and must all be included before claiming a whole-tick cap.

The qualified target keeps the same group identity and lifecycle semantics in separately shared, charged columns. Each nonempty column has a private `Vec<T>`, a fixed logical fill limit and one `Arc` owner. The pool reservation precedes allocation and covers exactly the requested slot bytes plus owner/header bytes; the charge lives through candidate construction and every shared reader. The wrapper cannot grow, shrink or convert the vector, and it never fills allocator-supplied spare capacity. Empty columns allocate nothing. Cloning a qualified group shares owners, and an unchanged peer-watermark column can be reused across idle ticks. A unique change column may transfer state values to the replica through a charged consuming iterator, while a shared column requires engine-controlled closed-value copies and a separately reserved replica destination. Outcome columns transfer or share their owner into host-delivered admitted outcomes.

The standard library [guarantees that `Vec::with_capacity(n)` requests exactly `n` elements](https://doc.rust-lang.org/std/vec/struct.Vec.html#guarantees), though the allocator may return extra capacity. This establishes an engine-requested logical byte cap, not an exact resident-memory cap. The selected, standalone [safe column probe](group-owner-probe/src/lib.rs) covers checked overflow, capacity refusal before allocation, zero capacity, zero-sized values with finite fill limits, partial-fill unwind, shared last-owner release, unique transfer, early iterator drop and concurrent readers under pool contention. Run its four correctness tests with `RUSTC_WRAPPER= rustup run 1.99.1 cargo test --locked --offline --manifest-path docs/evidence/i1-headless/group-owner-probe/Cargo.toml`. The clone probe is ignored by default and runs explicitly in release mode with `RUSTC_WRAPPER= rustup run 1.99.1 cargo test --release --locked --offline --manifest-path docs/evidence/i1-headless/group-owner-probe/Cargo.toml local_clone_cost_probe -- --ignored --nocapture`.

Two local macOS/aarch64 release runs of the selected fixture measured 256 clone-and-drop operations per sample, after 10 warmups across 100 samples. For one `u64`, deep `Vec` clone batch p50 was 9,500 ns and 8,084 ns, while shared-column clone p50 was 1,625 ns and 1,458 ns. For 4,096 `u64` values, deep clone p50 was 132,209 ns and 132,750 ns, while shared clone p50 was 1,250 ns in both runs. This is a primitive comparison, not whole-group or callback performance. The shared clone does not allocate or copy its values, while each deep `Vec` clone allocates a new buffer and copies the values.

The fixture also compares the complete current `StateGroup` clone with four shared-column owners for the same I1-shaped data: fixed-inline entity records sharing one charged 512-byte payload, two results, one event and two peer watermarks. Its [ignored release probe](group-owner-probe/src/lib.rs) runs with `RUSTC_WRAPPER= rustup run 1.99.1 cargo test --release --locked --offline --manifest-path docs/evidence/i1-headless/group-owner-probe/Cargo.toml local_group_clone_cost_probe -- --ignored --nocapture`. Two local macOS/aarch64 runs, each with 20 warmups and 100 samples of 64 clone-and-drop operations, gave these batch p50 values:

| Changed records | Current deep group clone | Four shared-column owners |
| ---: | ---: | ---: |
| 0 | 9,292 / 5,042 ns | 750 / 375 ns |
| 1 | 11,166 / 6,542 ns | 833 / 458 ns |
| 4,096 | 1,110,250 / 1,091,042 ns | 458 / 458 ns |

The current group clones the nonempty vector buffers and each changed record's payload handle. The candidate clones the same identity/tick header and shares the nonempty column owners; it does not clone record values or their payload handles. The zero- and one-change cases vary between runs, so their exact ratios are not stable. These are local clone-only measurements of a representative shape, not callback latency, construction cost, allocator counts or proof of replica handoff. At 4,096 changes, the deep-copy batch took about 1.1 ms for 64 operations, or roughly 17 µs per operation in that batch. The qualified path must still measure construction and whole-tick handoff before its overall cost can be judged.

The standalone fixture has no engine runtime consumer. Production integration still needs the qualified group wrapper, authority preflight, required replica capacity, baseline and host delivery. Measure construction, empty, one-change and large-change groups and the complete callback against the current path. The output profile for rejection/event values and the replica index strategy remain open. The [whole-tick design](../../design/I1-HEADLESS.md#whole-tick-byte-gate-bounded-profile-and-owner-plan) owns the complete contract.
