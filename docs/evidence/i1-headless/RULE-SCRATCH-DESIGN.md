# Reusable rule scratch for a bounded headless profile

2 November 2026. **Selected bounded byte-scratch design, locally implemented and qualified in the [proof record](RULE-SCRATCH.md).** This is a finite owner inside the existing I1 authority. It does not turn arbitrary Rust game callbacks into a whole-process memory bound. The authority continues to call one `GameRules::decide`/`prepare` implementation for local and multiplayer play, in the same canonical input order.

## Required behavior and owner

A game rule sometimes needs temporary bytes to parse an action, perform a bounded calculation or assemble an output. The selected publication pool already owns immutable output payloads and admitted engine columns, but a callback can still privately allocate a `Vec`, map or clone. A finite profile needs a cheap, explicit temporary owner whose capacity is protected before accepted inputs depend on it. Scratch is **authority-owned**, because callbacks execute serially inside the authority in standalone and hosted matches; a host-local owner would split the rule contract. Scratch never appears in a snapshot, replica, event or save. An action may use it through both callbacks, but no slice may survive an individual context borrow. Every new action starts at offset zero; rejection, terminal fault and unwind leave the owner's charge intact until authority drop.

The first usable API allocates checked byte ranges from `RuleContext` and a configured maximum per action. Activation reserves and allocates one requested-capacity byte buffer before the authority is accepted into the protected host. It preinitializes the buffer so returned slices are valid safe Rust. A request checks `used + len ≤ capacity` before advancing; a failed request sets a sticky contract fault that cannot be erased by catching the error or borrowing another context. Successful requests zero the new range before game code sees it, preventing one action from observing another's temporary data. The cursor resets and the action generation advances before the next decision. An empty request returns a zero-length range and consumes no capacity.

The allocation returns a private-field `(owner, generation, offset, length)` handle. Each scratch owner receives a process-unique checked ID at activation; a foreign authority's handle is invalid even if its action generation and byte range match. `view` and `view_mut` borrow a slice from `RuleContext` only for the duration of that use, validating all handle fields. A `Change` may carry a handle from `decide` to `prepare`, avoiding a temporary copy; it cannot retain a borrowed slice. A handle from a previous action is invalid and sets the same sticky contract fault. The generation never wraps: exhausting it faults before another callback. Two mutable views cannot coexist through this API; code needing two ranges can use one combined allocation and split its returned slice safely. `copy_payload_from_scratch(handle)` borrows the scratch range and output credit as distinct internal fields, so a rule can create an admitted immutable output without a temporary game-owned `Vec` or conflicting context borrow. No unsafe code or allocator interception is needed.

The owner is charged once for its requested capacity and retained through the match. It is not a per-pending-input credit: only one rule callback executes at a time in this authority, and the buffer is reusable after each action. The buffer is already resident when another pool user occupies all unreserved capacity, so an accepted input can still call it. A zero-capacity choice keeps no heap buffer or charge. Capacity is fixed for the authority lifetime; changing it requires a new authority/baseline, avoiding old/new overlap and in-flight action ambiguity. This is a *bounded engine-provided scratch profile*. Game-authored allocations outside the API remain unmetered and must be treated as an explicit violation of the selected profile, not silently advertised as covered. A general hard process cap would require a separate allocator or sandbox boundary and platform qualification.

## Cost and alternatives

Retained logical bytes are `K` for scratch capacity `K`, plus the in-authority cursor/generation/charge fields. Activation allocates at most one byte buffer and assigns one owner ID; ordinary callbacks make zero scratch allocations. Each successful allocation costs checked addition, a bounds check and `O(len)` zeroing; each action reset is `O(1)`. A rule that allocates `B` bytes across both callbacks pays `O(B)` initialization and cannot exceed `K`. The cursor does not refund space when a view ends, so `K` is a **cumulative allocated-byte limit per action**, not just maximum simultaneously borrowed bytes. Later views of an existing handle preserve its data until the next action. View lookup is `O(1)` and does not copy. The buffer remains resident while idle; games without scratch should use capacity zero. Per-action allocation would add repeated allocator work and may fail after sequencing under competing users. A global allocator wrapper might catch arbitrary game allocations but changes every dependency's allocation behavior, adds thread attribution/lifetime complexity and cannot safely be inferred from the publication pool; it is not selected for I1.

## Proof and rejection criteria

First prove activation refuses one byte below the requested scratch charge without changing the live authority or host. Then run a two-peer protected host with one action requesting ranges in `decide` and reading them in `prepare`, a rejected action, and a delayed action while a competitor holds the rest of the pool. Check stable canonical outcomes, fresh zeroed ranges, stale and foreign handle refusal, an admitted output copied directly from scratch, unchanged pool usage through callbacks apart from charged output ownership, explicit sticky overrun fault before that action's world edits, old snapshot readers and final charge release. Compare protected callback cost with capacity zero and a small used range in a paired local release fixture; report initialization bytes and timing separately. Verify the `RuleContext` API does not let a scratch borrow survive as a retained result. This proof does not cover typed map/vector scratch, game-private allocation outside the API or in `spawn_bound`, remote queues, OS RSS or device performance. The broader memory gate and I1 remain open.
