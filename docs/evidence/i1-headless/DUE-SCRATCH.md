# I1 reusable due-input scratch

1 November 2026. The authority now owns one reusable ordered due-key vector. Each new peer grows its logical limit by the existing eight pending slots. On a charged authority, peer admission reserves the requested new vector bytes while the old vector and charge remain live, then replaces the old owner. This covers the transient old/new overlap. The vector is empty between successful ticks and has a hard push limit. A tick scans peer pending inputs once in canonical peer/sequence order, uses the resulting count for snapshot preflight, and processes the same keys without allocating a new due list. A retryable precommit refusal clears the scratch before returning, so a new peer may join before retry.

A focused pool test permits the final two-peer footprint but refuses the second peer because the old and new scratch buffers cannot coexist during growth; the failed join leaves the first peer's charge unchanged. Another test blocks a charged tick on the snapshot pool, registers a second peer, releases capacity and verifies that the original due input commits once with both peer watermarks. The existing delayed-gap, two-peer, backpressure and host tests remain green under `RUSTC_WRAPPER= ./dev check` (19 core, 6 clock and 44 game integration tests).

Two local macOS/aarch64 release runs of the [complete batch fixture](../../../crates/thrum-core/examples/i1_cost.rs) measured charged p50 of 598/557 ns per input/tick/replica/ack on this path, versus 642/557 ns at pre-scratch commit `3ad288b`. Idle charged p50 was 49/49 ns versus 48/49 ns. Each point is a median of 100 batches of 1,000 ticks after 10 warmup batches. These overlapping ranges do not establish a complete-path speedup; source inspection establishes the removed due-key allocation and redundant scan. The buffer charge does not cover retained results/events, output groups, mutable world indexes, replica storage or future execution credit.
