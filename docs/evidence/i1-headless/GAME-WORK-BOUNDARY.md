# I1 game-work memory boundary: provisional architecture choice

**Direction update, 2 November 2026:** The general hard process cap discussed below was retired. The [current memory direction](MEMORY-DIRECTION-2026-11-02.md) uses direct native rules with measured allocation and pressure behavior; the strict alternatives below are optional future profiles.

2 November 2026. **Proposed, not selected or implemented.** The [protected host](PROTECTED-PATH-AUDIT.md) and [typed two-peer fixture](TYPED-PROJECTION.md) bound selected engine-owned allocations and cooperating `RuleContext` output. The [private-allocation control](PROCESS-ALLOCATION-AUDIT.md) proves that an arbitrary Rust `Vec` inside `GameRules::decide` raises allocator requests without changing the pool charge. A sealed returned value is therefore insufficient to certify a whole-process cap. C02's [whole-process publication target](../../design/CONTRACTS.md#c02-time-and-committed-state--f1-coordinator-w1-world) remains unchanged.

## The choice that changes the public engine

| Candidate | Game authoring and likely repeated-work cost | Enforceable boundary | Consequence for I1 |
| --- | --- | --- | --- |
| Trusted native rules with declared game-work budget | Direct typed Rust `GameRules`; current low-overhead callback and ordinary debugger. The game must cooperate with `RuleContext` for bounded scratch and outputs. | Engine-owned pool and declared rule outputs are preadmitted. Private native allocations remain an audited contract, not an enforceable precommit limit. | Keep this as the fast default candidate, label its memory claim narrowly, measure integrated RSS on named devices, and leave the general process target open. |
| Finite qualified native rule domain | Typed game declarations compile to native rule operations over closed values and precharged arenas, using the same authority callback semantics. Authoring expressiveness and code generation/validation need design; repeated work could remain close to direct native calls but has not been measured. | A restricted operation set must reject arbitrary allocation, pointer escape and unbounded recursion/calls by construction. Audit and a global allocator alone cannot make unrestricted Rust callbacks qualified. Host outputs and all generated temporary owners still need precommit admission. | Plausible strict profile without a guest runtime. Prove the validator/code generator and local/match behavior before claiming enforcement. |
| Restricted rule program with bounded guest memory and host calls | Game logic crosses a runtime boundary. Typed source/schema and efficient adapters would be needed so a game does not hand-author raw byte records. Call overhead, memory movement, fuel and mobile packaging require measurement. | A finite guest memory limit and bounded host API can constrain guest-owned work; host/store allocations, returned products and allocator overhead still need their own admission and margin. | Possible strict profile, subject to an independent module design and a two-peer end-to-end cost and failure proof. It cannot be introduced as an invisible implementation switch for the existing native callback. |
| Whole game in a separate limited process | IPC and supervision add lifecycle, latency and memory overlap; mobile feasibility is unknown. | OS-level process limit may stop the worker, but does not provide an atomic in-process precommit refusal or keep a phone app alive automatically. | Not selected for the initial headless or mobile shell. |

The Rust [`GlobalAlloc` contract](https://doc.rust-lang.org/core/alloc/trait.GlobalAlloc.html) permits the optimizer to eliminate allocations and does not make a counting wrapper a sound precommit guard. An infallible allocation failure can abort the process, so failing an arbitrary native allocation is not a safe application-level recovery strategy. [Rust allocation failure behavior](https://doc.rust-lang.org/std/alloc/fn.handle_alloc_error.html). Wasmtime documents separate [resource limits](https://docs.wasmtime.dev/api/wasmtime/trait.ResourceLimiter.html) for guest memory/table/instances and [fuel or epoch interruption](https://docs.wasmtime.dev/api/wasmtime/struct.Store.html) for execution; its limiter does not account for every host allocation. These sources establish feasibility boundaries, **not** performance or platform suitability for Thrum.

**Provisional recommendation:** retain direct native typed rules as the default and report a hard requested-byte cap only for the selected engine-managed owners. Treat rule-private allocations as a declared, audited game budget with process RSS qualification, never as pool-enforced bytes. If games need a precommit guarantee covering authored work, compare a finite generated native domain against a bounded guest runtime before selecting a strict profile. This leaves the general-process checkbox open and does not silently narrow C02. User acceptance of the native-default/strict-profile split is pending; bounded native engineering and audits can continue meanwhile.

Before selecting a strict profile, prove an end-to-end program with the same two-player authority semantics and public typed actions: bounded game-work memory and host-result ownership, finite callback work, terminal failure before the failing action's edits, no replay of a partly processed failed tick, delivery of earlier completed ticks, baseline/reconnect overlap, phone package compatibility and measured complete callback cost against direct native rules. A finite native candidate must prove its restricted operation set, validation and generated-code ownership; a guest candidate must prove guest-memory and host-call limits. Reject an option that duplicates authority, changes event/sequence semantics, hides extra state owners, or requires a second game rule implementation. A typed schema/adapter must preserve `PublicationRecord` ownership without a second authoritative state owner or uncharged persistent duplicate; bounded, charged host/guest marshalling copies may be necessary. The current bundled phone game's Rust enums should not be replaced with bare numeric protocol values just to enter a sealed profile.
