# I1 native mobile app shell: compile and packaging source record

2 November 2026. `examples/i1-mobile-game` embeds the `i1-tap-counter-v1` one-object tap counter under the existing `GameRules`, `HeadlessHost` and in-memory replica. The compiled package version is `0.1.0`; the window title records both identities. Winit owns one event loop and touch dispatch. The mobile gate owns finite gesture and lifecycle state; an Android Java Activity forwards pause/resume to its atomic generation through JNI. The app reconciles lifecycle before callbacks, admission and GPU work. A bounded 16-intent queue retains refused input and sequences only after admission. The local receipt cursor observes results/events in order before acknowledgement. The visible count reads the replica; no shell-owned world or second clock exists. A red overload frame must present after queued ticks drain before the local clock restarts from a fresh origin. Redraws are requested on changed visual state and deferred surface retry, without scanning the world on idle callbacks.

The GPU response clears one surface to a color selected from the committed count and fault/overload state. It has no authored scene, assets, lighting or content pipeline. `wgpu` uses Metal on iOS and Vulkan on Android. Surface loss drops the surface but retains device, queue, game and replica; a later resume recreates the surface. Lost/outdated/timeout/occluded acquisition has a bounded redraw retry. The renderer does not yet recover a lost **device**. This is a local-play shell; a future network client cannot pause its remote authority when the phone surface disappears.

The active loop now asks `HeadlessHost::next_due_in()` for the next world deadline, using the same integer remainder as the clock. A pending tick gets an 8 ms bounded retry, and a deferred visual response can wake at its 50 ms retry deadline; neither case makes the empty active loop poll every 8 ms. At the default 60 Hz, the previous fixed wait requested about 125 idle world callbacks per second versus 60 exact due callbacks in an event-free ideal second, a 52% reduction in **requested wakeups**, not a measured CPU or power saving. The 240 Hz test shows the rate follows game configuration without a presentation ceiling. Real winit/OS wake timing and callback cost remain unmeasured.

## Checks completed here

- `RUSTC_WRAPPER= ./dev check` passes after this source addition: the bundled game test commits one tap, observes one result/event and reads `taps=1` from the replica; core and mobile-shell suites also pass. `./dev check` does not compile the target-specific winit/wgpu modules on macOS.
- Pinned Rust 1.99.1 locked/offline iOS simulator target Clippy with `-D warnings` passes for the actual app. Release static libraries build for both `aarch64-apple-ios-sim` and `aarch64-apple-ios`.
- Eight portable clock tests pass, including fractional 60/240 Hz deadline driving, paused backlog and recovery; each ideal deadline-driven callback completes one tick through one second without an idle polling callback.
- `RUSTC_WRAPPER= bash examples/i1-mobile-game/ios/build-simulator.sh` links an unsigned `target/i1-mobile-ios-sim/ThrumI1.app`. `plutil -lint` passes; `vtool -show-build` identifies an arm64 **IOSSIMULATOR** executable, minimum iOS 18.0, SDK 27.2. Executable size is about 11.9 MB. Xcode/Swift prints a macOS sysroot warning while linking, but the produced binary's platform load command is IOSSIMULATOR. There is no simulator launch or screen/input/lifecycle evidence: CoreSimulatorService did not respond in this environment.
- Android source includes a Java `GameActivity`, matching `androidx.games:games-activity:4.4.0` for the Rust `android-activity` 0.6.1 glue, manifest library metadata, and a Gradle debug package project. Android SDK, NDK, Gradle and adb are absent locally. The Rust Android app library and APK have **not** built, linked or run. Portable core Android cross-compilation is recorded separately in [MOBILE-CORE-PORTABILITY.md](MOBILE-CORE-PORTABILITY.md).

The read-only review found and prompted fixes for background GPU work, deferred resize, stale redraw debt, input capacity and an early overload resume. Its final pass reported no remaining source-level finding in this slice. That does not prove Android JNI/Gradle compatibility, actual surface recovery, hardware behavior or performance. Neither startup time nor callback/presentation tails, allocations, process RSS, sustained thermal behavior or display cadence have been measured for this shell.
