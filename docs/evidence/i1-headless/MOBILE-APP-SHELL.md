# I1 native mobile app shell: compile and packaging source record

2 November 2026. `examples/i1-mobile-game` embeds the `i1-tap-counter-v1` one-object tap counter under the existing `GameRules`, `HeadlessHost` and in-memory replica. The compiled package version is `0.1.0`; the window title records both identities. Winit owns one event loop and touch dispatch. The mobile gate owns finite gesture and lifecycle state; an Android Java Activity forwards pause/resume to its atomic generation through JNI. The app reconciles lifecycle before callbacks, admission and GPU work. A bounded 16-intent queue retains refused input and sequences only after admission. The local receipt cursor observes results/events in order before acknowledgement. The visible count reads the replica; no shell-owned world or second clock exists. A red overload frame must present after queued ticks drain before the local clock restarts from a fresh origin. Redraws are requested on changed visual state and deferred surface retry, without scanning the world on idle callbacks.

The GPU response clears one surface to a color selected from the committed count and fault/overload state. It has no authored scene, assets, lighting or content pipeline. `wgpu` uses Metal on iOS and Vulkan on Android. Surface loss drops the surface but retains device, queue, game and replica; a later resume recreates the surface. Lost/outdated/timeout/occluded acquisition has a bounded redraw retry. The renderer does not yet recover a lost **device**. This is a local-play shell; a future network client cannot pause its remote authority when the phone surface disappears.

The active loop now asks `HeadlessHost::next_due_in()` for the next world deadline, using the same integer remainder as the clock. A pending tick gets an 8 ms bounded retry, and a deferred visual response can wake at its 50 ms retry deadline; neither case makes the empty active loop poll every 8 ms. At the default 60 Hz, the previous fixed wait requested about 125 idle world callbacks per second versus 60 exact due callbacks in an event-free ideal second, a 52% reduction in **requested wakeups**, not a measured CPU or power saving. The 240 Hz test shows the rate follows game configuration without a presentation ceiling. Real winit/OS wake timing and callback cost remain unmeasured.

## Checks completed here

- `RUSTC_WRAPPER= ./dev check` passes after this source addition: the bundled game test commits one tap, observes one result/event and reads `taps=1` from the replica; core and mobile-shell suites also pass. `./dev check` does not compile the target-specific winit/wgpu modules on macOS.
- Pinned Rust 1.99.1 locked/offline iOS simulator target Clippy with `-D warnings` passes for the actual app. Release static libraries build for both `aarch64-apple-ios-sim` and `aarch64-apple-ios`.
- Eight portable clock tests pass, including fractional 60/240 Hz deadline driving, paused backlog and recovery; each ideal deadline-driven callback completes one tick through one second without an idle polling callback.
- `RUSTC_WRAPPER= bash examples/i1-mobile-game/ios/build-simulator.sh` links an unsigned `target/i1-mobile-ios-sim/ThrumI1.app`. `plutil -lint` passes; `vtool -show-build` identifies an arm64 **IOSSIMULATOR** executable, minimum iOS 18.0, SDK 27.2. Executable size is about 11.9 MB. Xcode/Swift prints a macOS sysroot warning while linking, but the produced binary's platform load command is IOSSIMULATOR.
- Xcode 27.2's iOS 27.2 arm64 runtime (`24B8117`) was installed and an iPhone 13 simulator booted. `simctl install` and `simctl launch` started `org.thrum.i1`. The original bundle failed with UIKit's “UIScene life cycle is required for apps built with this SDK.” A single-scene manifest and empty `UIWindowSceneDelegate` now allow process launch. The settled screenshot remains black, so startup, rendering, touch and lifecycle are **not** qualified. A temporary FFI hook attached winit's `UIWindow` to the live scene and made it key/visible, but the settled screen remained black; that extra bridge was removed. The pinned winit 0.30.13 iOS backend creates its window without a scene; a future backend selection or complete host fix must be proven with a visible frame before claiming support. Simulator screenshots and logs were inspected locally under ignored `tmp/`; this record preserves the finding without promoting a black image as product evidence.
- Android source includes a Java `GameActivity`, matching `androidx.games:games-activity:4.4.0` for the Rust `android-activity` 0.6.1 glue, manifest library metadata, and a Gradle debug package project. The source pins NDK 28.2.13676358 and its build script selects API 28 LLVM wrappers; the Vulkan shell does not declare an unnecessary OpenGL ES 3 device requirement. `RUSTC_WRAPPER= ... bash examples/i1-mobile-game/android/build-debug.sh` built the ARM64 release Rust library and Gradle debug APK using the local pinned toolchain. `app-debug.apk` is about 14 MB, contains `lib/arm64-v8a/libi1_mobile_game.so`, declares `org.thrum.i1.MainActivity`, minimum API 28 and target API 35, and passes `apksigner verify` with one debug signer. This is package assembly only: no Android emulator or physical phone launched it, and JNI, touch, lifecycle, Vulkan surface and runtime cost remain unqualified. Portable core Android cross-compilation is recorded separately in [MOBILE-CORE-PORTABILITY.md](MOBILE-CORE-PORTABILITY.md).

## Stable toolchain choice

The 2 November upstream check found Xcode 27.2 and `wgpu` 30.0.1 current, while winit 0.30.13 remains its latest stable release; winit 0.31 is still beta and its published notes do not establish a completed iOS 27 scene migration. The upstream [winit scene issue](https://github.com/rust-windowing/winit/issues/4224) and [Apple's requirement](https://developer.apple.com/documentation/uikit/transitioning-to-the-uikit-scene-based-life-cycle) explain why a package manifest alone is insufficient. The Android build pin moved to stable Android Gradle plugin 9.4.1 with Gradle 9.6.0 and JDK 17, matching [Google's compatibility table](https://developer.android.com/build/releases/about-agp) and [9.4 notes](https://developer.android.com/build/releases/agp-9-4-0-release-notes). A first real package build found that GameActivity's public Java API also needs explicit AndroidX Core and AppCompat dependencies; current stable Core 1.19.1 requires compile SDK 37, so the build selects released API 37.2 while target SDK remains 35 pending device behavior testing. [Google's GameActivity migration guide](https://developer.android.com/games/agdk/game-activity/migrate-native-activity) also requires an AppCompat-derived theme for the startup Activity; the package now supplies a full-screen NoActionBar theme. `android-activity` 0.6.1 explicitly supports GameActivity 4.4.0, so that pair stays pinned despite newer GameActivity patch releases. The local verified tool archives and accepted SDK licenses live under ignored `tmp/android-sdk`.

The direct `pollster` pin moved from 0.4.0 to its stable 1.0.1 line. Locked/offline cross-target checks of the app pass for ARM64 iOS simulator and Android with the installed Rust 1.99.1 target libraries and Android NDK 28.2. This checks compilation of the synchronous adapter/device setup path, not simulator presentation or Android runtime behavior.

The read-only review found and prompted fixes for background GPU work, deferred resize, stale redraw debt, input capacity and an early overload resume. Its final pass reported no remaining source-level finding in this slice. That does not prove Android JNI/Gradle compatibility, actual surface recovery, hardware behavior or performance. Neither startup time nor callback/presentation tails, allocations, process RSS, sustained thermal behavior or display cadence have been measured for this shell.

Next qualification when phone-game work resumes: select a scene-aware iOS backend, prove a visible frame, then run iOS and Android input/lifecycle/surface smoke tests. Sustained thermal, CPU, allocation/RSS and presentation qualification on named physical devices belongs to later platform work. The source intentionally has no 60 fps display ceiling; its default local world update rate remains 60 Hz and presentation remains event driven.
