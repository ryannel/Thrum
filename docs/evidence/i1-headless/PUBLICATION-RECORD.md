# I1 closed record storage proof

1 November 2026. `PublicationRecord<INLINE, BLOBS>` has private fixed inline bytes and an array of optional `PublicationBytes` owners. Construction checks every present payload against one `PublicationPool`; its `Clone` copies inline bytes and clones the shared handles, with no game callback or payload-byte copy. An empty payload array has no pool identity and can be used with either pool. The type does not enforce profile maxima. The generic authority constructor does not validate record provenance; a later [qualified entry path](CLOSED-RECORD-ADMISSION.md) adds that check.

The unit test rejects a foreign-pool payload, checks record provenance, and holds a payload charge through clones until the last owner drops. The `i1_game` fixture runs a real charged match authority and replica with one fixed counter and one 512-byte immutable payload. The rule prepares a new record from the prior one. The old reader observes counter 4, the replica observes counter 5 and the same payload bytes, and the payload's exact charge remains after authority and old readers drop until the replica releases its final owner. `RUSTC_WRAPPER= ./dev check` is the repository qualification gate.

The release fixture `i1_record_cost` measures 4,096 record clone-and-drop operations per sample after 50 warmups, across 250 samples, on local macOS/aarch64. Two consecutive runs gave fixed-only batch p50 7,125 ns and 4,792 ns; one-shared-512-byte-payload batch p50 26,709 ns and 20,625 ns. The variation is large enough that these are scale observations, not a reliable regression threshold. The extra shared owner costs one atomic reference-count increment and decrement per clone, with no per-clone heap allocation. The payload itself has two allocations at creation, as recorded in [the byte proof](PUBLICATION-BYTES.md). Neither result includes typed game projection, authority admission, snapshot page cloning, replica application, or a whole-tick memory peak.

This is a storage primitive proof, not the finite qualified game-value profile. The [whole-tick owner plan](../../design/I1-HEADLESS.md#whole-tick-byte-gate-bounded-profile-and-owner-plan) still requires authority admission checks, profile maxima, output ownership, and pre-edit reservation across the required replica and host path.

A scoped read-only review found no actionable correctness issue in the primitive or its fixture. It flagged large const sizes and linear payload-content equality as costs to qualify with the eventual profile. The reviewer did not run tests; the repository check above is the execution evidence.
