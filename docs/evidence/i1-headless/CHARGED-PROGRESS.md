# Charged replica peer progress

1 November 2026. The sealed replica now owns finite peer progress in two pool-charged, sorted buffers. One is confirmed; the other is a validation candidate. Each row holds a peer ID, connection epoch, contiguous result watermark and a fixed 256-bit window for resolved sequences above a gap. The charged authority has the same 256-result per-peer bound. The requested heap storage charge is `2 × max_peers × size_of(row)`, acquired before either buffer is allocated; the two-peer profile requests 256 bytes on this build. The charge survives until replica retirement. The default charged-baseline constructor fixes `max_peers` to the baseline peer count; a separate constructor declares room for later peers. Prototype groups keep their existing unbounded tree representation and semantics.

Baseline conversion validates results and peer watermarks, converts outstanding above-gap results to the fixed window, and refuses an out-of-window gap or insufficient peer capacity. It retains duplicate-result validation, including a duplicate at or below the advertised contiguous prefix. A live charged group checks sorted advertised peers, result epoch and sequence identity, bounded gaps and exact advertised watermarks in the candidate buffer. It swaps candidate and confirmed only after event, lifecycle and object-capacity validation. An invalid final peer can therefore leave both object values and progress unchanged; retrying the corrected group succeeds. A charged replica can refuse an excess peer before mutation. The current sealed host has no post-baseline peer registration API; any future host join must preflight the required replica before authority registration.

The core unit tests cover a malformed final peer with a concurrent object update, corrected retry, a full 256-sequence gap, an excess peer, exact last-owner release, insufficient-pool refusal before replica visibility, duplicate baseline results and baseline gap closure across a later group. Existing two-peer, reconnect and host tests pass in `RUSTC_WRAPPER= ./dev check`. The review-agent found no scoped correctness issue. These tests prove the charged progress slice, not the entire process byte gate.

For local cost, the existing [changed-result fixture](../../../crates/thrum-core/examples/i1_charged_replica_cost.rs) ran in release mode on macOS/aarch64 against `be39e15` and this change. It uses two peers, 64 or 4,096 objects, 1,000 warmup and 10,000 measured ticks per case; each tick changes one object and resolves one result. Two sequential before/after pairings measured the charged replica plus acknowledgement p50 at 208/292 ns before versus 125/166 ns after for 64 objects, and 250/209 ns before versus 125/125 ns after for 4,096 objects. The complete sealed-host submit/callback/ack p50 was 833/958 ns before versus 750/833 ns after at 64 objects, and 1,208/1,084 ns before versus 1,084/1,000 ns after at 4,096 objects. The host path includes authority and scheduling work, so its smaller differences are subject to local noise and cannot establish a device-level speedup.

The [baseline fixture](../../../crates/thrum-core/examples/i1_baseline_cost.rs) also ran once before and after with 20 warmups and 100 batches. Charged baseline-plus-replica p50 was 2,209 ns in both sources at 64 objects and 144,125 versus 142,792 ns at 4,096 objects. Charged idle authority-plus-replica batches of 1,000 had p50 101,333 versus 97,084 ns at 64 objects and 87,333 versus 86,709 ns at 4,096 objects. These overlap at the scale of local variation. All timing fixtures use `PublicationPool::new(usize::MAX)` to isolate cost, so pool contention correctness comes from the separate finite-budget tests. Changed-ID validation still allocates a temporary tree; baseline peer-key validation uses temporary trees; mutable world indexes, future output credits and complete precommit byte overlap remain unqualified.
