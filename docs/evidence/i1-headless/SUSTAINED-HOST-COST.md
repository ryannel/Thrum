# Sustained selected headless host cost

> Status after the code-quality cleanup: the I1 timing examples cited here were removed from the active tree. Their historical measurements and source remain in Git; quoted example commands are no longer current commands.

2 November 2026. The ``i1_allocation_audit` example` (historical `git show 84d7673:crates/thrum-core/examples/i1_allocation_audit.rs`) has isolated `sustained_local` and `sustained_match` modes. Each creates a fresh closed-value authority, protected output host and required in-memory replica. The rule increments a targeted object, creates a 16-byte state payload through the admitted `RuleContext`, and emits a result and event. Every tick checks one atomic replica publication, committed results, consecutive event IDs, acknowledgements and final authority/replica state. These modes use the same rule in standalone and two-peer play; the match has 4,096 objects and the selected profile's maximum 16 actions due per tick. It changes 16 objects per tick, not 25% of the world. A reader holds one old snapshot for 100 ticks. On one later tick, an unrelated owner reserves every unused pool byte after input admission; the already accepted callback still commits. The host, replica and all retained owners release their pool charges at teardown.

The fixture warms up for 1,000 callbacks, then measures 30,000 callbacks with `Instant` around submit, callback, replica handoff, acknowledgement and local checks. It advances a synthetic 60 Hz clock through 500 seconds of game time; the actual process runs far faster, so this is a repeated-path and retention probe, **not** a 500-second wall-clock, thermal or device run. Successful Rust global-allocator requests and requested bytes are counted only in this standalone diagnostic binary. Its atomics cannot see allocator-internal overlap, C/OS/GPU allocations or compiler-elided requests. The retained requested-live and logical pool checkpoints are sampled after warmup and every 5,000 measured ticks. Process peak RSS comes from `wait4` for each isolated child process, including setup, sample storage, output and teardown. `pool_max` excludes the deliberately temporary competing reservation.

Three alternating serial runs on local macOS 26.6.2 ARM64 with pinned Rust 1.99.1 and a release build produced:

| Path | p50 / p99 / max, submit through acknowledgement | Successful allocator requests / requested bytes over 31,000 ticks | Requested-live checkpoints | Pool after callback / observed maximum | Whole-process peak RSS |
| --- | --- | --- | --- | --- | --- |
| 64 objects, one peer, one action/tick | 0.750–0.792 / 1.000–1.042 / 11.208–13.959 µs | 527,001 / 91,016,168 B in each run | 508,219 B at all seven points | 29,744 / 38,096 B | 2,654,208–2,686,976 B |
| 4,096 objects, two peers, 16 actions/tick | 3.875–4.042 / 5.292–6.333 / 36.875–61.042 µs | 1,457,008 / 223,205,040 B in each run | 2,111,915 B at all seven points | 1,633,440 / 1,840,688 B | 4,997,120–5,013,504 B |

The request counts average about 17 and 47 per tick respectively, including the 1,000 warmup ticks; total requested bytes are churn, not retained bytes. Requested-live and pool checkpoints do not grow after warmup in these fixtures. The local first run showed higher timing tails than later runs, so these are observed ranges rather than a portable latency bound or a claimed speedup. Fresh process invocations rebuild the world and host and release all pool owners; they do not restore a saved game. The 64-to-4,096 object comparison probes content scale, not live scene streaming or a general allocation profile. There is no transport, renderer, real device pressure or game-authored private allocation in these modes. The [earlier positive control](PROCESS-ALLOCATION-AUDIT.md) demonstrates how private rule work can bypass pool charges.
