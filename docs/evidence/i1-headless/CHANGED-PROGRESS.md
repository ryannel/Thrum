# I1 changed-only replica progress

> Status after the code-quality cleanup: the I1 timing examples cited here were removed from the active tree. Their historical measurements and source remain in Git; quoted example commands are no longer current commands.

1 November 2026. The replica now reuses its confirmed peer-progress map for a group with no new results when its sorted peer watermarks exactly match the existing map and every peer has no buffered sequence above a gap. This applies even when the group changes world state. It still validates changed identities, lifecycle and event/result consistency before applying any state. A new/reordered peer, changed watermark, result or buffered gap uses the full transactional progress path. No peer map or advertised-watermark map is cloned or allocated in the reuse path; checking the watermarks costs O(P) comparisons for P peers.

The focused two-peer fixture attempts a changed-state group with a false second-peer watermark and observes `IncompleteOutcome` without advancing the replica or changing the object. The same group with correct watermarks then applies. The existing baseline gap-normalization, duplicate-watermark, delayed-result and two-peer tests still pass under `RUSTC_WRAPPER= ./dev check`. The complete run passed 18 core, 6 clock and 40 game integration tests.

The `release fixture` (historical `git show 84d7673:crates/thrum-core/examples/i1_changed_progress_cost.rs`) applies 10,000 changed-only groups after 1,000 warmups, with group cloning outside the timed interval. Two local macOS/aarch64 runs measured replica `apply` p50/p95/p99 of 83/84/84 and 83/84/125 ns with two peers; 167/209/250 and 167/209/209 ns with 64 peers. These values include changed-ID and lifecycle validation and are local observations of the selected path, not a before/after speedup or a device latency claim. The fixture does not measure the authority step, group construction, host callback or a byte-complete gate.

The current replica still uses uncharged validation storage for changed IDs and a mutable `HashMap` for confirmed objects. Groups with new results or a changed peer set still clone the progress map. Those owners remain in the whole-tick memory proof queue.
