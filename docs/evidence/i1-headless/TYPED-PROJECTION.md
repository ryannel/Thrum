# Borrowed typed values in the protected two-peer path

> Status after the code-quality cleanup: the I1 timing examples cited here were removed from the active tree. Their historical measurements and source remain in Git; quoted example commands are no longer current commands.

2 November 2026. **Local fixture proof, not a finite native game-work or process-memory guarantee.** The `allocation audit example` (historical `git show 84d7673:crates/thrum-core/examples/i1_allocation_audit.rs`) now adds one typed counter rule to its existing allocator observer. `CounterView` decodes the closed record's eight inline bytes and borrows its optional charged stamp. Actions and events use eight inline bytes. The rule and its state/action meaning are identical in standalone and two-peer authorities; it creates one 16-byte state stamp per committed action through `RuleContext`, and uses an eight-byte authority-owned reusable scratch handle between `decide` and `prepare`. No second typed state owner is introduced by the view.

The two-peer fixture admits eight timed actions per peer for tick two, with fixed increments of one and two respectively. Tick one remains idle. A retained tick-zero snapshot and a competing pool reservation occupy every unreserved logical byte while tick two commits all 16 actions through the required charged replica. All 16 committed results and ordered events are checked; the replica's typed state and final stamp equal 24, while the old snapshot remains zero. Both peer prefixes are acknowledged. The replicated host refuses an existing peer's new connection epoch with `RequiresBaseline`; a fresh charged baseline then builds a new replica with the same state and no already acknowledged results. All owners release to zero after teardown. This tests fresh baseline construction, **not** successful host reconnect, arbitrary numeric actions or remote delivery.

Three serial runs of the optimized binary on local macOS arm64, pinned Rust 1.99.1, locked offline dependencies, gave identical Rust allocator and pool counters:

| Mode | Admission requests / requested bytes | Idle plus due callbacks requests / requested bytes | API-boundary peak above pre-admission live bytes | Pool before / after admission / after callbacks, excluding competitor |
| --- | ---: | ---: | ---: | ---: |
| Typed standalone, 8 inputs | 4 / 2,520 B | 34 / 2,408 B | 3,040 B | 4,613 / 43,525 / 7,229 B |
| Typed match, two peers, 16 inputs | 8 / 5,040 B | 50 / 3,768 B | 5,232 B | 5,717 / 83,797 / 10,525 B |

The typed view itself contains a decoded `u64` and a borrowed slice; it performs no allocation in source. The callback counters include the idle tick and 16 charged payload creations, as well as engine publication work. They do not isolate view-decoding cost and should not be compared as a speed result with the scalar rule: the typed fixture does different output work and keeps a 16-byte payload per action. Pool figures are **requested owner/reservation bytes**, not resident bytes. The peak is sampled at API boundaries and misses allocator-internal overlap and short-lived peaks. Post-ack fresh baseline construction is checked but falls outside the admission/callback counters.

The isolated `typed_two_peer` process mode measured maximum RSS of 1,900,544 B and macOS peak memory footprint of 1,114,424 B in each of three serial `/usr/bin/time -l` runs. Those whole-process values include startup, construction, submission, callbacks, baseline rebuilding and teardown. They do not provide phase attribution or a device budget. The original scalar/private-allocation modes remain in the binary and retain their earlier counter values; their earlier [record](PROCESS-ALLOCATION-AUDIT.md) refers to its own published binary identity.

Reproduce with `RUSTC_WRAPPER= rustup run 1.99.1 cargo build --release --locked --offline -p thrum-core --example i1_allocation_audit`, then run `target/release/examples/i1_allocation_audit` for both typed modes, or `/usr/bin/time -l target/release/examples/i1_allocation_audit typed_two_peer` for isolated process RSS.
