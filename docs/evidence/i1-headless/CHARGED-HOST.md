# Sealed charged host callback

> Status after the code-quality cleanup: the I1 timing examples cited here were removed from the active tree. Their historical measurements and source remain in Git; quoted example commands are no longer current commands.

1 November 2026. This is a bounded host handoff proof, not the complete process byte gate. `HeadlessHost::with_charged_replica` builds a finite charged replica from a sealed charged baseline. `on_callback_charged` runs the same validated authority-then-replica stage order as the prototype callback, publishes shared charged outcomes, and retains the committed snapshot until its caller releases the callback result. The ordinary callback rejects a charged host before advancing its clock.

Before activation, the sealed host reserves a shared floor for eight independent callback buffers. Each buffer admits at most `min(max_ticks_per_call, CPU-admitted ticks, 8)` publication entries. Review found that attaching a per-callback charge to `HostCallback` while exposing a public `Vec` would let callers move out the buffer and release its charge early. The public `HostPublications` wrapper keeps the Vec private with one floor permit, enforces the requested fill limit, offers read-only slice access, and transfers buffer and permit into its consuming iterator. A callback with no attempted tick allocates no vector; an empty failed callback releases an unused permit. A full competing pool still returns retryable publication backpressure for a due action whose group needs new bytes, with the failed clock tick retained and no rule edit. The two-peer test fills the pool, checks unchanged state/tick, releases it and retries the same callback time successfully. The requested Vec buffers are charged once at activation; allocator metadata and any allocator-supplied excess capacity are outside the logical cap, as with the other charged columns. The [idle delivery proof](IDLE-DELIVERY-FLOOR.md) covers clean progress under full pool contention and last-iterator release.

## Object headroom and liveness

The local replica table has a fixed maximum live count. The host now checks `replica.len + (all already queued inputs + this new input) × max_spawns_per_action` before a **new** input sequence enters the authority. Exact pending or resolved duplicates return their existing answer before this capacity check. A host constructed around pre-existing pending inputs also checks their conservative credits. This is an object-slot headroom guarantee, not a byte credit for future group/output/history allocations. It is conservative: a profile at its object limit can refuse an update, rejection or despawn if its game-wide declaration says that action could spawn. A useful profile needs enough spare object slots for its maximum accepted input envelope, or a later per-action bound; refusal occurs before sequence consumption and cannot strand an accepted action.

After the authority's single due-input scan, a defensive step check compares this tick's maximum declared spawns with the already charged replica table. If it fails despite host input admission, that is a terminal contract fault rather than an impossible retry loop. Ordinary snapshot/group/callback-vector pool backpressure remains retryable before edits. The later [history proof](COMPLETED-HISTORY.md) charges completed-history buffer growth before sequence admission; the [peer registry proof](PEER-REGISTRY.md) charges sorted peer storage at join. Replica progress maps/validation scratch and future output byte credits remain outside the pool.

The tests prove a two-peer callback with one committed event, one rejection, both results and watermarks, confirmed state and last-reader charge release. A second two-peer case reserves the last free slot for one accepted action, returns its pending duplicate, and refuses a future-timed peer's new sequence. When the first action is rejected, its credit is released; the future-timed action then enters, holds its credit across an idle tick and spawns at its due tick. Another new action is refused before sequence consumption, while resolved duplicate lookup and later idle ticks continue. A two-tick catch-up callback delivers the first charged group once before a later injected rule fault, then stays terminal. `RUSTC_WRAPPER= ./dev check` passes.

## Local callback cost

The `release fixture` (historical `git show 84d7673:crates/thrum-core/examples/i1_charged_replica_cost.rs`) runs 1,000 warmups and 10,000 measured callbacks, each with one closed-value replacement, one accepted action, immediate acknowledgement and two registered peers. Synthetic monotonic callbacks arrive at approximately 60 Hz; the wall time measured is submit + callback + acknowledgement. The intentionally loose one-second CPU budget avoids turning OS scheduling spikes into benchmark overload; overload behavior has separate [host evidence](HOST.md). Two macOS/aarch64 runs gave these p50 nanoseconds:

| Records | Prototype, runs 1 / 2 | Charged, runs 1 / 2 |
| ---: | ---: | ---: |
| 64 | 1,083 / 709 | 1,084 / 833 |
| 4,096 | 1,042 / 1,083 | 1,125 / 1,167 |

These post-floor samples show substantial run-to-run and tail noise, with the two modes run sequentially. The charged median ranges from nearly equal to about 17% above the prototype in these runs. This cost buys explicit shared-owner, finite-object and callback-buffer admission on this slice. The fixture does not measure a device, real callback scheduling, transport, remaining host-delivery owners, or 1%/25% multi-object churn. The parent memory gate and whole-engine performance qualification remain open.
