# Native source-store transaction proof

2 November 2026. The selected [native source policy](../../design/FOUNDATION-SPEC.md#3-native-admission-and-browser-runtime-persistence) uses one SQLite database for exact source blobs, roots and outcomes. This first test-only proof uses `rusqlite` 0.40.2 with its bundled SQLite 3.53.2; it compiles with the repository's pinned Rust 1.99.1. The dependency is dev-only in `thrum-source`, so it adds no production source-tooling or game-core linkage yet. [Rusqlite's package documentation](https://docs.rs/crate/rusqlite/0.40.2) describes the bundled option and its build tradeoff.

The file-backed fixture creates and reopens a database with 4,096-byte pages, incremental auto-vacuum, WAL, `synchronous=FULL` and the selected 13,631,488-page main limit; it queries each setting after open. An `IMMEDIATE` transaction checks the retry token and expected root generation, updates the root and inserts the stored outcome, then commits. A same-token retry after reopening returns the stored generation; a changed request conflicts, and a stale generation leaves the root unchanged. A trigger aborts the outcome insert after the root update; transaction rollback keeps the old root, and a later retry succeeds. The test runs through `RUSTC_WRAPPER= ./dev check` or `RUSTC_WRAPPER= rustup run 1.99.1 cargo test --locked --offline -p thrum-source sqlite_store -- --nocapture`.

Source fixture SHA-256: `623bc788a5930a43d7b00863721a4dcfd4abcb53902ac5248b656e74b94768ec` (`crates/thrum-source/src/sqlite_store.rs`); executed debug test binary SHA-256: `8f544ef87def90fea2d20e2a6c7b67a9d5a750d28878738a612ff0dc0b6c92f5`.

This is a transaction primitive, **not source admission**. Its digest bytes are supplied by the test and have no staged blob/manifest closure or authenticated predecessor; reopening after a normal process close is not a process-kill or power-loss recovery test. The production adapter still needs bounded chunk writes, full staged-byte verification, complete/non-deleting blob checks, disk/WAL preflight, root/outcome/dedup/pin publication, old-root retention and interrupted-write recovery. `FULL` sync and a queried pragma alone do not certify a filesystem's power-loss behavior.
