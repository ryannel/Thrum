# Sustained reader-blocked WAL staging, narrow probe

2 November 2026. A test-only SQLite connection holds a read transaction on the root while another stages distinct verified 4 MiB blobs in short transactions. WAL autocheckpoint is disabled for the fixture, and the existing guard's `PASSIVE` start and stop are injected at 8 MiB and 40 MiB. After WAL accumulates, `PASSIVE` cannot finish past the held reader and the next attempt threshold advances by 64 MiB, so repeated writes do not rerun it on every chunk. As the WAL approaches the trial stop, staging returns `WalBackpressure`. The selected root stays at generation zero. Once the reader commits, the deferred hash is restaged and reaches complete state.

One local macOS arm64 Rust 1.99.1 release run completed **8** blobs before deferral, observed **34,097,152 B** WAL and took **117.893 ms** from the first trial staging call to deferral. The subsequent reader drain and retry passed. Reproduce with `RUSTC_WRAPPER= rustup run 1.99.1 cargo test --locked --offline --release -p thrum-source sqlite_store::sustained_blocked_reader_defers_chunk_staging_and_resumes_after_drain -- --exact --nocapture`. Source SHA-256: `f3f8ba0c91685eb91c11a376f45ee8a883747622c4ebdcaa32f4f3513eca056f` (`crates/thrum-source/src/sqlite_store.rs`). The full `RUSTC_WRAPPER= ./dev check` gate passes.

The 40 MiB threshold is an injected test setting, not the selected 2 GiB production stop. WAL page growth and the guard's per-transaction allowance remain heuristic; this single run does not prove a hard cap, steady-state throughput, editor latency, multiwriter fairness, free-space floor or power-loss durability. It extends the [earlier one-blob backpressure proof](SOURCE-SQLITE-WAL-BACKPRESSURE.md) with repeated chunk writes under one blocked reader.
