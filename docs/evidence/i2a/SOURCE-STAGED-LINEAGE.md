# Staged source-history lineage

2 November 2026. `compare_staged_histories` takes two already checked provisional registries for the same project, rereads and rehashes each declared history file from its stage, parses both bounded source-carried records, and applies the existing monotonic field-meaning and type-version comparisons. The parsed entries borrow their two input buffers through the linear join; there is no copied third history vector. A fixture accepts a candidate that adds a retired field and an old type version, then rejects a candidate that drops the previously carried field or version. This establishes a **staged-byte relationship** only: the caller has not authenticated the earlier stage as the current admitted root.

An ignored release probe creates two stages of the same dense fixture. Each has 4,099 files and 22,851,816 captured bytes, including 100,000 history fields and 1,024 versions. Three serial local macOS arm64 runs of the history reread, parse and comparison took **50.194, 51.142 and 50.549 ms**. Separate fresh test processes peaked at **76,070,912; 75,939,840; 75,857,920 bytes RSS**. RSS includes fixture generation, two stages and registry validation; the timed portion begins after those stages and registries exist. The probe does not include root authentication, maximum reference-edge summaries, an admitted store, or the later transaction. These measurements inform a physical-peak decision but do not select or enforce a memory reservation.
