# SQLite space faults preserve the selected root

2 November 2026. **Test-only recovery proof for the selected planning policy.** Two local tests force SQLite's actual `SQLITE_FULL` error after an ordinary source preflight would allow work. `PRAGMA max_page_count` is set to the current database page count solely as a deterministic fault injector; the test store no longer fixes that pragma to the former 52 GiB planning value on open.

In the first test, a validated candidate adds a 1 MiB ordinary master to an already admitted three-record source. The injected SQLite page ceiling refuses its blob write with `DiskFull`. The prior root and retry outcome remain selected across reopen. Reopening without the injection and retrying the same request commits the new exact candidate revision. In the second test, an `outcome` trigger requests a 1 MiB SQLite blob during the final root/outcome transaction after the root row has been updated. `SQLITE_FULL` rolls back both changes; reopen sees generation zero and no outcome. Removing the injection permits the same request to commit both together.

Run `RUSTC_WRAPPER= cargo test -p thrum-source sqlite_full_` and `RUSTC_WRAPPER= ./dev check` with Rust 1.99.1. The two direct tests pass on local macOS 26.6.2 ARM64; `sqlite_store.rs` SHA-256 is `ff23a7fd22d6ad4ed7be509bfcc1579371024ab7890acdb3019843dbaa8a1d7d`. These are genuine SQLite space errors, but a low page ceiling is not the same as an exhausted host volume. The root-only trigger test uses a verified blob, not a full F3 candidate closure; the candidate test faults during blob staging, not final commit. Power-loss behavior, a production accepted-source API, collector-enforced pins, cross-platform fault handling and high-water measurements remain open.
