# Process kill inside the root/outcome transaction

2 November 2026. A local two-process test reaches a precise point inside the test-only final SQLite transaction: the child has executed both the root-generation update and retry-outcome insert, but has not called `COMMIT`. A second connection still reads generation 1 and no outcome for the new token. The parent kills and reaps the child, reopens the database, and again finds generation 1 and no outcome. The already complete new blob remains available; retrying the same request commits generation 2 and the outcome together, and both survive another reopen.

The test-only hook runs after both SQL mutations and immediately before `tx.commit()`. The same transaction and generation/closure checks used by the earlier root proof remain in place. The bounded child-start wait and on-drop kill guard are shared with the [committed-chunk interruption test](SOURCE-SQLITE-CHUNK-KILL.md). `RUSTC_WRAPPER= ./dev check` passes on local macOS arm64. Independent read-only review found no issue with hook placement, isolation, cleanup or retry. Source SHA-256: `5f70e6c3d2ea2958dd930957706f2e26bccec4c958295cca321d262144f33e7f` (`crates/thrum-source/src/sqlite_store.rs`). Reproduce with `RUSTC_WRAPPER= rustup run 1.99.1 cargo test --locked --offline -p thrum-source sqlite_store::process_kill_inside_root_transaction_rolls_back_root_and_outcome -- --exact --nocapture`.

This proves rollback after process termination with an **open transaction** for one complete blob. It does not show that uncommitted pages had reached the WAL, a power-loss flush guarantee, a complete staged source candidate, GC pin survival, physical-space exhaustion or production acceptance. Those remain separate gates under the [native source-store contract](../../design/FOUNDATION-SPEC.md#3-native-admission-and-browser-runtime-persistence).
