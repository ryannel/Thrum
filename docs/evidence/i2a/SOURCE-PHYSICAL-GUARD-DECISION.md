# Native source space planning and failure recovery

2 November 2026. **Selected policy after user steer; implementation still open.** The [Foundation specification](../../design/FOUNDATION-SPEC.md#4-working-files-crash-recovery-and-gc) now treats 52 GiB SQLite main, 2 GiB WAL, 2 GiB managed temporary and 8 GiB observed free space as configurable planning targets. The user explicitly chose planning limits with space-fault recovery over hard write-time disk caps. This does not change the source format's finite record/blob limits or the requirement that only a verified root/outcome transaction can accept a source revision.

The test-only store's preflight, live free-space check and `ensure_wal_room` already demonstrate early refusal and blocked-reader deferral. Their per-write allowances are estimates, so actual main/WAL lengths may exceed a selected target. Production must expose the selected plan and observed high-water separately, and must not claim a certified physical cap. It need not add a custom SQLite VFS merely to enforce these default numbers. SQLite documents that long readers can prevent WAL reset and that a transaction cannot reset the WAL midway; `journal_size_limit` is not a prewrite guard. See [SQLite WAL behavior](https://www.sqlite.org/wal.html) and the [journal-size pragma](https://www.sqlite.org/pragma.html#pragma_journal_size_limit).

## Production gate

1. Make the native project plan configurable before capture/admission. Use the selected values to estimate retained old/new closure, stage copies, unique missing blobs, main/WAL growth, managed temporary use and free headroom. Count shared hashes once. Refuse an estimate that does not fit; do not imply the estimate reserves physical blocks or excludes external writers.
2. Check actual volume free space, main/WAL lengths and managed temporary use before each bounded write and checkpoint. Start `PASSIVE` checkpoints at the selected high watermark; if a reader blocks `TRUNCATE` at the selected stop watermark, defer *new* staging transactions and report why. An in-flight transaction can cross the target; record its observed peak and avoid claiming it could not. Keep SQLite's main-file size policy independent of the default 52 GiB planning number.
3. On `SQLITE_FULL`, write, sync, checkpoint or commit failure, preserve working files and unaccepted intent. Reopen and verify the selected root and retry outcome together; the old pair remains selected unless the final atomic transaction committed. Incomplete blobs cannot satisfy closure and may be collected only after pin/grace checks. A lost reply after a successful commit returns its stored outcome. External actors can exhaust the volume between checks, so the reported guarantee is transaction recovery, not maintenance of an absolute free-space floor.
4. Prove the fault paths with two SQLite connections, a reader-blocked WAL, an injected low planning target, an actual or injected `SQLITE_FULL` during chunk and final root/outcome work, and process termination before/after the final commit. Reopen at each point, verify old-or-new complete root/outcome and exact blobs, then retry after the reader drains. Measure normal small edits, 4 MiB chunks, 1,000 tiny files, sustained blocked-reader behavior and physical high-water on macOS, Linux and Windows before claiming portable native admission.

This policy removes the old static-bound/custom-VFS decision from the critical path. It does **not** check the production-admission, collector-pin, cook or save boxes. The [Build Plan](../../BUILD-PLAN.md#parked-retained-in-git-history) retains them as separate gates.
