# Native source physical guard: decision still open

2 November 2026. **Engineering risk and proof queue, not a selected implementation.** The [Foundation specification](../../design/FOUNDATION-SPEC.md#4-working-files-crash-recovery-and-gc) selects a 52 GiB SQLite main-file ceiling, 2 GiB WAL stop, 2 GiB managed temporary bucket and an 8 GiB observed free-space floor for the first native adapter. The test-only store's `ensure_wal_room` and `preflight_candidate_space` use projected per-write allowances, then check live WAL length and volume free bytes. They prove useful early refusal and blocked-reader behavior, but their allowances do not establish a maximum for SQLite's actual writes. The unchecked [physical gate](../../BUILD-PLAN.md#after-the-foundation) remains open.

SQLite documents that a long reader can prevent checkpoint completion and WAL reset, so further writes may keep growing the WAL. It also documents that a transaction cannot reset the WAL midway and may grow it substantially. `journal_size_limit` acts at commit/reset, not as a prewrite cap. The SQLite VFS interface owns file `xWrite`, `xTruncate`, `xFileSize` and sync operations; a wrapper could observe or refuse physical file extensions at the actual write boundary. SQLite describes its `test_quota.c` VFS shim as an existing example of grouped file-size enforcement that returns `SQLITE_FULL`. It is a design reference, not a production dependency or qualification. Sources: [WAL behavior](https://www.sqlite.org/wal.html), [VFS interface and quota example](https://www.sqlite.org/vfs.html), [journal-size pragma](https://www.sqlite.org/pragma.html#pragma_journal_size_limit).

## Decision to resolve before a production accepted-source API

1. Try to derive and independently verify a conservative per-transaction main/WAL growth bound from the selected SQLite version, schema, page size, maximum chunk/batch and cache behavior. A bound that effectively charges the entire 52 GiB database for every transaction is safe but unusable near the 2 GiB WAL stop; if that is the only defensible bound, reject this route.
2. If a useful static bound is unavailable, prototype a narrowly scoped native SQLite VFS wrapper around the platform VFS. It must classify the project main/WAL/managed temporary files, serialize its own writer reservations, check logical extension before `xWrite`/`xTruncate`, and return an ordinary SQLite space error before exceeding a selected project-file cap. Checkpoint writes count against the main cap and live free-space floor. Keep foreign file I/O outside this project's accounting. Any FFI/unsafe exception needs a separate safety review and exact dependency/target policy; do not expose the wrapper merely because the test store compiles.
3. The 8 GiB floor can be checked against actual volume free space before each project extension, with a reserved allowance for the current operation and emergency rollback/checkpoint work. Other processes can consume space between checks, so this is an observed local admission condition, not a guarantee against all external writers or hardware failure. Report a real `SQLITE_FULL`/I/O fault as an unaccepted operation, keep the previous root, and recheck actual files and closure on recovery.

The selected route must preserve `synchronous=FULL` and the platform durability claim, root/outcome atomicity, complete-blob verification, short read transactions and pin/collector ordering. A wrapper cannot silently alter SQLite lock or sync semantics. Measure per-write overhead on unchanged small edits, 4 MiB chunks, 1,000 tiny files, sustained reader-blocked WAL and checkpoint catch-up; compare main/WAL/temporary file high-water and fresh-process RSS. Refuse a route whose hot edit cost or cross-platform maintenance burden is disproportionate to the guarantee it supplies.

## Required adversarial proof

Use a real SQLite file and at least two connections. Hold a reader across repeated bounded blob writes, approach the WAL boundary, inject refusal on the next would-extend write, and verify no selected-root advance; drain the reader and prove checkpoint/retry progress. Repeat at main-file and free-space boundaries, during chunk write, during final root/outcome commit and during checkpoint. Kill the process at those boundaries, reopen, verify old or fully committed root/outcome together, and check incomplete blobs remain unselectable. Include a competing writer and a foreign process that lowers free space after initial preflight. Run the same correctness matrix on macOS, Linux and Windows before claiming portable native admission. A local test's exact 2 GiB stop requires a practical sparse/controlled-volume fixture; injected low limits are useful for logic but cannot alone qualify the real threshold.

Until one route passes these tests, test-only SQLite probes must keep `accepted` out of their public API. F4 cannot cook from their provisional root, and the editable-game parent item stays unchecked.
