# Direct source-file closure at the SQLite root

2 November 2026. A test-only `commit_manifest_probe` derives the canonical manifest revision, requires its complete blob, then checks every direct manifest file hash and exact byte length against complete SQLite blob headers in the same `IMMEDIATE` root/outcome transaction. A missing second file and an injected wrong stored length both refuse with root generation zero. After the correct complete blobs are present, the transaction commits; reopen returns the root and matching token outcome. A matching retry returns the persisted result without rechecking closure, preserving the foundation protocol's idempotent outcome rule. Later damage to stored bytes needs a separate integrity check and recovery policy.

The fixture checks two direct file entries. `RUSTC_WRAPPER= ./dev check` passes. Independent review caught the first version's retry revalidation fault; the corrected test asserts the stored outcome survives a later header change. Source SHA-256: `62ddf3708fded6bcd05e48cd4d3ebd1eb8e1fc9aaf2559ba02456906be614893` (`crates/thrum-source/src/manifest.rs`) and `36eb27db19d515031a28a99de27d746e3fc6b58b60f14ecf95d4db11d7b1be48` (`crates/thrum-source/src/sqlite_store.rs`); executed debug test binary SHA-256: `bc77edc0cec1b95a0d733cda84fb202a6e328fdabab20be046cde51d01dd8bb6`.

The file check uses completed blob metadata, whose bytes were checked when each blob became complete. This fixture does not parse a manifest read from SQLite, authenticate a predecessor's registry history, resolve dependency roots, preflight peak disk/WAL space, pin retained roots, test process-kill recovery or expose accepted source to cook/run. It makes no whole-project admission or performance claim.
