# SQLite blob completion proof

2 November 2026. The test-only native SQLite fixture now writes a supplied blob in bounded **4 MiB chunks**. It records an incomplete header first, commits each chunk in a short transaction, checks the input's exact length and SHA-256, then rereads every stored chunk and checks its ordered layout, total length and SHA-256. The stored reread and transition to `complete` run inside one `IMMEDIATE` transaction. The root/outcome transaction refuses a missing or incomplete header.

Source fixture SHA-256: `593b63c0ebb215951cbf29679be17d7dc72f9ebe9a587900cdf75f2747f8e560` (`crates/thrum-source/src/sqlite_store.rs`); executed debug test binary SHA-256: `f7a6ac81bf1dd9a53c232da2b1655f842c1a3e579a8b1b2ee4b87a37ec4a2de5`.

Tests exercise a 4 MiB plus 17-byte blob, exact 4 MiB/17-byte stored chunk lengths, a wrong hash that remains incomplete, a truncated stream after its first committed chunk followed by a clean same-hash retry, and reuse of a previously complete hash. A second connection with no busy wait tries to reset the same hash after the first connection has verified its stored chunks; the final transaction holds the SQLite write lock, so the reset is refused until completion. Each chunk insert also requires the matching incomplete header in its own write transaction. A stale two-chunk stream is paused after chunk zero while another connection resets and completes the hash as a valid one-chunk blob; the stale stream cannot append its second chunk. `RUSTC_WRAPPER= ./dev check` runs these tests; `RUSTC_WRAPPER= rustup run 1.99.1 cargo test --locked --offline -p thrum-source sqlite_store -- --nocapture` runs them alone.

This proves a **blob-state prerequisite**, not source admission. The fixture's bytes are arbitrary and do not form a parsed `TreeManifest` or the transitive exact-file closure. Reusing a complete hash deliberately does not consume or verify a new caller stream; a production admission owner must independently verify its staged source bytes before deduplication. The proof has no physical disk/WAL reserve, source history comparison, old-root/pin lifecycle, process-kill recovery, multi-writer scheduling policy or measured sustained I/O cost. SQLite and its bundled C code are still dev-only dependencies while the production store boundary is selected.
