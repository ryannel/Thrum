# Candidate source-space preflight, provisional proof

2 November 2026. The test-only candidate-to-root path now runs a physical-space preflight after retry-outcome lookup and before its first blob write. It sorts candidate file hashes plus the canonical manifest hash, rejects equal hashes with inconsistent lengths, and charges each unique blob only if a complete blob of the same length is absent. It reads SQLite's logical page count, main/WAL file lengths and actual available volume space. The projected main growth is a conservative **planning allowance** of 64 KiB plus twice each missing blob's page-rounded length, 16 KiB per missing blob and 4 KiB per chunk. The main ceiling is checked against the larger of logical pages and current main-file length. Required free space adds projected main growth, remaining WAL capacity, existing checkpoint debt (`logical pages × 4096 − main-file length` when positive), and the configured free floor. The test helper uses the selected 52 GiB main/2 GiB WAL ceilings but a zero free floor so CI is not dependent on 8 GiB local headroom; an injected floor proves the refusal branch.

Unit tests prove that an injected main ceiling, WAL ceiling or free-space floor refuses before any blob header exists and before root generation changes. A normal retry succeeds after those refusals. Complete blobs fit a narrowly limited repeated preflight, including when unrelated stored blobs force indexed lookups. A separate pure arithmetic check uses observed WAL-only pages to confirm that checkpoint debt is added to required free bytes and overflow refuses; it avoids relying on a changing shared-volume free-space sample. The existing full candidate tests still cover staged drift, current-root lineage, reopened retry and concurrent same-token winner. `RUSTC_WRAPPER= ./dev check` passes.

Hash lookup is chosen by a bounded table count: an empty store skips lookups, a stored table no larger than the distinct candidate hash set uses one sorted merge, and a larger table uses one prepared indexed lookup statement. The choice reads at most candidate count plus one stored row. This keeps a one-file edit independent of the number of historical blobs. A local Rust 1.99.1 release probe with 100,000 **synthetic metadata** entries measured 19.298 ms for a fresh store, 83.552 ms for a comparably populated store, and 0.194 ms for a one-file candidate against 100,000 stored rows. The populated rows are header-only fixtures without chunks; they isolate preflight lookup cost and are not accepted source or a valid stored closure. The earlier direct-query populated variant measured 181.759 ms in one run, but those single runs do not qualify a general speedup or device performance.

Reproduce the cost probe with `RUSTC_WRAPPER= rustup run 1.99.1 cargo test --locked --offline --release -p thrum-source sqlite_store::measure_maximum_candidate_space_preflight -- --ignored --exact --nocapture`. Source SHA-256: `f26d2b870970f34236e99e1031e5d8a4d507ffa1f3fbd24be0c2e4b10de39bf6` (`crates/thrum-source/src/sqlite_store.rs`); executed release test binary SHA-256: `49924e9116ac02a0d2b37a7a5f69d2b87992b66892016a5dc3b2f17a641fa5fc`.

**This allowance is not a proven upper bound.** The path has no per-transaction WAL growth guard, checkpoint backpressure, temporary-use recheck, cross-process reserve lock or handling of space taken by another actor. Resetting an incomplete blob can rewrite extra pages. The preflight therefore proves early refusal for tested limits and a measured cost shape, not that successful admission preserves the 8 GiB floor or 2 GiB WAL ceiling under every workload. The [native physical-space contract](../../design/FOUNDATION-SPEC.md#4-working-files-crash-recovery-and-gc) still requires that guard, GC pins, process-kill recovery and a production accepted-source API before source admission is complete.
