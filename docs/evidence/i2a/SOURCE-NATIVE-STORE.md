# First production native source store

2 November 2026. **Implemented bounded accepted-source profile; local correctness and store-cost evidence.** This is the first production boundary from a checked `StagedCandidate` to a durable `AcceptedSourceRoot`, under [C10](../../design/CONTRACTS.md), the [selected native protocol](../../design/FOUNDATION-SPEC.md) and the [first consumer handoff](SOURCE-FIRST-PROFILE-CONSUMERS.md). It does not make a build ready or a game runnable.

`thrum-source::NativeSourceStore` owns an app-managed SQLite database. Its `admit` method derives the candidate manifest, checks the caller's configurable `SourceSpacePlan`, rehashes the staged history and every staged file (including already complete blobs), authenticates the previous selected root's canonical manifest and source-carried history, writes missing exact-byte blobs and the canonical manifest, and checks every direct file's completed hash and length in the final transaction. The root generation, retry outcome and publication epoch commit together. Reopen checks that the selected root has a matching outcome. A matching retry returns the recorded root, and `outcome` can recover that root by epoch/key/request hash without rebuilding a staged candidate after a lost response. Changed token, stale generation, changed staged bytes or lineage refusal leave the prior root selected. The initial profile refuses external dependency roots and retains all complete blobs, manifests and outcomes; the mark-only GC experiment is not a production deleter.

`pin_current` records a durable short-lived read pin on the selected root; `pin_accepted` can reopen an older generation/revision only when a durable admission outcome owns it. Both authenticate a bounded canonical manifest plus complete direct-file headers. `PinnedSource::copy_file_to` locates a file by binary search in the sorted manifest, copies SQLite chunks with one reusable at-most-4 MiB buffer, and verifies the declared length and SHA-256. A failed copy can have written partial output; the cook caller must discard it. A successful copy alone is verified source bytes, not a ready cooked product. `close` reports pin-release failure; a failed release remains queued for retry on this connection. The append-only profile retains bytes even if a process exits with a pin. A future deleting collector needs durable owner recovery and transitive pin enforcement first.

The store uses a versioned schema, 4096-byte pages, incremental auto-vacuum, WAL and `synchronous=FULL`; macOS connections also set and verify `fullfsync` and `checkpoint_fullfsync`. Initialization commits the tables and schema version together, and an incompatible existing database is refused before schema writes. The selected plan controls preflight and observed WAL backpressure, while live free-space checks run before bounded writes. These are planning signals, not a physical quota. The [SQLite PRAGMA reference](https://www.sqlite.org/pragma.html) describes the sync flags; actual power-loss durability remains conditional on the VFS, filesystem and device, and has not been tested here.

## Verification and cost

- `RUSTC_WRAPPER= CARGO_TARGET_DIR=/Users/ryannel/Workspace/thrum/target ./dev check` passed for this checkpoint. The `thrum-source` suite had 112 passing tests and 37 ignored measurement fixtures. The existing genuine `SQLITE_FULL` blob/final-transaction and process-kill tests still passed after the core moved to production compilation. Later production fault tests are recorded in the [native disk follow-up](SOURCE-NATIVE-DISK-FOLLOWUP.md).
- Production-API fixtures admit, reopen and verify a copied scene, same-token retry, changed-token and stale-generation refusal. An injected outcome insertion failure leaves the old root and no new token across reopen, then retries successfully. An incompatible preexisting SQLite file, including one with all user tables dropped, is left untouched. A same-length corrupt stored chunk and a failing consumer output are reported distinctly. A multi-chunk pinned asset remains readable after another connection advances the root, can be pinned again from its historical outcome, and rejects a fabricated generation/revision pair. An observed WAL overrun is drained before the next candidate preflight once its reader is gone; a plan too small for one full chunk allowance refuses at open.
- Local macOS arm64, Rust 1.99.1 optimized test binary, ten successive small three-file edits per run, three sequential runs at this checkpoint. Stage capture and semantic validation were complete before each admission timer. Admission min/median/max in milliseconds: `22.791/34.372/34.957`, `22.315/34.832/35.417`, `23.983/33.998/35.514`. Pin, manifest/closure check, one scene copy to an I/O sink and pin release: `7.996/9.980/10.159`, `9.010/9.972/10.174`, `8.036/9.203/12.931`. These include local SQLite syncs and cache state; they exclude capture, semantic validation, cook, world startup, RSS and device I/O. Other local workloads were not controlled. They are a development cost observation, not an edit-to-ready or p99 guarantee. The [follow-up](SOURCE-NATIVE-DISK-FOLLOWUP.md) reruns this fixture after adding usage observations.

## Remaining gates

The first cook consumer must read only this pinned revision and produce an independently verified `BuildRevision`; run and save remain separate authorities. Wider F3 schemas, external roots, coordinated editor application, collector deletion, host power-loss tests and target hardware qualification remain open in the [build plan](../../plans/BRIEF.md).
