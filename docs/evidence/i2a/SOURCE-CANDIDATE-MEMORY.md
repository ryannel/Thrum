# Dense source-candidate memory and cost probe

2 November 2026. These ignored release fixtures exercise real stage capture and the current validator with Rust 1.99.1 on local macOS arm64. Source fixture SHA-256: `273d541cf7d1cfe5bcb66291c902a8e94d9e49f493f010c710c76d8d21d4391b` (`crates/thrum-source/src/registry_stage.rs`). Executed test binary SHA-256: `ecc1a62128a17b2460e1145bc3196e180be33e704946819f144d592ea73d2e27`. Each RSS reading came from `os.wait4` for a fresh test process; it is whole-process peak resident memory, including fixture generation and stage capture, not the validator's retained heap alone. Timed elapsed starts after staging, so it excludes fixture generation and capture.

The second path stops after registry validation and a direct parse of the game record. The current scene/game closure deliberately refuses game records with more than one active descriptor, so its lower elapsed time cannot be compared as a full-candidate speedup. Neither path includes an authenticated prior history buffer, the maximum 65,536 required-reference summaries, a real editor process, or SQLite/root transaction memory. They therefore establish useful local observations, not a safe physical parser/graph reservation or an accepted-source memory bound. The first bounded source-carried profile remains open.

Reproduce the release fixture with `RUSTC_WRAPPER= rustup run 1.99.1 cargo test --locked --offline --release -p thrum-source measure_dense_combined_candidate -- --ignored --nocapture` and the same command with `measure_dense_registry_and_game_parse`. For isolated RSS, execute the resulting `target/release/deps/thrum_source-*` test binary in a fresh process and read its `os.wait4(...).ru_maxrss`; macOS reports bytes. Do not run both fixtures in one process when comparing their peaks.
