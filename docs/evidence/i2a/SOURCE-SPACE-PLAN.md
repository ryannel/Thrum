# Configurable native staging space plan

2 November 2026. **Partial implementation of the selected disk-planning policy.** The user chose configurable planning limits and explicit space-fault recovery rather than hard native disk caps. [C10](../../design/CONTRACTS.md#c10-persistence-reproducibility-and-authored-operations--p7f3t1) and the [Foundation specification](../../design/FOUNDATION-SPEC.md#4-working-files-crash-recovery-and-gc) now assign the default 52 GiB main, 2 GiB WAL, 2 GiB managed temporary and 8 GiB observed free-space values as targets. Only the *provisional source stage* is configurable in code so far.

`thrum-source` exposes `SourceSpacePlan` and `stage_declared_tree_with_plan`. The original `stage_declared_tree` uses the default plan. The stage still scans declared membership, checks its projected stage/main/WAL work and actual available space before copying, then rechecks observed free space and temporary use during capture. A test sets the temporary target to zero and verifies refusal before a stage directory exists, then raises it and obtains a valid stage while an older stage remains readable. A second test checks that a tiny capture plans bounded WAL work instead of charging the entire unused 2 GiB stop target. The WAL estimate is twice projected SQLite growth, capped by the selected remaining target; it is not an upper bound on SQLite page writes. This demonstrates that planning numbers can change without changing source identity or the old-reader rule; it does not reserve filesystem blocks or implement a durable store.

Verification: `RUSTC_WRAPPER= ./dev check` on Rust 1.99.1 (macOS 26.6.2 ARM64); the stage tests and repository checks pass. Source SHA-256: `budget.rs` `0ed91b4ac6852ea48608ff8d0fb219830dc09ae2737c03cfabf70ed29422a57c`, `stage.rs` `e4b494fe304ca0b3b5f0ec3071c1bc7e7873f9dc17887351677a6a9fad1d4445`. The new public plan is a few scalar values passed to the existing preflight, so it adds no per-file branch or copy. The changed WAL estimate can avoid premature low-space refusal on small captures; no elapsed-time gain or device qualification is inferred.

The SQLite proof remains test-only and currently uses its own fixed default planning values. Before a production accepted-source API, it must accept the same selected project plan, keep `max_page_count` independent of the default main target, report estimated and observed high-water, and prove `SQLITE_FULL`/I/O recovery during blob and final root/outcome work. [The open production gate](SOURCE-PHYSICAL-GUARD-DECISION.md) owns those tests. No source revision becomes accepted through this stage API.
