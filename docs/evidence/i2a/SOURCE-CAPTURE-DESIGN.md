# I2a exact-source candidate capture

2 November 2026. **Selected first implementation slice; not durable admission.** This is the staging step of the [foundation source protocol](../../design/FOUNDATION-SPEC.md#2-file-application-and-source-admission). The later SQLite root/outcome transaction remains the only authority that can call a source revision accepted. A failed candidate leaves the working files visible and the previously admitted root untouched. The same exact-byte candidate can feed a local build, a clean handoff or a future server build only after it has been admitted and pinned; gameplay authority never reads the mutable checkout.

## One owner and one complete interaction

The source-capture tool receives a project root, a project ID, declared dependency roots and an explicit complete list of relative file paths. It never applies an edit. Before writing, the owning storage adapter estimates the physical peak of staging, retained old closure, new chunks, WAL, temporary work and free headroom under the selected project plan; capture refuses when that estimate exceeds the plan, then rechecks observed usage as it stages. For each declared regular file it validates a portable normalized path, copies bytes to a new isolated staging tree while hashing SHA-256, and checks the source again after the copy. An unresolved Git LFS pointer is refused rather than hashed as the referenced master; the first slice has no LFS resolver and conservatively rejects pointer-shaped declared files. It scans membership before and after capture, so an undeclared file, deletion, rename or ordinary concurrent edit refuses the candidate. Source JSON records receive strict duplicate-key, finite-number, nesting, schema/identity and dependency validation before any candidate revision is returned. The sorted `TreeManifest` contains format, project ID, declared dependency roots, path, kind, length, exact-byte hash and parseable record identity; `SourceRevision` is SHA-256 over its RFC 8785 JCS representation. The staged bytes and manifest are immutable to the capture API and have one cleanup owner. A separate durable-admission adapter later consumes and verifies them; no caller may label this staging result an accepted root.

An initial fixture edits one `scene.json` in a small declared project with `project.json`, a game source file and the scene. Capture A yields a revision and staged bytes. The edit leaves A's staged bytes unchanged; capture B yields a different revision. A duplicate JSON field, `..` path, symlink, case-fold alias, undeclared member or source change during capture rejects B without modifying A or any working file. The eventual cook/run consumer must read only admitted bytes, so this slice alone does **not** check the parent editable-game box.

**First-adapter staging plan.** The default native plan assigns 2 GiB to managed temporary/cache bytes and targets 8 GiB of observed volume headroom. An ordinary staging tree uses that temporary bucket, so preflight refuses when its rounded estimate plus existing managed use exceeds the *selected* plan. An operator can raise the plan after inspecting available space; a 16 GiB format-valid blob is not inherently rejected by an unrelated 2 GiB default. A direct-to-store staging path may reduce duplicate bytes and copying, but is a performance/space option rather than a prerequisite for larger source. The stage checks observed free space and temporary use during capture; a race or filesystem fault still requires clean refusal and preservation of the prior stage. The plan is neither a physical byte guarantee nor permission to exhaust the volume.

The v1 manifest has known object keys and sorted arrays. Its emitter writes keys in JCS order and uses tested canonical primitives directly into SHA-256; it does not pass the whole `files` array as one property to a generic JCS object serializer, which would buffer that property. A small independent serializer oracle checks the exact representation. This metadata primitive remains separate from verified byte capture and F3 semantic closure.

The [manifest writer proof](SOURCE-MANIFEST-WRITER.md) now makes that same emitter feed either SHA-256 or a fallible `Write` sink. A native chunk writer can persist canonical manifest bytes without materializing a second 100,000-entry JSON tree; its output still needs a verified blob and the later root/outcome transaction.

## Representation and cost

The candidate holds metadata for at most 100,000 entries, sorted once. One reusable 4 MiB byte buffer streams each file into staging and SHA-256; a second read checks the source hash and membership after capture. Thus ordinary capture is O(total source bytes + N log N) CPU with roughly two full source reads and one staged write, O(N) manifest memory and O(4 MiB) streaming scratch **plus** bounded JSON validation memory. A source JSON record is at most 16 MiB with nesting at most 64; its parser and transient duplicate-key sets retain finite input-shape bounds and receive allocation/RSS measurement under representative and hostile fixtures. There is no hard process-memory admission cap. One immutable blob is at most 16 GiB; a growing source is refused during streaming, not only by its initial metadata. The staging copy adds one full candidate byte closure to the physical peak; the storage owner must estimate it with retained old source, new blob chunks and WAL before capture, then recheck observed usage as actual bytes grow. A future immutable verified Git tree may avoid the second mutable-read path, but cannot silently substitute HEAD for dirty working files. Reuse the pinned buffer across files, stream JCS into the revision hash, and avoid a second whole-tree byte vector. This work is outside the simulation callback; optimize cold/warm edit-to-ready latency and disk write amplification after the correctness boundary is real.

Paths use UTF-8 `/` components in NFC, with no absolute, empty, `.` or `..` component, backslash, symlink, device or case-fold collision. Reject Windows reserved characters (`< > : " | ? *`), NUL/control characters, alternate-data-stream syntax, device names and trailing dot/space rather than giving a source revision two target-dependent meanings. Excluded generated roots are explicit and versioned, not an arbitrary wildcard. Full Unicode case folding must be used for collision checks; ASCII-only lowering is insufficient. Refuse unknown membership rather than silently omitting a master. A cooperative writer window plus reread detects ordinary drift; no filesystem scan proves an instantaneous tree against an adversarial noncooperating writer or ABA. Report that limit instead of claiming atomic filesystem capture.

The first crate belongs to native tooling/source ownership, with no dependency from `thrum-core` or mobile gameplay. Its storage-budget input is issued by the native admission owner, not fabricated by the caller; the initial implementation must include a concrete budget/preflight adapter before writing stage files. Exact direct dependencies, versions, licenses and build/target cost must enter `.config/architecture.toml` before checks pass. Candidate capture has a streaming byte-cost counter and wall-time fixture at small and 100k-entry metadata scales. The latter is a planning scale, not a device pass. Rejection criteria: a revision with bytes missing from staging, a path alias, a stage write before physical-peak preflight, acceptance without a durable root, mutable checkout bytes read by the cook, or excessive repeated full-tree allocation during an ordinary edit.

## Next gate: F3 semantic closure

**Broad semantic gate remains open.** The stage now returns a provisional candidate from rehashed staged bytes and checked local scene/game references across up to 256 source-carried descriptors. The [first bounded consumer handoff](SOURCE-FIRST-PROFILE-CONSUMERS.md) preserves the F3/F4/T1/W1/P7/N1 authorities. A general F3 validator still needs supported dependency roots, broader record schemas and complete consumer implementation without reading the mutable checkout. It should emit compact record identities and reference edges. A first pass validates each explicitly classified engine record's bounded JSON, common envelope, registered type/version and known required fields; a second pass checks unique IDs and supported target/root resolution and any selected dependency cycles. Only checked staged hashes and F3 descriptors enter `TreeManifest`; a failure retains the old stage and leaves admission untouched.

The registry is an immutable input to validation, not a second mutable authoring database. Core schema meanings are fixed by the source format and each type/schema version; a future incompatible meaning requires a versioned format/schema migration rather than a silent native-tool change. Game-owned schema descriptors, when introduced, must themselves be ordinary captured source records validated by a fixed descriptor grammar before they can define other records. Their exact bytes then participate in `SourceRevision`. This lets an admitted draft be schema-valid even when new game Rust code fails to compile. Runtime component bindings and network wire indices must later prove compatibility with the pinned schema registry; neither Rust `TypeId`, file path nor array position becomes a durable/wire identity. A record's `schema` version and the registry decide whether a field is known and required. Unknown values in explicitly optional extension locations remain in staged exact bytes for round-trip; an unsupported required schema/version refuses. Record classification must be explicit in project/schema declarations, rather than treating every `.json` file as an engine record or letting an unclassified file satisfy a required reference.

Validation cost is one read of each staged JSON record plus compact O(records + reference edges) summaries and graph work; binary masters are not parsed as JSON. The 16 MiB input and 64-container-depth limits alone do not prove a useful parser heap peak: a small JSON token can allocate a much larger `Value` node. The v1 parser now refuses after 1,000,000 value nodes, including containers, before constructing the next value. Before semantic admission is active, measure adversarial dense arrays/maps, enforce the selected aggregate reference-edge allowance, and profile peak allocations/RSS and a representative edit. Optimize measured pressure without a hard process-memory reservation. The work is native/offline, but repeated edits still need bounded latency and no second whole-tree `Value` cache. The v1 100,000-entry tree bound does not imply that 100,000 maximum-sized records fit in memory simultaneously.

The first complete interaction must edit a declared scene in a small project, then show A/B candidate revisions with different exact bytes while unchanged authored objects retain their stable IDs. Fixtures must reject duplicate/nested IDs, wrong field units or shape, unknown required versions, missing or wrong-type required references, dependency cycles, unclassified referenced files and conflicting project/dependency roots. An allowed opaque optional field must survive unchanged when no edit touches its file. The validator's selected schema grammar, finite parser work bounds and cross-project root resolver need reconciliation with F3, F4, W1, T1, P7 and N1 before the unchecked capture item can close.

**First narrow schema proof proposal.** Bootstrap with fixed `core.project` schema 1 at exactly `project.json`. Its `id` is the manifest project ID; `fields` contains a v1 format marker, a sorted list of engine-record paths and a nonempty list of entry-scene stable IDs. Every listed path must exist in the staged tree and resolve to a registered record type; unlisted JSON outside reserved engine-record path patterns stays ordinary source and cannot satisfy a reference. A file in a reserved scene/prefab/asset/schema-record path pattern that the project omits must refuse rather than silently become ordinary data. A fixed `core.scene` schema 1 can initially admit an empty scene or a human label and expose a stable scene ID. The project-to-scene reference then proves type-checked closure, duplicate-ID refusal and an A/B label edit without selecting object transforms, prefab expansion or runtime scene storage prematurely. A scene with object data must refuse until its explicit nested schema and W1 constraints are selected; a validator cannot wave it through as an optional unknown field. Until a pinned cross-project resolver and profile/dynamic-root validators exist, the proof refuses nonempty dependency roots and unsupported target/dynamic-root declarations. Keep these narrow schemas in one fixed bootstrap table, then add source-carried game schema descriptors only after their grammar and cost are proven. This is a bounded proof target, not a claim that F3 is complete or that every game scene is an empty record.

The proposed bootstrap record spelling is exact: `project.json` uses `type:"core.project"`, `schema:1` and `fields` with `project.format:1`, `project.records:[portable scene paths]` and `project.entryScenes:[stable scene IDs]`; both arrays are strictly sorted and duplicate-free, and the latter is nonempty. A listed scene file uses `type:"core.scene"`, `schema:1` and `fields` that is empty or contains only an optional string `scene.label`. The root object may contain the common envelope and an optional string `documentation`, but no other top-level keys. This proof accepts no prefab, asset sidecar, schema descriptor, object, target profile, dynamic root or external dependency declaration; those require their own registered semantics. Unknown optional extension handling is therefore a later F3 gate, not silently simulated by this bootstrap.

The fixed bootstrap now decodes directly into bounded ID/path summaries using schema-specific `DeserializeSeed` visitors. Its known-key maps reject duplicates and unknown keys before retaining an unknown value; its path and entry arrays stop at actual staged membership, so a 16 MiB JSON record cannot first materialize a huge generic `Value` tree or impossible declaration vector. Exact staged bytes remain available for a later consumer and any accepted optional extension representation. The general F3 registry will need its own strict streaming treatment of unknown optional nested data, including duplicate-key rejection, before this fixed fast path can be generalized. This specialized parser keeps the frequent small edit path near its measured prior latency while reducing the peak caused by a malformed record with many tiny JSON values; measured parser-heap qualification remains open for the general registry.

## General registry selection before implementation

**Provisional architectural choice.** Use a small, versioned F3 descriptor language for authored record and field identities, with explicit kinds, units, validity bounds, defaults, reference target/policy, and designated optional extension locations. Keep the descriptor records as exact source bytes in the captured tree. A fixed core descriptor grammar bootstraps them; source admission can then validate a draft independently of whether new game Rust code compiles. A changed field meaning or unit receives a new permanent field ID and schema version, with explicit migration where needed, never silent reinterpretation. This follows the stable-identity lesson of [Protocol Buffers field evolution](https://protobuf.dev/programming-guides/proto3/) without making its binary wire numbers the authored source language. N1 still maps pinned F3 IDs into its own protocol manifest indices; runtime `TypeId`, path and array order do not become wire identity.

**Meaning lineage.** Candidate descriptors alone cannot prove that a familiar field ID did not mean something else in an earlier admitted revision. Keep a required, ordinary source-carried F3 registry-history record mapping every ever-admitted `(type ID, field ID)` to its fixed mechanical meaning signature (kind, unit/frame, reference target/policy and other interpretation-bearing attributes), including retired IDs. New descriptors must agree with existing signatures; removal retains the retired entry, and reintroduction with a different signature refuses. The authoring admission adapter compares the candidate history with the history pinned by the *current admitted root* under the same generation precondition as root/outcome publication. A candidate missing prior entries, changing a signature, or naming a now-retired ID as a new meaning conflicts; a branch with an older history needs a reviewed union patch. Imported registries remain under their own pinned dependency roots and authority IDs; conflicting exported type IDs across roots refuse unless an explicit versioned alias/mapping is declared, never by path-order precedence. This is ordinary reviewable source state, not a second editable database. A fresh project establishes its baseline history from its first admitted tree; a clean recipient verifies the included history as part of that tree, while old saves/releases still require their own pinned schema closure and migrations. The check can enforce declared mechanical meaning, not infer dishonest changes to game-code behavior or natural-language intent.

The [pure lineage proof](SOURCE-MEANING-HISTORY.md) now checks ordered histories without allocation. Its signatures are opaque inputs: the later fixed descriptor grammar must derive and check them, and the durable root adapter must supply the authenticated predecessor within its generation transaction. This proof alone grants no source-admission authority.

### First source-carried registry profile

**Selected narrow implementation target.** The one-active-descriptor staged-candidate subset and two-descriptor dispatch proof were extended to an [all-256-type candidate](SOURCE-ALL-TYPE-EDGE-COST.md) at the 65,536-edge boundary. The first consumer handoff is reconciled in design; runtime consumption and general F3 closure remain separate work. Add `core.project` schema 2 rather than changing the meaning of schema 1. It keeps the existing project ID and entry-scene declarations, extends `project.records` to explicitly list both `scenes/*.scene.json` and `records/*.record.json`, and adds sorted `project.schemas` paths plus one `project.registryHistory` path. The new reserved `schemas/*.schema.json`, `schemas/history.registry.json` and `records/*.record.json` paths must be declared in their proper role; omitted reserved records refuse. The v1 empty-scene bootstrap remains a supported narrow profile. Nonempty external dependency roots, scene objects, prefabs, target profiles and dynamic roots still refuse in this first profile.

The fixed `core.schema` schema 1 record at a declared schema path describes one `game.*` type and one target schema version from 1 through `u32::MAX`; this first profile permits exactly one declared version per game type and requires every current record to use it. Its fields are `schema.targetType`, `schema.targetVersion`, a strictly sorted `schema.fields` array and optional `schema.optionalExtensionPrefix`. Each field descriptor has a permanent ASCII `id`, `kind` and `presence`; the first two kinds are bounded UTF-8 `text` (`maxUtf8Bytes` from 1 through 4,096) and `record-ref` (`targetType`, required resolution, canonical record UUID). The only initial reference target is `core.scene`. A field's `presence` is `required` or `optional`; it controls whether the key may be absent, not whether a present reference may be unresolved. All numeric, transform, array, soft-reference, default and migration semantics wait for their own versioned kinds. Descriptors and history use the common record envelope and reject unknown/duplicate keys. Type and field IDs use at most 128 ASCII bytes, with lowercase dot-separated segments beginning with a letter and then letters, digits or hyphens; `core.*` is reserved to fixed engine records. Display labels may change without changing meaning, but they never participate in a record's field lookup.

The first game fixture uses one `game.marker` schema 1 record at `records/marker.record.json`: required `marker.scene` points by stable ID to a declared `core.scene`, and optional `marker.caption` is bounded text. The game record's `fields` map rejects any other key unless the descriptor explicitly declares a nonoverlapping prefix such as `x.game.marker.` for **optional opaque** keys. That prefix cannot contain a registered field ID or supply a required gameplay, save or wire value. The validator must still check full strict JSON syntax and duplicate nested keys inside opaque values, retain the exact staged bytes, and show an edit to a neighboring known field leaves the opaque value byte-identical. An unknown required version or a field outside the declared optional prefix refuses. A future game-code build may fail while this source schema remains valid; F4 separately checks bindings and target readiness.

For the first game-record validator, cap known fields at the descriptor's 128 and opaque extension fields at another 128. Within all opaque values in one record, cap total JSON nodes at 65,536, whole-record container depth at 64 **including the record and `fields` objects** (so at most 62 opaque containers), members of each nested object at 1,024, UTF-8 key bytes at 128, and decoded string-value bytes at 65,536. Refuse an excess object member before reading its key and an excess node before traversing its value; validate key length before storing it in the duplicate set. These are memory and work bounds for optional data with no gameplay semantics, not arbitrary source-file or function-length style rules. Keep the original staged bytes as the opaque round-trip authority; the validator only emits bounded known-field and required-reference summaries, pinned to the descriptor definition hash. Measure dense valid and hostile optional shapes, optimize their physical peak and report the qualified workload before this validator contributes to an admitted candidate.

The fixed `core.registry-history` schema 1 record at `schemas/history.registry.json` carries two strictly sorted, duplicate-free lists under `fields.registry.fields` and `fields.registry.versions`. A field-history entry has exactly `typeId`, `fieldId`, `signature` (64 lowercase hex digits) and `retired` (boolean); a version-history entry has exactly `typeId`, `targetVersion` and `definitionHash` (64 lowercase hex digits). `registry.fields` maps every ever-admitted `(type ID, field ID)` to its 32-byte signature and retired flag. For active descriptors, the validator derives the field signature as `SHA-256("thrum-f3-field-meaning-v1\0" || JCS(attributes))`, using UTF-8 domain bytes and one zero byte, where `attributes` contains `typeId`, `fieldId`, `kind`, `presence`, and exactly the kind-specific `maxUtf8Bytes` or `targetType` and `resolution` keys. It compares that digest with the source history, rejects a retired active descriptor, and requires every active descriptor field in history. A removed field must remain as a retired history entry.

`registry.versions` maps every ever-admitted `(type ID, target schema version)` to a fixed definition hash. The definition hash is `SHA-256("thrum-f3-type-version-v1\0" || JCS(definition))`; `definition` contains `typeId`, `targetVersion`, the sorted active `fields` array of `(fieldId, lowercase-hex field signature)`, and `optionalExtensionPrefix` as a string or `null`. A current descriptor must reproduce its version entry exactly. Every previous version entry and hash must remain in the candidate history, even after its records are migrated; a duplicate or reused `(type ID, version)` with changed field set, field meaning or extension policy refuses. The version history is bounded separately from field history. Display labels and source paths are excluded from both hashes. A new descriptor kind or interpretation-bearing attribute requires a new signature domain and reviewed format version, never an untracked change to the v1 preimage.

A first admitted project can establish a baseline history; each later candidate must additionally compare **both** candidate histories with those from the current admitted root under its generation precondition. The source parser alone cannot assert that predecessor. Field additions, retirement or extension-policy changes require a new target schema version; current records need migration to that version before this first profile can accept them. A changed field signature requires a new field ID and an explicit migration where old data exists. Imported schema roots and exported-type collisions remain outside this first profile. The [pure lineage proof](SOURCE-MEANING-HISTORY.md) now compares both sorted histories, but derives neither hash and cannot authenticate the predecessor root.

The [canonical hash proof](SOURCE-DEFINITION-HASHES.md) now derives both first-profile digests from checked value shapes and independently verifies their JCS byte representation. It still receives values directly, not from staged source records, and does not certify history consistency or the prior root.

The [fixed descriptor-record proof](SOURCE-SCHEMA-RECORD.md) now decodes one bounded `core.schema` record directly from supplied JSON bytes and derives those hashes. Its caller has not yet proved that the bytes came from a declared, rehashed stage path, that source history agrees, or that a game record follows the descriptor.

The [registry-history record proof](SOURCE-REGISTRY-HISTORY.md) now decodes bounded sorted field and type-version entries directly from supplied JSON bytes. It borrows ordinary unescaped identifiers from its input buffer, while escaped spellings take owned fallback storage. The authenticated predecessor and staged-tree path checks remain open.

The [active-registry consistency proof](SOURCE-REGISTRY-CONSISTENCY.md) now joins parsed active descriptors with those parsed histories without copying the history vectors. It does not select a project declaration or compare with the current admitted root.

The [carried-lineage proof](SOURCE-CARRIED-LINEAGE.md) now compares two parsed histories with the same field and type-version rules and no second entry vector. It measured two live maximum field-history inputs, but does not authenticate the prior buffer or measure the later descriptor/graph peak.

The [schema 2 project declaration proof](SOURCE-PROJECT-V2.md) now parses bounded sorted paths for records, schemas and history from supplied JSON bytes. It has not yet joined them to the rehashed staged tree or resolved entry-scene IDs.

The [game-record proof](SOURCE-GAME-RECORD.md) now checks known fields and opaque extension syntax directly under a parsed descriptor and emits a compact typed-reference summary with the descriptor hash. Cross-record resolution, staged-byte provenance and editor round-trip remain open.

The [staged registry proof](SOURCE-STAGED-REGISTRY.md) now joins the schema 2 project declaration to rehashed staged project, descriptor and history records. It checks all declared paths exist, refuses unlisted or unsupported reserved record paths, sorts descriptors by type, compares active fields and immutable versions with the carried history, and rejects duplicate registry-record IDs. Project and descriptors reuse one input buffer, which drops before the borrowed history input; the history buffer drops after the consistency join. Scene/game records are deliberately not parsed in this slice, so this result is not a complete semantic candidate or manifest.

The follow-on [staged record closure](SOURCE-STAGED-RECORDS.md) rehashes and parses declared scenes and game records under one active descriptor, then resolves unique IDs, entry scenes and required game-to-scene references. A reusable record buffer avoids one new input allocation per file, and 65,536 required edges cap retained graph summaries. That first one-descriptor proof remains provisional; later fixtures cover 256-type dispatch and one bounded opaque edit, while combined editor/store peak and authenticated prior lineage remain open before an admission-ready candidate can be returned.

The [provisional candidate revision](SOURCE-PROVISIONAL-CANDIDATE.md) now combines those checked summaries with captured exact-byte file metadata under one object and derives a JCS manifest with an independent oracle. The candidate remains provisional because ordinary staged bytes are not rehashed at this point and neither the authenticated predecessor nor the full combined peak-allocation profile is qualified. The durable root/outcome transaction remains the admission authority.

The [first opaque-preserving text edit proof](SOURCE-OPAQUE-EDIT.md) validates an existing game record under its staged descriptor, replaces one known text value, and streams a new record while copying untouched optional JSON values as raw spans. A fresh stage derives a new provisional revision; the previous stage remains unchanged. This proves one narrow source-editor round-trip, not coordinated file application, a general field editor, prior-root authentication or accepted source.

**Cost gate before activation.** The checked staged-candidate path caps `project.records` at 4,096 scene/game records. It can carry 256 active descriptors, plus one project and one history record: at most **4,354 engine records** within the existing 100,000 staged-entry limit. The [all-type cost record](SOURCE-ALL-TYPE-EDGE-COST.md) measures one candidate with a game for every type and the 65,536-edge boundary; authenticated predecessor, editor/store overlap and full edit-to-ready cost remain unqualified. Each descriptor has at most 128 fields; history has at most 100,000 field entries and 1,024 type-version entries; each JSON record has at most 16 MiB. These are initial proof bounds, not SDK-wide limits. Reject a count before growing its summary vector. Parse rehashed records into bounded summaries and retain no whole-tree JSON values. Ordinary record buffers can drop after their summaries, but borrowed registry-history entries **pin their complete input byte buffers**. An in-memory candidate/prior comparison may therefore hold two 16 MiB history buffers, both history vectors and a third record buffer at once; measure that combined peak and use a streaming join where it materially improves allocation or latency. Retain at most O(records + fields + required edges + history) metadata. Opaque nested JSON requires bounded per-container key tracking; select and test per-container and aggregate node/edge limits, then measure the combined parser/graph allocation and RSS profile before promoting a general validated candidate. The one-marker A/B fixture, missing or wrong-type scene target, changed text-limit signature, reused type version, stale history, unknown required version and opaque round-trip must pass before extending this profile. The first consumer handoff is [recorded](SOURCE-FIRST-PROFILE-CONSUMERS.md); actual F4 provenance, T1 stable field operations, W1 transform schema, P7 version binding and N1 wire mapping still need implementation and qualification before general F3 closure is claimed.

The [dense candidate cost probe](SOURCE-CANDIDATE-MEMORY.md) now measures a one-descriptor full candidate with maximum declared record/history counts and a separate 256-descriptor registry plus direct game parse. Those earlier local peaks guided allocation work. The later [all-type candidate](SOURCE-ALL-TYPE-EDGE-COST.md) adds maximum simultaneous required edges and a game for every descriptor. A [two-candidate overlap probe](SOURCE-CANDIDATE-OVERLAP.md) retains both full graphs while restaging and comparing history. It does not authenticate the prior root or include SQLite/editor allocation and full edit-to-ready cost. Keep combined store/editor peak and prior-root authentication open.

The [native SQLite transaction proof](SOURCE-SQLITE-TXN.md) now exercises selected page, incremental-vacuum, WAL and full-sync settings alongside an atomic root-generation/retry-outcome update. It is test-only and holds no source blobs or authenticated history. The production store must verify complete blob closure, space planning and fault recovery, predecessor lineage, interruption recovery and pins before it may expose an accepted-source API.

The [follow-on blob proof](SOURCE-SQLITE-BLOB.md) uses bounded 4 MiB chunks, checks the full stored digest and chunk layout before a complete-state update, and requires a complete header at root commit. Failed streams remain incomplete and can retry; complete hashes can be reused. Each chunk write checks the matching incomplete header, while final verification and completion share an IMMEDIATE transaction. These guards prevent a stale stream from appending to another writer's complete blob or removing verified chunks before publication. This remains test-only: an arbitrary blob hash is not a validated manifest or transitive source closure.

The [staged lineage proof](SOURCE-STAGED-LINEAGE.md) now rereads and rehashes both carried-history records and compares their parsed field and type-version entries directly. It rejects deletion of a retired field or old version from a supplied predecessor and measures two live dense input buffers. The predecessor is still a supplied provisional stage, not the current root authenticated by SQLite; that trust boundary remains open.

The [small manifest-blob bridge](SOURCE-MANIFEST-BLOB.md) passes canonical manifest bytes through the test-only verified SQLite blob and root/outcome transaction and recovers the identical bytes after reopen. The follow-on [bounded chunk-writer proof](SOURCE-MANIFEST-CHUNKS.md) emits a maximum 100,000-entry manifest directly into 4 MiB SQLite chunks and measures local time/RSS without a whole-manifest output buffer. The production path still needs an authenticated prior history, physical disk/WAL preflight, interruption recovery and a consumer-facing admitted-root API before this can be source admission.

The [direct-file closure proof](SOURCE-DIRECT-FILE-CLOSURE.md) now checks each manifest file hash and exact length against a completed SQLite blob inside a new root/outcome transaction. It refuses a missing or mismatched file without changing the root, while a matching token retry recovers its persisted outcome without repeating closure work. The proof still trusts a caller-provided in-memory manifest and has no authenticated prior root, dependency closure, space-fault recovery, pins, integrity scan or production API.

The [small-blob batch proof](SOURCE-SMALL-BLOB-BATCH.md) addresses the transaction count in a many-file source tree. The original test-only path opens three transactions per tiny blob; a bounded group of at most 128 files and 1 MiB input bytes checks each input hash and rereads each stored value before one commit. A failed group rolls back, and the integrated fixture uses batched file blobs in a manifest-root closure. Local helper timings favor batching strongly, with storage tails observed in the one-file path. Production must plan WAL/main-page growth and prove interrupt/space-fault recovery for batches; a 1 MiB payload cap alone does not bound SQLite's physical write amplification.

The [stored-root lineage proof](SOURCE-STORED-ROOT-LINEAGE.md) now begins from the selected SQLite root generation and revision, rereads and rehashes its complete manifest blob, decodes the exact canonical first-profile representation without a generic JSON tree, then locates one typed history file. It checks root generation again, rereads and rehashes that file blob, matches its record ID and compares permanent fields and type versions with a supplied candidate history. A concurrent root advance still loses the final generation CAS. The first store profile refuses dependency roots and manifest bytes over 64 MiB at staging/publication/recovery, matching this decoder. The two read transactions end before JSON decode/lineage work; without GC pins this is only a test-only trust-boundary proof. Candidate history bytes are still supplied rather than bound to a rehashed staged candidate inside one admission API. General dependency roots, combined parser allocation/RSS qualification, space planning/fault recovery, process-kill recovery, pins and a production accepted-source consumer remain open.

The follow-on [staged-candidate lineage handoff](SOURCE-STAGED-CANDIDATE-LINEAGE.md) now obtains candidate history bytes by rereading and rehashing the validated candidate's captured stage, then runs the stored-root comparison. A same-length stage mutation after F3 validation refuses. Complete SQLite blob reuse also hashes the caller's supplied input, so a changed staged file cannot pass merely because its recorded hash is already stored. One reusable scratch buffer grows only to the currently streamed file or 4 MiB and survives ordinary errors; this avoids a large allocation for every unchanged tiny file. The fixture has one project, scene and history record, not a general game-schema or dependency closure. A production admission operation must still rehash and persist every staged file, hold the needed source/GC pins and apply the selected space plan with fault recovery, compare the current root, and commit root plus outcome under one generation precondition.

The [SQLite space-fault proof](SOURCE-SQLITE-SPACE-FAULT.md) now injects genuine `SQLITE_FULL` during candidate blob staging and after a root-row update inside the final metadata transaction. Both preserve the old root/outcome across reopen and permit retry after the injection clears. The store remains test-only and does not qualify host-volume exhaustion, power loss or production admission.

The [candidate-to-root proof](SOURCE-CANDIDATE-ROOT-PROOF.md) now assembles those logical steps in a test-only operation: a validated staged candidate yields a provisional manifest; its history is rehashed and compared with the verified current root; every staged file is reopened and rehashed while staging a new or reused complete blob; the manifest is verified; then one root/outcome transaction checks direct file closure and the expected generation. It proves a three-file A/B scene edit, stable scene ID, retained old root, same-token retry after reopen and concurrent matching outcome recovery. A precommit error rechecks the token so a concurrent matching winner does not become a false stale-generation answer. This is still a logical proof, not a production acceptance API: it has no production space plan/fault recovery, GC pins, process-kill recovery or general game-schema/dependency fixture, and its source application intent is absent.

Do not make an unrestricted [JSON Schema 2020-12](https://json-schema.org/draft/2020-12/) evaluator the admission authority. Its dynamic references, applicators and annotation/assertion vocabularies offer useful interchange and tooling ideas, but the initial engine needs a finite, inspectable set of field semantics and predictable validation work, including units and reference closure. Likewise, compiled game callbacks alone cannot be the source-admission gate: a schema-valid authored draft may need to remain admitted while its new game code fails build. Compiled callbacks may add target-readiness checks later, under F4 and the game build, without changing an admitted source identity. The F3 descriptor subset can export a JSON Schema projection for external editors later, but that projection does not define F3's own semantic or dependency rules.

Unknown values are retained only at descriptor-declared **optional** extension locations, with strict JSON syntax and duplicate-key rejection even inside opaque nested data. Unknown required fields or a required higher schema version refuse. The exact staged file remains the round-trip authority, so a tool must preserve an untouched optional value when editing neighbouring fields; reserializing known fields alone is unsafe. This is analogous to [Protocol Buffers unknown-field retention](https://protobuf.dev/programming-guides/proto3/#unknowns), whose JSON conversion caveat illustrates why a source editor needs an explicit preservation rule. Required local references resolve by stable ID and target type in the captured tree; external required references need a pinned, verified declared root; soft references keep their declared policy and diagnostics. Cycle checks apply to specific DAG owners such as prefab expansion, rather than rejecting every graph cycle by accident.

One streaming pass should validate each staged record under its pinned descriptor and emit only ID/type/version plus required/soft reference edges and bounded owner-specific summaries. A second pass checks uniqueness, resolution and selected cycles. This is O(total JSON bytes + record/path sorting + reference edges) with a bounded reusable record buffer and summaries proportional to bounded records/edges; it must not retain a generic `Value` tree per file. Before activation, select descriptor count/size, per-record field/collection and aggregate edge limits, then measure and optimize the combined parser/graph peak on dense valid and adversarial records. F4 product keys include descriptor/source provenance; T1 inspector and operations use the same field IDs/units; W1 validates its transform/hierarchy subset; P7 saves bind schema/provider versions; N1's wire manifest remains a separate pinned mapping. The first implementation should prove one source-carried game schema with an optional field and a typed required reference in a small A/B scene, then check one missing target, an unrecognized required version and an opaque optional round-trip. A separate pure lineage fixture should compare candidate and pinned-prior histories for changed units, deleted/reused IDs and branch union; only the later durable adapter can make that prior root authoritative. This choice remains provisional until these consumers and its bounded grammar are reviewed together.

## Remaining work

The source record validator and manifest schema must be reconciled with F3 component/schema IDs before the capture API is public. Directory prefixes as well as whole file paths need full Unicode case-fold alias checks; distinct `Assets/a.bin` and `assets/b.bin` cannot share one portable manifest. Durable intent, disk reservation, SQLite blobs/root/outcome CAS, GC pins, cook/build compatibility, replay and P7 private saves remain separate dependent work. This slice introduces no source-to-runtime command and no claim that I2a is complete.
