# Accepted-source cooperating owner lock — 3 November 2026

`NativeSourceStore::open` now obtains an exclusive `fs4` advisory sidecar lock before opening SQLite. The lock lives in the shared owner, so a `PinnedSource` keeps it after the store handle drops. It is paid once at open, with no lock syscall on an admitted-source read, source copy or game tick. The SQLite mutex still serializes this owner's SQL phases. A second cooperating opener receives `SourceStoreErrorKind::Busy` before SQLite recovery, checkpoint or writes.

The sidecar is beside the database, named `source.sqlite.owner.lock` for the fixture. The opener requires an absolute database path, canonicalizes its parent, and rejects a non-regular or symlink sidecar. On Unix it also refuses an existing database inode with more than one hard link: two names for one SQLite file would otherwise derive different lock and WAL names. It never deletes the sidecar on close; reopening uses the same inode. This is a cooperative lock for an app-managed directory, not defense against a noncooperating SQLite opener or a hostile actor that can replace directory entries. Windows path-identity aliases remain unqualified. The lock file itself is not a storage quota or physical-space reservation.

Focused tests show that a live accepted lease keeps a second same-process open busy after its store handle drops; after lease close, reopen sees the same root and no pin row. A parent-path alias resolves to the same lock; a hard-link alias is refused, including when reopening through the original name while the extra link exists. A child process holds the owner; the parent is refused, kills the child, then reopens and reads the empty root. A test-only native VFS reports an error after B's final WAL COMMIT sync while A's accepted lease is live: another opener is busy, later old-owner lease SQL refuses without new WAL/main writes, and after that owner and lease drop a fresh opener recovers B by its exact request key and retains A's durable pin row. This injected fault enters the final commit helper after verified B blobs are prepared, not the entire public admission method.

The selected owner shape avoids independent cooperating SQLite connections racing an uncertain final COMMIT. The test process kill proves OS lock release, not crash recovery of an interrupted admission. Format-1 accepted and format-2 provisional schemas remain separate. Full public-admission before/after commit interruption, cross-platform and power-loss behavior, owner-lock hold/wait distribution under edits, sustained checkpoints, source-to-build memory and physical-space high-water remain open in the build plan.

Verification: focused owner and live-lease fault tests, `RUSTC_WRAPPER= ./dev check` (repository checks, Clippy, workspace tests), and the affected opt-in admitted A/B build all pass locally. The build fixture reports 58 materialized files, 1,608,004 source bytes and a 2,306,232-byte binary; its 1,225 ms nested build time is one warm local result, not a performance claim about the owner lock.
