# WAL backpressure with a live reader, narrow proof

2 November 2026. The test-only SQLite store now checks WAL file length before each blob metadata, small batch, chunk, verification and root/outcome write transaction. Its selected trial thresholds are a `PASSIVE` checkpoint beginning at 1 GiB and a `TRUNCATE` attempt before the next **estimated** write reaches 2 GiB. A blocked or ineffective truncate returns `WalBackpressure` before starting that write. `PASSIVE` attempts are spaced by 64 MiB of observed WAL growth so a pinned reader does not cause a checkpoint attempt on every short transaction. The store opens with and verifies zero busy timeout for this nonblocking proof. Existing retry outcomes and complete blobs are resolved read-only before the guard; the root transaction still rechecks outcomes under its write lock.

The deterministic two-connection test starts a reader on an old snapshot, writes another blob and observes incomplete `PASSIVE` progress. `TRUNCATE` reports busy, and the WAL file length remains unchanged. With an injected near-stop threshold, a third blob is refused before any header row is created; a matching committed token still returns its generation, a changed token still conflicts, and complete blob reuse still checks supplied bytes. After the reader commits, `TRUNCATE` succeeds, the WAL file becomes zero length, and the refused blob stages on retry. The full repository check, including the assembled candidate and two-connection outcome tests, passes. Independent read-only review found and resolved retry-ordering and busy-timeout problems; its final pass had no findings.

The final Rust 1.99.1 release helper measured one three-file edit from fixture writes through capture, validation and root proof at **1.979 ms** in one local macOS arm64 run with the guard. This is a smoke cost check, not a speedup, sustained workload or device claim. Reproduce with `RUSTC_WRAPPER= rustup run 1.99.1 cargo test --locked --offline --release -p thrum-source sqlite_store::measure_small_candidate_edit_to_root -- --ignored --exact --nocapture`. Source SHA-256: `2a561bb0ba02fd93a3670a4874679fba8aa9917cae31f9e10ed0a0fa7639e5cf` (`crates/thrum-source/src/sqlite_store.rs`); executed release test binary SHA-256: `f87d9945af2d4f8cf70f77561dcdc412dcab6b7ec62e339cd6743a5b56a898ca`.

The allowance is 1 MiB for a metadata/root transaction, 5 MiB for a ≤1 MiB small-file batch, and twice the next chunk's rounded input plus 1 MiB for a ≤4 MiB chunk. These are **heuristics**, not proven maxima for SQLite page rewrites, incomplete-blob replacement, concurrent writers or filesystem allocation. No actual free-space recheck runs before each transaction, and a `PASSIVE` checkpoint may write main-file pages. This proof establishes visible reader-blocked deferral and retry semantics; it does not establish the selected 2 GiB physical WAL cap, 8 GiB free floor, production busy policy, sustained latency or crash recovery. See the [native physical-space contract](../../design/FOUNDATION-SPEC.md#4-working-files-crash-recovery-and-gc) and [SQLite checkpoint behavior](https://www.sqlite.org/wal.html).
