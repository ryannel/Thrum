# Short SQLite root-read pin, narrow proof

2 November 2026. The test-only source store now registers a durable `read_pin` for the selected root revision in a short `IMMEDIATE` transaction before it decodes the root manifest and source-carried history. The two bounded blob reads still close their SQLite read transactions before JSON decoding and lineage comparison. Root generation and revision are checked again on each read, and the final root CAS remains separate. The pin is released after either success or validation refusal. A root advance and database reopen preserve an explicitly held old-revision pin until its release; a project mismatch leaves no pin from the automatic read path.

The pin table uses non-reused row IDs. Pin insert/delete run through the test store's provisional WAL guard. If a competing SQLite writer makes release fail with zero busy timeout, the store retains that pin ID and retries it before the next history read. Tests hold a competing `IMMEDIATE` transaction, observe failed release and retained ID, then verify both automatic and explicit retry clear the pin before another read. If an uncertain commit already removed a row, the pending cleanup treats its absence as completed. `RUSTC_WRAPPER= ./dev check` passes; independent read-only review found the release leak and stale-ID risk in the first version, then found no issue after correction.

An existing local Rust 1.99.1 release probe read a 100,000-entry root manifest and compared its history in **63.421 ms** with the short pin path included. This single local macOS arm64 run does not prove a general latency change. Reproduce with `RUSTC_WRAPPER= rustup run 1.99.1 cargo test --locked --offline --release -p thrum-source sqlite_store::measure_maximum_root_history_resolution -- --ignored --exact --nocapture`. Source SHA-256: `49dfe8f8f967ae55d5397d0702fc643c893e2e3bd109ec3fb5553eb4495a6014` (`crates/thrum-source/src/sqlite_store.rs`); executed release test binary SHA-256: `e3179202fc1d845b71a82536ff951b33a989c6ae533332c666f6360a198948a5`.

This is **pin registration**, not a qualified retention system. No collector yet follows pins through a manifest's transitive file closure, prevents deletion, or recovers pins abandoned by a killed process. A store instance can retry a failed release while it lives; process loss needs a durable owner/lease recovery policy. The root remains selected during a reader's work but may advance before it finishes, so the generation checks still refuse stale lineage. Retained old roots, staged admission pins, two-epoch deletion and physical peak accounting remain open under the [GC contract](../../design/FOUNDATION-SPEC.md#4-working-files-crash-recovery-and-gc).
