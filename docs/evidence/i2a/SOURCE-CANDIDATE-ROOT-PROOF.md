# Validated candidate to SQLite root, narrow proof

2 November 2026. A test-only operation accepts a validated staged candidate, derives its provisional manifest, rehashes its staged history and compares it with the verified current SQLite root, then reopens and rehashes **every** staged file while staging complete blobs. It stages the canonical manifest and commits root generation plus retry outcome in one transaction after direct file-closure checks. A three-file project and scene-label edit produce different revisions while the scene keeps its stable ID. The old root blob remains complete. Same-token retry recovers after database reopen; changed request hash conflicts. A same-length staged-file mutation, missing permanent history and stale generation refuse without advancing the selected root. A deterministic two-connection race verifies that a writer which loses after its first outcome lookup recovers the matching winner's persisted outcome. Independent review found that race in the first version; it is fixed and the final read-only pass found no further issue. `RUSTC_WRAPPER= ./dev check` passes.

Three fresh local macOS arm64 processes took **3.891, 2.836 and 2.554 ms**, with peak RSS **8,994,816, 8,994,816 and 8,945,664 bytes**. The three files are tiny; the path excludes initial database open and baseline admission, and includes fixture working-file writes. This is a narrow local development workload, not a maximum-source, crash, device or sustained edit-to-ready qualification.
