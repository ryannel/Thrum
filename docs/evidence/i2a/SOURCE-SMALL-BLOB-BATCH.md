# Bounded small-source-blob batch

2 November 2026. The test-only SQLite store can stage up to 128 small blobs and 1 MiB of input bytes in one `IMMEDIATE` transaction. Each input hash is checked before insertion; each newly stored nonempty blob is read back and rehashed before its header becomes complete. A wrong second input rolls back the first. Reuse of a complete hash, reopen and a root manifest naming both batched files pass. The 4 MiB chunk path remains for larger blobs. Independent read-only review found no actionable correctness issue, and `RUSTC_WRAPPER= ./dev check` passes.

The prior helper opened three transactions for each tiny blob. On the same local macOS arm64 Rust 1.99.1 release fixture of **1,000 distinct eight-byte files**, three paired fresh-process runs, alternating order, measured one-file helper **148.981, 131.838, 456.043 ms** and bounded batch helper **9.489, 9.386, 9.525 ms**. The 456 ms one-file result is retained as an observed storage tail; another development sequence also saw a 186.972 ms batch outlier. Process peak RSS for these final pairs was **8,683,520–8,732,672 bytes** for one-file and **4,440,064–4,456,448 bytes** for batch. These are helper timings from just before staging through verified completion; they exclude fixture generation and database open, and include SQLite/WAL work and different allocation patterns. They do not establish full candidate latency, durable source admission, a sustained tail distribution or device performance. Reproduce with `RUSTC_WRAPPER= rustup run 1.99.1 cargo test --locked --offline --release -p thrum-source --no-run`; run `sqlite_store::measure_small_blob_transaction_cost` and `sqlite_store::measure_small_blob_batch_cost` on the resulting test binary with `--ignored --exact --nocapture` in fresh processes, alternating order, and collect `wait4` maximum RSS.

The batch has a logical input bound, not a measured physical WAL/page bound. Its test-only caller already owns exact staged bytes; no production admission API, disk/WAL peak reserve, process-kill recovery, concurrent GC pins or prior-root authentication is claimed.
