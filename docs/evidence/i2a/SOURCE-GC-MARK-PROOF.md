# SQLite source GC mark, narrow proof

2 November 2026. The test-only SQLite source store snapshots its selected root, durable `read_pin` revisions and a GC epoch in a short read transaction. It reads each root's complete verified canonical manifest in another short transaction, then decodes it after closing the transaction. The first profile follows direct file hashes and refuses dependency roots. A separate read transaction scans at most 4,096 complete blob headers and chooses at most 128 unreachable hashes. An `IMMEDIATE` transaction rechecks the root/pin epoch before replacing the mark table; a changed epoch leaves prior marks intact. Mark publication has no JSON decode or full blob inventory scan under its writer lock.

Tests publish two source revisions, hold the old revision by a durable read pin, and stage an orphan blob. The first mark names only the orphan; after pin release, the old manifest and its unique scene blob also become candidates while the selected revision's closure remains unmarked. Injected root publication and pin registration between scan and mark each refuse with `StaleGcEpoch`. A 128-candidate mark succeeds; the 129th candidate refuses before replacement and leaves prior marks unchanged. A partial covering index on complete hashes keeps 4,097 incomplete headers out of the inventory scan; the test checks SQLite's selected query plan. `RUSTC_WRAPPER= rustup run 1.99.1 cargo test --offline -p thrum-source --lib gc_mark -- --nocapture` and `RUSTC_WRAPPER= ./dev check` pass. Source SHA-256: `7af9948efe3d36d375c103a208a12fd9f4eab96f878b9ba7b7e59a8389750b7e` (`crates/thrum-source/src/sqlite_store.rs`).

This is **mark only**. There is no `deleting` state, second publication epoch, chunk removal, publisher exclusion, physical-space recovery, or process-abandoned pin policy. New unreferenced blobs staged after the inventory snapshot wait for a later mark. The 4,096/128 limits bound this proof rather than qualify a full project collector; the 8 MiB WAL allowance is heuristic, not a certified physical upper bound. A production collector needs bounded resumable inventory and mark batches, all retained owner classes, a second epoch and transactional reachability recheck before deleting. No GC duration or disk-reclamation claim is made.
