# I2a provisional source staging

2 November 2026. **Local native staging proof, not a validated candidate or accepted source.** The [source capture design](SOURCE-CAPTURE-DESIGN.md), [foundation specification](../../design/FOUNDATION-SPEC.md#2-file-application-and-source-admission) and [C10 contract](../../design/CONTRACTS.md#c10-persistence-reproducibility-and-authored-operations--p7f3t1) govern the remaining F3 schema/dependency closure and SQLite root/outcome admission. No runtime cook, save, or multiplayer match consumes these provisional bytes.

The first adapter scans the entire declared tree before writing stage files. It excludes only the exact top-level `.git`, `.engine` and `target` generated roots under v1 policy; every other file must appear in the explicit declaration. The selected 100,000 source-tree-entry bound counts files **and directories**. It refuses non-UTF-8/unsafe paths, aliases, undeclared members, missing files, symlinks/devices, file growth and ordinary observed drift. A cooperative `source.lock` window begins before the first inventory. It uses one 4 MiB buffer to copy each regular source file to a private `.engine/staging` owner while hashing SHA-256, scans membership again, then rereads and hashes every source file. A file of at most 1,024 bytes whose first nonwhitespace line is a recognized Git LFS pointer version is refused as unresolved, including CRLF and [legacy version aliases](https://github.com/git-lfs/git-lfs/blob/main/lfs/pointer.go); the size bound follows [Git LFS's pointer specification](https://github.com/git-lfs/git-lfs/blob/main/docs/spec.md). The stage API never applies a working-file edit. A read lease keeps old staged bytes alive even after their owning `StagedTree` drops; a failed new stage cleans its partial directory and does not change the earlier stage. The later durable consumer must rehash staged bytes before use.

Before creating the staging tree, the native preflight probes filesystem allocation granularity, available space and existing `.engine` physical usage under the writer lock. It caps rounded live temporary plus projected stage at 2 GiB, existing plus conservatively projected SQLite main at 52 GiB, and WAL at 2 GiB, while reserving 8 GiB actual free space after the projected stage/main/WAL peak. The stage projection includes per-file rounded bytes and metadata/directory allowance; the provisional main projection is twice source bytes plus 64 MiB and one allocation unit per file. Each copy chunk checks available space before/after writing; the final stage checks actual temporary use. The usage scan tolerates a managed stage disappearing when its final reader drops during the scan; actual available-space checks still account for blocks that have not yet been freed. These checks provide a conservative local planning refusal, not an OS disk reservation against unrelated writers or the later durable SQLite transaction. Larger candidates need the separately selected direct-to-store path.

Reproduce with `RUSTC_WRAPPER= ./dev check` and `RUSTC_WRAPPER= rustup run 1.99.1 cargo test --locked --offline -p thrum-source`. Fixtures cover declaration membership, generated roots, symlinks, directory replacement, existing-store and lock refusal, a tiny temporary bucket before stage creation, an edit producing different staged bytes, old-reader lifetime, same-size source drift, a new undeclared file after copying, unresolved LFS pointers, and stage retirement while a later budget scan is in flight. The release-mode 64 MiB fixture is `RUSTC_WRAPPER= rustup run 1.99.1 cargo test --locked --offline --release -p thrum-source measure_provisional_stage_64_mib -- --ignored --nocapture`. Two initial local arm64 macOS 26.6.2 runs reported 399 ms and 301 ms for the full provisional capture path; a later run after removing duplicate path ownership reported 305 ms. Runs with the retirement fix and LFS gate reported 298 ms and 322 ms. These are local warm/cache-sensitive elapsed samples, not disk-durability, peak-RSS, target-device or edit-to-ready claims.

The stage has **no F3 semantic record validation, dependency closure, LFS payload resolution, candidate manifest, durable pin, SQLite root/outcome, crash recovery, cook or save**. It does not establish a single filesystem instant against a noncooperating writer or ABA. A failed best-effort stage-directory cleanup remains visible to the next budget scan; automatic orphan reclamation needs durable pin/lease ownership. The 100,000-file manifest probe in [the metadata record](SOURCE-MANIFEST.md) is separate from the 100,000-entry inventory limit: a tree with one directory can contain at most 99,999 files in this v1 profile.
