# Staged scene and game-record closure proof

2 November 2026. `validate_staged_records` consumes a previously checked `StagedRegistry` and rereads only its declared scene and game paths from the immutable provisional stage. Each record's length and SHA-256 must still match capture. The fixed `core.scene` schema 1 parser checks scene identity; one active source-carried game descriptor checks each game record's identity, known fields, optional opaque syntax and required reference summary. The first closure profile refuses game records when there are zero or multiple active descriptors, so it never dispatches by JSON key order or repeatedly tries all schemas. A larger multi-schema profile needs a separately selected dispatch and peak-memory proof.

The pass keeps one reusable record-byte buffer, preallocates scene/game summary vectors from declared path counts, and sorts borrowed stable-ID views after parsing. It rejects collisions across project, history, descriptors, scenes and games. Entry IDs and every present typed game reference must resolve to staged `core.scene` IDs. Required-edge summaries are capped at 65,536 before the next record is retained. Work is O(total reread/parse bytes + record-ID sorting + (required edges + entry IDs) × log(1 + scene count)); scene lookup uses binary search and the small one-scene probe does not measure its larger-tree factor. It retains one input buffer rather than a JSON value tree per file. The 16 MiB record bound and the game parser's opaque limits still apply; the **combined physical peak** of parser scratch, descriptors, record summaries and later lineage comparison has not been reserved or measured for the maximum profile.

Local tests cover one scene and one game marker with an optional caption, opaque nested value and required scene reference; the descriptor hash is carried into the game summary. They also prove that an edit leaves an older staged record intact, while a fresh stage with a missing reference refuses; duplicate scene/game IDs, wrong game type and an entry ID naming a game refuse. The ignored Rust 1.99.1 release probe ran the small two-record closure 1,000 times in **42.446583 ms total** on the local macOS arm64 environment (about 42 µs per validation, including staged-file opens, hashes and parses). This is not a dense-record, whole-capture, RSS or device measurement. Reproduce with `RUSTC_WRAPPER= rustup run 1.99.1 cargo test --locked --offline --release -p thrum-source measure_small_staged_record_closure -- --ignored --nocapture`.

The result is still provisional. A follow-on [candidate revision](SOURCE-PROVISIONAL-CANDIDATE.md) combines these summaries with the registry and captured manifest metadata, but does not compare history with an authenticated predecessor, prove source-editor opaque round-trip, reserve the combined memory peak, admit a durable root or run/cook a game. These remain open in the [Build Plan](../../plans/BRIEF.md#parked-retained-in-git-history).
