# First Unix F4 job host slice — 3 November 2026

This records the first executable slice of the [provisional same-volume job
account](../../design/research/T2-SAME-VOLUME-JOB-ACCOUNT-2026-11-03.md).
The source is `crates/thrum-jobs` and the narrow F4 explicit-close/recovery
handoff in `crates/thrum-cook/src/native_worktree.rs`. The local fixture ran
on macOS arm64 with Rust 1.99.1; the branch was based on `fa8bc43` before
this slice. It is one synchronous F4 input phase, not the complete T2 account.

## Ownership and cost

`MaterializationHost::open` binds a live selected `NativeSourceStore`, one
canonical project and its deterministic private, same-`st_dev` sibling
`<project-name>.thrum-jobs`. An alternate parent for that project refuses
before creating a lock or claim. The
cooperating host lock is exclusive. A pin from a different store is rejected
before admission even when its generation, revision and complete source bytes
match. The parent, job root and completed input each have held directory
descriptors for path-identity checks; this is within the selected development
profile that trusts other processes running as the same local user.

For the test policy, each F4 copy has a 16 MiB scratch target, while the
host's simultaneous managed-temporary target is 24 MiB. The host adds two
filesystem allocation granules for parent/lock control and two per job for
root/registration. The first 12 MiB source copy succeeds; the second full
claim is refused before a second root exists. Closing the first input and
durably retiring its registration refunds only that job's claim; a second
copy then succeeds. A free-space check samples once per admission and compares
the proposed phase claim plus headroom with available space. Completed active
jobs are already reflected in that available-space sample. The host does not
scan all active trees or add per-file/per-chunk claim work to F4's copy path.
These are planning charges, not observed physical high-water or a hard cap.

## Failure and restart cases

The initial fifteen ordinary `thrum-jobs` tests covered:

- Two individually affordable copies share one conservative target; stale
  job IDs cannot close a later job, including after host reopening.
- A foreign store pin with identical accepted root identity refuses before
  registration, leaving no active claim or job root.
- After A's registration sync and before its input copy, F3 stages and admits
  a scene-only B edit while A's pin remains live. F4 then copies exact A
  scene bytes, B's generation is selected, and a further F3 capture succeeds
  while the complete A input remains externally registered. This is ordered
  overlap of owners, not a concurrent F3 scan/retirement race.
- A too-small F4 scratch plan fails after T2 registration, then checked empty
  root retirement removes the registration and refunds the claim.
- An extra unknown root entry causes explicit close to quarantine and retain
  the full claim; a later admission and reopened host both refuse.
- Killing a child after its registration is durably synced leaves a root that
  the next host quarantines before new work.
- A second live host sees the owner lock as busy; normal host destruction
  leaves its active registered input for restart quarantine.
- A pre-existing lock symlink refuses before opening an existing sentinel or
  creating a dangling target. The lock opener checks regular single-link
  identity before use and rechecks the opened inode.
- A second private parent for the same project cannot start an independent
  claim account; the canonical parent still excludes a second live host.
- A separate test process opens the same accepted store after the parent drops
  its F3 handle, then receives `Busy` from the live T2 host's filesystem lock.
  The child itself runs as a guarded test helper when no fixture variables are
  present.
- Parent, job-root and input-directory path replacement each refuse checked
  close and preserve a sentinel at the replacement path. The host does not
  use F4's implicit path-based `Drop` cleanup after such refusal.

Reproduce the focused proof with:

```sh
RUSTC_WRAPPER= rustup run 1.99.1 cargo test --locked --offline -p thrum-jobs
RUSTC_WRAPPER= ./dev check
```

The focused tests and `RUSTC_WRAPPER= ./dev check` passed locally. The gate
checked repository policy and documentation links, formatting, Clippy and the
workspace tests. An independent review found no remaining issue in this
F4-only slice after the path, cleanup and free-space-account fixes.

## Per-job reader lifetime extension

The host now returns an owned `InputLease` instead of a bare borrowed input
path. A lease holds only its job's input owner, so another complete F4 copy
can be admitted while A is being read. Explicit close of A returns
`ReadersActive(A)` without removing its root or refunding its claim. Closing
an independent B still succeeds. After A's last lease is dropped, checked
F4/root close refunds A. If the host is destroyed first, the last lease
disarms F4's implicit path cleanup and leaves the registered input for
restart quarantine. A cooperating compiler must hold its lease for its
entire supervised read lifetime; process ownership and output claims are
still future T2 work.

Two additional ordinary tests exercise both paths: A's live lease survives
B materialization and B close, and a lease that outlives the host preserves
the registered input after its own drop. The focused run had 17 passed,
one ignored native APFS fault test and no failures. This is one `Arc`
allocation and clone per job/lease; no refcount work occurs in F4's streamed
copy loop. CPU, allocation, and concurrent F3 scan/retirement cost have not
been measured for this extension.
The slice has no direct F3 admission/scan concurrency, compiler output or
external cache owner, native ENOSPC or injected sync fault, retained-job
recovery, Windows implementation, observed CPU/RSS/physical-allocation
measurement, or ready-build claim. The top-level T2 plan item remains open.
