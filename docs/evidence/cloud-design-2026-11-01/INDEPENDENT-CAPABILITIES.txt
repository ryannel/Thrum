# Independent cloud capability inventory

1 November 2026. Bounded capability-discovery commission for Thrum. **No mechanism selection, code inspection, build, GPU work or qualification.** This inventory was derived before seeing the parent proposal or any existing cloud implementation/technical plan. Inputs were the original task requirements supplied by the coordinator and Thrum's engine-level sources below. The engine's selected initial attenuation mechanism is disclosed as baseline context, not adopted as the answer for visible evolving clouds.

## Basis and status

**U — explicit commission/user requirements:** production-style convincing clouds; coherent motion; actual growth and breakup at normal and accelerated speeds; shared shadow/reflection/lighting behaviour; responsive Mac trackpad inspection; physical fidelity may be reduced; preserve the existing renderer where it fits; align with reusable Thrum for desktop, WebGPU browser and native mobile; games can retain cloud light attenuation without visible clouds. Approaching storms/weather transitions are stretch goals and must not compromise the base delivery. Apply the updated module skill, itemise capabilities and independently challenge coverage, revise the complete design before building.

**I — necessary implications:** outcomes without which U or an applicable engine contract cannot hold. These do not add a meteorology product or require every engine-supported composition in the first demonstration.

**B — existing engine requirements/baseline:** the brief E01–E03/E07/E09/E11/E19/E20; C01/C02/C04–C10/C11 and their owning specifications. These constrain the module; they are not evidence that it already works or a mandate to construct every neighbour. **A — proposed assumptions**, **O — optional extensions**, and **X — exclusions** remain separate below. All proof needs are proposed and unrun; visual acceptance belongs to the user, separately from correctness and device measurements.

C01's visual language is an acceptance interpretation of “convincing”, not an independently selected cloud taxonomy. C03 demands actual evolution in the represented system; it does not require conserved water mass, physically simulated condensation or precipitation. Render detail can remain presentation-only, but it cannot be the only evidence offered for a required state change.

## Existing baseline versus this commission

Thrum's selected first portable air path is a flat-ground exponential atmosphere plus bounded homogeneous local fog, scene-linear Rec.709/D65 photometric RGB, with an authored terminal HDRI and separate Sun. Its initial clouds are an authored nonnegative source-direction optical-depth field with a declared direction/altitude regime, **not a visible overlapping cloud volume**. Transparent cloud cards are labelled approximate surfaces. C4 already permits cloud attenuation without visible sky/cloud drawing; zero attenuation is explicit clear value 1. The family documents allow a stronger provider later.

That baseline satisfies a composability service, not U's complete visible/evolving cloud deliverable. Adding visible cloud media must revise the admitted optical recipe and participating consumers before construction if it exceeds that selected scope. It need not replace the clustered-forward renderer, V1 executor or V4 display path. Conversely, “keep the existing renderer” does not establish that a cloud-specific implementation fits: this worktree's README says no engine runtime exists yet. The coordinator must identify the actual retained renderer/artifact and migration boundary; this independent commission intentionally did not inspect it.

Baseline qualification candidates are M2 Mac/Metal and Windows RTX 3060 at 1080p/60, M2 Chrome/WebGPU at 720p/30, iPhone 13/Metal and Pixel 7/Vulkan at a 720p-equivalent sustained 30. Whole-scene CPU/GPU planning envelopes are 5/10 ms desktop, 8/16 ms browser and 7/16 ms mobile; memory caps 3 GiB/512 MiB/1 GiB. These are selected, unmeasured engine recipes, **not cloud entitlements or acceptance evidence**. R3 includes cloud-attenuation-only; none of R0–R4 specifies the new visible evolving cloud workload.

## Conditional responsibilities and optional profiles

- **Gameplay-significant cloud visibility/irradiance (B, conditional):** if a game selects this use, E1 owns compatible authority/query semantics and N1 projections; clients cannot change those facts with visual tiers. Headless authority cannot depend on rendered pixels or mandatory GPU readback. This is an engine boundary, not an added requirement to build cloud gameplay, multiplayer replication or a climate/thermal model for the current demonstration.
- **Reflected clouds without main-view clouds (I for retained consumer, exact profile A):** reflections are distinct consumers. Hiding the main draw may retain a reflection/environment source; it must not accidentally erase required lighting/reflections. Whether a particular shadow-only game needs cloud-shaped reflection detail is selected by that game, not automatic.
- **Reduced visible browser/mobile presentation (B capability, detailed profile A):** representations can differ if claimed cues and shared semantics remain within a declared envelope. Cards, layers, a volume or a native specialization are candidates, not requirements or selections. Equal desktop appearance on every phone is not commissioned.
- **Approaching fronts/storms and weather transitions (O, explicit stretch):** spatially approaching weather and associated changing cloud conditions may be added after the base deliverable is complete. Wind/rain/audio/wetness consumers require explicit external providers if selected. Cloud growth and breakup remain base requirements and cannot be deferred under this stretch label.
- **Game-specific style and cloud populations (A/O):** the system needs sufficient authoring to reproduce its intended cloud scenes. Multiple art styles, all cloud genera, exhaustive presets, multi-layer taxonomy and physical meteorology are not justified requirements here.

## Material questions to return to the coordinator

1. **Acceptance domain:** Which cloud regime(s), representative appearance references, distances, layer heights/extents, camera envelope and sustained observation duration define C01–C04? Is entering/going above a cloud required, or can the base recipe declare a ground/shore exterior envelope? Thrum's support for first-person cameras does not imply aircraft, arbitrary cloud interiors or planetary travel. Proposed assumption: a bounded exterior viewing envelope is acceptable until explicitly widened; keep the exact envelope open.
2. **Renderer identity and integration target:** Which existing renderer/build/source is to be retained, and is the deliverable an engine provider design, an independently hosted demonstration or both? Thrum currently records scaffold-only maturity. This is an artifact/contract question, not permission to inspect or adopt a historical Broadsides implementation.
3. **Authority and source boundary:** Does cloud evolution remain cosmetic E1 state, or must any game consume gameplay-relevant cloud queries? What inputs actually exist now (authored motion/source controls versus a weather/wind provider)? Pick one owner per quantity; do not silently commission weather simulation to obtain a wind field.
4. **Light/transport envelope:** Which light sources, altitude/direction ranges, atmosphere/fog overlaps and receiver types must base proof cover? Shared Sun lighting is grounded; exact multiple scattering, night-time Moon/local-light cloud illumination and arbitrary media overlap are not selected by “shared lighting”. Admit the chosen closure explicitly, including what offscreen reflections sample and how fast they may update.
5. **Time and inspection policy:** Does acceleration advance the same simulation faster, seek an evaluable source or use a bounded authored playback path? What rate range/duration is promised, what happens under overload, and does pause freeze cloud time while leaving inspection responsive? Select P1/P2 gestures/focus and latency expectations. None of these choices permits a second view-owned evolution clock.
6. **Delivery/quality scope:** Which targets must receive a built provider in the first base slice, versus designed reductions awaiting target qualification? Set a visible-cloud workload and cloud allocation inside the shared budget, including active receivers/reflections. A high-quality Mac demonstration cannot alone close portable profile proof.
7. **Continuation and replacements:** Which control edits restart, which presentation changes can be live, and which source/state must survive saves or suspend? Baseline restart/stop-load is valid; generic live cloud-provider migration, streamed meteorology and universal resume checkpoints would expand scope.

These questions must be explicit in the complete design; not every answer requires interrupting the user. Existing contracts resolve ownership and safe default lifecycle. The coordinator can select bounded proposed assumptions and leave numeric qualification unrun, while keeping unsupported regimes visible.

## Scope guard and completion

Do not add rainfall, lightning, acoustics, wetness/snow, flight physics, aircraft turbulence, all ten genera, planetary curvature, global climate, long-range forecast, exact thermodynamics/water conservation, arbitrary renderer replacement, executable hot reload, universal live migration or a new plugin framework by association. Neighbouring consumers need contracts only where actually retained. Weather stretch cannot delay C01–C07; an accurate shadow map or fast renderer cannot substitute for failed growth/breakup.

The independent capability set and consequential contract questions are explicit. No proposed mechanism has been qualified and no user acceptance is claimed. Stop this commission here; the coordinator can now compare its saved proposal, reconcile justified omissions/unsupported additions and revise the governing design before building.
