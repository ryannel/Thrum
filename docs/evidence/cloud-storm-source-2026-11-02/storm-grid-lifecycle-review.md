## Consequential findings

1. **[P1] An immediate Cb probe after provider recreation can fail; a same-scene reset can mix old observation controls with new q.** `Scene.create` initializes `lastSubmission=null`. `configure` creates and resets the scene, then releases `busy`; the next animation frame has not necessarily submitted a presentation. If Probe is clicked in that interval, `Scene.probe()` reaches the Cb-only `probeColumns()`, which reads `this.lastSubmission.controls` and `this.lastSubmission.weatherInput` without a prior submission and throws. Once Probe sets `busy=true`, the animation frame cannot fill in that missing submission. Conversely, `Scene.reset()` clears `lastPresentation` but leaves `lastSubmission` from the preceding epoch, so an immediate same-grid Cb probe uses the old frame's control and weather input to compute optical columns from new q. This is an observer attribution issue, not a source-update failure. Gate the column observer on a same-epoch submitted frame, or supply the reset's current immutable control/weather snapshot without claiming an image submission. Include a recreate→immediate Probe and reset→immediate Probe check in the Cb witness.

2. **[P2] Queued reset intent is last-wins while a configuration or observation is busy.** `reset()` stores one `pendingReset={clear,newWorld}`; a subsequent reset request overwrites it. For example, Clear followed by a family change during a long provider configuration drops `clear=true`; New World followed by optical Recover can drop `newWorld=true`. The ordinary Cb grid mismatch path itself starts the CPU world once, calls `configure()` once, and applies a subsequent optical clear with `reset(true,false)`, so I found no double-world reset in that path. If last-wins is the intended UI contract, record that in the queued status/receipt; if Clear or New World is meant to remain effective across coalescing, preserve those stronger intents when combining pending requests. Exercise the queued sequence, since a solo reset does not reveal it.

## Closed by the current code path, with evidence limits

- Full-provider Cb selection enters `Scene.create(..., family)` with `[128,80,128]` and the `[-12000,12000]` horizontal / `[500,15000]` vertical domain. Other full-provider families use `[96,80,80]`; source-less shadow/clear providers use `[1,1,1]`. `bench.reset()` compares the x dimension to the selected family, which distinguishes the two currently defined full-provider grid sizes. It starts a requested new CPU epoch, serializes old-scene disposal through `configure`, creates the selected size, and then applies an optional clear as an optical-only reset. In ordinary execution this does not reset the CPU world twice.
- `Scene.dispose()` waits for submitted GPU work, unconfigures the canvas, and destroys the old device before the new scene is created. `configure` retains version coalescing; requests during its busy window drain afterward. With optics globally off, New World resets CPU Weather/WorldClock without constructing q; re-enable seeds a new optical epoch from the current weather. Shadow/clear allocation has only one-voxel source placeholders and no source pipeline or full velocity field.
- `Gpu.bytes` sums sizes of created textures and buffers, including the Cb q/scratch/carrier and dynamically allocated full velocity field, so the larger grid enters the existing logical-allocation receipt. It is not a measured physical peak or proof of the target memory budget. Source-less providers still own a full optical image and air pass; “Volume source retired” accurately describes the source omission, not zero optical cost. A provider transition receipt should compare the live logical ledger after old-device retirement, not add allocations across retired devices.

The next Cb run still needs actual 480 s face occupancy, 1×/16× cadence, and physical/host cost observations. None follows from this lifecycle inspection.
