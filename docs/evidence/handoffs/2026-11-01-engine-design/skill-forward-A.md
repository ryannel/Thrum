# Forward task A — architecture commissions

**Status:** provisional whole-engine design, not a runtime specification or qualified implementation. This responds to the supplied request using the 31 October reusable-engine brief and C2 shared-contract baseline. The custom host, 3D camera range, Mac/PC/browser/native mobile ambition and selectable features are confirmed. The exact minimum devices, budgets, content scales, networking and authoring experience remain open. Earlier Bevy direction in `notes/DESIGN.md` is superseded for this new engine by the later custom-host decision; current code does not select this target.

## Supported workloads and derived responsibilities

| Workload | Required capabilities | Profile-dependent work |
| --- | --- | --- |
| Isometric town | Orthographic or long-lens view, multi-object picking, dense near-to-mid scene, local interactions, characters, authored settlement, coherent light | Visible clouds and sunsets may be absent while sun/sky illumination and cloud attenuation remain |
| Third-person exploration | Follow/obstruction camera, traversal, animation/physics contact, streaming, terrain, weather, spatial audio, save | Weather and surface response can vary independently from sky presentation |
| Browser demo | Same authoritative scene semantics, cold-start/cook path, WebGPU feature discovery, device recovery and reproducible route | Smaller assets, reduced render quality, optional module exclusion; no assumed native filesystem or unrestricted threads |
| Native mobile | Touch and accessibility, suspend/resume, memory/thermal management, safe save and GPU recreation | Smaller residency and sustained quality, with gameplay-relevant state retained |

A whole-engine module map follows ownership, not a crate count: (1) host/runtime, time and jobs; (2) feature/profile composition; (3) stable identity/schema; (4) content cooking, dependency and residency; (5) canonical scene/streaming; (6) input/actions, camera/views, physics/query, animation, navigation/behaviour, persistence; (7) graphics execution, extraction/visibility, materials/light/environment, reconstruction/display, audio/UI; (8) authoring/automation and diagnostics/delivery. Game rules and authored content remain outside reusable services. Retain one world authority and one physics body authority. Distinct rendering, collision and navigation representations share stable IDs, units and committed timestamps. This is a proposed boundary map; each commission may return a reasoned change to the central contracts.

## Shared contract and representative execution

The proposed world step is `X[n+1] = F(X[n], ordered commands[n], dt)`. At a pre-tick barrier, validate profile/content changes; then input and agents submit intent, physics resolves motion, environment advances from a common time-indexed weather source, and world state commits. Animation receives resolved motion; two views extract the same committed state independently, with per-view visibility and histories. A save captures committed durable state, not render caches. A streamed region is admitted only after assets and collision/nav products match the intended content revision. A profile switch validates dependencies and headroom, installs replacements at a safe barrier, invalidates affected histories, then retires old resources. Suspend checkpoints/policies bound elapsed-time catch-up; GPU loss invalidates the device generation and recreates derived resources without losing world state. These handoffs follow the C2 baseline, with exact scheduling and consistency still provisional.

Capability selection has three dimensions: capability, provider and quality. A provider declares input/output semantics, owner, validity regime, dependencies, substitute and lifetime. Example: `visibleClouds=off` may leave `solarAttenuation=authoredField` and lighting active; `surfaceResponse=off` may supply authored constant traction to physics, but a consumer requiring accumulated snow rejects that configuration. Build exclusion removes code/assets where known; load-time selection chooses provider/residency; live change is supported only for named safe transitions. Off means no avoidable tasks, allocations or content products. A cheap substitute may still cost work and must be reported honestly.

## Boundary-changing decisions and evidence

- **GPU portability:** WebGPU adapters have negotiated features/limits and a lost device makes its resources unusable ([W3C WebGPU specification, devices and limits](https://www.w3.org/TR/webgpu/)). Apple GPU families differ in available features and limits ([Apple Metal feature tables](https://developer.apple.com/metal/capabilities/)). Therefore choose a portable raster/compute baseline and optional advanced providers after device discovery; a uniform high-end renderer across all four profiles is unsupported. Whether graphics execution should use one cross-platform library plus narrow native extensions remains a commission, not a preselected wrapper.
- **Browser concurrency/startup:** browser shared memory requires secure cross-origin isolation ([MDN SharedArrayBuffer](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/SharedArrayBuffer)). Hence no core contract may assume native filesystem access or unrestricted workers; browser asset cooking/startup and scheduler fallbacks require separate design. Site deployment headers and practical threading benefit remain unqualified.
- **Native mobile lifetime:** iOS scenes can be suspended/disconnected and should save/release work on background transitions ([Apple UIKit lifecycle](https://developer.apple.com/documentation/uikit/managing-your-app-s-life-cycle)); Android thermal state limits sustained performance ([Android Thermal API](https://developer.android.com/games/optimize/adpf/thermal)). Thus persistence, render-resource lifetime and sustained quality are architecture inputs, not late adapter details. No device class or frame/memory number is yet certified.
- **World representation and multiplayer:** metre-scale coordinates and stable IDs are a coherent starting convention; the town and exploration workloads do not settle huge-world precision or network determinism. Decide world extent, region size and ordinary co-op requirements before selecting transform storage, rollback or replication contracts.

## Coordinated commissions and acceptance gates

The architecture owner retains the requirement ledger, C2 shared-contract revisions and whole-scene budget. Each commission receives both town and exploration scenarios, browser/mobile constraints, upstream producers, downstream consumers, a budget envelope marked `TBD`, required design depth and a change-escalation path. Workers return one canonical design, evidence locators, open choices, contract diffs and an ordered proof with rejection conditions. The owner sends proposed boundary changes to both sides, traces complete paths, updates shared contracts, and only then accepts a commission; parallel reports are not independently integrated.

| Commission / owner | Contract question and worked handoff | Completion for design stage |
| --- | --- | --- |
| Host, profile, identity and time | One tick/two views; provider validation; resource/state lifetime on mobile suspend and GPU loss | Stable authority/scheduling/transaction semantics; unsupported profile combinations explicit |
| Asset, world and authoring | Edited prefab through cook, stream, collision/nav/render activation, save/reload | Versioned identity/products and atomic activation/invalidation; source/runtime provenance |
| Movement and game services | Input/AI → root motion request → physics contact → pose, navigation and interactions | No duplicate transform authority; contact/streaming failure cases reasoned |
| Graphics/material/environment | Illumination without visible sky; rain → accumulated surface → material and traction; two cameras | Producers/consumers, energy/quantity units, view histories, approximate providers and cost bounds |
| Audio, UI and persistence | Spatial events, touch/text/accessibility, interruption/replay/save | Event identities and platform lifetimes; game policy distinguished from engine service |
| Quality/diagnostics/delivery | Combined scene across desktop/browser/mobile; build-time removal and live transitions | Allocation model, profile checks and reproducible measurement plan; no false certification |

First proofs should be selected for architectural rejection value: shared scene with two cameras but one world step; visible cloud removal with illumination retained and measured disabled cost; stream/edit/save/reload while a character crosses a region edge; rain-driven surface appearance and traction from one state; browser device loss and mobile suspend/resume; sustained mobile and browser startup measured on named devices. Each proof must preserve the interaction it tests. The first four design reviews can be completed analytically; runtime proof and perceptual acceptance remain planned.

**Still open:** target hardware/OS/browser floors, numerical frame/startup/memory budgets, scene scale and content throughput, ordinary networking, renderer-library choice, source license and contribution venue. These cannot be filled by a guessed threshold. The high-level commission is ready; detailed modules must not inherit a fabricated performance certificate.
