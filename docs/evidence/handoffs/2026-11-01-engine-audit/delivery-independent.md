# Independent creation-to-delivery checklist (before reading engine-rebuild notes)

Scope: reusable modern 3D custom host for overhead/isometric/first/third-person games; Mac, PC, browser demos, native mobile stores. AI assistance is a development aid, not a runtime requirement. This is a decision checklist, not a demand to copy every feature from surveyed engines.

## Consequential choices to look for

1. **Authored world versus running world.** Specify the editable canonical scene/entity data, stable identity and references, derived runtime state, play-session isolation or restart, and whether edited changes can be applied back. Options: headless text/data authoring with external DCC; integrated editor sharing runtime code; hybrid. The boundary matters to persistence, asset references, transactions, tools and simulation authority.
2. **Gameplay iteration.** Choose a minimum credible edit/play loop and code-change behavior: rebuild/restart, selective data hot reload, script VM/hot reload, or native code reload. State migration and deterministic replay matter if live changes are offered. A scripting language is an option, not an automatic requirement.
3. **Asset identities and cook graph.** Define source assets, imported/intermediate assets, derived runtime packages, dependency/version keys, deterministic import, platform-specific conversion, invalidation and missing-asset diagnostics. The runtime cannot assume editable source files are deployable.
4. **Shader/material workflow.** Define the authored material/shader surface, offline validation/translation for target graphics APIs, variant policy, build-time stripping versus runtime selection, cache invalidation and fallback. This interacts with configurable feature profiles and platform targets.
5. **Scene and content scale.** Decide how authored scene units become loadable worlds/chunks, stable cross-boundary references, prefetching and unload, plus whether a bounded continuous world is enough. Avoid inventing open-world requirements, but keep asset and scene contracts compatible with selective loading.
6. **Platform host and build products.** Mac/PC/browser/native-mobile imply potentially different windows, app lifecycle, input, storage, GPU backend, shader packaging, signing and distribution. Decide engine core/host/API boundaries, support matrix, fallback modes and platform build profiles before module APIs freeze.
7. **Configuration timing.** Distinguish compile inclusion, content cook, load-time profile and live toggle. Feature removal should avoid resource and processing cost while preserving shared inputs needed by retained features. Specify invalid combinations and dependency validation.
8. **Performance and observability.** Define whole-scene frame/memory/loading budgets by target class where possible, trace/event identity across CPU/GPU/asset loading, leak/resource accounting, reproducible capture, and an on-device profiling loop. These are service contracts if modules must emit data, not just later QA tasks.
9. **Production workflow and reproducibility.** Define project format, versioned authored data and migration, headless build/cook/validate CLI, build manifest/provenance, CI smoke coverage, error surfacing, and how developers iterate on target devices. An integrated GUI editor is optional; reproducible creation and delivery is not.
10. **Extension and reuse boundary.** Specify engine capability APIs, game-specific code and content, external-library adoption/upgrade/licensing policy, and extension points where needed. Do not infer universal plugin packages from Bevy's example; ordinary internal modules may be enough.

- Unreal: [Play/Simulate duplicates the level for play](https://dev.epicgames.com/documentation/unreal-engine/ineditor-testing-play-and-simulate-in-unreal-engine); [build, cook, stage, package, deploy](https://dev.epicgames.com/documentation/en-us/unreal-engine/packaging-your-project); [profiling](https://dev.epicgames.com/documentation/en-us/unreal-engine/introduction-to-performance-profiling-and-configuration-in-unreal-engine).

- Bevy: [plugin selection](https://bevy.org/learn/quick-start/getting-started/plugins/) illustrates one composition mechanism only.
- PlayCanvas: [Editor uses the runtime engine](https://developer.playcanvas.com/user-manual/editor/); [publishing](https://developer.playcanvas.com/user-manual/editor/publishing/web/playcanvas-hosting/) illustrates a web-specific creation and delivery path.

This is a sampled documentation comparison, not a comprehensive engine survey, production benchmark or proof that any particular editor/build architecture is superior.
