# Independent core-engine decision checklist

Derived 2026-11-01 from the stated product intent and primary engine documentation **before reading `notes/engine-rebuild`**. This file records competing approaches, not selections; keep it unchanged during the subsequent audit.

## Given constraints

- A reusable custom 3D engine for overhead, isometric, third-person and first-person games; visually exceptional and performant on Mac, PC, browser demos and native mobile app stores.
- AI-assisted development means code and content must be inspectable, deterministic where useful, and easy to change; it does not imply a runtime LLM.
- Pure 2D and MMO are outside current scope. Ordinary networking remains undecided. Custom host is selected; Bevy is a reference, not the host. Library reuse is allowed.
- A capability may be useful without its visible object (for example lighting and cloud shadow without a drawn sky). No rule requires every feature to be a plugin.

## Decision checklist and competing approaches

1. **World and entity identity.** Decide one lifetime and identity model for authored objects, dynamically spawned objects, simulated state, and render instances. Competing patterns: Bevy's ECS entities/components/resources and query systems; Unreal's actors with attached components plus game-instance/world lifetimes; Godot's scene tree/nodes over servers. The choice determines save/load, references, hierarchy, streaming, editor serialization and net IDs. Sources: [Bevy ECS](https://bevy.org/learn/quick-start/getting-started/ecs/), [Unreal actors](https://dev.epicgames.com/documentation/en-us/unreal-engine/actors-in-unreal-engine), [Unreal gameplay framework](https://dev.epicgames.com/documentation/en-us/unreal-engine/gameplay-framework-in-unreal-engine), [Godot nodes/scenes](https://docs.godotengine.org/en/latest/getting_started/step_by_step/nodes_and_scenes.html).
2. **Authoring vs runtime representation.** Decide whether editable scenes/prefabs are the same objects as runtime, are converted/baked to compact runtime data, or use a hybrid. Unity Entities explicitly bakes flexible GameObjects into runtime entity scenes; Godot instantiates saved node scenes directly; O3DE uses components supplied by Gems and an asset-processing pipeline. The choice affects hot reload, source provenance, iteration speed, memory, loading and AI-authored content validation. Sources: [Unity baking](https://docs.unity.cn/Packages/com.unity.entities%401.0/manual/baking-overview.html), [Godot nodes/scenes](https://docs.godotengine.org/en/latest/getting_started/step_by_step/nodes_and_scenes.html), [O3DE assets](https://docs.o3de.org/docs/user-guide/assets/), [O3DE components](https://www.docs.o3de.org/docs/user-guide/components/reference/).
3. **Gameplay execution and scheduling.** Decide fixed and variable phases, ordering, barriers, side effects, pause, background work, and deterministic replay scope. Bevy schedules systems with explicit chains while unrelated systems can run in parallel; Unity has system groups including fixed-step simulation; Unreal exposes tick groups and dependencies; Godot offers scene-tree frame and fixed physics callbacks. An ECS is not itself a schedule. Sources: [Bevy ECS/scheduling](https://bevy.org/learn/quick-start/getting-started/ecs/), [Unity systems](https://docs.unity.cn/Packages/com.unity.entities%401.0/manual/concepts-systems.html), [Unity time](https://docs.unity.cn/Packages/com.unity.entities%401.0/manual/systems-time.html), [Unreal ticking](https://dev.epicgames.com/documentation/en-us/unreal-engine/actor-ticking-in-unreal-engine), [Godot SceneTree](https://docs.godotengine.org/en/latest/tutorials/scripting/scene_tree.html).
4. **Data layout and extension point.** Decide whether all gameplay uses an archetype ECS, objects with components, data-oriented stores only for dense populations, or a hybrid. ECS can improve query iteration and scheduling but imposes structural-change, hierarchy and object-reference costs. Unreal's Actor/Component model and Godot's nodes favor direct composition and scene authoring; Unity demonstrates authoring-to-ECS conversion. Require workload evidence before asserting one model wins for all game types. Same primary sources as 1–3.
5. **Simulation/render boundary.** Decide ownership of transforms and presentation state, snapshot/extraction cadence, interpolation, temporal history, and visible-instance identity. Bevy's post-process example explicitly extracts a component from main world to render world; Unreal's components create and dirty render state; Godot scene objects mount on a low-level RenderingServer. These are different tradeoffs between isolation, latency and direct update. Sources: [Bevy render-world example](https://bevy.org/examples/shaders/custom-post-processing/), [Unreal components/render state](https://dev.epicgames.com/documentation/en-us/unreal-engine/components-in-unreal-engine), [Godot RenderingServer](https://docs.godotengine.org/en/4.4/classes/class_renderingserver.html).
6. **Renderer replaceability level.** Decide whether swappable means graphics API backend, render pipeline, graphics feature/provider, or the whole renderer. O3DE separates graphics features, render-pipeline interface and hardware interface; Godot has a scene/server split; Bevy registers renderer as an optional plugin. These are not equivalent replacement promises. The hard boundary must account for GPU resource ownership, material/shader data, render graph, camera views and platform fallback. Sources: [O3DE Atom](https://docs.o3de.org/docs/atom-guide/what-is-atom/), [O3DE RHI](https://docs.o3de.org/docs/atom-guide/dev-guide/rhi/rhi/), [Godot architecture](https://docs.godotengine.org/en/stable/engine_details/architecture/godot_architecture_diagram.html), [Bevy plugins](https://bevy.org/learn/quick-start/getting-started/plugins/).
7. **Capability composition.** Decide compile-time inclusion, load-time providers, per-world configuration and live toggles separately. Specify dependency/compatibility validation, ordering, cleanup, migration and fallback; an absent visual feature must not accidentally remove its physical effects. Bevy's plugins register App behavior; O3DE Gems package code/assets and supply components; Unreal's subsystems use scoped lifetimes. No evidence says every module should be a plugin. Sources: [Bevy plugins](https://bevy.org/learn/quick-start/getting-started/plugins/), [O3DE Gems](https://www.docs.o3de.org/docs/user-guide/gems/), [O3DE components](https://www.docs.o3de.org/docs/user-guide/components/reference/), [Unreal framework](https://dev.epicgames.com/documentation/en-us/unreal-engine/gameplay-framework-in-unreal-engine).
8. **World lifecycle and streaming.** Decide what survives scene/level changes, how regions load/unload, how references to unloaded objects behave, and whether multiple worlds/preview worlds exist. Unreal distinguishes persistent game instance from a level/world and its actors; Godot scenes enter/leave the tree and can stall if changed synchronously. This choice reaches saves, editor previews, render resources, physics and navigation. Sources: [Unreal framework](https://dev.epicgames.com/documentation/en-us/unreal-engine/gameplay-framework-in-unreal-engine), [Godot SceneTree](https://docs.godotengine.org/en/latest/tutorials/scripting/scene_tree.html).
9. **Asset/content contract.** Decide canonical source IDs, dependency graph, build products, versioning/migration, async loading, platform variants and runtime handles. O3DE Asset Processor separates source and cache/jobs; Unity baking makes conversion dependencies explicit. A content format is an engine interface, especially for AI-assisted editing and mobile delivery. Sources: [O3DE assets](https://docs.o3de.org/docs/user-guide/assets/), [Unity baker](https://docs.unity.cn/Packages/com.unity.entities%401.0/manual/baking-baker-overview.html).
10. **Networking deferral.** Do not require a protocol now. Decide only whether authority, state IDs, time/replay and serialization choices would preclude normal co-op or competitive networking later. Unreal bakes replication into Actors, while Godot's SceneTree has optional multiplayer polling and node authority; ECS engines can construct separate worlds. A single-player-only contract should be an explicit choice rather than an accidental consequence. Sources: [Unreal actors](https://dev.epicgames.com/documentation/en-us/unreal-engine/actors-in-unreal-engine), [Godot SceneTree](https://docs.godotengine.org/en/stable/classes/class_scenetree.html), [Unity systems/worlds](https://docs.unity.cn/Packages/com.unity.entities%401.0/manual/concepts-systems.html).

## Questions to apply to every selected or deferred choice

- Which supported game profile forces it? What counterexample fits another supported profile?
- Which state is authoritative? What can be cached, derived, streamed or rebuilt?
- What is a stable public contract, and what is an internal implementation choice?
- What must be decided before parallel module construction, and what can safely wait?
- What is the cost model (per entity, per frame, per view, per active provider, peak memory, load time), and how is it bounded on browser/mobile?
- Which owners and consumers would need to change if the choice reverses?
