# Measurement contract for AI-led engine optimization

1 November 2026. Design handoff only; no benchmark, runtime, or device qualification exists. Applies to the proposed custom Rust/wgpu host across macOS, Windows, browser, iOS, and Android. The architecture owner retains C12 and the whole-scene budget; T2 supplies the measurement path. This refines [C12](../../../design/CONTRACTS.md), [T2](../../../design/modules/TOOLS-DELIVERY.md), the [construction plan](../../../design/CONSTRUCTION-PLAN.md), and the [AI development design](../../../design/AI-DEVELOPMENT.md). A01–A05 stay open.

## Decision rule

An optimization is a candidate only if it preserves the required world semantics and visual/motion quality, improves a predeclared cost on the integrated workload, and does not violate another selected device/profile's budget. Analytical cost and error models should predict *why* it could win; experiments test that prediction and locate its valid regime. A faster isolated pass is diagnostic evidence, not an engine improvement. A fast frame with missing work, a lower resolution, stale history, delayed uploads, hidden background queues, or a colder device is a failed comparison.

The optimization record must state: changed mechanism; predicted work/traffic/critical-path change and approximation error; affected owners and consumers; workloads and device tiers where it should help or hurt; exact baseline and candidate revision; predeclared quality invariants and decision thresholds; measurements; and unresolved limits. Do not use an AI critic or a benchmark score to silently alter the acceptance condition. Threshold, reference, scene, camera, profile, shader, instrumentation, or test changes appear as separate reviewed diffs.

## Workload and comparison contract

Define each benchmark as an immutable **scenario descriptor** plus a **measurement protocol**. The descriptor pins source/build/toolchain and selected content/product hashes; target triple, backend, adapter/driver, negotiated features and limits; profile/provider plan; resolution, DPR, display mode, color space and exposure; camera route and views; world snapshot, seed, tick-ordered input/operation stream and nondeterministic external results; active content and presentation/history epochs; expected state, image, and motion cues. Record source dirty state and a hash of the full descriptor. Verify the candidate build actually ran: capture executable/shader/product identities from the active process rather than inferring them from the command line. A01/A02 source/session rules will determine how this identity is admitted; no mutation claim is certified before they close.

Use a small, fixed suite with distinct purposes:

1. **Mechanism microcase:** bounds arithmetic, memory traffic, occupancy, and scaling; vary the independent dimension through the claimed regime. Run it to diagnose a mechanism, never to select a whole-engine winner.
2. **Integrated representative scene:** the construction plan's two-region, animated character/body, instancing, lighting, transparency, environmental coupling, audio/UI, two camera styles and streaming boundary. Both views read one world tick. It tests real contention and combined critical paths.
3. **Adverse transitions:** cold launch/first interactive; stream across a boundary; edit/cook/activate; profile change; missing/disabled provider; resize; suspend/resume/device loss where supported. Capture peak old/new/staging residency and recovery, not just steady frames.
4. **Held-out scenes:** at least one different game/camera/content distribution and one stress case chosen before tuning. Keep their exact inputs inaccessible to the optimization agent until a candidate is frozen. Rotate/replenish after disclosure; preserve prior results. A single scene will teach agents to exploit its camera, visibility, or shader inventory.

Predeclare the *work and output*, not only a frame count: actual objects/triangles/pixels/visible lights, animation/physics/agent steps, streamed bytes, shader/pipeline variants, number of views, and feature plan. Report an equivalent-work check for A/B. If an optimization legitimately culls more or changes LOD, compare the delivered cue and workload semantics, and account for any shifted cost. Disabled-feature savings require proof that no retained consumer loses its provider and that avoidable CPU jobs, GPU passes, uploads, and resident bytes actually disappear.

## Four measurements, kept separate

| Claim | Primary observations | Common false positive |
| --- | --- | --- |
| CPU/scheduler | Per-frame main critical path, thread work and wait, job queue depth/age, tick cost/backlog, input→submit span, allocation/lock/stall samples | Summing parallel jobs as frame time; moving work to an unbounded queue; faster submit with slower input latency |
| GPU | Per-queue/pipeline pass intervals and dependencies, command-submit→completion, upload/transfer, bandwidth or occupancy diagnostics where available | Adding overlapping pass durations; interpreting a replayed isolated pass as live throughput; timing CPU API calls as GPU work |
| End-to-end | Presented-frame intervals and deadline misses, input→visible response where observable, startup/first useful frame, load/stutter, audio continuity, memory/energy/thermal trajectory | Reporting average FPS while p99 stalls or display queue latency rises; measuring only a GPU capture |
| Correctness/quality | World assertions and hashes within declared determinism envelope, geometry/collision/transport invariants, view captures and motion clips, temporal defects and human review | Pixel match hides wrong semantics; faster result is blurrier, darker, lower-resolution, temporally unstable or silent |

The frame is a dependency graph. Report the *longest dependent path*, total work divided by effective parallel capacity, queue waits, GPU execution, and present/display intervals separately; none is a substitute for another. CPU and GPU clocks may have different epochs, so only align them via a calibrated platform trace or recorded correlation, with uncertainty. Label GPU byte counts and times `estimated` or `unavailable` when the backend cannot expose them. The WebGPU `timestamp-query` feature is optional and timer values are precision-reduced for privacy; its absence cannot become a fabricated GPU pass time. [WebGPU specification](https://www.w3.org/TR/webgpu/).

Use low-overhead counters/markers on the normal run, then focused native traces to explain a candidate. Measure trace overhead against the uninstrumented run; do not put debug overlays, screenshots, GPU captures, or readbacks into the primary timing window. Save a trace/capture linked to the same scene/build but treat profiler replays as diagnosis: PIX says single-frame GPU capture timing can change async queue overlap, while Timing Captures observe running CPU/GPU overlap. Apple's counter profiler likewise serializes passes for some pass-level counters. [PIX GPU capture](https://learn.microsoft.com/en-us/windows/win32/direct3dtools/pix/articles/gpu-captures/pix-gpu-captures), [PIX Timing Capture](https://learn.microsoft.com/en-us/windows/win32/direct3dtools/pix/articles/timing-captures/pix-timing-captures), [Apple GPU counters](https://developer.apple.com/documentation/xcode/analyzing-apple-gpu-performance-using-counter-statistics).

## Sampling and noise protocol

Each target/device is its own stratum. Pin power mode, refresh policy, window/foreground state, network and storage condition, compiler optimization level, diagnostic flags, and ambient/load conditions as far as the platform permits; log what cannot be fixed. Never run two GPU measurement jobs concurrently on one device. Use short calibration runs to find warm-up stabilization and baseline variance, then freeze the window and repetition count before candidate evaluation. Present **cold** source/build/cache/download/startup trials separately from **warm** steady-state trials; shader/pipeline/cache warm-up and asset residency must be equivalent within each trial type. Record cache state and first-run cost; do not discard shader compilation stalls from a startup claim.

For warm comparisons, randomize or counterbalance paired A/B order across blocks (for example ABBA or BAAB), resetting state and cooling as needed. Include a same-binary A/A control to estimate harness noise and drift. On mobile, reserve long exclusive runs for the sustained state and record thermal status, clocks/power when available, battery/charging condition, and performance over time; report cool burst and thermally settled windows independently. If thermal state or system load diverges between A/B, rerun or mark the pair inconclusive. Android documents throttling under thermal stress; Apple's Game Performance trace exposes thermal, display, CPU and GPU events. [Android game optimization](https://developer.android.com/games/optimize), [Apple Metal app profiling](https://developer.apple.com/documentation/xcode/analyzing-the-performance-of-your-metal-app/).

Compute distributions from independent *runs/blocks*, not millions of correlated frames treated as independent samples. For each stratum, report median, p95/p99 frame intervals, miss rate and its denominator, worst relevant stall, CPU/GPU critical cost, memory peak and sustained trend with interval estimates or paired deltas. Use robust paired confidence intervals (or a predeclared equivalent) and a practical improvement threshold above measured A/A noise. An interval that spans both a meaningful gain and a meaningful regression is **inconclusive**, not a win or tie. Keep raw time series and metadata for reanalysis; cap artifact retention by retaining the exact accepted and rejected decision evidence plus reproducible recipes.

The mobile/browser planning targets in [platform runtime](../../../design/modules/PLATFORM-RUNTIME.md) are *unmeasured envelopes*, not certification. Select named minimum devices, scene scales, and thresholds before promotion. Native desktop, browser, and native mobile are separate rows; a browser inside a mobile shell does not qualify native mobile. A browser run records browser version, flags, WebGPU feature set, page lifecycle and network/cache state. Present cadence is not identical to GPU completion or physical scanout; use platform traces when asserting input-to-display latency.

## Correctness and visual guardrails

First reject regressions in fixed-tick world transitions, authoritative state, save/replay, ownership, resource lifetime, provider closure, content generation and transition recovery. Test the mechanism's mathematical invariants and approximation error bounds across the declared domain, including extreme/corner inputs and a changed frame cadence. Render quality is an explicit constraint: compare native-resolution images and time-aligned clips at locked camera/exposure/gamut, with masks only for documented nondeterministic regions. Check temporal stability, disocclusion/ghosting, motion vectors, LOD popping, shadow/light continuity, transparency, UI/text and audio where affected. Use objective image/motion metrics as *alerts* tuned per cue; do not optimize one global similarity number. Human acceptance applies to the exact build/content/view/profile under review, and cannot be inferred from an AI judgment or still image alone. This follows C12 and the existing golden-capture policy; performance experiments do not mint approved goldens.

For physically based providers, separate numerical fidelity to a specified model from perceptual/artistic quality. A cheaper approximation can be a valid profile only with a declared regime, error and failure behavior; it cannot silently replace gameplay-authoritative water, collision, lighting input or shared environmental cause. Check lower quality and off-state semantics as well as maximum quality. If a provider/algorithm changes the work rather than merely its implementation, compare it on a quality–cost frontier, not by claiming equal-work speedup.

## AI search without benchmark gaming

Give an optimization agent the analytical model, public contracts, training scenarios and a finite evaluation budget. Require each proposed edit to state the cost/quality hypothesis and affected contracts before a run. Keep the held-out scene content, camera routes, seeds and acceptance thresholds in a separate evaluator-owned manifest; an agent receives only aggregate failure reasons until its candidate is frozen. Do not let candidate code detect benchmark mode or scenario IDs to choose a special path. Verify an ordinary packaged build and trace active work. Keep *all* attempted variants, including failed/slow ones, in the decision log so repeated search does not launder a lucky result. Use a fresh holdout or independent replication before accepting a novel high-gain claim; if holdout fails, revise the model and keep the candidate unqualified. No autonomous threshold/golden/profile changes or cherry-picked device exclusion.

Allocate expensive devices by uncertainty and impact: analytical bound → cheap headless/unit correctness → microcase → one representative device → cross-device/held-out → sustained mobile/browser and human review. The evaluator owns the hardware queue, environment reset and artifacts; agents can request jobs with exact revisions/descriptors but cannot change the measurement protocol during a comparison. Queue jobs by device availability and expected decision value; stop a clearly failing candidate early on correctness, memory or quality, while preserving failure evidence. Do not use early-stop timing from a cold device as a sustained performance result.

Report a **per-device Pareto frontier**, not one universal speed score. Each point includes quality tier/cues, p95/p99 and miss rate, latency, peak memory, startup/download, sustained energy/thermal behavior and build/package footprint. Reject dominated points under the same semantic and visual constraints; retain a portable baseline plus justified target-specific enhancements. Aggregate or weight devices only after product owners name the supported device mix and priorities. A gain on one desktop GPU does not compensate for a mobile regression by arithmetic average; a fallback that fails its minimum floor is unqualified even if its weighted score is good.

## Cross-owner obligations and first delivery

| Owner | Needed contract before trustworthy optimization |
| --- | --- |
| Architecture/F2/F1 | Freeze representative workload, finite profile tiers, whole-scene budgets, deadlines/transition policy and named device matrix; derive predicted critical paths before trials. |
| T2/T1/P7/F3/F4 | Immutable scenario/evidence schema, actual source/build/session and active-product identity, replay/input ordering, cold-cache/streaming state, bounded traces and evidence status; do not conflate accepted edit with active build. A01/A02 still gate source/session mutation claims. |
| V1/V2/V3/V4/E1 | Pass/resource and view/history markers; consistent GPU lifetime, quality cue and temporal invalidation identities; profiler support without mandatory timestamp queries. A03–A05 still gate the corresponding shader/environment/media paths. |
| Platform adapters | Device/backend/driver and power/thermal/display metadata; native packaging and browser trace hooks; lifecycle reset and exclusive benchmark jobs. |
| Model/feature owners and reviewers | Cost/error predictions, valid domain, equivalent-work assertions, independent correctness checks, motion/visual acceptance and cross-consumer regression review. |

First practical deliverable, after D0/D1 contracts, is one versioned scenario/evidence schema and a reproducible single-device A/A then A/B harness for the complete reference scene. It should produce a compact result, raw series and a trace/capture link with explicit `passed`, `failed`, `skipped`, `unavailable` or `inconclusive` per claim. Add target adapters and held-out scenes as the relevant I3/I4 slices become runnable. Do not create a universal optimizer or a large benchmark service before this path proves provenance and comparability. Review integrated revisions sequentially; module-only wins remain candidates until combined-scene qualification.
