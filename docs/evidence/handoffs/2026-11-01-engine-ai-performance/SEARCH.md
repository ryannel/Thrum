# AI-driven engine optimization: search design challenge

1 November 2026. Research handoff, not a selected architecture or an implemented optimizer. Applies to the proposed custom Rust/wgpu engine for Mac, Windows, browser and mobile. It challenges the search scope of [AI development](../../../design/AI-DEVELOPMENT.md), [system design](../../../design/SYSTEM-DESIGN.md), [composition](../../../design/COMPOSITION.md) and [construction plan](../../../design/CONSTRUCTION-PACKAGES.md). A01–A05 remain open; no performance or quality result is claimed here.

## Recommendation

Treat optimization as **constrained program and product search**, not automated local code cleanup. Keep authority, causality, profile semantics, source identity, physical validity and minimum quality as hard constraints. Search the feasible Pareto frontier of frame tails, sustained power, memory peak, startup/download, loading stalls and engineering complexity. Give agents freedom to change algorithms, representations, work placement, offline products and portable kernels together, provided each candidate declares its changed contracts and passes independent evaluators. Select a small number of whole-scene candidates for human visual judgment and named-device qualification. This is an I3/I4 capability built on D1/D2 contracts; it should not postpone resolving A01–A05 or substitute an optimizer for those decisions.

The opportunity is larger than a one-function speedup. A candidate could jointly alter visibility partitioning, cooked instance layout, LOD representation, material variant set, GPU pass fusion and upload cadence. That search space is too coupled for routine hand tuning, yet has executable outcomes if the scene and invariants are fixed. The search system should reveal which contract or budget limits the result, including negative findings.

## Search surface and governing gates

| Search scale | Candidate freedoms | Non-negotiable boundary / typical failure |
| --- | --- | --- |
| Algorithm | Culling hierarchy, light assignment, shadow update policy, animation/skin evaluation, streaming priority, broadphase/query data structure; compare asymptotic and workload-specific choices | Same required visible/physical events; no hidden missed collision, missing light or priority starvation. State owner stays fixed unless architecture coordination changes it. |
| Representation | Dense/sparse layout, quantized cooked geometry, mesh clusters, instances, impostors, volume basis, shadow/indirect caches, CPU/GPU query mirror | Error and validity domain explicit; durable IDs and world authority unchanged; physical queries cannot silently consume a visual proxy. |
| Schedule | CPU job partition, dependency order within allowed graph, pass fusion/aliasing, transfer batches, background preparation, temporal update rates | Preserve fixed tick and causal barriers; no async result writes live state, stale generation publishes, or unbounded queue. Account for latency and transient overlap, not only throughput. |
| Content/cook | LODs, texture/mesh encoding, region packing, variant closure, static baking of declared invariants, profile-specific payloads | Provenance and rebuild closure retained; authored change invalidates affected products; A03 demand/readiness validated; no scene-specific hardcode pretending to be a general engine win. |
| Compiler/kernel | WGSL workgroup sizes, memory layout, branch/specialization choice, stage fusion, CPU SIMD, shader/compiler flags within supported targets | Compile and conformance on actual backends; no undefined behavior, reduced output coverage, target detection that bypasses work, or unmeasured native-only optimization. |

Two optimization tracks should remain distinct. **Exact or contract-equivalent** changes preserve outputs within a declared numerical envelope and all gameplay state. **Deliberate approximation/quality** changes alter visual or physical fidelity only where an owner has defined a validity domain, consumer tolerance and profile transition. Approximation can be valuable; it needs an explicit product decision and separate acceptance. A candidate that merely exploits a weak test (zeros, skipped pixels, frame skipping, a warmed cache absent from the real product, altered thresholds, or omitted required work) is invalid, even if its benchmark score improves.

## Evaluator stack: expensive truth, cheap screening

1. **Freeze the workload and identity.** Record candidate revision, source/content hashes, effective feature/profile lock, target/backend/driver, camera route, scripted actions, seeds, time samples, resolution, duration and compiler/tool versions. Do not compare changed scenes, hidden build flags or prior running sessions. Use holdout scenes and actions that the search agent cannot tune against; include empty/headless and full simultaneous-scene cases.
2. **Build a slow trusted reference per obligation.** Use straightforward CPU/high-precision or high-sample implementations where practical, plus analytical conservation, geometry, temporal and identity invariants. For rendering, a slow high-quality image/sequence may be a reference for a *specific cue*, not a universal aesthetic oracle. For physics and water, validate against the selected physical model and conserved quantities; a pretty image cannot establish buoyancy or flux. Preserve independently authored fixtures and reference implementation from candidate patches.
3. **Screen cheaply in increasing cost order.** Static contract and dependency checks → compile, sanitizer/validation and property tests → differential state/geometry/energy checks → GPU image and motion comparisons → isolated CPU/GPU microbenchmarks → representative whole-scene traces → long sustained target runs and human visual review. Recheck rejected candidates if the evaluator itself changes; never let an agent edit its own pass threshold as part of a performance patch.
4. **Use an error vector, not one image score.** Examples: world-state/event mismatch (normally zero), query position/normal/force error by support domain, energy/flux residual, projected silhouette/coverage/depth error, temporal shimmer/disocclusion, color/exposure error, missed visible cue, and audio/input latency. Set tolerances from D2 physical/visual contracts and approved looks. Report worst region/time and confidence, not only mean. If no accepted tolerance exists, label the result exploratory and request product judgment before promotion.
5. **Measure the whole product.** Report p50/p95/p99 frame intervals and missed deadlines, CPU critical path, GPU pass dependencies/traffic, memory including staging plus replacement overlap, shader compilation, load stalls, input-to-display latency, startup/download and sustained mobile thermal/power behavior. Maintain both unmodified baseline and current best on identical targets. A microbenchmark win is a hypothesis until the complete profile improves.

This preserves [C12's](../../../design/CONTRACTS.md#c12-budgets-evidence-and-acceptance--t2-with-all-owners) separation of design, implementation, correctness, perceptual and platform proof. The [platform budget table](../../../design/modules/PLATFORM-RUNTIME.md#whole-scene-budget-proposal--all-unmeasured) is a planning envelope, not a measured acceptance threshold. Before device targets and scene scale are chosen, use relative Pareto comparisons and reject claims of certified 60/30 fps.

## Three search campaigns worth commissioning

**1. Joint geometry, visibility and shadow representation.** For the first reference scene's orthographic and first-person cameras, search cooked instance grouping, mesh/plant LODs, culling hierarchy, shadow caster selection/update and upload layout together. Keep physical/nav geometry and durable identity separately governed. Objective: lower GPU critical path, traffic and resident peak while preserving camera-visible silhouette/coverage, stable motion, contact alignment and shadow cues across transitions. A whole-scene win can exceed a kernel win because the representation changes how much work reaches every later pass. Reject popping, missing interactive objects and a mobile-only gain that increases browser startup beyond its profile budget.

**2. Material/light/medium execution plan.** Once A03 and A05 are closed, search finite shader variants versus dynamic branches, light/bin structure, pass fusion, transient aliasing and profile-specific cooked products. The evaluator checks identical required material/light/overlap semantics, shader demand closure and time-coherent outputs, then measures pipeline creation stalls and pass traffic on Metal, Windows backend, browser WebGPU and mobile. Do not use a preintegrated atmosphere pair where the selected overlap contract requires joint coefficients; a faster invalid medium composition is not an optimization.

**3. Streaming and background-work policy.** On the two-region edit/save/unload/reload path, search region chunking, compression, dependency ordering, decode/upload batches, reservation and eviction policy. Objective: less startup and p99 stall at a bounded peak memory and no missed tick deadline. Replay failures at arbitrary cancellation/suspend points; test stale generation rejection, full collision/nav readiness before region activation and save restoration. Browser single-thread cooperation and mobile background/surface loss are separate target cases. This campaign makes the optimizer answer an expensive system question, rather than polishing a decoder in isolation.

Further campaigns such as water-domain discretization, coupled weather/vegetation update rates or physics broadphase are legitimate only after their owners define physical/domain interfaces and error budgets. A04 in particular is an open design mechanism, so search cannot decide whether a river–sea exchange is conservative, prescribed or visual-only by optimizing frame time.

## Coordination, compute and promotion

- One architecture owner fixes the semantic contract, reference workload and evaluator version. Specialized agents propose independent hypotheses at algorithm, content and kernel levels in isolated branches/products. The coordinator assigns affected producers/consumers before candidates cross contracts, deduplicates similar ideas and runs an integrated candidate after sequential review. Search history stores candidate lineage, rejected hypotheses and exact evidence, so another agent can resume without repeating trials.
- Rank first by feasibility, then maintain a Pareto archive rather than a single speed score. Allocate cheap evaluations broadly; spend scarce GPU/device time on diverse candidates whose predicted full-scene benefit is material. Use profiling and a cost model to prune candidates whose addressable fraction is small, but recalibrate the model with measurements and keep an exploration allowance for new representations. Cap trials, wall time, cloud cost and reviewer time per campaign before launch; stop when improvement saturates, constraints fail repeatedly, or the next experiment's plausible gain is below its implementation and validation cost.
- Promote only a candidate with an inspectable diff and source/product hashes, independent conformance pass, whole-scene gain on the intended target(s), no material regression on retained profiles, target-specific fallback where declared, and human acceptance for changed appearance/feel. Re-run the integrated revision; holdouts and device measurements cannot be inherited from a parent candidate. A target-specific optimized product is valid when its source, required variants and portable fallback are explicit. The runtime should select among prequalified finite products, not run open-ended AI search or silently modify game semantics on a player's device.
- If a search discovers a better architectural representation, return it as a proposed contract revision through D1/D2 and affected consumers. Do not smuggle a new state owner, source authority or coupling law through a performance patch.

## Research comparison and limits

- [AlphaEvolve paper](https://arxiv.org/abs/2506.13131) and [DeepMind account](https://deepmind.google/blog/alphaevolve-a-gemini-powered-coding-agent-for-designing-advanced-algorithms/) show an LLM/evolution/evaluator loop finding nontrivial algorithms and infrastructure improvements. Their strongest lesson here is to make the evaluator executable and allow changes larger than local rewrites. Their verified results do **not** show that this engine's physics, images or cross-platform product can be optimized automatically.
- [KernelBench paper](https://arxiv.org/abs/2502.10517) and [project evaluation](https://github.com/ScalingIntelligence/KernelBench/blob/main/README.md) show correctness-plus-speed measurement for generated GPU kernels and the value of iterative profiling feedback; the original paper also reports substantial difficulty. CUDA/PyTorch operator results do not transfer to WGSL render graphs, game semantics or sustained mobile performance. A [2026 independent workload study](https://arxiv.org/abs/2609.21058) reports that addressable wall-clock fraction can be small and documents false correctness passes from weak numerical tests; this is direct motivation for holdouts, output coverage and whole-scene measurement, not a performance forecast for Broadsides.
- [Halide GPU autoscheduling](https://arxiv.org/abs/2012.07145) and [TVM](https://arxiv.org/abs/1802.04799) provide primary evidence that search over representation/schedule with cost models can outperform routine schedules across hardware. Their domains have more regular computation and clearer equivalence than a full game engine. Use their search discipline, not their measured speedups as predictions.

**Next concrete decision:** During D0/D2, choose one fixed representative scene and its semantic/quality error vector, named target devices, and a small campaign from the three above. Then implement the evaluator and baseline before commissioning candidate search. This is the minimum infrastructure that makes ambitious AI optimization reviewable rather than a collection of impressive isolated benchmarks.
