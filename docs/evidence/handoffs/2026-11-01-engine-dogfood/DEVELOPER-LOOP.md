# Developer loop dogfood: smallest coherent creator experience

1 November 2026. Paper design review only; commands and formats below are illustrative, not implemented or tested. Scope: a custom 3D engine for Mac/PC, browser demos and native mobile, with more than one camera style. No Bevy host, mandatory editor, runtime LLM, pure-2D/MMO, universal plugins, or ordinary networking promise. Existing source/cook, identity, authority and lifetime contracts remain design inputs, not proof of working tools.

Read against `notes/engine-rebuild/ARCHITECTURE-AUDIT.md`, `SYSTEM-DESIGN.md`, `COMPOSITION.md`, `CONTRACTS.md`, `modules/TOOLS-DELIVERY.md`, and `modules/WORLD-CONTENT.md`. The audit's A01–A03 and J01/J02/J04 are the decisions tested here. This handoff recommends a creator interface; the root architecture owner must reconcile F1/F2/F3/F4/W1/P7/T1/T2/V1/V3 before selecting contracts.

## Recommendation in one screen

The default project is **ordinary source files under version control**, a small explicit game setup, assets and scenes/prefabs, and named delivery targets. `check`, `play`, `inspect`, `capture`, and `build` are enough for an initial CLI. Play runs an **isolated player process/world pinned to one validated source/code/profile snapshot**. Stopping discards its simulated state; saves stay in a session namespace; an explicitly selected scene change can be proposed back as a source edit with a revision precondition. Code/schema changes rebuild and restart the player. The developer may choose a scene, target, feature/model where behavior changes, and a provider only where more than one is meaningful. A normal game should not configure a graph, register its own scheduler, reason about GPU epochs, or resolve every provider choice.

The pleasant CLI is conditional on hard internal guarantees. A01 needs actual play/save isolation and apply-back; A02 needs a coherent external source snapshot and conflict handling; A03 needs shader demand/readiness for every selected target and permitted transition. Mark these **open design obligations** until specified and proven. Do not document `play` as safe, branch switching as seamless, or `build` as complete while these are missing.

## Baseline versus richer machinery

| Decision | Small default | Add richer mechanism only when the use case proves it |
| --- | --- | --- |
| Project/source | Files are canonical, with one explicit project setup and generated source-snapshot/product locks. Source control remains Git; cooked cache is disposable. | A database-first asset editor or remote collaborative source authority adds export/merge/recovery semantics to every game. Defer. |
| Feature composition | Typed static game recipe and target profiles, validated against finite capabilities. Optional compiled packages for genuinely expensive/rare features. | A universal runtime registration/plugin graph is not justified by small-game omission. Add a public extension seam for a real optional effect/model without making every feature a plugin. |
| Code iteration | Save files, validate, rebuild, restart isolated play; report source/compile/schema error while the previous good session can remain open against its pinned snapshot. | Binary hot reload, dynamic scripting VM and process-lifetime plugin replacement add state migration/ABI problems. Defer. Asset-only preview may recook and republish when its transaction is safe. |
| Play isolation | Separate player process/world with exact source pin and save namespace. Explicit apply-back of selected authored changes only. | In-place checkpoint/restore makes side effects, crashes and leaked state harder to bound. A same-process duplicate world may later optimize latency if it preserves the same session contract. |
| Targets | One semantic game setup; desktop, browser and mobile profiles choose budgets/products/backend support. Browser demo may omit costly presentation while retaining gameplay semantics. | Per-target forked game logic/content sources invite drift. Live arbitrary provider switching is unnecessary; qualify only specific transitions. |
| Renderer extension | Extend declared material/effect/pass hooks, with V1 execution and V3 transport ownership. | Full drop-in renderer replacement needs a demonstrated pipeline incompatibility; a custom effect alone does not establish it. |
| Tool surface | CLI plus structured diagnostics/queries; an editor, if built, is an adapter over the same source and operations. | A mandatory integrated GUI, remote API and general agent protocol can follow demonstrated workload. AI uses development queries and artifacts; shipped game has no LLM dependency. |

The simple recipe still needs truthful validation. Dependency and authority constraints can be internal; they should surface only as actionable choices when a project requests an unsupported combination. Package selection is build-time, not a promise of live unload. A custom effect may compile into one game without a new general plugin ABI. A small game can use one always-active scene and one camera, while the engine retains support for multiple views and streaming where required.

## Creator-facing vocabulary and first workflow

Creator-facing concepts: **project** (source files and code), **game setup** (entry scene, gameplay systems, required capabilities), **scene/prefab** (reusable authored composition), **asset** (editable master and imported runtime representation), **target** (desktop/browser/iOS/Android plus quality/budget profile), **play session** (isolated experiment), **change** (source edit with before/after and status), **build/capture** (traceable output). A target is not a separate world or duplicate gameplay authoring tree. A camera belongs to the game/scene; adding an orthographic preview does not duplicate state.

Explicit choices: game-specific rules; capabilities that affect meaning or content (e.g. rigid bodies versus trigger-only collision, physical versus decorative water, cloud attenuation with or without visible clouds); entry scene and cameras; intended targets; optional custom implementation/provider; permitted fallback and quality where visual claims differ; whether a play-created authored change should be applied. Defaults may fill in mundane presentation choices, but the resolved plan is inspectable and locked in a build. Never silently swap an authoritative simulation model for a cheaper visual substitute.

Invisible in routine work: F1/F2 graph solving, stable/runtime ID distinction, cook dependency DAG, shader variant keys, snapshot leases, GPU device generations, save RecoveryRoot, region epochs and per-view temporal invalidation. These remain inspectable in diagnostics. The creator must see desired versus active status when an edit is pending/failed, and the source/profile pin used by a preview or build.

Illustrative CLI, not an API proposal:

```text
engine check                         # validate saved project source and target closure
engine play --target desktop         # pin snapshot, build/restart isolated player
engine inspect actor:<id>            # bounded schema/state/source/provenance query
engine capture --camera harbor       # image + exact build/content/profile identity
engine build --target browser-demo   # full target gate and artifact provenance
```

`play` may imply `check` and incremental cook, but reports each step. Unsaved editor buffers are not source; save or explicitly stage them first. A source snapshot is an immutable selected set of file hashes, schema/profile lock, code revision and worktree identity; a new snapshot is admitted by an explicit workspace sync after external edits (possibly invoked by `check`/`play` after the developer declares edits complete). A watcher only detects dirtiness; a quiet timeout is not evidence that a checkout or multi-file save finished. The source snapshot mechanism must detect changing HEAD/index/worktree identity and files during capture; a stable double read alone cannot prove a multi-file operation was semantically complete. A truly atomic source transaction requires one cooperating writer or an explicit external-edit phase; noncooperating editor/Git writes cannot be promised atomic. Dirty files are allowed as an explicitly identified snapshot, not attributed to a clean commit.

## Paper walk 1: programmer and AI team on concurrent branches

**Normal:** Programmer A edits a movement system on one worktree while an AI agent edits a scene schema on another. Each runs `check` against its own source snapshot, receives file/field diagnostics, then `play`; two player processes have separate world and save namespaces. The AI inspects a bounded actor/schema query and a named capture, commits a source patch, and the programmer integrates it through ordinary Git review/merge. On the integrated worktree, `check` resolves schema/provider/content closure, rebuilds changed code/cook products, and starts a *new* play session pinned to the merge snapshot. An old session can remain for comparison, visibly labelled with its older source pin. No agent writes another worktree's runtime state or imports a hidden editor database.

**Branch change while a prefab edit is pending:** A T1 edit has been accepted for desired source revision R but its required product cook has not activated. The programmer switches branches. Source admission pauses; the pending operation stays associated with its original worktree/source base and is not replayed onto the new branch. `check` reports `source changed during pending edit` with old/new source roots, affected stable IDs/fields, and choices to finish/cancel on the original branch or rebase the semantic patch with a fresh precondition. The active player remains pinned to its old manifest or is stopped explicitly. A crash restores only a RecoveryRoot coherent with that old base; it never combines the pending desired edit, a new branch's files and an old save overlay. A local recovery patch is evidence to review or apply with a fresh source precondition, never an automatic overwrite of changed files. If the edit was made through a source file directly, the source patch belongs to Git; T1 must not revive a second journal copy of it after restart. A file rename preserves stable object identity through source metadata or an explicit rename mapping; a path is not the ID. Rename conflicts are shown rather than guessed.

**Developer value:** agents and people can use ordinary branches and reviewable diffs, with structured inspection when needed. Internal optimistic revisions and durable recovery matter, but the ordinary visible act is a file change plus a check. This directly exercises A02/J04 and exposes where the current T1 journal needs a source-of-truth decision.

## Paper walk 2: artist and programmer reuse one character and scene

**Normal:** An artist saves a character master, texture/material and clips with stable IDs and import settings. The programmer adds a character prefab with animation, collider, interaction and game-owned behavior; the scene references that prefab. The project declares desktop and browser-demo targets. `check` validates the actual dependency closure (skeleton/clip compatibility, collision, shader/material support) for each target. F4 cooks target products from the same masters and recipes; the browser uses smaller textures/LOD/quality, perhaps an overhead camera, while desktop uses a closer camera. Both draw one semantically shared character and scene with target-specific products. A capture names camera and target. Source masters and recipes remain durable per the current asset-storage contract; cooked runtime products are replaceable.

**Play/edit/stop:** The artist changes a material and previews against the pinned player. If a valid recook is safe, it stages then publishes a new presentation product and invalidates affected histories; otherwise restart with a new snapshot. A running body is moved by gameplay in play; stopping discards that movement and any play save remains session-scoped. If the artist intentionally wants the placement, `apply` creates a proposed source scene edit against the source revision, showing stable ID, selected authored fields, old/new values and dependent changes. Runtime handles, transient simulation fields and session save data are excluded. A concurrent programmer edit causes a precondition conflict, not silent overwrite. Nothing automatically exports a simulated pose to the authored scene.

**Missing browser shader:** The desktop variant succeeds but browser lacks the required skin/material/pass combination. Browser `check` or build fails at shader demand/preparation, identifying asset/material, pass, provider, target and the missing variant. It may offer a declared compatible material fallback or explicit omission policy; it may not ship an unlit/bind-pose/absent collider surprise. Desktop play remains usable; browser artifact is not promoted. A03 requires enumerating finite demand from selected content, material/pass/geometry/provider combinations and allowed transitions; selected bounded runtime specialization needs a visible loading/fallback policy. This is F4/V1/V3 closure, not a second asset system.

**Developer value:** one reusable authoring graph supports materially different targets and views. The artist deals with assets, prefab, target preview and clear failure, not per-backend shader cache internals.

## Paper walk 3: engine contributor adds optional effect/model

**Normal:** A contributor builds one optional wet-surface sparkle effect or a specialized water response model in an engine package. They declare its input/output meaning, valid regimes, target support, products, cost and effects on view history. A game opts into it in its setup. A second small game omits it and has no recurring effect work or cooked products; build exclusion can remove package code/dependencies where separately selected. The custom effect uses V1 pass/resource registration and V3 material/transport semantics; it cannot own a second GPU queue or alter authoritative wetness. If it is a physical water model, E1 owns the field/query and P3 receives declared forces at the shared tick boundary; the model is selected by the game/domain, not smuggled into a visual quality tier. A contributor writes a small conformance fixture and the two games run `check`; no generic plugin SDK is needed to change one engine-owned package.

**Failure:** The new effect requires a depth/velocity input unavailable in the browser profile, or a shader variant was omitted from the cooked demand set. `check` reports the unsatisfied input and affected target; the small game still builds because it never requested the effect. The opted-in game can explicitly choose a compatible fallback or remove the effect, then rebuild. Existing running sessions keep their pinned plan; failure does not half-register a pass, silently install a default provider, or change the other game's world. If a contributor later replaces an authoritative model, live migration is rejected unless an explicit state migration/quiescence contract exists; restart is the baseline.

**Developer value:** the extension seam is real where needed and omission has a measurable effect. The simplest game setup remains a list of chosen behaviors and targets rather than a registry implementation project. This tests J01/J02 and A03 without assuming full renderer replacement.

## Contract effects and safe simplifications

| Finding | Minimum contract effect | Simplification safe at the creator surface |
| --- | --- | --- |
| A01 session isolation | Name source pin, play session/world ID, save namespace, side-effect policy, stop/discard and explicit apply-back; restore after crash cannot treat play state as authored state. F1/W1/P7/T1 must agree. | One isolated player process and restart; no in-editor in-place play, rollback of live world, or automatic apply-back. |
| A02 source authority | Select files as canonical source; define coherent snapshot admission, branch/worktree identity, pending edit binding, rename/conflict and restart rules. T1 journal records operation status, not a rival editable truth. F3/F4/P7/T2 use the same source root. | Explicit `check`/`play` sync boundary; watcher is advisory. No collaborative DB or automatic cross-branch rebasing. |
| A03 shader availability | F2/F4/V1/V3/T2 declare finite demanded shader closure from selected target/profile/content and permitted transitions; identify cache keys and stripping/preparation gate. Missing required variant blocks target publication or enters declared loading/fallback. | Compile finite selected set at build/load; no universal dynamic specialization or arbitrary live provider switching initially. |

Retain internally: stable IDs and units; one authoritative world per play session and one tick; source-to-cooked hash graph and atomic manifest; desired/active/checkpoint distinction where live edits exist; safe leases, generations and recovery roots; typed capability/authority validation; per-target provenance and visual/performance qualification. These are what make the simple experience honest. Retire or defer from the *initial creator promise*: mandatory universal plugins, hot executable reload, all-purpose service locator, default remote API, database-first editing, editor-only truth, arbitrary live profile changes, full renderer replacement, automatic simulation apply-back, and a bundled runtime LLM. Do not delete ownership contracts merely because the UI hides them.

## What remains to decide or prove

1. A02 needs an exact source snapshot and crash transaction protocol for dirty multi-file edits and external Git operations. Decide whether T1 writes source files through one cooperating writer, submits patches for an explicit apply, or uses a versioned source manifest. External edits require an explicit completion/sync boundary. A journal plus direct file watcher with no shared source root is unsafe. Preserve a previous good source root and pending edit evidence on crash. A02 stays open until this backend is designed and proven.
2. A01 needs a complete process/session save and side-effect policy, especially network/filesystem side effects in game code, and a source-edit mapping for apply-back. Process isolation alone does not prevent external effects. Specify what a player process can write and how a crash or unsaved scene edit is reported.
3. A03 needs a finite shader-demand representation and target check that includes material, geometry/deformation, render pass, provider and supported transitions. Compile/warm timing and cache/stripping behavior still need target-specific proof.
4. Measure the actual rebuild/restart latency on representative desktop and browser projects after mechanisms exist. If it is unacceptable, optimize incrementality or evaluate asset live refresh first; do not assume binary hot reload is the cure. Compare package size and idle work for the small game with and without the optional effect. Prove browser/mobile quality on named hardware and scene budgets separately.

The three walks are paper counterexamples and a decision recommendation. They do not close A01–A03 or qualify any runtime, build, target, visual result or tool UX.
