# Small-game developer walkthroughs — paper design review

1 November 2026. These are three bounded, hypothetical game-development traces against the proposed custom 3D engine. They are **paper walkthroughs**, not implemented sample games, runtime tests, measured performance, accepted APIs, or a claim that the design gaps are closed. The current references are [architecture audit](../../../design/ARCHITECTURE-AUDIT.md), [integrated design](../../../design/SYSTEM-DESIGN.md), [composition candidate](../../../design/COMPOSITION.md), [brief](../../../design/ARCHITECTURE-BRIEF.md), and [shared contracts](../../../design/CONTRACTS.md). Their five A-gaps and J-choice status still govern. The user chose a custom host rather than Bevy, 3D across overhead/first-person and Mac/PC/browser/native mobile, and AI-assisted *development* rather than a runtime LLM. Pure 2D and MMO do not drive these cases. Reusing suitable libraries remains allowed. No game or engine source was changed for this review.

## Minimum developer needs before choosing an abstraction

| Developer | Minimum successful first delivery | Why it is enough |
| --- | --- | --- |
| Solo browser puzzle/tactics maker | One overhead 3D board, picking, turn/state rules, a movable light and a cloud-shadow effect, a small downloadable package, inspectable scene edits and a repeatable play test. | The maker does not need a weather simulation, visible sky, world streaming, runtime executable plugins or a full editor to ship a board. |
| Mobile puzzle/management maker | One touch-driven 3D scene with authoritative progression, a durable offline save, safe suspend/resume, a boot-critical asset set and a sustained device tier. | A second platform and persistence lifecycle are real constraints even with a tiny world. |
| Mac/PC interior story maker | One room, first-person control and interaction, dialogue/branch state, local light/audio, saved progress and native packages. | Terrain, weather, navigation agents and outdoor atmosphere are irrelevant unless the story later calls for them. |

All three need a clear path from authored source to a running scene, small game-owned rules, diagnostics that say *which revision is active*, and a way to package only required runtime work. These are requirements on the engine surface; they do not imply a plugin descriptor for every game rule. The hypotheticals below use illustrative plain-language requests. Any code-shaped recipe is a **candidate notation**, not an implemented API.

## Case 1 — solo top-down browser puzzle/tactics game

**Circumstances and selection.** A solo maker is building a compact 3D tile board for a web page. Each turn, the player selects a token, sees legal destinations, moves it and triggers a small lighting change. The scene is viewed orthographically, with a constrained pan/zoom and mouse plus keyboard input. The maker wants warm sunlight and drifting cloud-shaped shadows on the board, with no sky pixels, sunset cycle, cloud volume, weather solver, terrain streaming, characters, navigation service or rigid-body dynamics. A bounded cloud-opacity field at world time feeds Sun visibility; if shadows affect tactics, its time and values must be authoritative, deterministic input to the rule or frozen per turn. If it is only decoration, render time can animate it independently, but gameplay never reads render pixels. The game can use simple picking and authored tile adjacency instead of a physics solver or generic pathfinder.

**First scene and authored data.** Create a project with a board scene containing stable tile IDs, transforms/mesh references, a board material, a Sun descriptor, an overhead camera rig, a few token prefabs and a game-owned `Tile`, `Token`, `TurnState` schema. A level record states adjacency and win conditions. A low-cost authored cloud-attenuation source has a seeded phase or authored animation; it has no visible cloud draw. Import source meshes/textures, cook only board/tokens/material/light/shadow products for the browser target, and inspect the resulting dependency/variant closure before first play. A missing required board collider/picking proxy must be reported; a blank visual placeholder cannot pretend the move is valid.

**Ordinary behavior.** Pointer hover picks a tile; a selected token computes legal moves from game-owned rules; a click submits one move intent; the fixed world tick commits token position, turn state and one identified event. Rendering reads the committed board state and Sun attenuation. The cloud field can make beautiful moving shadows while the visible background remains a simple clear colour or room backdrop. UI reads the same move/event state. This needs the C02/C03 world authority and C08 light semantics, but not a network model or general weather lifecycle.

**Edit → play → inspect → stop.** The maker changes a level tile and its material in source, requests a build/preview, and sees source revision, cooked product set and active play revision. Start play from a pinned source/cook revision in a separate play world (recommended below); inspect selected tile ID, legal-move reason, active light/attenuation source, frame cost and a capture. Moving tokens and completing turns modify only play state. On stop, discard that play world by default; a separately requested *apply selected change* would produce a source edit with revision preconditions, not silently write runtime positions back. An accepted source edit during play can be queued for the next session or offered as a staged, explicitly compatible live edit. A shader/material compile error leaves the last valid preview active and reports the failed product. This paragraph is a **proposed A01/A02 policy**, not current settled contract.

**Midway change.** The maker asks for a second perspective camera close to the board. The world and rules remain one authority; add a view and its independent picking/projection/history policy. The same cloud attenuation and Sun are shared, while view-dependent shadow resolution and LOD may differ. The recipe must validate shader demands for both camera/material/pass combinations; this exposes A03. If the request becomes a mobile port, it is a new target cook/package and touch/safe-area work, not a magical live profile toggle. The cloud field can remain, but its shadow quality/provider may change after platform qualification.

**Package and failure/recovery.** The browser package includes only boot-required assets, declared material variants and the small scene; it does not include visible cloud shaders, weather solvers, terrain or editor code. The maker tests a cold cache on a named browser/device. A realistic failure is a requested shadow/material variant stripped because the original single-view cook never declared the added view. The build should fail with the missing material/pass/view demand path or use an explicitly authored fallback, never render a silent pink/black tile. The last valid browser bundle remains publishable while a new complete package is cooked and checked. Browser WebGPU support and numerical download/startup limits remain target qualification, not values this paper invents.

**Value versus ceremony.** The engine earns its place through separable light inputs, stable scene/schema identity, deterministic turn authority, target cooking and a simple inspectable edit/play loop. Making this maker publish a versioned native plugin with system access declarations, package compatibility, disable migrations and hot-removal policy just to add `TurnState` is needless. A typed game rule registration in a static application recipe is enough; the engine can internally validate system reads/writes and ownership without exposing package lifecycle to every solo game.

## Case 2 — native mobile 3D puzzle/management game

**Circumstances and selection.** A small team makes a single-screen 3D workshop where players place machines, queue jobs and collect output. It must run offline on iOS and Android, support touch/drag and safe areas, recover from app backgrounding, and keep startup/download and sustained thermal cost tight. Use one perspective or isometric view, simple collision/picking, UI/text, audio, small game rules, local save and target-specific raster lighting. Omit terrain, weather, streaming regions, character animation, navigation, cloud shadows and dynamic physics unless the actual puzzle needs them. Use a small pre-cooked scene rather than exercising W2 streaming merely because the engine has it.

**First scene and authored data.** Author a workshop scene, machine prefabs, placement sockets/occupancy rules, recipe table, currencies/timers, a `Queue` and `MachineState` durable schema, touch action map and semantic UI layout. Mark the first workshop, core textures, font and required pipelines as boot-critical offline products; optional decorative audio/skins can load later under explicit fallback. A game-owned progression policy decides whether production runs while the app is suspended. The default local policy in C02 pauses world time; any wall-clock catch-up would be a separate, bounded game rule using a recorded trusted-ish time source and a clear anti-tamper/clock-change stance. The engine must not silently advance many simulation ticks after resume.

**Ordinary behavior.** A drag begins in UI focus, becomes a placement preview, checks an occupied socket, then commits a machine purchase at one world boundary. Queue progress is fixed-tick while foregrounded. UI and audio consume identified events; touch and controller, if offered, map to the same game actions. Autosave captures the durable machine/currency/queue state at a committed barrier; GPU resources and transient touch gestures are excluded. Offline save availability is distinct from asset cache availability.

**Edit → play → inspect → stop.** Change a recipe yield and a machine prefab in source. The cook identifies the affected prefab and target products for both mobile builds; preview starts from a pinned source revision and a disposable copy of a test save. The developer plays, checks queue state, save-diff and active revision, then stops. The test save never replaces a user's real local save. A deliberate apply-back can select authored layout edits, not earned currency or elapsed play time. If source files change during the preview, the current world stays on its pinned revision until a validated transition or restart. This needs A01/A02 resolution and a save namespace rule before authoring APIs freeze.

**Midway change.** The team asks for a browser demo. The same world/rules can run with a smaller scene and browser adapter, but the browser package needs a separate cooked product/shader closure, input map and storage policy. An offline native save cannot be assumed to transfer to browser storage without an explicit import/export or account service. Conversely, adding landscape to the mobile game later is a genuine capability/content expansion; do not include W2 terrain today to make that request theoretically easy.

**Package and failure/recovery.** Prepare iOS and Android app artifacts through their SDK adapters, with source/profile/product lock and an offline boot manifest; signing/store acceptance is outside the engine's shared runtime. A cold-start and sustained warm-device run must qualify startup, memory, frame pacing and thermal behavior on named devices. A realistic failure: the OS suspends during an upload and a save checkpoint. F1 closes GPU submission, cancels/stales the upload by surface/device generation, and P7 either publishes a complete RecoveryRoot or retains the prior one. On resume, reacquire device/surface, reupload needed products from cooked bytes, restore the last complete save, reset view history and audio interruption state, and report any unsaved recent gameplay. This is consistent with C02/C06/C10/C11; it requires actual device testing before claiming success. A second realistic constraint is storage exhaustion: keep the previous root valid and report that the newest save did not complete.

**Value versus ceremony.** The engine's value is platform lifecycle, stable save schemas, source/cook separation, touch action mapping, explicit offline assets and admission of low-cost render tiers. Runtime plugin replacement, a generic weather stack, deep world streaming and a universal component scheduler add little to a one-room management game. Target packages and the save lifecycle are real complexity and should remain visible.

## Case 3 — short first-person Mac/PC interior story game

**Circumstances and selection.** One writer/designer and a technical partner build a 30-minute 3D apartment story for Mac and Windows. The player walks, examines objects, makes dialogue choices and saves progress. Select first-person camera/mouse/controller input, simple static collision, interaction rays, local lights/materials, a small dialogue/sequence runner, spatial audio and UI/subtitles. Omit terrain, weather, water, sky, cloud attenuation, vegetation, navigation agents, large-world origin and streaming. A window can use an authored exterior image and light probe; a physical atmosphere is not required. The engine must support close material quality and exposure inside a dim room without coupling that to outdoor modules.

**First scene and authored data.** Author one apartment scene with room mesh, static collision proxy, interactable stable IDs, dialogue graph/text/localization keys, inventory flags, checkpoint definition, first-person camera rig and audio emitters. Use game-owned `StoryFlag`, `DialogueState` and `Inspectable` data. Import meshes/audio and cook native target products. If a dialogue branch references a missing object or subtitle key, validation points to that reference before play. No dynamic rigid-body provider is needed if doors and drawers use authored animation plus collision-state updates at a world boundary.

**Ordinary behavior.** Input produces movement and look intent; character/camera policy requests a step; the collision owner resolves body motion; the camera reads the committed pose. An interaction ray identifies a photograph, plays a voice line and commits a story flag once. Audio follows the selected primary listener; UI subtitles and choices consume the same identified sequence state. A desk lamp affects local illumination; no Sun or environment field is active. The scene can use a simple authored room/portal visibility hint, but one compact apartment may need no general streaming representation.

**Edit → play → inspect → stop.** The designer changes a line, adds a branching choice and moves the photograph. A typed source edit reports exact referenced scene/dialogue records, cooks affected text/audio/scene products and starts a play world at a pinned revision. During play, inspect the selected object ID, story flags, branch path, audio event ID and current source/active revision; stop discards the play state. Applying the photograph's new authored transform is a deliberate source operation. A new dialogue schema may require restarting the play world and migrating a test save; a failed migration keeps the old source and save readable. Code changes follow a rebuild/restart handoff, not assumed binary hot reload.

**Midway change.** The team requests an overhead shot for a trailer or an optional map room. A second camera can view the same scene for capture; it gets its own history/exposure policy and cannot move the audio listener by being active. If overhead is now gameplay, introduce a picking/action policy and possibly revise interaction affordances; no new world state copy is required. If the team requests a Linux build, it is a separately qualified target, not an automatic consequence of Mac/Windows support.

**Package and failure/recovery.** Native packages include the room, dialogue/audio, required pipelines and save reader; outdoor providers and editor UI are excluded. Mac/Windows input, audio, display and save locations need named target qualification. A realistic failure is an external branch checkout that updates the scene and dialogue files nonatomically while the authoring tool has an accepted pending edit. The watcher must not cook a mixed branch or replay its journal over the new checkout. Hold the last complete manifest, identify the external change set, and ask for a semantic rebase/conflict resolution against the new source revision. A02 has no selected canonical boundary yet; until it does, this recovery cannot be claimed implemented. The player package remains on its last complete manifest.

**Value versus ceremony.** The engine earns its place with stable cross-scene references, validated dialogue/interaction state, edit/play isolation, audio/UI/input lifecycle and target packaging. It should let game code register a small rule/sequence module without forcing a general quest plugin, network transport, external scripting VM or entire replaceable renderer.

## What composition actually costs in these traces

Consider the same developer request in the three projects: “add one game-owned durable state type and a rule that changes it.” A **typed static recipe** might say, illustratively:

```text
game recipe (candidate notation, not an API):
  content: board-scene / workshop-scene / apartment-scene
  target: web / ios+android / mac+windows
  capabilities: selected input, world, view, render, UI, save as needed
  providers: explicit light/physics/audio bindings only where consumed
  game schemas: TurnState / MachineState / StoryFlag
  game rules: turnMove / completeJob / chooseLine
validate -> cook target closure -> run pinned revision
```

The developer declares the state schema, rule phase and access to world-owned data; static compilation and F2/F3/F1 validation reject duplicate writers, missing products or unsupported targets. To change it, edit the recipe/code, rebuild, restart the play session and migrate saves only when the durable schema changed. Build exclusion follows the actual selected code/products; runtime quality changes remain a separate, prevalidated presentation policy. An extension author can still implement a provider contract in code without every project adopting a package registry.

The **rich plugin candidate** in [COMPOSITION](../../../design/COMPOSITION.md) instead asks the game author to create a versioned package descriptor, register schemas/systems/operation handlers/product recipes, declare package and contract compatibility, access sets and lifecycle scopes, resolve a registry/profile lock, then handle load/disable dependencies and retained-save migration. For a reusable third-party physics or renderer extension these steps may buy isolation and distribution. For the three in-project rules above, the extra registration and removal paths mostly restate a fixed application build. In neither model may a rule bypass world authority, mutate a GPU resource, silently delete save state or make shader demand implicit. The comparison is based on the named work, not measured code size or build times.

The concrete asks sound like this (illustrative interaction, **not existing tools/API**):

```text
Developer: “Show which source revision my preview is playing, and why this tile has no shadow.”
Engine design should report: pinned play revision, active product/profile lock,
  selected Sun and attenuation providers, missing/failed pipeline or shadow input.

Developer: “Stop play and keep only the photograph's authored placement.”
Engine design should report: play-world state discarded; selected placement proposed
  as a source operation against a stated revision; conflict if source changed.

Developer: “Package the mobile workshop so it opens offline after a cold install.”
Engine design should report: boot-critical product and shader closure, target package
  gates, save-store policy, and named device startup/thermal evidence status.
```

## Keep, remove from the baseline, and defer

**Keep as core boundaries:** one committed world authority and fixed tick; stable authored identities and typed schemas; source revision versus cooked immutable manifest versus active world versus save checkpoint; typed game-rule registration and explainable dependency validation; build/load/live selection as different promises; render scene and light inputs separable from visible sky; GPU/resource lifetime; platform lifecycle and target-specific packaging; concise human/AI inspection over the same operations. These features are exercised even by small games.

**Simplify the initial developer surface:** start with a typed static application recipe and a small set of explicit provider binding points. Let a game register its own state and rules directly in that recipe. Keep internal schedules, access validation and content closure, but do not require a separately versioned plugin package for every game system or data component. Provide one straightforward `edit/source -> validate/cook -> start pinned play world -> inspect -> stop/apply selected source edit` story before offering live world mutation. Use full streaming, navigation, weather and environmental coupling only when a selected game asks for them; their absence should remove avoidable code/products/jobs. Expose a minimal target report: required capabilities/products, omitted work, unresolved demands, package identity and evidence status.

**Defer behind explicit use cases:** executable native hot loading; general live removal of gameplay systems and their migration machinery; arbitrary renderer replacement; universal event bus/DI container; a runtime scripting VM; cloud/weather/water model families for games without those phenomena; automatic cross-target save sync; generic world streaming for tiny scenes. A third-party distributed extension ecosystem may justify plugin descriptors later, but the current small-game traces do not. Keep subsystem implementation boundaries where necessary without claiming arbitrary swaps.

## Decisions still open versus later details

| Decision that affects the public path now | Suggested direction from these cases | Status |
| --- | --- | --- |
| J01 feature/composition promise | Static typed recipe for applications; optional provider packages only at justified distribution/implementation seams; no mandatory rich plugin lifecycle for game rules. | Recommendation, not selected. Compare against a real extension/distribution case before committing. |
| A01 edit/play session | Separate play world pinned to a coherent source/cook revision; test saves isolated; stop discards runtime changes; selected apply-back becomes a preconditioned source operation. | Recommendation; crash, side effects and exact isolation must be contracted. |
| A02 canonical source/external changes | Require a coherent external change-set boundary before activation; never replay accepted journal over an unrelated checkout. Versioned manifest selecting source records is a credible route, but source-files-first/database-first comparison remains due. | Open; this is the sharpest unresolved failure in case 3. |
| A03 shader demand | Every selected content/material/pass/geometry/provider/view and allowed transition declares product demand for each target; build rejects unavailable mandatory variants with a dependency path. | Open joint F2/F4/V1/V3 decision; caching/variant format are details. |
| J02 renderer extension level | Keep optional features/material/style/provider hooks and headless mode; promise whole-renderer replacement only with an actual game/platform need. | Recommendation, not selected. |
| J04 code iteration | Rebuild/restart a pinned play session is a sufficient minimum; state handoff is explicit and save/schema aware. | Recommendation; responsiveness must later be measured. |

A04 water-domain coupling and A05 overlapping atmosphere representation remain genuine architecture gaps for games that select those systems. None of these three games exercises a river–sea join or overlapping physical media, so they should stay open rather than be “closed” by omission. Exact file format, GUI, ECS/storage library, shader compiler/cache implementation, device floors, frame/download/thermal numbers and native SDK bridge are later design or empirical choices. No trace above certifies implementation or performance.
