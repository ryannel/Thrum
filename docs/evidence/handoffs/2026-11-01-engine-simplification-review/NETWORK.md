# Independent network and authority challenge

1 November 2026. Read-only design review. The current selected design is C3 plus the G01–G10 specifications; older audits and walkthroughs are evidence about earlier states, not a second live decision queue. No runtime, device, or transport proof exists. This review does not assume the selected protocol details must survive merely because they are specified.

## Minimal contract derived before comparing the plan

For a reusable engine with optional ordinary multiplayer, the irreducible shared contract is small:

1. One world authority advances a fixed, identified tick. Standalone and server run the same rules; a listen host has both authority and client presentation, and a dedicated host may omit presentation. A replica and any prediction branch never commit server state.
2. Authoring IDs, durable save IDs, match/wire IDs, and process-local handles have distinct scopes. Content and schema compatibility names *gameplay meaning*; cosmetic client products can vary. A running match pins rule/physical meaning until an explicitly designed transition.
3. A client submits a typed, ordered, bounded actor intent. The server admits/rejects it, applies it at a declared tick under game validation, and exposes enough outcome identity for the client to reconcile UI, prediction, and effects. An application-message receipt alone is not a game-action result.
4. A replica admits a complete baseline and then atomic, dependency-complete changes with tick/visibility generation. It never exposes a spawn without required initial state or substitutes missing physics/query data with a default value. Interest, source streaming, and local render readiness are separate.
5. The authority alone saves durable gameplay and performs irreversible effects. Reconnect creates fresh transport state and may discard uncertain prior inputs; a game promising durable operation retry needs an additional durable idempotency key/result. No universal rollback, bitwise cross-platform simulation, per-group delta codec, or water solver copy is implied by the five points above.

The plan gets most of these boundaries right: [C01–C03](../../../design/CONTRACTS.md), [C10/C13](../../../design/CONTRACTS.md), [N1](../../../design/modules/NETWORKING.md), and [the selected decision](../../../design/ARCHITECTURE-DECISIONS.md#multiplayer--n1-is-a-first-class-responsibility) consistently distinguish world authority, handles, source revisions, replicas, and visual products. The failures below are narrower and fixable without another framework.

## Ranked findings

### 1. Blocker — the exact protocol has no per-action outcome path

**Evidence.** The protocol lists only twelve kinds; `InputBatch` may contain eight independently validated actions ([NETWORK-SPEC.md:58–75](../../../design/NETWORK-SPEC.md)). N1 keeps a dedup entry with a committed tick or rejection, but the wire does not say how that result reaches the client ([NETWORK-SPEC.md:77–90](../../../design/NETWORK-SPEC.md)). `StateGroup` is described as field state, with no processed-input watermark, rejection entry, or action-origin field ([NETWORK-SPEC.md:98–104](../../../design/NETWORK-SPEC.md)). Yet the module says prediction discards acknowledged inputs and confirmed effects suppress matching speculative effects ([modules/NETWORKING.md:130–149](../../../design/modules/NETWORKING.md)); the spec says server confirmation echoes the origin key ([NETWORK-SPEC.md:178–188](../../../design/NETWORK-SPEC.md)). “Other interaction queries” also promise authority results without identifying their encoding ([NETWORK-SPEC.md:168–172](../../../design/NETWORK-SPEC.md)). A header acknowledgement covers a whole application message, not the outcome of each action inside it.

**Counterexample.** A client sends one batch with `move 40`, `purchase 41`, and `fire 42`. N1 accepts the envelope, P6 accepts movement, rejects the purchase on insufficient funds, and fires. The client receives a header acknowledgement and a pose/state group. It cannot tell which input to remove from prediction, why the purchase UI failed, or which speculative fire cue the committed event confirms. On disconnect after the fire commits but before the result arrives, a new connection cannot safely replay that old one-shot. The plan already forbids old-epoch replay ([modules/NETWORKING.md:82–85](../../../design/modules/NETWORKING.md)); that is a valid bounded choice, but the client must report the action as uncertain until a new authoritative state/result resolves it.

**Smallest correction.** Define one bounded per-input outcome stream (or equivalent fields in a committed group): `(actor, inputSequence, accepted/rejected, resultTick, reason/event-origin when relevant)`, plus a contiguous processed-input watermark for prediction. Record outcomes only after P6's commit; distinguish packet admission from action execution. Reconnect discards old pending inputs and rebuilds from the fresh baseline; no transparent retry guarantee is necessary. A game that offers retryable purchases/payments across reconnect or server restore adds a *game-owned durable operation ID and P7 outcome*, with its external effect idempotency policy. Reuse P6's identified event ledger rather than adding generic RPC. **Owners:** N1, P6, F1, P7 for durable effects, A1/U1/V5 for reconciliation.

### 2. Blocker — reliable ordering does not make spawn plus first state atomic

**Evidence.** `LifecycleBatch` carries spawn/despawn/leave/re-enter, while `StateGroup` separately carries field records and group IDs. The text calls the group the atomic dependency closure, but only says that one ordered stream makes a spawn *precede* state ([NETWORK-SPEC.md:98–104, 122–126](../../../design/NETWORK-SPEC.md)). C13 requires coherent lifecycle and dependent state groups ([CONTRACTS.md:375–378](../../../design/CONTRACTS.md)); N1 promises a replica barrier only for the full join baseline ([modules/NETWORKING.md:73–77](../../../design/modules/NETWORKING.md)). No cross-message transaction ID, complete-state marker, or staging rule is specified for an ordinary spawn/re-entry.

**Counterexample.** The server sends `spawn actor A` in lifecycle sequence 80 and its position, attachment, and inventory in state sequence 81. The client receives 80, reaches an extraction barrier, and exposes A with absent/default transform or attachment. WebSocket guarantees that 81 follows 80; it does not guarantee both arrive before that barrier. The same gap appears when A re-enters interest with a new visibility generation. A missing collider or attachment can be mistaken for a real gameplay state.

**Smallest correction.** Let one `StateGroup` inline a lifecycle record and its required first full projection, then admit that group at one replica barrier. This realizes C13's existing atomicity invariant without a new transaction subsystem. Despawn and dependent detach/inventory effects can use the same form when game invariants require it. If the group exceeds the profile bound, reject that recipe. Keep ordered transport and visibility generations. **Owners:** N1, W1, F3 schema, P6, affected specialized stores.

### 3. Qualified unsupported scope — universal one-shot lateness makes the board/co-op baseline unnecessarily fragile

**Evidence.** The reference is direct-connect cooperative/board/exploration, not a fast shooter ([NETWORK-SPEC.md:8–21](../../../design/NETWORK-SPEC.md)). Every one-shot more than two ticks late rejects; initial lead is three ticks; the future window is twelve ticks ([NETWORK-SPEC.md:77–94](../../../design/NETWORK-SPEC.md)). The acceptance fixture explicitly includes 50/150/300 ms RTT and jitter but makes no promise that a one-shot succeeds at every test point ([NETWORK-SPEC.md:220–226](../../../design/NETWORK-SPEC.md)).

**Counterexample.** At 60 Hz, three ticks are 50 ms. At symmetric 150 ms RTT, a packet takes about 75 ms one way, reaching the authority about 1.5 ticks after its intended tick; little jitter is needed to exceed the two-tick allowance. At 300 ms RTT, about 150 ms one way makes it roughly six ticks late, so ordinary board moves and inventory interactions are rejected despite being perfectly valid against the current turn/state. The clock estimator cannot solve transit time. This is an initial-profile usability limit, not a contradiction with an unpromised latency guarantee.

**Smallest correction.** Give action schemas a simple timing mode: *execute at next authoritative tick if state preconditions still hold* for turn, purchase, and ordinary interactions, with bounded age/order and no rewind; retain intended-tick lead/lateness for controls or abilities that actually need it. The server still decides legality and order. A competitive reaction/lag-compensation guarantee remains unsupported. **Owners:** N1, P1/P6, F1. This removes a needless dependence of board actions on sub-RTT clock precision.

### 4. Bounded implementation detail — confirmed water query and body pose need an explicit correspondence unit

**Evidence.** The water projection is a body-specific sample with `sampleTick`; the text correctly forbids mixing it with a pose from a different time ([NETWORK-SPEC.md:146–166](../../../design/NETWORK-SPEC.md)). State groups may have different sample ages when consumers permit it ([NETWORK-SPEC.md:100–104](../../../design/NETWORK-SPEC.md)). The group example calls a water sample complete but does not explicitly include the matching body pose or a retained pose reference. E1 and P3 are authoritative; the client may use confirmed projections without the full solver ([PLAY-ENVIRONMENT-SPEC.md:59–61](../../../design/PLAY-ENVIRONMENT-SPEC.md)).

**Counterexample.** Pose at tick 120 is coalesced while a tick-120 water sample arrives, then pose 123 arrives. A consumer either combines sample 120 with pose 123 (prohibited) or marks water unavailable (safe, but avoidably frequent). **Smallest correction:** include the body pose and water sample in the same `StateGroup`, already the plan's atomic unit, or require a specific retained pose tick and publish only when it exists. This is an optional E1 replication recipe, not a generic N1 core requirement. **Owners:** E1, P3, N1, V2.

### 5. Bounded contract clarity — define the exact *wire* schema hash separately from all local schemas

**Evidence.** `Hello` carries game/protocol/schema/semantic hashes and requires exact protocol/schema matching; visual products may differ ([NETWORK-SPEC.md:58–68](../../../design/NETWORK-SPEC.md)). F3's registry also covers editor, source, component, and local presentation schemas ([FOUNDATION-SPEC.md:5–19](../../../design/FOUNDATION-SPEC.md)); the renderer explicitly allows different peer visual builds ([modules/RENDERING.md:60–73](../../../design/modules/RENDERING.md)). N1's family text calls this a replication schema, which is probably the intended meaning ([modules/NETWORKING.md:53–71](../../../design/modules/NETWORKING.md)).

**Counterexample.** A browser client recooks a purely visual material schema while the server's game/wire schema is unchanged. If the `schema hash` is over the entire F3 registry, the client is rejected despite the promised visual independence. **Smallest correction:** use the *existing semantic gameplay manifest* as the exact gameplay-meaning lock, including rule/action meaning, authority/tick policy and required physical/query semantics. Define the protocol hash over the envelope and negotiated wire action/state schemas; call the current `schema hash` that wire-schema hash or fold it into the protocol hash. Remove the ambiguous `game hash`, or alias it to the semantic manifest hash. Cosmetic/source/tool schemas stay in build manifests; role-specific physical product mappings stay in the semantic manifest. This adds no third lock or first-profile schema translation. **Owners:** F3, F4, N1, V2/V3.

### 6. Preference, with status drift — keep the first profile's static server boundary without making it the engine's world model

The initial server preloads its finite authoritative region and cannot stream new authority or activate source edits during a match ([FOUNDATION-SPEC.md:95](../../../design/FOUNDATION-SPEC.md), [NETWORK-SPEC.md:106–113](../../../design/NETWORK-SPEC.md), [CONTRACTS.md:383–385](../../../design/CONTRACTS.md)). This is a coherent way to avoid a per-client pause and does **not** contradict W2's general standalone/editor streaming transaction ([FOUNDATION-SPEC.md:87–95](../../../design/FOUNDATION-SPEC.md)). It loses live authoritative expansion for the first multiplayer profile; an eventual streamed-server profile needs an independently staged, nonstalling commit, not a changed meaning of “interest.” Keep that qualification visible in SDK examples. Some older prose still says networking scope/wire schema is open ([modules/WORLD-CONTENT.md:10](../../../design/modules/WORLD-CONTENT.md), [modules/PLAY-SYSTEMS.md:101](../../../design/modules/PLAY-SYSTEMS.md), [CAPABILITY-SURVEY.md:78](../../../design/CAPABILITY-SURVEY.md)); their header/status dates and [MATURITY.md:119–144](../../../design/MATURITY.md) identify the later C3/G08 decision as controlling. These stale sentences should be marked historical or updated during the next coordinated doc edit; they are not evidence that the decision remains open.

## Three reductions worth testing before implementation

1. **Test full bounded state groups before per-group deltas.** The selected design already needs baseline, ordered lifecycle, coherent groups, bounds and resync. Two retained bases per group, 64-tick delta history and multiple acknowledgement meanings add state and failure paths before any measured benefit ([NETWORK-SPEC.md:115–126](../../../design/NETWORK-SPEC.md)). One message per entity at 128 entities × 20 Hz spends 160 KiB/s on 64-byte headers alone, so the simple candidate would batch independently atomic full groups inside a bounded message. For illustration, 64 bytes/entity × 128 × 20 is 160 KiB/s of payload plus group metadata and batched headers. A concrete R4 projection and worst-cadence inventory must establish whether it fits the 256 KiB/s cap. **Do not select a codec replacement from this estimate.** The lost guarantee, if full groups are chosen, is support for a larger/denser recipe at the same bandwidth; that can remain an explicit admission failure until delta evidence exists. This is a conditional design preference.
2. **Move the fixed 96-byte water record out of core N1 into an optional E1 network recipe.** R4 does not require water, while R3 is a distinct optional coastal workload ([BASELINE-SPEC.md:53–73](../../../design/BASELINE-SPEC.md)). Preserve sample validity/time/error and atomic pose correspondence. A networked coastal game would enable/qualify this recipe; a board game would carry no water codec or manifest coupling. No authority guarantee is lost.
3. **Keep prediction as an opt-in contract, not an I2n completion dependency.** The construction row says “optional static-controller prediction” ([CONSTRUCTION-PLAN.md:43–52](../../../design/CONSTRUCTION-PACKAGES.md)). Implement and prove confirmed interpolation, action outcomes, baseline/reconnect and effect identity first. Prediction can be admitted for a latency-sensitive game after its complete static-collision subset is proved. The lost guarantee is immediate locally predicted body motion in the first network demo, not multiplayer correctness.

## Preserve and verdict

Preserve the single authoritative tick, role-separated worlds, stable scoped identities, purpose-specific projections, pinned semantic gameplay content, atomic replica barriers, bounded queues, and server-only durable saves. Preserve the explicit statement that initial water prediction is unavailable and that visual quality cannot mutate physical meaning. These are the architecture's strongest protections against a future networking retrofit ([CONTRACTS.md:42–94, 366–385](../../../design/CONTRACTS.md); [ARCHITECTURE-DECISIONS.md:181–195](../../../design/ARCHITECTURE-DECISIONS.md)).

**Verdict:** the selected server-authority model is viable and small enough. The exact G08/N1 protocol is **not yet implementation-ready** for the promised action/result and coherent replica path because findings 1–2 lack a defined commit-to-wire mechanism. Correct those before I2n. Finding 3 is a needlessly narrow initial action policy; findings 4–5 are bounded contract details. The numerical limits and wire layout are already described as one first profile, so they should remain qualified profile settings, not be described as universal engine limits. No finding requires a new ECS, transport framework, universal rollback or permanent restriction to four players/static worlds.

## Cross-challenge of the other fresh reports

The [creator/SDK report](SIMPLICITY.md) is right that ambiguous `game hash` can undo the promised client visual independence. Its proposed gameplay lock should **reuse** the existing semantic manifest, with exact wire/protocol schema identity alongside it; a third independently maintained compatibility hash would worsen the problem. Its concern about N1 packet policy becoming a universal law is a useful SDK warning, but [NETWORK-SPEC.md:1–6](../../../design/NETWORK-SPEC.md) and [modules/NETWORKING.md:12–30](../../../design/modules/NETWORKING.md) already present it as an initial replaceable profile. The correction is to keep public authority contracts separate from that profile in examples and API exposure, not to infer that the architecture currently caps all future games at four players or WSS.

The [delivery report](DELIVERY.md) correctly shows that 128 *independent, changed* groups at 20 Hz can spend most of the bandwidth on per-message headers, and that the plan lacks an actual R4 field/cadence inventory. Those are conditional stress assumptions, not proof every R4 recipe violates its cap. Its 300 ms RTT arithmetic agrees with finding 3, but [NETWORK-SPEC.md:220–226](../../../design/NETWORK-SPEC.md) specifies a fault test, not successful interaction at every test point. State a playable/degraded/rejected latency envelope for the selected game. The 64-tick prediction ring versus at most eight replay ticks/frame deserves a clear purpose or smaller cap if prediction is selected; it does not affect confirmed-state multiplayer correctness. Delivery's off-world replacement peak and browser-authoring costs reinforce a narrower first portable path, while leaving C13's authority and identity invariants intact.

**Minimum coherent G08 fix set before I2n:** (a) one committed per-input outcome/watermark path using P6 event identity; (b) one `StateGroup` form that admits lifecycle plus required first state together, also usable for dependent water/pose samples; (c) a single existing semantic gameplay manifest with an unambiguous protocol/wire-schema hash, not a whole-build equality gate; (d) a named R4 action/projection/byte/latency recipe that says which adverse network cases are expected to reject. These are bounded corrections to the selected protocol. Full-group batching, deferred water codec and postponed prediction are recommendations to evaluate against that recipe, not selected replacements or a request to rewrite every module now.
