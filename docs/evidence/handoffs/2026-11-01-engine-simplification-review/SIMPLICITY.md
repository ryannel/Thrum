# Fresh creator and SDK simplicity challenge

1 November 2026. Independent paper review of the selected C3 plan. No engine was implemented or run. These findings challenge selected choices at their current scope; the existing reviews and their `closed` labels are historical evidence, not proof of creator usability. Priority is relative to the promised first SDK, not a claim that the underlying invariants are optional.

## The smallest public model I would teach

Four nouns suffice: **project** (ordinary source and assets), **world** (one authority advancing game rules), **target** (platform and selected features), and **run** (a pinned build of the project, local or server/replica). A scene is authored world input. A game registers components, actions, systems and chosen providers in ordinary code. A target chooses rendering and delivery; a run says what revision is actually active. Every editor, CLI and AI change is a reviewable source change. Save files checkpoint authoritative world state; they are not scene edits. Multiplayer adds a server run, replica runs, explicit replicated data and actor actions through the same rules. The public API can expose opaque object references and revision labels while the implementation privately uses epochs, slots, leases and manifests. This model preserves the brief's feature selection, cameras/styles/platforms and first-class optional multiplayer ([ARCHITECTURE-BRIEF.md:10-28](../../../design/ARCHITECTURE-BRIEF.md); [ENGINE-EXPERIENCE.md:13-24](../../../design/ENGINE-EXPERIENCE.md)).

Creator trace: start a solo overhead game from empty source; register a pickup action and rule using an ordinary library; omit physics, weather, audio and visible sky while retaining light; import a lantern, place it, edit its material, reimport it with stable placement; play, inspect and save; later declare actor ownership/replicated fields and run a local server plus browser replica. An AI agent changes the rule in a branch, runs the same checks and presents a diff; an optimization agent compares an isolated candidate against a pinned evaluator. The plan describes each step, but the implementation order and several protocol surfaces make that short trace needlessly long.

## Ranked findings

### 1. [Rebuild risk] The first useful rendered loop comes after too much substrate

The construction sequence makes I3a's one camera and one interaction depend on I1 and the required I2/D2 subset, while I2 is already import/cook/load/**region/save/edit** and I1 includes both native mobile shells ([CONSTRUCTION-PLAN.md:37-47](../../../design/CONSTRUCTION-PLAN.md), [ARCHITECTURE-DECISIONS.md:197-206](../../../design/ARCHITECTURE-DECISIONS.md)). R0 itself needs only 64 entities and explicitly omits animation, water, media, navigation, networking and audio ([BASELINE-SPEC.md:59-65](../../../design/BASELINE-SPEC.md)). A creator or SDK team could spend months proving transactions, region activation and device shells before learning whether code → source edit → visible play → export is pleasant. This is a schedule risk, not a reason to postpone the N1 authority boundary.

**Smallest correction:** make I1/R0 an end-to-end vertical slice: one source snapshot, a local authoritative world, one game action/rule, one minimal render path, inspect/restart, one target export and clean recipient rebuild. Implement ID/action/authority contracts and an in-memory two-peer authority fixture there. Add region streaming, full editor transactions, additional mobile shells and N1's complete transport in bounded follow-on slices; retain I2n before any broad multiplayer or I3b claim. Owners: F1/F2/F3/W1/F4/T1/T2, V1–V4, N1; construction plan. Tradeoff: the first slice is narrower and does not prove mobile/streaming, so its support claim must say so.

### 2. [Creator-model contradiction / avoidable complexity] “Source files are canonical” still leaves a second everyday edit destination

The public guide says versioned files are durable project source and a play build pins a project revision ([ENGINE-EXPERIENCE.md:17-24](../../../design/ENGINE-EXPERIENCE.md)). Yet a T1 spatial edit is first accepted into immutable bytes inside a SQLite/IndexedDB root, and an unmanaged checkout receives only a patch; even managed checkout materialization is a separate fallible job ([FOUNDATION-SPEC.md:34-56](../../../design/FOUNDATION-SPEC.md), [modules/TOOLS-DELIVERY.md:181-206](../../../design/modules/TOOLS-DELIVERY.md)). After moving a prop in the workbench, the creator's editor or `git diff` can show *no* change, while play builds the new state. Calling both the file checkout and the admitted root “source” is technically qualified, but it makes collaboration, branch review and AI handoff surprising. A second copy of every admitted master in SQLite is explicitly budgeted ([FOUNDATION-SPEC.md:62-77](../../../design/FOUNDATION-SPEC.md)).

**Smallest correction:** make the default SDK path **file edit → explicit snapshot/admission → build/run**, with T1 typed edits producing a patch to the working tree and reporting `proposed` until the selected file tree is admitted. Restrict automatic multi-file editor commits to a later managed-writer mode with a clear exclusive-workspace contract. Keep the immutable admitted snapshot, exact dependency hashes, durable save roots, last-good build and conflict-safe recovery; do not build from half-written files. A Git tree or transactional local snapshot can be the admission input. Browser-only authoring may retain IndexedDB, but the UI must explicitly label exported files versus locally admitted revision. Owners: T1/F3/F4/P7 and C10. Tradeoff: an editor cannot promise immediate durable `accepted` for arbitrary shared checkouts; it must preserve a pending patch and tell the author to sync/review it.

### 3. [Multiplayer integration contradiction risk] “Game hash” can accidentally require identical client builds

C13 and the selected decision allow per-client visual builds and server-only physical solvers when compatible query projections exist ([CONTRACTS.md:366-378](../../../design/CONTRACTS.md), [ARCHITECTURE-DECISIONS.md:181-195](../../../design/ARCHITECTURE-DECISIONS.md)). N1 `Hello` carries `game/protocol/schema/semantic-manifest hashes`, while the first protocol requires exact protocol/schema hashes ([NETWORK-SPEC.md:58-68](../../../design/NETWORK-SPEC.md)). “Game hash” has no sufficiently narrow definition here. If it is a build or whole-project hash, changing a browser texture or platform binary rejects a compatible Mac/server/client game. If it omits rules/content without a specified semantic closure, an incompatible action or collider could join. The add-multiplayer-later trace depends on this distinction.

**Smallest correction:** use the **existing semantic gameplay manifest** to cover rule/action schemas, authority policy, tick semantics and required physical/content query meanings. The protocol hash covers the envelope and wire action/state schemas; each peer additionally names its own visual/physical product provenance and a role-specific compatibility mapping. Remove an ambiguous whole-game hash from the join gate or define it as an alias of that existing semantic manifest; do not create a third lock. Test a server-only water solver with a browser visual client, and a browser-only material edit that must still join. Owners: N1/F3/F4/P3/E1/V1/T2. This retains strict multiplayer compatibility; it narrows what must be equal.

### 4. [Avoidable complexity / rebuild risk] A prop edit can rebuild and pause the whole authoritative world

The initial correctness path for an authoring or region transaction captures all provider state, constructs a replacement W1 generation off-world, may rebuild the entire component store O(N), reserves old+new memory, pauses simulation and swaps the generation ([FOUNDATION-SPEC.md:87-95](../../../design/FOUNDATION-SPEC.md)). The ordinary creator loop already permits rebuild/restart for code/schema changes and only promises data preview through a declared safe path ([ENGINE-EXPERIENCE.md:86-110](../../../design/ENGINE-EXPERIENCE.md)). A lantern position or material change should not force every provider to implement full state transfer before the first workbench is useful. This can make apparently simple third-party providers ineligible for live authoring and consume the 10% staging/replacement memory share before real content is known ([BASELINE-SPEC.md:89-93](../../../design/BASELINE-SPEC.md)).

**Smallest correction:** default source edits to **restart a disposable play session** from the new admitted source. Permit targeted live visual updates only for a small explicitly qualified field/product set; introduce full-world or scoped transactional replacement when a named streaming/live-edit case needs it. Region activation still must publish collision/nav/gameplay closure coherently; a live match remains pinned. Owners: W1/W2/F1/P3/P5/E1/F4/T1. Tradeoff: slower iteration for edits outside the safe preview set, with a simpler and honest initial provider contract.

### 5. [Avoidable complexity / preference] Keep the reference N1 protocol out of the public world API

The N1 architecture needs server authority, scoped IDs, typed intents, coherent replica groups, bounded queues and optional complete prediction ([modules/NETWORKING.md:12-30](../../../design/modules/NETWORKING.md), [modules/NETWORKING.md:87-149](../../../design/modules/NETWORKING.md)). The selected first profile additionally fixes a 64-byte `ENG1` header, twelve message kinds, single-use five-minute invitations, exact tick windows, 96-byte water samples, 100 ms interpolation, 512 KiB histories and four-player/128-entity limits ([NETWORK-SPEC.md:8-30](../../../design/NETWORK-SPEC.md), [NETWORK-SPEC.md:32-68](../../../design/NETWORK-SPEC.md), [NETWORK-SPEC.md:96-212](../../../design/NETWORK-SPEC.md)). Those choices are appropriate **initial protocol-profile settings**, not universal game limits. The specification itself says another genre may replace this protocol ([NETWORK-SPEC.md:3-6](../../../design/NETWORK-SPEC.md)); this is a documentation and SDK-boundary risk, not evidence that the current plan claims a permanent universal cap. A turn-based board game and an action game may need different intent cadence, interest and transport; new variants should not require redesigning the engine's public world contract.

**Smallest correction:** keep the byte layout, invitation policy, quantization and numerical thresholds under a named `small-session WSS reference adapter` and its conformance fixtures; avoid copying them into game-facing world contracts. Keep N1's engine-owned authority/replica/command contracts and require each adapter to declare bounds and fidelity. Add a creator-facing host/join/reconnect example, including how a token is issued and delivered, before calling multiplayer usable; the current design specifies token validation but explicitly leaves distribution outside the implementation ([NETWORK-SPEC.md:25-30](../../../design/NETWORK-SPEC.md)). Owners: N1/F2/P1/P6/T2. Tradeoff: the first SDK supports only one qualified profile, which is acceptable if stated as support scope.

### 6. [Avoidable complexity] Authoring retries, roots and generations have leaked into the simple edit vocabulary

A local source operation carries expected SourceRevision, read/write sets, actor, correlation ID and `(authority,epoch,key)` token; rejected validation advances a metadata root generation; epochs expire after 10,000 operations/seven days with a 30-day dedup index, plus separate undo horizons ([FOUNDATION-SPEC.md:34-42](../../../design/FOUNDATION-SPEC.md)). These rules solve real lost-response/concurrency problems, especially remote tools. But a local agent changing one JSON field may now see an accepted revision, unchanged checkout, pending cook, old active revision, old checkpoint, metadata generation and expired operation token ([modules/TOOLS-DELIVERY.md:181-224](../../../design/modules/TOOLS-DELIVERY.md)). More labels make the first edit harder to diagnose.

**Smallest correction:** retain the internal state machine and durable dedup where remote/retry semantics require it, but expose creator-facing `working files`, `selected snapshot`, `running build`, `saved checkpoint` and one operation status. Generate retry keys in the client SDK; put metadata generation and lease detail in advanced diagnostics. Allow simpler local single-writer operation handling while preserving exact retry results for the public API. Owners: T1/T2/F3/P7 and the CLI/workbench. This is an API and documentation simplification, not a request to discard recovery guarantees.

### 7. [Maintenance risk] The plan has multiple near-canonical descriptions of the same operation

The source/checkout/recovery protocol appears in [ENGINE-EXPERIENCE.md:191-220](../../../design/ENGINE-EXPERIENCE.md), [CONTRACTS.md:264-320](../../../design/CONTRACTS.md), [FOUNDATION-SPEC.md:5-77](../../../design/FOUNDATION-SPEC.md), [modules/TOOLS-DELIVERY.md:161-232](../../../design/modules/TOOLS-DELIVERY.md), and the selected decision. The README routes a newcomer through many current, historical and review files ([README.md:1-28](../../../design/README.md)); the ledger stores current hashes and historical review status while 30 module rows are mostly high-level designs ([MATURITY.md:119-142](../../../design/MATURITY.md)). A changed root rule can be reconciled in one file but silently stale in another. The large documentation set also risks making authors implement prose-level specifics before a running vertical slice supplies evidence.

**Smallest correction:** make ENGINE-EXPERIENCE the public task guide, CONTRACTS the invariants, the five initial specs the sole algorithm/adapter choices, and MATURITY the status ledger. Turn duplicated module text into links plus owner-specific consequences; move historical audit/review narratives out of the “start here” reading path. Generate status tables from `maturity.json` instead of editing parallel claims. Owners: architecture coordinator and document owners. Tradeoff: fewer self-contained module files, compensated by precise links and short owner summaries.

## Three concrete deletions/combinations

1. Remove **full-world live authored replacement as the initial default** and combine ordinary edit/play with source admission plus restart. Retain the coherent region activation contract and optional qualified safe preview (finding 4).
2. Remove **automatic managed checkout mirroring from the first SDK**. Combine all normal edits in one reviewable file/patch-and-sync path; retain immutable snapshots, conflict reporting, durable saves and a future exclusive managed mode (finding 2).
3. Combine **repeated C10/T1 source protocol prose** into one normative specification and concise cross-references, and relocate exact N1 packet policy under its reference adapter (findings 5 and 7). This removes duplicated decisions, not the authority or wire conformance tests.

## Keep without dilution

- One authoritative world per run, typed actor intents, server-only gameplay side effects, coherent replica state, and explicit prediction dependency closure. A transport toggle cannot make arbitrary local code multiplayer-safe.
- Durable source/save identity separate from runtime handles; pinned builds and compatible restore closure; no checkout watcher can activate half-written source. Exact old/new product hashes and retained masters remain necessary for reimport, rollback and cold rebuild.
- Provider ownership, explicit supported combinations, no-sky lighting separation, no silent physical model substitution, and headless execution. A visual tier cannot alter server rules.
- Three distinct dependency schedules for source cooking, CPU simulation and GPU passes; these have different lifetimes. Keep the renderer's local readiness and lease/fence discipline, while teaching them only to extension authors.
- Evidence boundaries: paper design, running SDK usability, rendered beauty, target performance and mobile delivery are separate claims. Optimization agents need evaluator isolation and exact candidate provenance ([AI-PERFORMANCE.md:39-58](../../../design/AI-PERFORMANCE.md), [AI-PERFORMANCE.md:90-149](../../../design/AI-PERFORMANCE.md)).

## Cross-review qualification of the network and delivery reports

Read peer [NETWORK.md](NETWORK.md) and [DELIVERY.md](DELIVERY.md) after their initial reports stabilized. Their strongest new findings are **real protocol omissions**, not a reason to enlarge the architecture: the selected twelve-kind wire specification does not define a committed per-action result path needed for rejected actions, prediction acknowledgement and effect reconciliation ([NETWORK-SPEC.md:58-90](../../../design/NETWORK-SPEC.md), [modules/NETWORKING.md:130-149](../../../design/modules/NETWORKING.md)); separately ordered spawn and first-state messages do not guarantee one atomic replica admission at a frame barrier ([NETWORK-SPEC.md:98-126](../../../design/NETWORK-SPEC.md), [CONTRACTS.md:375-378](../../../design/CONTRACTS.md)). Add one bounded outcome representation and one staging/commit rule inside N1/P6/W1. They are I2n blockers for the exact selected protocol, but do not require a generic RPC layer, new ECS or transport framework.

The peers' numerical warnings need narrower labels. At 300 ms RTT the default three-tick lead plus two-tick late window predictably rejects many one-shots; the written fault matrix asks for measurements, not that every such request succeed ([NETWORK-SPEC.md:77-94](../../../design/NETWORK-SPEC.md), [NETWORK-SPEC.md:220-226](../../../design/NETWORK-SPEC.md)). That is an **unsupported playability assumption**, not a logical protocol contradiction. Set a playable RTT/jitter envelope; for board/transaction actions use next-authoritative-tick execution with state preconditions rather than forcing a long prediction lead. Likewise 128 entities × 20 publications/s × per-group headers is a useful stress estimate, but the plan does not demand every entity or water body change in every publication ([BASELINE-SPEC.md:59-73](../../../design/BASELINE-SPEC.md), [NETWORK-SPEC.md:96-104](../../../design/NETWORK-SPEC.md)). Require an actual R4 field/group cadence inventory before declaring the 256 KiB/s cap feasible or impossible. Full state groups first and optional deltas are reasonable implementation candidates, not a proven bandwidth win.

The delivery report reinforces finding 4's cost risk: a full second world/provider copy can exceed the 10% transition reserve on browser/mobile. The design already requires stop/load/restart when peak admission fails ([FOUNDATION-SPEC.md:91-95](../../../design/FOUNDATION-SPEC.md), [BASELINE-SPEC.md:89-93](../../../design/BASELINE-SPEC.md)), so it is a **missing target-specific live-transition acceptance recipe**, not a memory-safety contradiction. Its browser IndexedDB source-authority adapter is a strong additional deletion candidate: the confirmed browser requirement is a playable demo, not browser-side authoring ([ARCHITECTURE-BRIEF.md:14-28](../../../design/ARCHITECTURE-BRIEF.md), [FOUNDATION-SPEC.md:44-50](../../../design/FOUNDATION-SPEC.md)). Browser play and saves still need appropriate storage, but the full browser editor root/GC can wait for a named creator workflow. The 25 MiB/5 s startup and pipeline counts are already labeled provisional/arithmetic by the plan ([BASELINE-SPEC.md:95-107](../../../design/BASELINE-SPEC.md), [RENDER-SPEC.md:154-168](../../../design/RENDER-SPEC.md)); require a measured boot DAG before making them general SDK admission caps.

The additional E1/V1/A1/U1 and AI/storage/lifecycle reading did **not** change the core recommendation. Their off paths preserve retained light, gameplay water, event and semantic UI consumers while removing avoidable work ([modules/ENVIRONMENT.md:109-125](../../../design/modules/ENVIRONMENT.md), [modules/RENDERING.md:85-122](../../../design/modules/RENDERING.md), [modules/AUDIO-UI.md:42-81](../../../design/modules/AUDIO-UI.md)). The lifecycle walkthrough already advocates compact records, owner-scoped cleanup and no automatic collector for the first manual path ([LIFECYCLE-WALKTHROUGHS.md:125-147](../../../design/LIFECYCLE-WALKTHROUGHS.md)); AI campaigns keep evaluator isolation and selected evidence ([AI-PERFORMANCE.md:90-149](../../../design/AI-PERFORMANCE.md)). These are reasons to keep the invariant and defer machinery, not to erase it.

**Minimum coherent recommendation:** ship the first SDK as file-first source snapshot → local authoritative action/world → minimal render/inspect/restart/export, with a real art/reimport path and one qualified target. Build the N1 authority seams and in-memory two-peer fixture with it; make I2n's first WSS profile complete by adding per-action outcomes and atomic spawn/state admission, then prove a concrete R4 recipe. Keep a pinned server match, coherent saves and product closure. Defer full-world live edit, browser authoring authority, universal automatic GC, deltas/prediction and advanced live provider removal until named games and measured budgets require them. State browser/mobile support and gameplay feature combinations as qualified profiles, never as universal restrictions. This is a review recommendation: selected G01/G02 remain challenged alternatives, while G08's action/lifecycle gaps and G09's R4 recipe need reopened qualification before implementation. Do not silently replace the selected source protocol or world-staging contracts during this review.
