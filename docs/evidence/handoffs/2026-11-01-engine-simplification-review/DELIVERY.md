# Independent delivery, runtime and maintenance challenge

1 November 2026. Fresh review of the selected custom-engine plan. This challenges the *initial admitted scope*, not the user's custom-host, reusable 3D, Mac/PC/browser/native-mobile or first-class optional-multiplayer decisions. File:line references are to the baseline listed in `BASELINE.json`. No build, device run or canonical source edit was made. The machine ledger calls 23 module decisions selected but 29 of 30 designs `high_level`; all target implementation and platform evidence remains unrun. Its `architecture_resolution.stage` is `architecture_and_initial_specification`, which should not be read as a delivery claim.

## Ranked findings

### 1. Whole-world replacement consumes the mobile/browser transition reserve before provider replacements exist

**Category:** rebuild risk and empirical uncertainty. **Owners:** F1, W1, W2, F4, P3/P5/E1, T2.

`notes/engine-rebuild/FOUNDATION-SPEC.md:91-95` makes a live standalone/editor source or streamed-region transaction capture the entire committed state, construct a replacement W1 generation off-world, retain the old generation until readers retire, and pause authoritative ticking during construction. The requirement includes provider state that can exceed the durable save codec. `notes/engine-rebuild/BASELINE-SPEC.md:75-91` gives R2 browser 512 MiB and mobile 1 GiB logical caps with only 10% for staging/replacement. **Counterexample:** if replaceable world/provider state occupies the permitted 15% world/solver/snapshot share, one replacement copy is 76.8 MiB browser or 153.6 MiB mobile, exceeding the respective 51.2/102.4 MiB transition share before cooked products or upload scratch. The stated admission rule correctly rejects or enters stop/load/restart, so this is not a memory-safety contradiction. It means the selected R2 steady envelope does not imply an R2 live-region transition. `notes/engine-rebuild/CONSTRUCTION-PLAN.md:43-47` nevertheless places two-region edit/activate/unload in I2 and cross-platform profile qualification in I4 without an explicit target split. A new provider also needs an internal state-transfer path solely to support this first correctness implementation.

**Smallest correction:** make R0/I3a and the initial R2 browser/mobile variant fully preloaded within a bounded gameplay region; use restart or a visible stop/load transition for gameplay-affecting edits. Keep epochs, immutable source, admission and staged presentation publication. Treat *live authoritative* region replacement as a later named workload requiring a measured `M_live + M_staged_W1 + providers + products + readers` peak and each provider's transfer protocol. If seamless R2 region streaming is actually required now, lower its admitted steady residency or allocate a larger transition reserve before claiming R2. This removes the generic full-generation transfer obligation from the first game while leaving the ownership boundary intact.

### 2. Browser authoring duplicates a difficult durability product that the confirmed browser requirement does not demand

**Category:** needless complexity and rebuild risk. **Owners:** F3/F4, T1/T2, platform shell.

`notes/engine-rebuild/ARCHITECTURE-BRIEF.md:14-28` confirms a browser **demo** and native/mobile delivery, not a durable in-browser editor. Yet `notes/engine-rebuild/FOUNDATION-SPEC.md:44-50` selects six IndexedDB stores, multi-store strict transactions, blob rereads, root/CAS/GC coordination, quota/persistence reporting and an export recovery path for browser authoring alongside SQLite native authoring. `FOUNDATION-SPEC.md:17` admits a source tree of 100,000 entries and one immutable blob up to 16 GiB; `:64-77` acknowledges the immutable store is an extra copy of source bytes, with another full copy for a changed binary. Those are upper admission bounds, not intended browser payloads, but they expose two distinct storage/recovery implementations and failure matrices before the first browser game. The [IndexedDB specification](https://www.w3.org/TR/IndexedDB/) calls `strict` a durability **hint**, matching the plan's qualified claim; it cannot make that editor equivalently durable to the native one.

**Smallest correction:** keep one source/operation/schema format, native CLI/workbench authoring and exportable immutable bundles in the first SDK. Browser *play* needs verified content fetch/cache and separate player-save policy, not the full browser source-authority protocol. Admit durable browser authoring only for a named creator workflow and constrained source-size/quota envelope. This is a scope deletion, not a second source format or a weakening of native recovery.

### 3. The R4 counts do not yet fit a concrete replication byte and timing recipe

**Category:** empirical uncertainty with a potential admission contradiction. **Owners:** N1, F3, P6, E1, F1/T2.

`notes/engine-rebuild/BASELINE-SPEC.md:53-73` and `notes/engine-rebuild/NETWORK-SPEC.md:8-11` pair 128 replicated entities/peer and 20 state publications/s; `NETWORK-SPEC.md:32-58,96-104,190-202` specify a 64-byte header, individually atomic dependency groups and 256 KiB/s state bandwidth per peer. If 128 independently changing entities each need one group per publication, **headers alone cost 128 × 20 × 64 = 163,840 B/s (160 KiB/s)**. A modest 32-byte group payload raises this to 240 KiB/s, leaving 16 KiB/s for lifecycle, clocks, schema/group metadata and retransmission/resync. A 96-byte water record (`NETWORK-SPEC.md:145-166`) for each such group would cost 400 KiB/s. The design does not actually require every entity to update every publication, and the water record applies to at most four floating bodies; those examples show why the stated maxima cannot substitute for an authored R4 projection inventory. The reference 256 KiB baseline is 2 KiB/entity *before* global state, dependency groups and protocol metadata. WebSocket reliable ordering can further make a bandwidth-compliant recipe miss state-age limits.

**Smallest correction:** before I2n, specify the R4 game actions and per-field projection: bytes/group, number of groups, changed-group frequency, baseline contents, lifecycle burst, water-contact subset, retransmission/resync case and age limit. Keep the 128/20/256 numbers as **simultaneous** admission constraints only for a recipe whose calculated worst ordinary cadence fits; otherwise reduce one axis or allow larger bandwidth explicitly. Do not redesign the authority model or add a datagram transport merely to make this first recipe work. The [WHATWG WebSocket standard](https://websockets.spec.whatwg.org/) confirms `bufferedAmount` excludes protocol framing and OS/network buffers, so client-side buffered bytes cannot close the full resource proof by itself.

### 4. The default three-tick command lead rejects ordinary one-shots in the plan's 300 ms RTT fault case

**Category:** empirical usability uncertainty; the test expectations need a playable-versus-expected-reject label. **Owners:** N1, P1/P6, T2.

`notes/engine-rebuild/NETWORK-SPEC.md:77-94` gives a three-tick (50 ms) default lead, rejects one-shots more than two ticks (33 ms) late, and permits a game-declared larger lead up to twelve ticks. With a symmetric 300 ms RTT and a correct server-clock estimate, a one-shot sent for current-server-tick +50 ms arrives about 150 ms later: **roughly six ticks late**, so the one-shot rejects. Even 150 ms RTT leaves only about 8 ms margin before the two-tick rejection threshold, prior to the specified 30/100 ms jitter. `NETWORK-SPEC.md:220-226` includes 50/150/300 ms RTT and jitter tests but says only to check whole-game response/state age, with no declared playable-versus-expected-reject criterion. This is intentional protocol behavior, yet it can make the four-player cooperative baseline appear to pass by consistently rejecting interaction at a tested network condition. A larger lead of at least about seven ticks is required for symmetric 300 ms RTT just to fit the two-tick late window; jitter/asymmetry needs a separate margin. The 64-tick prediction history (`:178-183`) also exceeds the maximum 32 ticks replayable within four frames at eight ticks/frame, unless it serves another stated purpose.

**Smallest correction:** declare R4's playable RTT/jitter envelope before judging I2n. For board/purchase interactions, let the action schema request *execute at the next authoritative tick if state preconditions still hold*, with bounded age and order; keep intended-tick lead/lateness for controls or abilities that need it. A game choosing the latter must select a lead compatible with its declared latency envelope. Treat more adverse settings as explicit degraded/rejection cases. Set the prediction retention horizon from the actual four-frame replay/dependency budget, or state why older input history is retained; do not add server rewind to this cooperative profile.

### 5. Startup and pipeline limits are chosen before a boot-closure estimate, risking policy numbers becoming format constraints

**Category:** empirical uncertainty and needless complexity if frozen as general SDK limits. **Owners:** F2/F4, V1/V3, T2.

`notes/engine-rebuild/BASELINE-SPEC.md:75-107` chooses ≤25 MiB cold browser transfer and ≤5 s first play at 50 Mbit/s/40 ms RTT, while `notes/engine-rebuild/RENDER-SPEC.md:129-168` requires *all* first-play pipelines device-ready and rejects target builds over 512 descriptors, with 64 boot-critical and 128 per live switch. **25 MiB takes 4.19 s of ideal payload transfer**, leaving about 0.81 s for nonoverlapped round trips, Wasm startup, decode, GPU upload, shader compilation, world preparation and first successful input. The baseline itself acknowledges this arithmetic and permits smaller boot bytes/overlap; no selected R0/R2 bundle byte or pipeline-demand inventory yet demonstrates the target. The descriptor counts are called workload controls rather than hardware limits, but a hard build failure can turn unmeasured early caps into a de facto SDK compatibility rule across game styles and both camera types.

**Smallest correction:** keep 25 MiB/5 s and descriptor counts as provisional *reference-recipe gates*, not general engine ceilings or wire/source ABI. Before I3a browser export, produce one boot DAG table with compressed Wasm, content, shader/product bytes; dependent fetch/decode/prepare times; maximum concurrent scratch; and exact descriptor tuple counts for R0 and R2. Tighten or revise the numbers from that admission result. The [wgpu 30.0.1 documentation](https://docs.rs/wgpu/30.0.1/wgpu/) confirms WebGPU on Wasm and native Metal/DX12/Vulkan backends, but it gives no compile/startup guarantee for these selected devices.

## Three deletion or consolidation candidates

1. **Defer the IndexedDB source-authority/GC/editor adapter** (`FOUNDATION-SPEC.md:44-50`) until browser authoring is an explicit product; retain browser runtime cache and save adapter as needed.
2. **Remove full-generation live authoritative replacement from the first portable game path** (`FOUNDATION-SPEC.md:91-95`); use preloaded bounded regions and restart/visible load, while preserving stable identity and publication barriers for a later scoped streaming implementation.
3. **Move the 96-byte physical-water projection and mixed coastal fixture out of generic I2n admission** (`NETWORK-SPEC.md:145-171`, `PLAY-ENVIRONMENT-SPEC.md:61-75`). Keep N1's typed group/error rules, then qualify the water codec only for a game that combines R3 and R4. The small network game should validate authority, content, interest and correction without loading the optional shallow-water model.

## Preserve

The authority/replica separation and server match pin (`CONTRACTS.md:366-385`), one tick with per-view read models (`CONTRACTS.md:42-75`), exact source/build/save identities (`CONTRACTS.md:264-315`), finite feature recipes and removal of unused work (`COMPOSITION.md:28-72`), target-specific release evidence (`MATURITY.md:1-37`), and bounded AI evaluation/storage (`AI-PERFORMANCE.md:90-155`; `STORAGE-LIFECYCLE.md:78-140`) all address real rebuild or maintenance risks. The early I3a game and I2n vertical path are worth keeping. A smaller first content scope makes those paths more credible without demoting multiplayer or platform ambition.

## Cross-review and minimum coherent reduction

The independent [network review](NETWORK.md) found two more urgent N1 implementation gaps than my throughput estimate: no committed **per-action** result path for a mixed accepted/rejected InputBatch, and no atomic admission unit spanning spawn/re-entry plus required first state. I agree; these are correctness requirements for even the smallest network game. Its 128-entity arithmetic is likewise conditional on the actual grouping/cadence recipe. The 300 ms test point does not promise playable one-shots, so finding 4 is a missing acceptance label and an avoidable board-game timing policy, not a claim that the protocol violates its own stated guarantee. The network review's proposal to start with full bounded groups before delta baselines and to keep static-controller prediction optional would cut more N1 state machinery than relaxing the bandwidth number without evidence.

The independent [simplicity review](SIMPLICITY.md) finds the same live-world replacement cost from the creator side and adds a strong default-flow issue: a T1 edit can be durably accepted in a private immutable store while ordinary working files and `git diff` still show old source. A file/patch → explicit immutable admission → pinned run default deserves consideration. It must retain C10's atomic accepted root/outcome and build-from-admitted-tree invariant; an unadmitted patch should be labelled proposed, not quietly built. I also agree the first end-to-end R0 game should precede full region/editor machinery. Thin iOS/Android boot shells should still exercise F1 lifecycle early, before deeper I2/I3 content decisions depend on the host; they do not require completing browser authoring or live world replacement first.

The smallest coherent first delivery is therefore: **(1)** native file/snapshot admission, one bounded R0 world and one rendered action/export, with restart for substantive edits; **(2)** an I2n static preloaded four-peer session using typed intents, committed per-action outcomes, atomic full state groups, exact gameplay compatibility and bounded reconnect, with water/deltas/prediction absent until a named game needs them; **(3)** browser and native mobile variants with measured boot/residency/lifecycle budgets, then live authoritative streaming and richer providers only against a specific workload and peak-state transfer proof. This preserves the authority, identity, content and presentation contracts that prevent a multiplayer or platform rebuild. It changes construction order and first-profile admission, not the destination range.
