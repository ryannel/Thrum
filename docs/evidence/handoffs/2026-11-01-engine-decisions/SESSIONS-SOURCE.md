# Decision proposal: source admission, play sessions, code iteration, transforms

1 November 2026. Commission A01, A02, J04 and WP01. **Selected design proposal for coordinator reconciliation; no implementation or runtime proof.** Read with [CONTRACTS](../../../design/CONTRACTS.md), [WORLD-CONTENT](../../../design/modules/WORLD-CONTENT.md), [TOOLS-DELIVERY](../../../design/modules/TOOLS-DELIVERY.md), [ENGINE-EXPERIENCE](../../../design/ENGINE-EXPERIENCE.md), and [PLAN-REVIEW](../../../design/PLAN-REVIEW.md). This proposal retains C10's recovery, deduplication, storage admission and save-closure obligations; it scopes them to the authority that owns each root.

## Selection and alternatives

| Boundary | Select | Stronger alternative considered and reason to defer |
| --- | --- | --- |
| Source authority | Ordinary project files and masters are the canonical editable format. An admitted revision is a frozen, immutable, content-addressed file tree selected explicitly by one root; builds and restores consume that selected tree, not whichever bytes happen to be in a mutable checkout. T1's log records transactions/outcomes, not a second mutable asset database. | Journal/database-primary source with export makes Git checkout and DCC changes imports into a second editing truth. A VCS-commit-only source is coherent but excludes useful uncommitted work. |
| External change set | Explicit `sync` selects a coherent candidate. Watcher only marks the checkout dirty. A named immutable Git tree is the strongest external boundary; otherwise the author declares the dirty edit complete, the tool captures and validates the complete declared source closure, and exposes the exact manifest for review. | Per-file watcher admission is unable to distinguish an intermediate checkout from a finished one. Quiet time is no completion signal. Automatic merge is too ambiguous for stable-ID changes and tool-write conflicts. |
| Play | Each play run creates an isolated world/session from one pinned accepted source, build, products and target profile. Gameplay deltas are disposable; private test saves require explicit retention. Native development uses a child process by default. Browser/headless may use a separate worker/process where available or a separate in-process instance with the same logical isolation and mediated storage/operations. | Reversible play in the editor world creates a much larger rollback/side-effect surface. Mandatory process isolation on every target is unnecessary and cannot itself sandbox native code's external I/O. |
| Code iteration | Compile/cook a new candidate, then restart a new play session. A failed build leaves source editable and the old session visibly pinned to old inputs. | Binary hot reload and a script VM add code/schema migration and state-quiescence contracts before first use. A safe data-only preview update may be added per field/product with a named activation barrier, but is not baseline. |
| Local transforms | Store authored local `T·R·S`; reject preserve-world reparent if the required local affine matrix is not representable within specified f64 tolerance. Preserve-local remains explicit. | General affine local storage permits shear but pushes affine semantics into animation, physics, collision, normal handling, editor controls and import/export. The first ordinary 3D game does not require that cost. |

### Identity and authority

Use distinct identifiers: `ProjectId`, `SourceRevision = H(sorted path → type, bytes hash, stable-ID metadata, declared source closure)`, `BuildRevision = H(SourceRevision, SDK/toolchain lock, game code, schema/profile/target, product closure)`, `SessionId`, `WorldId`, `WorldEpoch`, `CheckpointId`, and `OperationId`. A Git commit/tree ID is provenance, not the source revision: dirty captures and non-Git projects use the same hash scheme. A renamed path with the same stable asset ID changes the source revision and may preserve logical references only after identity/rename validation. Source revision records include code and import masters, not merely parsed scene data. A build pins its exact source and all derived product hashes. Products may be shared by hash across sessions under F4 leases; mutable world, clocks, event cursors, provider instances and save roots are never shared.

Session identity includes `authorityRole = local-authoritative | server-authoritative | replica/predicted`, the authority world, source/build revision, target profile and session epoch. The initial local player and developer play use local authoritative worlds. Future server authority can issue replicated state into separate client worlds without treating a render snapshot, save capture or source tree as a replication schema. A replica cannot publish the authoritative save root or an authored apply-back. Cross-process/session messages include session, world and epoch so a late job or old UI response cannot publish into a restart. Two views read the same committed session world snapshot under C02; neither owns a second tick.

### Source state machine and admission

Visible source states are `(working-tree fingerprint/dirty reason, last admitted SourceRevision, mirror status, pending candidate, last runnable BuildRevision, active sessions)`. `mirror status` is `matches | not-materialized | external-pending | conflict`; an accepted revision may be not-materialized in the shared checkout while its immutable file tree is available. A valid *draft* may lack a runtime entry/camera/products; schema/operation validity and target play/build readiness are separate. The state changes are:

1. **Detected**: watcher or explicit command observes changed paths, VCS HEAD/index, or an incomplete tool intent; it marks `external-pending`. No cook, activation or session pin follows just from detection.
2. **Capture**: explicit sync chooses a Git tree, a cooperating tool transaction, or a declared finished dirty tree. Enumerate the declared project source closure (including deletions, renames, metadata, symlink policy and imported masters); copy bytes to immutable staging and record a sorted manifest. A Git LFS pointer is not the master: resolve and hash required payload bytes or mark that dependency unavailable. File hashes and membership are reread after capture. If they drift, capture retries within a bounded limit then reports `changing`; it never admits the observed intermediate set. This reread is a race detector, **not proof of an atomic snapshot against a noncooperating writer**. A Git tree has its own immutable tree identity. For a dirty tree, the initiator explicitly attests that the captured manifest is the intended complete change set; semantic validation checks cross-file references and stable identities. Unknown external writers require visible conflict/review rather than an automatic admission claim.
3. **Validate/admit**: validate structural schemas and cross-record invariants over the *captured immutable file bytes*, including stable-ID uniqueness, rename correspondence, required references, import settings and migrations. A malformed or ambiguous external candidate remains in the checkout for repair, with last accepted revision still available. Admit by durable compare-and-swap of the project authoring RecoveryRoot, linking immutable source manifest, accepted operation outcomes and desired revision, plus the previous consistent authoring-preview checkpoint tuple if one exists. Its tuple is `(tick, base authored revision, manifest, overlay, schema/provider versions)`; an empty project has no preview checkpoint yet. Root updates preserve that tuple until a new checkpoint is durably published, so a new desired source cannot be paired with an old overlay as if active. Admission means durable desired source, not checkout mirroring, runnable code, cooked products or active world. If candidate base differs from the current accepted root, reject/reconcile; do not silently rebase.
4. **Prepare/activate**: build/cook target products from one admitted revision. F4/W2 stage the complete affected active instance/region closure, reserve old/new overlap and recheck active-set generations at the pre-tick barrier; only then publish authoritative state and required products together. A target can fail readiness while its source remains accepted. A new session starts only from a ready `BuildRevision`. Running sessions never change pin merely because source advances.

The dirty-tree attestation is the irreducible boundary for arbitrary external tools. It is an explicit author action, not a lock claim. If a writer changes files after admission, the immutable admitted revision remains valid and the checkout becomes external-pending. If a writer changes one file back to identical bytes during capture (ABA), the two scans cannot detect its timing; the engine can guarantee the stored bytes and validated closure, not that the physical checkout had those bytes simultaneously. Any process requiring stronger provenance uses an immutable VCS tree or a cooperating transaction. A `git checkout` can update files while preserving some local edits and fail on conflicts; therefore HEAD alone does not identify the dirty working tree [Git checkout documentation](https://git-scm.com/docs/git-checkout).

### Tool writes, undo, crash and conflict

T1 tool operations use C10's typed operation, stable target/field IDs, expected source revision, sorted read/write sets, idempotency key with durable operation epoch, correlation ID and declared undo policy. T1 computes the semantic diff and affected paths against the **immutable admitted base**, writes a new immutable candidate file tree in staging, validates the complete closure, reserves disk for old/new roots and outcomes, and durably publishes its authoring RecoveryRoot by generation CAS. The accepted operation/result names the new `SourceRevision` and explicitly says whether the checkout mirrors it. The root publication, not a sequence of path replacements, is the desired-source transaction. A lost acknowledgement retries through the durable operation epoch/outcome. If a concurrent external sync wins the root CAS, the tool candidate stays inspectable and reports a conflict; it is never rebased or written over the new source implicitly. SQLite's atomic-commit design illustrates why ordered data/journal/root durability is needed; a pointer swap without flushed referenced bytes is insufficient [SQLite atomic commit](https://www.sqlite.org/atomiccommit.html).

**Working-tree materialization is a separate operation.** Default for a shared/unmanaged checkout is a reviewable patch or immutable candidate path; T1 does not write its files into that checkout. Automatic mirroring is allowed only in a declared managed writer window where every participant touching those paths has handed off write authority (for example an isolated tool-owned worktree with editor/CLI clients joined to the same lease). The window records its base tree/hash and VCS branch, then applies the already-admitted revision with a durable materialization intent and verifies the resulting tree. A cooperative lease is not an OS-wide exclusion of arbitrary tools: if an uncoordinated writer can still target those paths, the engine cannot guarantee against a check-then-replace race and must stay in patch/conflict mode. Never promise that a per-path hash precheck makes replacement safe against a noncooperating writer. If a managed writer window is violated, stop, mark the checkout conflicted and preserve both the admitted revision and observed external bytes; do not silently declare a mirror. The operation can be `accepted` while mirroring is `not-materialized` or `conflict`; target build/cook reads the admitted immutable tree, never a half-written checkout.

On restart, load the last durable root and verify its immutable source closure and operation outcomes first. A pre-root tool candidate has no accepted outcome; retry its token against the current root or report conflict. If a managed materialization was interrupted, inspect its durable intent and the actual path hashes/branch. A fully matching tree becomes `matches`; an old or mixed/different tree remains `not-materialized` or `conflict` with an exportable patch. **Do not replay or roll back over different current bytes or another branch automatically.** A root published before a later external edit remains admitted while the checkout is external-pending. Recover a missing checkout file only via explicit managed materialization or patch application; retained immutable source bytes protect the accepted revision without authorizing overwrite. If storage admission cannot reserve prior root, staged revision, log and safety headroom, reject before publishing the new root.

Undo/redo are new forward authoring operations against the current admitted revision, with field/path preconditions. Undo of a pending cook invalidates its generation; after activation it stages a replacement. It does not rewind Git, an external DCC write, private play save, or player save. A conflicting inverse remains a reviewable candidate. Retry of an identical idempotency token returns its durable outcome; changed payload rejects. A retired epoch returns `expired`, never `never seen`; its pending outcomes must have been made recoverable before retirement. This preserves C10's deduplication promise without forever-valid keys.

### Play, saves, apply-back, restart

`startPlay` requires a target-ready build/product closure and creates fresh session/world epochs, clocks, events and a private save namespace under that session. Workbench or CLI source edits can proceed, but the running process remains on its pinned revision. `stopPlay` closes input/jobs, retires leases after readers and GPU fences, and discards unsaved gameplay state. An explicit `retainTestSave` writes a session-private C10-style RecoveryRoot: checkpoint tick, base source/build/manifest, overlay, schema/provider versions and operation outcomes. It keeps the needed content or qualified recook closure under the chosen retention window. Restart with a retained test save is a deliberate restore/migration test; absent compatible migration, it fails without altering either the old save or source. Released player saves are separate authority-root namespaces; server-owned saves belong to the server authority. C10's old single-root wording therefore means **one immutable durable restore choice per persistence authority**, not one root globally for authoring, every play run and shipped players. A runtime can run ahead of its checkpoint; only a completed durable save promises its checkpoint, and later gameplay may be lost on crash.

Apply-back is explicit and narrow. The developer selects stable source objects and schema-marked authored properties from the play diff against its pinned base; gameplay inventory, spawned runtime-only identities, solver state, handles, event cursors and simulated earnings are excluded unless a particular operation declares a reviewed conversion. T1 displays a three-way diff `(pinned base, selected play value, current admitted source)`. It emits an ordinary typed batch operation with current revision/read-set preconditions; any changed touched field, deleted/ambiguous ID or schema mismatch reports conflict for manual selection. Untouched source fields can advance. The result follows normal source admission, cook/activation and undo; it never mutates source files directly from the player process. A remote server or replica has no developer apply-back authority by default.

Code/schema edits produce a new source candidate and build. The old session stays labeled `running old build` or is explicitly stopped; a successful rebuild creates a new session, with fresh world epoch. There is no automatic carry-over of live gameplay state. Optional retained test-save restore uses explicit schema/content migration and C10 checkpoint pairing. A failed compile or migration leaves the old ready build and save closure intact and reports the new source/build failure. Data-only live preview is opt-in per operation and must use the same F4/W2 barrier and pinned-generation checks; a forced restart from the new admitted revision is always supported. Browser fallback may host editor and player in one OS process, but distinct instance/state/storage adapters must enforce the same scopes. Native arbitrary game code can make external calls; engine-managed file/network capabilities route through declared adapters, while external side effects beyond them are outside undo and require a game-specific policy. Process separation is failure containment, not a security claim.

### Transform contract WP01

W1 stores only authored local translation (f64 metres), normalized proper quaternion and finite signed scale, composed `T·R·S`; world matrices are derived. Import accepts glTF node TRS or decomposable matrix, but rejects or explicitly bakes unsupported shear under an authored import conversion with a reported fidelity change. glTF itself requires matrix node transforms to be decomposable to TRS and forbids matrix on animated nodes [Khronos glTF 2.0 transformations](https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html#transformations). A general DCC affine input outside glTF is not quietly projected to TRS. Negative scale is allowed for static visual nodes and retained as signed scale/reflection; importer/render use determinant-aware winding, normals and tangent handedness. Physics/collision and skeletal consumers declare whether reflected or nonuniform scale is supported; otherwise admission requires a baked derived shape or rejects the use. A zero scale may exist only for a render-only visibility/content node explicitly marked non-invertible; no preserve-world inverse, dynamic body, collision or normal transform may depend on it.

For `preserveWorld` reparent, compute `L* = inverse(W_newParent) · W_old` in f64 after checking parent ancestry, invertibility and authority-mode constraints. Reject if the new parent linear part has smallest singular value below `1e-8` in scale units or condition number above `1e8`, or if any value is nonfinite. Decompose `L*` into translation, a **proper** rotation (determinant +1) and signed scale using a deterministic sign convention; a negative determinant is represented by one signed axis, not an improper quaternion. Recompose `L̂ = T·R·S`. Admit only if `||linear(L*)−linear(L̂)||_F / max(1, ||linear(L*)||_F) ≤ 1e-10` **and** `||W_newParent·L̂−W_old||` meets both a world-linear relative tolerance `1e-10` and a translation tolerance `max(1e-6 m, 1e-12·||old_world_position|| m)`. These are numerical round-trip limits, not permission to visually approximate shear. Report the residual, required tolerance, parent chain and `preserveLocal` alternative on rejection. The tolerance constants are protocol constants fixed with the operation schema, not user tuning; implementations may tighten them but cannot silently loosen them. A 45° rotated object under a new `(2,1)` scale parent gives nonorthogonal required local basis columns and fails. Reparenting a subtree preserves each descendant's world transform if its root world is preserved; `preserveLocal` instead keeps the stored local TRS and intentionally changes world pose. Static/kinematic/dynamic restrictions in C03 still apply; this transform decision never grants physics a second motion authority.

### Hard-case trace and closure

| Case | Expected state/diagnostic |
| --- | --- |
| Checkout changes prefab, mesh metadata, then scene; watcher fires each time | Source becomes external-pending. No intermediate cook/activation. Explicit sync captures a Git tree or attested dirty closure; broken links/ambiguous rename reject the candidate while last admitted/play remain named. |
| Editor has accepted pending `R+1`; branch changes same files | Checkout remains external-pending. Sync fails base/revision or yields conflict; durable `R+1` is not replayed over new bytes. Candidate and operation outcome remain inspectable. |
| Tool crashes after root admission but two of three managed checkout replacements | New root and operation outcome remain valid; build reads its immutable file tree. Materialization intent/path hashes expose a mixed checkout, marked conflict/not-materialized; no automatic replay over unknown contents. |
| Play body moves; editor changes its source transform; play stops | Play pose disappears by default; editor's new desired revision remains. Apply-back sees changed touched transform and conflicts rather than overwriting it. |
| Code edit fails to compile while old play runs | Old process stays explicitly pinned to old build; new source is accepted or pending independently; no claim that new code runs. |
| Retained private save after schema change | Restore exact old tuple or approved migration into a new root before exposing world; failure leaves old save and source intact. |
| Reparent under rotated nonuniform ancestor | Preserve-world rejects if local shear/conditioning breaches tolerance; preserve-local can succeed with visible world-pose change. |
| Two views, or future server and predicted client | Views share one committed session tick; client replica has separate epoch and replication projection. Neither view nor replica may publish authoring/player authority roots. |

**Exact owner edits for coordinator:** C01 add source/build/session/authority identities; C02 state session-scoped snapshot/tick ownership; C10 scope RecoveryRoot per authority and connect authoring root to immutable admitted source manifest, source-file conflict and private/player save namespaces while preserving operation epoch/durable closure/storage rules. WORLD-CONTENT F3/F4/W1/W2/P7 add source capture and manifest identity, transform rejection/consumer compatibility, session world epochs and save ancestry. TOOLS-DELIVERY T1/T2 add explicit sync, root-first tool admission, separate managed-checkout materialization/intent recovery and mirror status, apply-back three-way operation, code restart matrix and provenance of admitted tree versus dirty checkout. PLATFORM-RUNTIME F1 add child-process default plus in-process/browser logical-isolation fallback and stale-session cancellation. COMPOSITION/ENGINE-EXPERIENCE clarify static build/restart and no live code replacement. CONSTRUCTION-PLAN D1 must close these contracts before source/session APIs freeze; WP05 spatial trace includes the shear rejection. Future N1 network owner must define authority/replica session projections without treating save/render snapshots as wire state.

**Design closure gate:** coordinator and both producers/consumers accept the exact identities, state transitions, crash/root order, external-writer limitation, private save routing and TRS rejection rule in governing contracts; paper traces above cover concurrent edit, branch, lost response, crash, save, restart, and scaled ancestry with no contradictory owner. A prototype or test plan alone does not close A01/A02/J04/WP01. **Later bounded qualification:** adapter-specific durable flush/CAS implementation and crash injection; browser persistence/eviction guarantees; compile/restart latency; native child-process overhead; numerical transform fixtures and importer/physics/render conformance; actual artist usability. These tests check the selected boundary rather than choose it.

## Cross-review with N1, shader/media and water handoffs

Read 1 November 2026 against [NETWORKING](../../../design/modules/NETWORKING.md), [SHADERS-MEDIA](SHADERS-MEDIA.md) and [WATER-DOMAINS](WATER-DOMAINS.md). The designs are compatible if the following boundaries are made explicit in the governing contracts:

1. **Two session namespaces.** This handoff's `SessionId` is a local run instance, whether editor play, server process or client process; it owns a local `WorldId/WorldEpoch`, jobs and save routing. N1's network session is a shared match/protocol namespace for wire IDs and peer negotiation. Call it `NetworkSessionId` (or equivalent), and map it to each peer's local run session. A listen host contains at least two local world roles under one network session. N1's phrase “each world/session has its own clock” must mean each authority has a simulation clock and each replica has received authoritative tick/time plus a local presentation clock; a replica cannot advance the authoritative tick independently. This prevents stale messages and the accidental global world singleton.
2. **Per-peer source/build pins versus shared gameplay compatibility.** Each local run pins its own admitted `SourceRevision`, `BuildRevision`, product closure and target. A server match additionally pins its authoritative game-rule/schema version and gameplay-content manifest. Clients may have different source revisions and target-specific shaders/textures if N1's protocol and gameplay semantic compatibility check passes. A running server does not admit a new checkout or accepted source edit merely because T1 advances the project head. A gameplay code/schema/content change requires an explicit coordinated stop/restart or a separately designed versioned activation with peer renegotiation, content readiness and migration. Preserve old saves' source/product closure until their supported migration/replacement roots publish. This is the same J04/C10 rule applied to server authority, not a new live multiplayer hot reload promise.
3. **Authority-root routing.** N1's server/standalone P7 checkpoint root, private developer play roots and client speculative/replica state must be distinct. Only the authority writes its checkpoint root. A predicted branch may be captured for bounded replay but is not a durable authoritative save, and neither it nor a remote client's UI may call T1 apply-back into server project source. Editor apply-back is a local developer operation with a three-way source precondition; any server administration edit is a separate authorized workflow. N1's replication projection must remain schema/versioned and distinct from C02 render snapshots, P7 save captures and immutable source manifests.
4. **Readiness has an authority dimension.** The shader handoff correctly separates F4 cooked descriptors from per-device V1 pipeline preparation. N1 synchronization should require compatible gameplay rule/content/query products before the replica can act, but a client's missing local visual pipeline only blocks or reduces that peer's view according to its declared visual policy; it does not pause the server tick or invalidate other peers. A headless server has no shader demand. Water domains and edge ledgers are authoritative per server world; clients receive versioned gameplay fields/events and may render different visual residuals. E1 water prediction is admitted only with its provider's full captured state, boundary forcing, dependent bodies and replay budget. Do not use a seed or visual surface height as a substitute. Source admission of authored water edges follows the same explicit immutable snapshot and F4/W2 activation barrier as other multi-file edits.

No contradiction was found with the shader finite-demand closure or water's physical query/edge authority. These four clarifications are **design corrections to reconcile**, not evidence that networking, shader preparation, water prediction or source recovery has run. The limitation on noncooperating writers remains: a dirty-tree hash reread plus semantic validation cannot prove that all files coexisted at one instant; use immutable VCS trees or cooperating transactions for that stronger claim, and leave uncertain external changes pending explicit review.
