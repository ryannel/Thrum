# J03 decision — W1 component storage reuse

1 November 2026. **Selected initial architecture for coordinator reconciliation; no dependency installed or runtime qualified.** Choose **hecs 0.11.2 as W1's private general-component storage backend**, with a small W1-owned identity/access seam. F1 still schedules systems; F3 still owns stable schemas; W1 still owns identity, hierarchy, committed transforms and world lifecycle. P3, P4, P5, V2, A1 and F4 retain their specialized stores. This replaces the [WORLD-CONTENT](../../../design/modules/WORLD-CONTENT.md#selected-representations-and-authority) proposal to build both an in-house archetype table and general sparse-set planner at the outset. It does **not** import Bevy's host, scheduler, reflection or renderer.

## Why this choice

[hecs' own documentation](https://docs.rs/hecs/0.11.2/hecs/) describes an ECS **library**, not an application framework or scheduler. Its `World` provides typed, contiguous archetype component storage, queries, batch spawning and component insertion/removal from ordinary Rust code. It has no required `System` abstraction; F1 can keep the selected fixed-tick stage graph. This fits the current target: W1 needs modest entity composition and traversal, while the numerically and spatially specialized stores already have separate owners. `hecs` 0.11.x is [MIT OR Apache-2.0 licensed](https://docs.rs/crate/hecs/0.11.0/source/Cargo.toml); the pinned crate/dependency and notice audit remains an I1 build gate, not a claim that the package already ships.

| Choice | Strength | Cost against this engine | Decision |
| --- | --- | --- | --- |
| hecs private to W1 | Mature archetype storage/query primitive; no host/scheduler takeover; regular Rust components and a small initial API | Backend `Entity` lifetime/collision and unordered query iteration need a W1 seam; archetype moves cost when optional components churn | **Select for ordinary W1 components.** Keep only stable or modest-churn components there initially. |
| Owned dense archetypes plus generic sparse sets | Exact allocator/layout, iteration and migration control; no external crate | Rebuilds archetype migration, borrow/query machinery, change tracking and sparse planner before a measured need; adds two general storage mechanisms to maintain | **Reject as initial default.** Retain as a replacement if the pinned backend fails measured workload or platform/license gates. |
| Flat `HashMap<Id, Record>` or one giant component struct | Small implementation and direct lookup | Full scans and optional component growth force per-entity branching; weak for ordinary dense iteration and typed extensions | Suitable only for tiny tools/fixtures, not the selected reusable W1 backend. |
| Bevy ECS as a standalone dependency | Rich storage, scheduling and reflection available without adopting the full Bevy application host | More framework concepts and dependency surface than this initial W1 storage job needs; would compete with already selected F1/F3 ownership unless tightly confined | Do not select initially. The user's no-Bevy-host choice does not itself prohibit standalone libraries. |

**Selected layout, not a later promise:** W1 stores general scene/game component columns in hecs archetypes. A small W1 side table holds public runtime identity, durable-ID mapping, hierarchy/dirty-order metadata and links to specialized owners; it is not a second generic component database. F3 schemas map stable schema/field IDs to typed component adapters and codecs; Rust `TypeId` or hecs serialization is never the authored or save schema. P3 body state/broadphase, P4 pose state, P5 nav state, V2 draw data, A1 voices and F4 assets remain specialized. A frequently added/removed optional feature stays in hecs initially if churn is modest. When measured archetype moves dominate, that *specific* feature moves to an owner-specific slot-keyed side store, with W1-owned lifecycle and access declaration; no global sparse registry is prebuilt. This is an explicit change from the earlier simultaneous table-plus-sparse recommendation.

## Exact identity and access seam

- Public runtime identity remains `(world epoch, W1 slot, W1 generation)` under C01. W1 keeps a slot table `slot → {generation, current hecs Entity, stable/durable ID when present}` and a durable-ID index. Reuse increments W1 generation; generation wrap retires the slot. A fresh world/session has a fresh epoch. Every external/job/specialized-store lookup resolves and validates this W1 identity before touching hecs. A hecs `Entity` is an **internal pointer-like token**, not the public handle, save ID or wire ID. The extra slot table is small identity machinery, not a competing ECS.
- A hecs handle is held only inside the current W1 world and a bounded access stage. It never enters components as an enduring cross-world reference, asynchronous jobs, snapshots, save records, network messages or external plugin APIs. Components that link entities use W1 runtime IDs for live links and stable IDs for durable links. W1 drops the hecs world at session retirement and reconstructs from stable IDs/save state; it does not restore old hecs handles. Ban `spawn_at`/`spawn_column_batch_at` and same-world `clear` in the W1 adapter: [the hecs `World` documentation](https://docs.rs/hecs/0.11.2/hecs/struct.World.html) says `spawn_at` can resurrect an old handle and `clear` can repeat handle values. It also warns an ancient `Entity` may collide after billions of spawn/despawn cycles. The seam prevents those backend handles from acquiring the long-term C01 promise. A debug assertion checks current mapping and `World::contains` at resolution; a failed mapping is `stale/unknown`, never a different entity.
- W1 exposes typed, registered component read/write views and structural commands scoped to a declared F1 stage; hecs `World`, `Entity`, archetype/query internals and raw mutable borrows are not public engine contracts. Iterators/borrows cannot outlive their stage or a pre-tick structural barrier. W1 batches spawn/despawn/add/remove commands at the admitted barrier, so structural migration does not occur halfway through a consumer traversal. F1 owns semantic order, access declarations, conflict validation and worker dispatch; hecs' borrow checks are an implementation guard, **not** the schedule or authority policy. W1 owns hierarchy topological order, transforms and versioned committed read models; hecs never becomes snapshot/save authority.
- hecs query order is [documented as arbitrary](https://docs.rs/hecs/0.11.2/hecs/struct.World.html). Any rule whose result depends on iteration order takes a stable ID ordered worklist or an explicit reduction order before committing. P7 capture, N1 replication projection and event identity use stable schema/ID order, not hecs row/archetype order. This preserves the existing reproducibility envelope without promising cross-platform bitwise identity or a deterministic ECS allocator.

## Failure trace and qualification

At a pre-tick region activation, W2/F4 present a complete prefab/content closure. W1 validates and reserves the structural command plan before mutation, then allocates public slots, spawns registered general components into hecs, records stable-to-runtime maps and binds specialized P3/P5 products under those public IDs; only then does F1 publish the new active world generation. A P3 or async result from the previous cell generation fails W1 identity/content checks. During a later despawn, W1 tombstones the stable object, detaches specialized stores, invalidates the slot/generation and despawns its current private hecs entity at the barrier. A stale job holding the prior public handle cannot reach a recycled hecs row. A save uses F3/P7 codecs from the committed stable-ID state; restore allocates fresh hecs handles. A semantic/product/budget failure is detected **before** mutation and leaves the old active world intact. If a future operation can fail after W1 mutation starts, it needs a staged replacement world or a proven rollback path; hecs does not provide an atomic world transaction, and `spawn_at` is not a recovery mechanism.

**Architecture closure:** reconcile WORLD-CONTENT's initial table/sparse wording, CONSTRUCTION-PLAN's W1 row and C01/C02 identity/snapshot language with this private backend and public W1 handle. F1 scheduling, F3 schemas, P7 saves and N1 wire projections must remain independent of hecs internals. **Build qualification before adoption:** pin exact crate/transitive versions and notices; compile native Mac/PC, Wasm/browser and mobile targets; run representative density/churn/region activation and multi-world memory measurements; check the W1 wrapper's stale-handle, generation-wrap, `clear`/`spawn_at` exclusion and stable-order scenario behavior. Failure of a named gate selects the bounded owned-registry fallback or another standalone library behind the same seam. No benchmark, target compile or license-distribution audit was run here, so this selects an architecture candidate rather than certifying its shipped use.
