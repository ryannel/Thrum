# D1 closure: admitted source, operations, W1 staging, TRS

1 November 2026. **Selected detailed design for coordinator reconciliation; unimplemented and unqualified.** Scope is D1 source/transaction and WP01 only. It refines [decisions](../../../design/ARCHITECTURE-DECISIONS.md), [C01/C02/C10](../../../design/CONTRACTS.md), [world/content](../../../design/modules/WORLD-CONTENT.md) and [tools](../../../design/modules/TOOLS-DELIVERY.md). N1 owns match/wire policy; this design keeps local authority/session identities independent. Exact API names below are protocol sketches, not Rust signatures promised to SDK users.

## 1. Source format and identity — select one ordinary file language

Use UTF-8 JSON for editable engine records: `project.json` (project ID, format version, entry scenes, target profile references, declared dynamic roots), `scenes/<name>.scene.json`, `prefabs/<name>.prefab.json`, and adjacent `<master>.asset.json` for imported assets/settings/ID mapping. Game Rust/WGSL and binary masters remain ordinary files in the same project tree. Human names/paths are mutable; each record has `id` (lowercase RFC-4122-form 128-bit UUID), `type` (stable ASCII schema type ID), `schema` (positive integer), and `fields` keyed by permanent ASCII field IDs such as `transform.translation`; display labels are registry metadata. Prefab node IDs are scoped stable 128-bit IDs; instance/node pairs follow W1. Field IDs never change meaning/units; a rename changes display text, a semantic change receives a new field ID and explicit migration. UUID collision, duplicate record/node/field IDs and required unresolved references reject admission. Optional unknown fields round-trip as JSON; required unknown fields reject.

Example source record (readable, paths are not identity):

```json
{"id":"2a5ef644-7225-4770-9f4d-e1d9c0a7d515","type":"core.scene-object","schema":1,"fields":{"transform.translation":[2,0,4],"transform.rotation":[0,0,0,1],"transform.scale":[1,1,1]}}
```

Parsing is strict I-JSON: no duplicate keys, NaN/Infinity, invalid Unicode, out-of-range integer IDs or implicit units. JSON numbers are finite f64 and negative zero normalizes to zero on semantic write. SourceRevision hashes **exact file bytes**, so formatting changes yield a new source revision; recipes may separately hash schema-validated canonical values using [RFC 8785 JCS](https://www.rfc-editor.org/rfc/rfc8785.html). Registry and root JSON are JCS encoded for their own hashes. Records may use comments only in a separate documentation field, not JSON comments. Version 1 has no automatic major-version coercion; an admitted migration creates a new file tree and records old/new revision and migration ID. Client writes use stable field IDs and schema version, never array positions or human labels.

`SourceRevision = SHA-256(JCS(TreeManifest))`. The manifest contains format version, project ID, sorted normalized relative paths, entry kind (`file` only), byte length, SHA-256, stable record ID/type where parseable, and declared dependency roots. Source paths use `/`, Unicode NFC, no `..`, absolute paths, symlinks, devices or case-fold collisions, so the same project has one cross-target membership interpretation. Exclude `.git`, `.engine` stores, build caches and known generated outputs by versioned project policy; no wildcard that silently drops an undeclared master. A referenced Git LFS pointer is insufficient: resolve and hash the master payload or mark unavailable. Membership, deleted paths and renames are part of the manifest. The maximum v1 source tree is 100,000 entries; JSON record bytes ≤16 MiB, nesting ≤64, operation payload ≤16 MiB, and a single immutable blob ≤16 GiB. These are admission bounds, not performance promises; larger assets require a versioned profile/format change before admission. Build and cook never read the mutable checkout.

`RecoveryRoot` is JCS JSON with `format:1`, authority ID/kind (`authoring`, `private-play`, `standalone-save`, `server-save`), monotonically increasing `generation`, desired SourceRevision (authoring only), `journalHead`, dedup epoch/index head, and a nullable checkpoint tuple `(tick, baseSourceRevision, BuildRevision, manifestHash, overlayHash, schema/provider versions)`. The tuple is copied unchanged when desired source advances; never pair old overlay with new desired source. A save root always has a non-null tuple. Root hash and referenced closure are verified before use. MatchId, local SessionId/WorldEpoch, wire ID, W1 slot and source ID have distinct type tags; none is reconstructed from another. N1's initial u32 action/type numbers are **indices in a pinned protocol manifest** mapping these F3 stable type/field/action IDs to wire numbers; neither Rust `TypeId` nor source path is a wire identity. MatchId is a fresh 128-bit value, not a SourceRevision.

## 2. Operation and source-sync protocol

An authoring mutation is `{kind, schemaVersion, targetStableId, expectedSourceRevision, readSet[(id,fieldId,revision)], writeSet, parameters, actor, correlationId, token:(authorityId,epoch,key)}`. A batch is one all-or-nothing candidate. T1 validates token/payload equivalence, expected root, schemas/units, stable-ID references, hierarchy/cycles, TRS representability/consumer support, provider/content closure and source-tree limits **before** acceptance. Preserve-world uses the operation's expected **desired authored source** matrices, including previously admitted pending edits, never an active/play physics pose. Apply-back is the same batch after a three-way `(play base, selected play fields, current source)` precondition; no remote replica/server path. Failed validation creates a rejected outcome, with no candidate root or W1 mutation.

For T1 edits: (1) read current root generation/revision; (2) register a durable bounded staging pin/intent **before** writing or reading candidate blobs, so GC cannot collect them; (3) derive a complete immutable candidate file tree, preserving unchanged blobs by hash; (4) validate and reserve old root, new blobs, outcome/journal, required save closure and disk headroom; (5) durably stage every new blob and TreeManifest; (6) in **one metadata transaction**, compare expected root generation, insert accepted operation outcome/dedup record, advance root to the new manifest/generation and convert the staging pin to root/candidate-retention pins; (7) acknowledge `accepted` only after that transaction's declared durability condition. A losing CAS retains its candidate as a proposal under a bounded review pin and returns current root/diff, never rebases or mirrors it. `accepted` is desired source durability, not checkout match, cook, world activation or save completion. F4 cooks from the new immutable tree; W2/P3/P5 stage the complete active dependent closure; F1 commits required world/products/manifest at one pre-tick barrier after rechecking active-set and source/product generations. Failed cook leaves desired accepted and active old, with cause. Undo/redo are new operations creating new trees against current revision; pending active work is cancelled by generation, not source-root rewind.

Idempotency: within an authority's live operation epoch, `(epoch,key)` plus canonical payload hash has one stored outcome; same key/different payload rejects. Accepted outcome and source-root advance commit together. A validation rejection also commits its outcome and **metadata** root generation atomically, with the logical desired SourceRevision unchanged, before returning `rejected`; no candidate world/source mutation follows it. A lost response may query/retry and receive the exact accepted/rejected/failed status and source revision. An epoch accepts at most 10,000 operations or seven days of new requests, whichever arrives first; then a new epoch opens. At most 1,024 operations may be pending cook/activation per project; excess admission returns `busy` without an accepted source edit. A pending operation reaching seven days is terminalized `failed` with cause and a durable outcome; its publication generation is invalidated so a late cook cannot activate it, and an author may submit a new retry operation. Keep a closed epoch's dedup/outcome index for at least 30 days after its last request and until all its outcomes are terminal/recoverable, then publish an explicit retirement marker. A token from a retired epoch returns `expired`, never `never-seen`, and the client must query current source/root before making a new request. Keep inverse field deltas/source closure for the last 1,000 operations or 30 days, whichever limit is reached first, unless a save/release/pin requires longer; after that undo reports expired rather than guessing. This retention is separate from supported save closure. Correlation ID groups diagnostics, not deduplication. External effects (signing/upload/payment) are separate non-undoable operations, never hidden in a source edit.

External sync has `(baseRootGeneration, selectedGitTreeOrCapturedManifest, intentDeclaration)`. A watcher only sets `external-pending`. An immutable Git tree is a strong capture boundary (after resolving required LFS bytes). For a dirty checkout, the initiator explicitly selects a finished change set; the capture copies all declared members, rereads path membership and hashes to detect drift, then validates **the captured bytes**. A reread cannot prove that arbitrary noncooperating writers had a coherent point-in-time tree, including ABA; the initiator's declaration is recorded, and uncertain capture remains pending. Git HEAD alone is not the dirty tree. Sync publishes by the same root CAS; if T1 accepted an edit or a branch sync won since base, the loser conflicts. It never silently merges or overwrites either proposal. A branch switch while T1 is preparing produces one of: T1 wins, checkout becomes external-pending; sync wins, T1 candidate conflicts; neither outcome writes new branch files automatically. [Git checkout](https://git-scm.com/docs/git-checkout) documents that a checkout may preserve local changes or fail on conflicts, so branch name cannot substitute for selected bytes.

## 3. Native and browser commit adapters

**Native desktop/build host.** Use **one SQLite database** for roots, exact immutable source bytes, manifests, journal/outcomes, pins and GC state; it is a content-addressed byte store, not a mutable property database. Source files remain ordinary JSON/code/masters and can be exported byte-for-byte. At new database creation, before any table, set `page_size=4096` and `auto_vacuum=INCREMENTAL`, then verify both; an existing database with another mode needs an explicit migration with reserve, not a silent pragma toggle. Store blobs as 4 MiB `blob_chunks(hash,index,bytes)` with a `blob_header(hash,length,chunkCount,state)`; prewrite chunks in bounded transactions, verify full SHA-256/length by reading them back, then mark the header `complete`. Use `journal_mode=WAL`, `synchronous=FULL` on a qualified local SQLite VFS/filesystem. On qualified macOS VFS, set and verify `fullfsync=ON` and `checkpoint_fullfsync=ON` before claiming the strongest local power-loss condition; `fullfsync=ON` already covers checkpoint sync, but both settings make the adapter requirement explicit. If the VFS/device cannot provide its claimed sync behavior, report a weaker guarantee. The **single final SQLite transaction** checks root generation and every referenced complete/non-deleting blob, then commits root/outcome/dedup/pins together; successful commit is the native `accepted` point. This avoids a cross-file blob-versus-root flush race and needs no portable directory-fsync assumption. SQLite documents WAL+FULL per-transaction durability under its VFS/sync assumptions; it cannot defend against lying hardware, arbitrary deletion or unsupported network filesystems. [SQLite synchronous/WAL and fullfsync pragmas](https://www.sqlite.org/pragma.html), [SQLite atomic commit](https://www.sqlite.org/atomiccommit.html). On failed reserve, chunk write, verification or DB commit, old root stays selected; orphan chunks are collected later. Do not split roots/outcomes/chunks across attached WAL databases: SQLite does not promise cross-database WAL power-loss atomicity [SQLite temporary files](https://sqlite.org/tempfiles.html). A separate content file cache may accelerate reads but is never accepted-source authority.

**Browser authoring/storage.** One IndexedDB database has `blobs`, `manifests`, `roots`, `outcomes`, `pins`, `gc` object stores. Prewrite blobs/manifests in bounded `durability:"strict"` transactions, wait for `complete`, reread and verify hashes. The final single `readwrite` transaction spans **all six stores**, checks root generation and that every referenced blob is present/not `deleting`, then writes root, operation outcome and pins atomically; wait for `complete` with `durability:"strict"`. This shared scope serializes root publication against GC marking. IndexedDB defines strict as a **hint**, and a transaction may abort on close/quota; completion is an adapter-level local acceptance, not a universal power-loss guarantee [IndexedDB 3.0](https://www.w3.org/TR/IndexedDB/). Before relying on local persistence, request/report `navigator.storage.persist()`; if denied, show `best-effort local` and require explicit export/backup for a durable handoff claim. Even granted persistence does not protect from user deletion or browser/profile loss [Storage Standard](https://storage.spec.whatwg.org/), [StorageManager.persist](https://developer.mozilla.org/en-US/docs/Web/API/StorageManager/persist). Browser play can run from pinned IDB blobs but never treats Cache API/driver caches as source or saves. If strict transactions or adequate quota are unavailable, reject *durable-authoring* claim and offer exported immutable project bundle/native adapter; do not report a stronger `accepted` state than the adapter provides.

The native/browser storage adapter reports `commitGuarantee`, root generation and verified closure; C10's “accepted” is always qualified by that declared guarantee. A player checkpoint uses its own authority root and the same tuple/publication protocol. Running world may exceed last checkpoint; crash restores exactly that tuple and marks newer desired source pending. Periodic checkpoints, not final suspend callbacks, bound gameplay loss. A private play save never writes a released/server authority root; a server pins its BuildRevision/gameplay manifest for a match until explicit restart or migration/rehandshake.

## 4. Checkout mirror, crash recovery and GC

The mutable checkout is a **mirror**, not the accepted transaction. In shared/unmanaged mode T1 returns a reviewable patch/candidate tree and writes no checkout path. In managed mode all participants must explicitly hand off writes to an isolated writer window with recorded branch, base manifest and cooperative lease. Materialization is a separate job: durable intent `(root revision, expected old path hashes, new path hashes, branch)`, staged replacements, verified final manifest, then `matches`. If interrupted or external bytes/branch differ, mark `conflict`/`not-materialized`, preserve observed files and patch; never replay or roll back unknown bytes. Per-path hash-then-rename does not exclude a noncooperating writer; if such a writer may target the window, stay in patch mode. Root acceptance survives a mixed mirror. Builds always use admitted blobs. Managed mode's exclusivity is an operating assumption checked by the workspace owner, not a filesystem guarantee against every same-user process.

GC uses two publication epochs. Every durable root/checkpoint/release, retained private save, live build/session, reader/serializer lease, pending operation outcome, materialization intent and candidate under review pins its transitive blob/product closure. A pin is registered in the metadata transaction **before** a reader or publication can depend on bytes; release is recorded only after CPU readers/GPU fences and backup/export duties finish. Collector first marks from a consistent root/pin snapshot and records a candidate deletion generation; in a later exclusive store transaction it rechecks that the blob is still unreferenced and no new pin appeared, marks it `deleting`, then removes SQLite chunks or IDB blobs in bounded transactions. A publisher checks the same store transaction and treats `deleting` as unavailable, restaging before root CAS. Crash at any point leaves a retained blob or an explicitly unavailable unreferenced blob, never a published root whose newly needed bytes were collected. Reserve prior root, staged new bytes, journal/outcome, supported save/release closures and headroom counting shared hashes once; failure rejects publication. Browser eviction beyond storage guarantee is a diagnosed lost-store condition, not a GC success.

**Native physical-space lifecycle and admission.** V1 local authoring has a configurable **64 GiB project disk budget**: at most 52 GiB for the SQLite main file (`max_page_count=13,631,488` at 4 KiB, set/verified on each open), 2 GiB for WAL, 2 GiB for managed temporary/cache files, and 8 GiB unallocated headroom. An operation must reserve its projected *physical peak* (retained old closure, complete new chunks, WAL growth, mirror staging and temporary files, counting shared hashes once) against those caps **and** leave at least 8 GiB actually free on the hosting volume after the projected peak; failure returns `insufficient-space` before acceptance. A user can explicitly raise the profile budget after a fresh volume check; no silent growth or deletion of pinned history. WAL writes are in ≤4 MiB blob chunks/short metadata transactions; at 1 GiB WAL begin `PASSIVE` checkpoint work, seek a `TRUNCATE` checkpoint when readers drain, and defer new staging at 2 GiB until checkpoint/truncation succeeds. `journal_size_limit` may cap *retained* WAL size but is not the admission guard. No SQL read transaction spans CPU decode, GPU upload/fence, editor review, or network lease: register the logical pin in a short metadata transaction, close it, then use bounded chunk reads; release the pin after the external lease ends. A blocked checkpoint remains visible and cannot be counted as reclaimed space. [SQLite WAL and checkpoints](https://www.sqlite.org/wal.html), [SQLite checkpoint pragma](https://www.sqlite.org/pragma.html#pragma_wal_checkpoint).

After GC deletes chunks, `freelist_count × page_size` is **reusable inside SQLite**, not bytes returned to the volume. In maintenance outside the simulation tick, run `incremental_vacuum(256)` per slice (up to 1 MiB of 4 KiB pages), then checkpoint `PASSIVE`; after short readers drain, run `wal_checkpoint(TRUNCATE)` and inspect its busy/result columns. Continue bounded slices until the freelist is below 256 pages or the current maintenance window ends; resume later. Report separately logical unpinned bytes removed, reusable freelist bytes, main DB/WAL/temporary **physical file lengths**, and observed physical bytes reclaimed (`stat` before/after successful truncation/checkpoint); only the last is advertised as returned disk space. This is why GC completion alone never reports disk cleanup. Do not use full `VACUUM` as normal maintenance: SQLite may need up to twice the original DB size free, beyond the v1 reserve. Browser storage reports quota estimates and observed successful deletion separately; it cannot promise immediate filesystem reclamation. [SQLite auto-vacuum, freelist and incremental-vacuum pragmas](https://www.sqlite.org/pragma.html), [SQLite VACUUM disk requirements](https://www.sqlite.org/lang_vacuum.html).

## 5. WP01 numerical transform admission

Select initial **authoring envelope** for the reference workloads: world coordinates within ±`10^6` m on each axis; each object's authored local geometry/subtree radius ≤`10^3` m, and every transformed bound must remain inside that world extent; finite nonzero local scale magnitudes in `[10^-4,10^4]` for preserve-world operations; new-parent linear condition number ≤`10^3`. Static render-only zero-scale records may exist but cannot be preserve-world operands or physical/normal-transform inputs. These are v1 schema admission limits, not an astronomical-world promise, and can change only by a versioned profile with a new error proof. With a view origin ≤512 m from the visible position, f32 conversion has ulp scale `2^-23·512 ≈ 0.061 mm`; the P3 provisional local physics radius ≤2 km gives `≈0.244 mm` and has its own contact/query qualification. Choose a 1 mm initial game placement tolerance and a much tighter **authored preserve-world round-trip budget of 1 µm**. At ±`10^6` m, f64 roundoff is order `10^-10` m; the `10^3` condition cap can amplify this toward `10^-7` m before the explicit residual test, leaving analytical margin below 1 µm. These are rounding-scale estimates, not measured solver or GPU guarantees. A game needing smaller/larger spatial regime selects a separately specified envelope before those operations are admitted.

For `preserveWorld`, evaluate old object and candidate new-parent **authored** world matrices from the operation's expected SourceRevision, not runtime/play pose. Reject cycle, dynamic-body authority violation, nonfinite values, singular/condition limit and unsupported transformed descendant/consumer regimes before root CAS. Compute `L*=inverse(WnewParent)·Wold` in f64. Compute the 3×3 singular values of the parent linear map by fixed-order Jacobi sweeps on `AᵀA` (plane order XY, XZ, YZ, at most 32 sweeps; off-diagonal norm must fall below `10^-14` times diagonal norm); reject nonconvergence or condition above `10^3`. Let `L*`'s linear columns be `c_i` with lengths `s_i>0`; if determinant is negative, assign the one negative scale to the largest `s_i` (tie X then Y then Z), otherwise all scales positive. Form sign-adjusted unit-column matrix `N`. Compute its proper polar factor by `X_0=N`, `X_(k+1)=0.5·(X_k+inverse(X_k)ᵀ)` for at most 32 iterations; each 3×3 inverse uses fixed-order partial pivoting (largest absolute pivot, row-index tie), rejects a nonfinite/zero pivot, and stops when `||XᵀX−I||_F≤10^-12`. Reject nonconvergence. Set `R=X`, convert to normalized quaternion, canonicalize sign (`w>0`, or if `w=0`, first nonzero x/y/z positive), and recompute signed scales by column projection `dot(R_i,c_i)`. Recompose `Lhat=T·R(q)·S`; all threshold comparisons use unrounded f64 values, with diagnostics rounded only for display.

Reject unless `||linear(L*-Lhat)||_F / max(1,||linear(L*)||_F) ≤ 10^-10` **and** `||Δt_world||_2 + r·||ΔA_world||_2 ≤ 10^-6 m`, where `Δ = WnewParent·Lhat−Wold`, `r` is the declared object/subtree local bound (≤`10^3` m), and the matrix norm is spectral (a conservative Frobenius bound may be used). This bounds displacement of every supported point, does not loosen with distant world position, and rejects shear rather than projecting it visually. Use a proper quaternion and signed parity for reflected static visuals; render normal/tangent/winding, physics shape and skeletal consumers each declare support, bake or reject. `preserveLocal` keeps exact stored TRS and explicitly changes world pose. A 45° rotated object under a `(2,1)` new parent requires nonorthogonal local columns and fails the residual. The rejection reports `base SourceRevision`, object/parent IDs, condition, linear/spatial residuals, thresholds and `preserveLocal` alternative. Logical SourceRevision, checkout mirror, active W1 generation and product manifest remain unchanged; the metadata root generation may advance solely to durably record the rejected outcome.

## 6. W1 typed access and structural publication

W1's public runtime handle is `(WorldEpoch,slot,generation)`; its private side table maps to current `hecs Entity`. That backend token may persist **inside W1's identity table** but never leaves W1; query borrows are stage-bounded. F3 schema IDs/field codecs do not use Rust `TypeId` or hecs serialization. F1 registers systems as `(phase, read component/resource IDs, write IDs, explicit before/after, authority role)` and rejects conflicting unordered writes, unknown schema/phase and forbidden cross-role mutation. A stage-scoped `WorldRead/WorldWrite` resolves public handles and exposes typed views only for declared access; borrows cannot cross a structural barrier. Order-sensitive queries sort stable IDs before reduction. Structural commands are `spawn/despawn/add/remove/reparent` with expected world/content/region epochs, stable IDs, dependency and product leases, plus a deterministic order key. No system receives raw `hecs World` or `Entity`; disallow `spawn_at`, `clear` and backend freelist restoration.

For an **authoring or streamed-region transaction in standalone/editor play**, validate and reserve the complete active dependent closure and pre-cook products asynchronously. At a pre-tick barrier F1 enters visible loading/pause, captures the exact committed authoritative X[n] (including all provider state needed to resume, which can exceed P7's durable save codec), and constructs a replacement W1 generation **off-world** from that capture plus the candidate source/overlay, binding staged P3/P5/E1 representations. A provider unable to transfer or explicitly reset a state under its contract rejects live activation and requires session restart. No authoritative tick advances during this first correctness-path construction. It may rebuild the whole ordinary-component store, with O(N) time and old+new peak bytes. Reserve `M_live + M_staged_W1 + M_provider_replacements + M_retained_snapshots + M_F4_old/new_products + M_scratch + headroom`, with shared hashes charged once and GPU/physical memory accounted separately. Apply the native 4,096-static/32-skinned/128-body/16-nav and mobile 1,024-static/8-skinned/32-body/8-nav reference workloads to that formula before I2; a target whose peak does not fit rejects or shows loading before world mutation. Recheck source, product and active-set generations, then swap the single W1 generation pointer plus required owner representations/manifest and resume; old generation remains leased until readers retire. hecs is not asked to roll back a half-mutated live world. A newly active dependent joins the stage or causes reprepare before pause/commit. Ordinary per-tick gameplay commands may mutate the exclusive world under F1's tick barrier after validation; no reader sees the in-progress tick. Engine-managed events/effects are buffered until tick commit; an unexpected failure after mutation is a terminal fault for that world generation: publish no X[n+1] or buffered effects, stop that session and recover from the last valid in-memory/durable checkpoint; do not claim in-process rollback or reversal of arbitrary native external effects. If full-generation staging/pause cannot meet a named workload's budget, a later scoped copy-on-write/undo implementation must prove the same atomic publication before replacing it. This is a cost limitation of the initial implementation, not permission to expose partial activation.

**Initial active N1 server match:** preload and validate its entire finite authoritative gameplay region/collision/nav/query closure before accepting peers. No authoritative source/content/region structural activation or full-world pause is allowed during that match; network interest changes visibility only and cannot unload required solver support. Source edit/recook produces a future build, never mutates the live match. A request to enter unsupported/unloaded gameplay space rejects against the match's predeclared bounds; expanding it requires a new match or a separately specified non-stalling staged server transaction protocol. Client replicas may locally pause their own synchronization/view during a content rebuild while the server continues. This restriction fits the four-player/128-replicated-entity initial profile and avoids contradicting N1's slow-client/server-tick rule.

## Normal/adverse closure traces

| Trace | Required result |
| --- | --- |
| T1 reparent of a static prop on admitted R | F3/W1 compute authored matrices from R; TRS/consumer checks pass; immutable R+1 root/outcome CAS; F4 cooks; staged W1 generation commits at tick; checkout may remain `not-materialized`. |
| Shear reparent or dynamic pose used as source | Validation rejects **before** source CAS and W1 staging. Logical SourceRevision R, active world, checkout and private play remain unchanged; only metadata root generation may advance to durably record the rejected token/outcome. |
| Git branch switch while T1 edit prepares | Explicit sync and T1 race on one root generation. One wins; other retains candidate/conflict. Watcher never activates intermediate checkout. |
| Crash after accepted root, midway through managed mirror | On restart root/outcome R+1 and its blobs verify; mixed checkout is conflict, not replayed over new branch. Build reads R+1 immutable tree. |
| Crash between blob flush and SQLite/IDB root commit | Old root remains selected; orphan bytes have no accepted outcome and are GC candidates after pin/grace checks. |
| Desired R+1 accepted, cook fails, prior checkpoint uses R | Desired R+1 stays pending/failed; restore exact R checkpoint tuple; never apply R overlay to R+1 source. |
| Private play save and live server match | Play save root uses its private authority/source/build; server match and server-save root remain pinned to their own gameplay revision. Client/replica cannot publish either root or apply back. |
| GC races source publication | Blob marked deleting cannot satisfy root CAS; publisher restages/pins. Published root closure cannot be reclaimed until root replacement and reader/retention release. |

**Design closure:** identities, file/record/root syntax, CAS/outcome order, failure states, storage adapter guarantees, checkout behavior, GC exclusion and TRS numerical admission are selected here. D1 owners must reconcile the two shared contracts and producer/consumer modules before calling the design integrated. **Unrun qualification:** test SQLite/IDB adapters with forced process/power loss where possible, quota/storage eviction, concurrent branch/tool races, hecs target/license and W1 staging cost, transform fixtures including scale/reflection/large coordinates, and artist preview. A successful prototype is evidence for this design, not a substitute for the mechanisms above.
