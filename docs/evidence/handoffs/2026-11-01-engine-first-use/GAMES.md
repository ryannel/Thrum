# First-use game journeys: programmer audit

1 November 2026. Three **paper journeys**, not running games, implemented APIs, observed usability or measured timings. I read [the developer experience](../../../design/ENGINE-EXPERIENCE.md), [the prior scenarios](../../../design/SCENARIO-WALKTHROUGHS.md), [composition](../../../design/COMPOSITION.md), [the brief](../../../design/ARCHITECTURE-BRIEF.md) and [the open audit](../../../design/ARCHITECTURE-AUDIT.md). These journeys deliberately begin one step earlier than the prior cases: a programmer who knows how to code a game but does not know this engine's vocabulary. No CLI spelling, file format, function name or target certification is assumed. A01–A05 remain open.

## 1. Overhead tactics, WebGPU browser demo

**Intent.** Make a small elevated hex board where clicking one unit shows legal moves and a push attack can knock another unit off a ledge. Share a link to a browser demo. A programmer would first look for a minimal 3D browser starter that already has a scene, overhead camera, pointer-to-world selection, lit placeholder pieces, one rule system and a target profile. The current documents say examples should expand into ordinary source, but do not define the starter inventory or tell a newcomer whether an overhead game should select orthographic or perspective projection, what the first scene contains, or how to inspect its target qualification. This is an entry-path decision, not an engine module design.

**First mechanic.** The programmer adds board-cell data, an active-player turn record and a rule that computes legal destination cells. A pointer action selects a cell; a move command changes game-owned turn/board state, and the view moves the piece after the accepted rule. The tutorial needs to show where an action enters, where a rule is registered, how it declares read/write state, and how one rejected command is inspected. Without that one complete vertical example, “direct typed registration” still leaves the first-time user guessing whether the move belongs in scene data, a per-object script, a system, or a package. The push attack uses a query or authored board topology; it does not need a dynamic rigid-body solver. Any collision used for picking is named separately from solved motion, so choosing the simple starter does not silently choose game physics.

**Composition.** Keep world/content, input/actions, picking/camera, UI, lighting, meshes and game rules. Omit navigation, rigid dynamics, terrain streaming, weather, visible sky, water and animation. Add sound only when the author asks for it. The proposed [composition example](../../../design/COMPOSITION.md#two-games-one-engine) selects “rigid-body queries” for an overhead browser demo; a first-use recipe should say whether board picking alone requires that selection, and distinguish ray/shape queries from a simulation. A plain fixed key light should be valid; cloud attenuation is an optional later choice, not an unexplained default prerequisite.

**Play, change, deliver.** Start isolated play from an accepted revision; click a move, inspect why a destination is legal, stop, and find the authored board unchanged. Change a move rule in source, explicitly admit the coherent edit, then rebuild/restart play. Build the declared WebGPU browser profile with required meshes, UI/font and shader variants. A plausible failure is that a newly added outlined selected-piece material lacks a required browser pass variant. The beginner needs an error naming the piece/material, pass, target and supported fix (choose a compatible material or implement/declare the variant), while the last valid build stays identifiable. “Desktop preview works” cannot be treated as browser readiness. This is an A03 obligation, not a hypothetical implemented diagnostic.

## 2. Stylized third-person exploration, desktop first

**Intent.** Make a compact hillside with a walking character, a bridge, and a lantern that opens the bridge after interaction. Target Mac/PC first; later offer a bounded WebGPU browser excerpt. The programmer needs a third-person starter whose character controller, chase camera, input actions, collision, a basic authored light, a simple material style and a scene are already connected and visible in editable source. The proposal supports these pieces but does not identify the minimum usable character path: whether animation is optional for a placeholder character, which owner moves the character, which coordinate/unit conventions the starter exposes, or what happens when both controller and animation request motion. These choices should be settled in a starter and documented at the point of first edit, not presented as the full P3/P4 scheduling design.

**First mechanic.** Add a lantern interaction that changes a game-owned `bridgeOpen` state; collision/scene activation follows that state at a declared world boundary, and presentation plays an animation/light cue. The programmer should see the small rule as ordinary typed game code, with an action and inspectable state change. If a third-person starter forces a quest package, inventory package, weather stack or full animation graph to express this switch, it contradicts the advertised direct game registration. The bridge must not become traversable merely because its visual mesh moved; its collision owner needs the same committed change. A save decision is explicit: if the bridge state must persist, opt it into the game's save schema; otherwise restarting begins from source. “Persist all components” would store transient poses and editor test state accidentally.

**Composition.** Keep character control, camera, body collision/query, input, UI prompt, basic render/material/light, and the rule. Add animation/audio only when desired; add terrain and vegetation only when the hillside requires them. Omit water, atmosphere simulation, navigation, weather, cloud rendering and rigid-body piles. Style should begin with material/light choices within the shared scene-linear/display convention. A stylized starter should not require writing a renderer provider to obtain a coherent simple look; conversely, its style preset must expose which effects and lighting assumptions it actually expands to.

**Play, change, deliver.** Play, open the bridge, inspect the rule and collision state, stop, then change the lantern placement in source. If an authored placement is adjusted during play, apply back only that selected property against its pinned base; bridge progress stays in the private session. Build Mac/PC, then separately check the browser excerpt. A plausible failure is adding a character material/skin whose required browser shader or texture product is unavailable. The author needs a target-specific dependency path and the option to narrow the browser content or choose a supported presentation without silently dropping the skin/collider or changing bridge semantics. Browser size and performance remain unqualified until measured on a named build/device.

## 3. Touch puzzle/building, native mobile ambition

**Intent.** Make a small room where players place and rotate wooden blocks on a grid to complete silhouettes, undo moves, and resume after an interruption. The programmer searches for a native mobile 3D starter with touch selection/drag/rotate, semantic buttons, a bounded scene, simple lights and a named target. The current recommendation says mobile native is an ambition; it does not supply a certified starter or device/OS floor. The first-use path must label target preparation and packaging as designed/qualified/unsupported per target, not imply that a desktop play session proves a store build.

**First mechanic.** A touch action proposes a placement. A game-owned rule checks occupancy and orientation, commits the grid state, and emits an accepted/rejected result for view/UI/audio. Undo reverts an intentional game command, not an editor source operation. Drag preview is presentation until release/acceptance; it cannot author the scene or a player save through the editor. The starter should show one complete action-to-rule-to-feedback trace and the explicit choice between a durable puzzle solution and session-only progress. An authoritative rigid solver is unnecessary if blocks snap to cells; static picking and optional overlap queries suffice. The engine should not silently instantiate dynamic bodies because meshes look physical.

**Composition.** Keep touch actions, focus/gesture arbitration, camera/picking, UI/text, meshes, simple lighting, game rules and a save adapter if progress is durable. Omit terrain, navigation, character animation, weather, sky, water and rigid dynamics. Add an audio cue if useful. A mobile quality tier may reduce presentation cost, but it may not change grid occupancy, accepted placements, undo history or save meaning. The developer needs a visible default for what happens on suspend: pause immediately, complete/abort the in-flight command at a known boundary, and checkpoint only committed state. Exact lifecycle and save mechanics remain A01/P7/T2 design.

**Play, change, deliver.** Play with a private test save, solve part of a puzzle, simulate interruption/resume, inspect the committed grid and undo record, then stop without touching a player's slot. Change a piece recipe in source; schema compatibility must be checked before an old private save is resumed. A realistic failure is a revised block shape that no longer fits a saved placement. The tool should report the incompatible source/save identity and offer a deliberate migration or a fresh test save; it must preserve the old save and last valid source/build. Native iOS/Android packaging, touch behavior and sustained thermal cost require named-device qualification. A browser preview can help inspect rules but cannot stand in for that qualification.

## Bounded findings for the design owner

1. **Define three editable first-use recipes, not a feature catalogue.** Each should reveal the exact ordinary source it expands to, its scene, selected capabilities, omitted work, named target and one complete mechanic. The three journeys above need different defaults. Today the path from “create an example” to “write direct typed game code” is underspecified in [ENGINE-EXPERIENCE](../../../design/ENGINE-EXPERIENCE.md#the-ordinary-loop). This is the highest first-use friction. Graduation is the test: after replacing the sample scene and deleting its sample rule, the game should still use the same documented setup and build path, with no hidden sample-only registry or mode.
2. **Teach the smallest rule boundary with one end-to-end trace.** Show action → validation/rule → committed state → presentation/inspection, including a rejected action and a save choice. The author must know when a component is plain game data, when a system owns a rule, and when a specialized engine owner is required. Keep direct static registration; do not make the mechanic a distributable package.
3. **Make defaults inspectable and semantic.** Camera projection, coordinate units, light/style expansion, picking method, collision versus solver motion, save routing and target tier cannot be hidden “magic starter” choices. A recipe can pick a named default; changing to a different physical model requires a deliberate choice and validity check. Present only the handful of decisions relevant to that starter, with the expanded plan available on inspection.
4. **Give first-time users a target truth table and prerequisite check.** A desktop run, WebGPU browser build and native mobile build have different prerequisites, content products and qualification. Before the first play/build attempt, report the selected target's pinned compiler/runtime/content-toolchain requirements, which are present, and the next actionable missing item. Establish one supported baseline path before asking the newcomer to install other target SDKs. The build report should state selected target, supported profile, missing requirement, and evidence status. Do not infer browser or mobile readiness from the desktop path. A03 governs actual shader/product closure; mobile delivery remains unqualified until implementation and device evidence. A preflight is a recommended contract, not an implemented command.
5. **Resolve the source/play/save boundary before calling any starter complete.** Newcomers will confuse editor undo, game undo, play-state progress, authored apply-back and player saves unless the tools use distinct labels and examples. An isolated process helps, but private save routing, source-write authority, conflict/recovery and side-effect limits still need A01/A02 mechanisms.
6. **Keep the first successful build small.** Browser tactics can omit a physics solver and clouds; the exploration scene can omit weather/water; the mobile puzzle can omit almost every world subsystem. Validation must explain an added prerequisite locally, instead of silently activating a broad package. “No avoidable work” remains a design target until actual builds measure it.
7. **Bound the files and registrations a beginner must edit.** Canonical files and explicit setup are useful only if a new rule does not require hand-editing a scene record, component schema, game registration, target manifest, cook recipe and package descriptor merely to display one state change. Some declarations are necessary for identity, persistence and access validation; the starter should co-locate or generate the mechanical declarations and show their expansion. No implicit directory scan or hidden auto-registration should decide rule order or authority. The first-use proof should count user-edited files and explain each one; exact formats remain D1/T1 decisions.

## Proposed beginner path

Choose a **game-shaped editable example and one named supported target** → run a prerequisite check for that target → see its one-page expanded choices, declarations and omissions → change one scene object → write one typed action/rule and inspect accepted/rejected state → play an accepted revision in a private session → stop, optionally apply back one authored property, then build/export and read a target-specific readiness report. A code/schema change restarts play; source files remain canonical. Replace the sample rule and scene with original ones to verify the starter graduates into an ordinary project. Advanced providers, package descriptors, domain physics and other target SDKs appear when a concrete game need introduces them. This path is a design recommendation and a future dogfood script, not an available workflow.
