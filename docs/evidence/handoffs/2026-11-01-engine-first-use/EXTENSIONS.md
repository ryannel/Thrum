# First use: bring your own code and choose modules

1 November 2026. Paper dogfood of the proposed custom engine, not a running SDK, user test, measured iteration time, or promise of a binary plugin ABI. The host is custom; Rust is the current recommendation, not a selected compiler/API. Mac, PC, browser and iOS/Android are ambitions with unqualified device and package support. The traces start from a working scene with an accepted source revision and a selected target. They use the [developer recommendation](../../../design/ENGINE-EXPERIENCE.md), [composition rules](../../../design/COMPOSITION.md), [shared contracts](../../../design/CONTRACTS.md), [play systems](../../../design/modules/PLAY-SYSTEMS.md), [environment](../../../design/modules/ENVIRONMENT.md), and [open audit](../../../design/ARCHITECTURE-AUDIT.md). Any API-shaped wording below describes a required operation, not an implemented command or selected syntax.

## The smallest useful distinction

| Developer brings | Minimum engine integration | What it does **not** imply |
| --- | --- | --- |
| Pure algorithm/library called by game code | Normal source dependency and a call from a game-owned system; no engine registration for the library itself | No package descriptor, provider binding, engine-controlled lifecycle or plugin ABI |
| Game-owned state/rules | Typed component/resource schema if persisted or inspected; direct system registration with declared reads/writes, phase and requirements | No reusable feature package merely to add one rule |
| Replacement for a selected engine service | One explicit provider binding to that service's public contract, plus its state/product/target obligations | No global service locator, second world/physics/GPU authority or promise that another provider's private state migrates |
| Distributed reusable feature | Optional versioned package descriptor that declares the same registrations, dependencies and products | No mandatory packaging for local game code and no live executable unload |

The first-use UI/docs should lead with these four choices. “Add a module” is otherwise ambiguous: an imported library, a game system, an optional engine feature and a replacement provider have very different costs.

## Journey 1 — ordinary AI library and turn rules in a board game

**Known scene.** S01's overhead browser board already has tokens, picking, a camera and a working visual target. The creator adds a Rust decision library for legal-move search and writes game-specific turn rules. The library returns candidate actions from a supplied board snapshot; it is not an engine AI provider. The game owns turn, piece and objective state. A turn system consumes one admitted action, checks the rule, changes game-owned state at the declared world barrier, and emits an identified move/end-turn event. Inspection should show the token, current side, source rule and why a move is illegal. If the decision library uses nondeterminism, its seed/input/output or chosen action must be captured according to the game's replay envelope; the engine cannot infer reproducibility from a crate dependency.

**Shortest path from working scene.** Add the source dependency; define the few game data fields and their save/inspection meaning; register the rule and AI decision system directly in static game setup with their access and causal order; update the scene's token recipe to require those fields; validate, rebuild/restart play and make one move. Only the game system using the library needs registration. A pure helper used inside an existing system needs no new engine declaration. If the rules do not require physics, navigation, animation or weather, they stay absent. The browser target builds the same authoritative turn code; a touch target changes input mapping and presentation products, not legal moves.

**Failure, change and removal.** Missing required token data fails scene admission with the token and rule requirement named. Two systems claiming ambiguous writes to turn state fail schedule validation, rather than acquiring an order from registration order. If the library will not compile for Wasm or mobile, that target is unsupported until the author chooses a portable implementation or explicitly authors a different rules variant; a native success must not certify it. To remove the library, change the game-owned system or remove the AI-controlled opponent, rebuild, and keep rule/save schema readers needed by retained scenes and saves. Removing the whole turn feature while tokens/saves still require it fails dependency validation or needs an explicit game migration. A failed rebuild leaves the old accepted player/build identifiable; source recovery still follows A01/A02.

**Friction test.** Requiring a package manifest, provider implementation, lifecycle hooks, schema for library-internal search nodes, or a physics/nav service for this case is needless. The legitimate burden is declaring actual persistent game state and ordered writes. Before a starter can advertise “bring your own code,” a tiny example must show this direct path and a missing-field/conflicting-write error. Exact syntax is D1 work; this trace is not evidence that the path is fast in practice.

## Journey 2 — external physics or navigation implementation

**Known scene.** A third-person room already has a moving character, collider and path request using a selected P3 physics and P5 navigation implementation. The developer evaluates an external solver or path library. First ask which boundary it crosses: a path-search algorithm called inside the existing P5 owner can be an ordinary library; replacing P5's tile/query service is a provider change. A rigid-body solver that owns contacts and solved pose is a P3 provider change. These are separate choices, even if one crate offers both.

**Shortest path for a P3 replacement.** Pin the external library/version and audit license, dependencies, native/Wasm/mobile compilation and required features. Adapt stable IDs and cooked shapes to solver handles, but keep handles private to P3. Bind one selected P3 provider for the scene/world scope in static setup. It must support the scene's actual body modes, casts, sensors/joints, contact events, snapshots and fixed-tick/query semantics; declare unsupported cases instead of emulating them silently. P3 returns resolved pose/velocity and identified contacts through C02/C03; W1 publishes the authoritative transform once. F4/W2 prepare matching collision products before the room activates. P7 saves durable body state through a declared provider/save schema, not raw transient handles. Run the same character/contact fixture headlessly, then on each intended target. A native build and a Wasm compile are narrower than browser device qualification.

**Shortest path for a P5 replacement.** Keep P5's public path request/result and generation semantics, with W2/F4 owning the region/tile product lifecycle. The adapter maps agent class and terrain products to its private representation, returns a corridor/guidance with tile and obstacle generations, and cancels or rejects stale async results. It may not write the character transform; guidance goes through the movement policy and P3. A library used only for a game-specific board graph can remain inside game code without claiming to replace P5.

**Mismatch and recovery.** The existing scene may require a joint type, continuous contact, agent radius, off-mesh link or streaming boundary the candidate cannot supply. Profile/content validation must report the consuming object, required operation, candidate support limit and target; no implicit fallback to a different physical behavior. A failed preparation retains the old active plan. Switching a running world to another solver is not the baseline: stop, rebuild/restart from accepted source, and validate saved-state restore or an explicit migration. If the candidate cannot read retained saves, keep the old restore path or decline the switch. To uninstall, remove the binding/dependency only after rebinding or removing all required bodies/paths/content and preserving restore closure; a clean empty build is insufficient if an existing scene/save still requires it.

**Friction test.** The proposal already has the right authority rule, but “implement the physics/navigation contract” hides material first-use effort. D1/P3/P5/F4/W2/P7 need one discoverable contract sheet each: required operations, units/time, ownership, lifecycle, content products, save data, error/absence meanings and supported target claims. Give a small conformance fixture for the *chosen* interface and a mismatch diagnostic. Avoid a broad universal solver interface that erases joints/contact or imposes streamed nav on a single room. A provider authoring path is a specialist feature; the starter needs a built-in selected provider and a clear explanation of how to change it, not a complete third-party solver SDK.

## Journey 3 — custom water or atmosphere model

**Known scene.** S04's coast has a prescribed sea, authored river and a still pool. S06's vista has fixed environment light and local fog. A specialist wants to bring a custom sea-wave/contact model or dynamic atmosphere. The first task is to name the output the game actually needs. A visual water material is a V2/V3 render extension; a contact surface or flow field is an E1 water provider used by P3/gameplay. A sky background is presentation; direct Sun transmittance, environment illumination and aerial media are separate outputs. One custom model may supply several outputs, but each retained consumer must see one named owner and declared validity.

**Water path.** Start with one region/model and state its support in space/time, units, query accuracy and available surface/flow/contact quantities. Bind it explicitly for that domain; let E1 own the fluid state/query and P3 own body integration. Its force samples enter P3 once at the named tick boundary; any returned disturbance has an identified receiving water step. The render representation may derive finer waves, but cannot silently become a different gameplay contact surface. F4 cooks required geometry/query/shader products for the selected target and F2 checks the scene's actual consumers. Where the custom sea meets the river, A04 is still open: choose and document a visual-only seam, prescribed/open boundary or a specifically designed conservative coupling with transferred level/flux/time and a single contact-query owner. No generic solver-coupling framework is justified by this scene. An unsupported falling/volumetric region must report absence, not a fabricated height sample.

**Atmosphere path.** Declare which of background, environment light, direct transmittance and local/aerial media the new model supplies, along with its spatial interval, spectral/RGB basis, time support and render products. V3 remains the one light/media composition owner; V1 owns device/submission and V4 owns final reconstruction/display. If the custom atmosphere overlaps local fog, A05 prevents treating two independently preintegrated whole-ray `(T,L)` pairs as exact overlap. The creator must use compatible coefficient/source access for joint integration, a joint preintegrating owner, disjoint segments, or an explicitly approximate policy; unsupported exact composition fails validation. A dynamic sky can replace a fixed sky for the vista without replacing the whole renderer. A top-down game may retain light/cloud attenuation while drawing no sky.

**Target mismatch, removal and help.** Shader/pass variants, depth/history inputs and GPU feature limits must be declared for each selected target/tier; A03's finite demand and readiness closure is not yet designed. A desktop model may lack a browser/mobile implementation. The target must fail with the missing product/input/provider path, or use an author-selected compatible presentation alternative that preserves any retained physical/light semantics. Removing a water or air model requires rebinding/removing its consumers and checking persistent region state/saves; changing gameplay water or source air state is a restart/migration question, not a live quality toggle. The specialist needs an example domain and an output/consumer diagram, a query inspection at a point/ray/time, and a target support report. These are later specialist docs and fixtures, after A03–A05 and the shared E1/V3/P3/F4 boundary are reconciled. The starter only needs a built-in simple water/light choice and an intelligible “this scene requires X” explanation.

## Findings for the coordinator

| Finding | Concrete action | Timing |
| --- | --- | --- |
| The simple path is at risk of inheriting specialist ceremony | Make direct game registration the documented first path; show pure imported helper versus persistent rule state. Keep descriptors optional for distributed reuse. | **Before starter** |
| “Module” obscures what is being selected | In setup inspection, show selected capabilities, concrete providers, target, required content and why each is present. In docs, distinguish source library, game system, provider and package with one example each. | **Before starter** |
| First-use errors need a causal path | Diagnose from the scene object/field or system through required capability, selected provider, unavailable operation/product and target, with the source revision and old valid build visible. Do not merely say “profile invalid.” | **Before starter**, then enrich per provider |
| Code/library portability and target certification are different | Report compile/dependency, content/product readiness and actual device qualification separately for Mac, PC, browser, iOS and Android. Do not allow an alternate target implementation to change game rules silently. | **Before multi-target claim** |
| Provider integration is conceptually defined but not yet executable | D1 with P3/P5/E1/V3/F4/W2/P7 should specify narrow typed registration, ownership, failure, save and lifecycle contracts and a small per-contract fixture. Do not invent a universal plugin ABI or generic provider search. | **Specialist provider work**, with core hooks designed before APIs freeze |
| Uninstall/recovery needs dependency and save closure, not just removing a crate | Validate retained scenes, instances, queued work and saves; keep readers/migrations, pin old active revision on failed change and name what restart restores. A01/A02 still own exact source/session recovery. | **Before starter** for ordinary rule changes; **later** for provider removal |
| Environmental replacement cannot be truthfully demonstrated yet | Close A03 shader demand and A04/A05 water/media semantics before publishing custom model examples as supported. | **Later specialist gate** |

The useful starter proof is one accepted board scene where a developer adds a plain library-backed rule, sees its state in inspection, changes code, restarts play, and builds one named target with a comprehensible failure. The useful provider proof is a separate fixture that changes one selected P3 or P5 implementation and demonstrates that authority, saves, target support and failure remain explicit. Neither paper journey closes A01–A05 or establishes real first-use usability.

**First specialist conformance case: one P5 navigation provider swap.** Start with a two-cell character scene whose default P5 implementation returns a corridor to a destination while P3 alone moves the body. Replace only the selected P5 implementation with an adapter around an external path library. The fixture needs one supported agent class, cooked walkability and a border portal, a path request with stable ID, and a moving obstacle or cell revision that makes an in-flight result stale. Check that the alternate provider returns the same *public meaning* (path or declared unavailable/stale, target and tile/obstacle generations, bounded request/cancellation behavior); it must never apply a transform or treat unloaded space as traversable. Then build the scene for one named target, remove its binding with a dependent path-seeking actor still present, and require a diagnostic naming that actor and missing P5 service. Rebind the prior provider and confirm that restart admits the scene again. This is a bounded conformance recipe, not a claim that every nav algorithm shares the same quality, cost, supported agent classes or platform set. Built-in and external implementations meet the same contract **for the capabilities and targets each claims**; the public seam must not be weakened to make an arbitrary crate pass.
