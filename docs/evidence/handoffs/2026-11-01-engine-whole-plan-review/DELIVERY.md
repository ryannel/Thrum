## Findings new to this review

### D1 — No named thin rendered/exported milestone precedes the full integration scene

**Severity:** high delivery risk. **Owners/gate:** programme coordinator with F1/F2, T1/T2, P1, and V2–V4; settle before I3/I4 exit criteria. **Evidence:** `CONSTRUCTION-PLAN.md:45-48` makes I3's character motion/animation, renderer, audio/UI and environment provider one dependent package after I2, with I4 target packages following I3. Its public starter and empty-project paths need an I3 action/rule/state/feedback result and relevant I4 export (`:108-124`), while the reference scene adds a skinned character, moving body, masked and transparent surfaces, lights, instancing, sound, focusable UI, two cameras, streaming, editing, save, tier switching and suspend during pending content (`:126-134`). The experience document permits an unlit simple scene and headless-first work (`FROM-SCRATCH-WALKTHROUGHS.md:27-30`).

**Failure path:** the plan already promises a game-owned headless rule path at I1 and expressly says the reference scene is not every creator scenario. Yet its first *rendered and exported* game has no independently named acceptance gate before the broad I3/I4 work. If a nonessential component, such as spatial audio or an environment visual provider, is late, the smaller game path can remain unproven. This delays the first feedback on game-code iteration and target handoff until after expensive integration. The paper walkthroughs are good design tests but do not replace this executable learning loop.

**Small correction:** retain I1 headless and I2 content/edit gates, and name an early I3 rendered interaction using simple geometry, one camera, plain material and direct feedback, plus its relevant one-target I4 development export slice. Include a clean recipient handoff and an absent-capability/package-cost check. Then retain the full two-view, animated, lit, streamed reference scene as the *I3 integration* gate. This changes sequencing and exit evidence, not the target ambition or required eventual features. The existing `CONSTRUCTION-PLAN.md:118-123` already hints at this split; make it operational in the package table.

### D2 — Native mobile shell feasibility can surface after host contracts have hardened

**Severity:** high schedule/portability risk if mobile is in the first delivery set. **Owners/gate:** F1/P1 platform owner and T2, with A1/U1 and F4 consumers; after the D1 lifecycle design, before substantial I2/I3 integration. **Evidence:** the plan includes native iOS/Android as working targets but calls shells, packaging and devices unqualified (`modules/PLATFORM-RUNTIME.md:7-15,31-41`). The platform module's own validation order tests minimal native/web/headless substrate first and iOS/Android shells immediately afterward, before renderer portability (`:112-119`). The programme's implementation table instead gives I1 “selected platform adapters,” makes I2/I3 content and presentation depend on that substrate, and does not package native mobile variants until I4 (`CONSTRUCTION-PLAN.md:40-49`). D0 is told to name separate authoring OS, build host and player/backend support (`:57-60`), but the early shell result is not a stated I1 checkpoint.

**Failure path:** desktop/web clock, surface, audio and content-source APIs can become fixtures of I2/I3 before the first native app proves callback ownership, suspend, touch/IME, audio interruption and asynchronous asset availability. A late mismatch then forces a shared-host rewrite instead of a narrow adapter fix. A Rust target triple or `wgpu` backend compiling is explicitly insufficient (`modules/PLATFORM-RUNTIME.md:29,41`).

**Small correction:** carry the platform module's existing early shell validation into the master I1 sequence. For *both* mobile families, launch on one named development device, tick a headless-compatible world, create/lose/recreate a surface, route one touch and IME event, interrupt audio, read boot-critical local content, and produce a development package. Record build host, SDK/toolchain, backend and unsupported features in the D0 matrix. Keep sustained thermal, visual parity, store-ready packaging and broad device coverage at I4. This is a compatibility proof for the chosen host boundary, not an early mobile content port.

### D3 — The reusable SDK has no explicit cross-release support promise

**Severity:** medium maintenance/release risk. **Owners/gate:** T2/F2/F3/F4 and SDK owner; state a policy before an externally consumed SDK release, and prove it before the first breaking upgrade or promoted external game. **Evidence:** release-matched starter, tools, assets, docs and dependency versions are required (`ENGINE-EXPERIENCE.md:36-46`), and package locks carry exact contract/schema/provider versions (`COMPOSITION.md:96-109`). T1/F3 defines authored-schema migration and P7 save migration separately (`modules/TOOLS-DELIVERY.md:184`); T2 checks a single release candidate's source/product/device closure (`:192-196`). The plan says engine updates should not silently rewrite game code (`ENGINE-EXPERIENCE.md:43-47`), but it does not state which older SDK/project releases remain supported, whether upgrading a game is an offered workflow, or what compatibility is promised for public source APIs, cook products and save readers *between engine releases*.

**Failure path:** game A pins release R, game B starts on R+1, and an upstream Rust/`wgpu` or schema change ships. Both releases may individually pass their current target gates, yet game A's team cannot tell whether a project upgrade is supported, must rebuild/re-cook from masters, can reopen old saves, or should remain pinned indefinitely. Without a policy, dependency security/API updates and platform SDK churn create an unbudgeted maintenance obligation, especially across five target families. The existing version fields identify incompatibility but do not decide support lifetime.

**Small correction:** select a finite compatibility policy: supported SDK release window (or explicitly pinned-release-only baseline), source API change rule, required recook/rebuild behavior, save-reader/migration promise, and how a project detects an unsupported upgrade before mutation. Add a tiny consumer project or previous-supported-release fixture to T2's clean-source handoff and release checks. Do not invent a stable binary plugin ABI; `COMPOSITION.md:48,127-129` rightly excludes that baseline.

## Existing open work and deliberate selections

A01–A05 remain the current architecture audit's explicit gaps: play session, external source admission/recovery, shader demand/readiness, water-domain exchange, and overlapping media (`ARCHITECTURE-AUDIT.md`; `CONSTRUCTION-PLAN.md:7-13`). They are prerequisites for their dependent D1/D2 mechanisms, not findings discovered here. J01–J04 already capture composition/reuse/code-edit follow-ups. Exact minimum OS/device/browser, content scale, numerical budgets, physics/audio/text libraries, native SDK glue, shader representation and ordinary networking scope are expressly D0–D2 decisions (`CONSTRUCTION-PLAN.md:15-28,42-44,57-68`; `WHOLE-ENGINE-REVIEW.md:55-57`), not evidence of a contradictory current architecture. Their gate owners must still put a date/artifact against each selection.

The timing, memory and download numbers in `modules/PLATFORM-RUNTIME.md:100-110` are labeled planning envelopes. They should become admission thresholds only after D0 fixes actual content, resolution, hardware, build host and workload. The proposed two ticks per 30 Hz mobile frame, async streaming, two retained views, audio/UI and thermal overhead must be included in the same measured p95/p99, peak-overlap and sustained-power result (`:49,100-110`; `modules/TOOLS-DELIVERY.md:186-196`). An isolated renderer median or candidate-level AI speedup is not whole-engine success. The AI campaign plan already calls for separately versioned evaluators, A/A noise checks, independent final runs and integrated candidate promotion (`CONSTRUCTION-PLAN.md:70-88`; `modules/TOOLS-DELIVERY.md:198-215`). I found no basis to call that an integrity defect at the design level; implementation has not earned the claim yet.

## Strengths and scope discipline

- The custom host and no-Bevy-runtime choice is respected while leaving mature commodity kernels available for physics, audio, text, formats and compression after target/license/dependency audits (`modules/PLATFORM-RUNTIME.md:13-15`; `CONSTRUCTION-PLAN.md:136-147`). This reduces needless original numerical and codec work without surrendering world/time/lifecycle ownership.
- Causal clock, immutable snapshot leases, asset/product publication, private play sessions, source revision and GPU lifetimes are treated as different authorities. The lifecycle and storage plans budget old/new overlap and preserve selected masters rather than assuming caches are backups (`CONTRACTS.md`; `STORAGE-LIFECYCLE.md`; `modules/TOOLS-DELIVERY.md:178-184`).
- The maturity ledger makes a design, a compiled package, a functioning target, an accepted image and a qualified device different claims (`MATURITY.md:8-22`). The papers mark estimates and prospective campaigns honestly.
- The plan already defers universal provider search, gameplay hot removal, binary reload, a scripting VM, a full visual editor, remote optimization workers and advanced I5 rendering until a specific game or measured constraint justifies them (`COMPOSITION.md:127-160`; `CONSTRUCTION-PLAN.md:62-68,79-82`). Keep those deferrals. Prioritize the first executable paths and target shell probes above new infrastructure.

## Readiness verdict

The design is **ready for D0 and coordinated D1/D2 detailed commissions**, with A01–A05 and the three delivery corrections above attached to owner-specific gates. It is **not ready to claim an implemented, performant, artist-usable or five-platform engine**; the ledger correctly says these are unbuilt/unmeasured. I would start I1 only after D0 names a concrete game workload, first development/build hosts, initial devices and the small headless outcome. I would require an early mobile shell feasibility artifact while D1 host contracts are still cheap to change, and I would make the first rendered playable artifact explicit before the full integrated reference scene. This preserves the broad reusable-engine ambition while making failure discoverable early.

## Cross-review after the independent systems and creator reports

I read `SYSTEMS.md` and `CREATOR.md` after completing the independent report. **Retain** the systems review's transform finding at medium severity: `modules/WORLD-CONTENT.md:27` promises preserve-world reparent by matrix inversion while local storage is TRS. A nonsingular inverse can contain shear, so a successful edit could move a static prop or mismatch its collider. This is a representability/validation decision at D1 before I2 scene editing, not a reason to mandate affine transforms everywhere. Require either a representable affine local form with consumer rules or a TRS round-trip check that rejects unsupported preserve-world edits; test scaled, rotated ancestry.

**Retain and narrow** my D1 and the creator C1 as one sequencing correction. The headless game is already an I1 outcome and the reference scene is already labeled an integration workload. The missing artifact is a named, thin *rendered and one-target exported* small game before that broad integration gate. It may be a board/empty-game fixture using only selected capabilities. It must satisfy A01–A03 only where its actual source/play/material path depends on them. Do not read the I3 scene's character, audio or environment list as mandatory features in every runtime profile.

**Retain with later gate** the creator C3 workbench trace. Existing T1 typed edits and multi-selection plausibly support placement, but the minimum artist acceptance list could pass without place/rotate/scale/duplicate, game-camera preview, undo and reimport preserving authored overrides. Put this short spatial-composition fixture in I3's artist-usability claim, not I1 and not as a new editor architecture. **Retain with an even later gate** the shared SDK-upgrade finding: state pinned-only versus supported-upgrade policy before publishing a reusable SDK; require a two-release ordinary-game/extension/save check before the first breaking upgrade or promoted external consumer. A full migration tool is not a prerequisite for the first single-release starter.

**Retain as ledger hygiene, not an architecture blocker** the systems review's leaf-status observation: E1 parent has A04/A05 open while `E1.atmosphere` and `E1.water` leaves show `reconciled` with historical review basis (`maturity.json:650-684,711-717,825-843`). Expose inherited open findings on affected leaves or make parent status visibly controlling before D2 assignments. **Narrow** my platform finding to master-plan reconciliation: `modules/PLATFORM-RUNTIME.md:112-119` already asks for early mobile shell validation; `CONSTRUCTION-PLAN.md:40-49` should explicitly schedule that I1 result before substantial I2/I3 work. This does not accelerate full mobile qualification or add a new mobile requirement.

Recommended master sequence: D0 names workload and author/build/player matrices; D1 closes A01/A02 plus the TRS operation rule and exact source/host boundaries; I1 proves headless semantics and thin desktop/web/mobile shell feasibility for selected targets; I2 proves source/content transactions; an early I3 plus relevant I4 slice produces the small rendered/exported game; full I3 then exercises the two-view animated/environment reference scene; I3 artist acceptance checks spatial composition; I4 qualifies target profiles; later SDK releases test the chosen compatibility policy. A03 follows the first selected material/export dependency, A04/A05 the selected water/media combinations. This ordering preserves the ambitious final engine and avoids making optional capabilities or unbuilt infrastructure universal prerequisites.
