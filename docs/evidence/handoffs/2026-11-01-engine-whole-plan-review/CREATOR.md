# Whole-plan creator and integrator review

1 November 2026. Independent paper review of the custom-engine proposal as a first-time game creator, game technical director and experienced subsystem integrator. I made no canonical design edits, ran no engine or device, and did not inspect the other two current reviewers' drafts. Findings below compare the stated creator promise with the planned construction and qualification gates. They are recommendations, not selected changes.

## Coverage and status basis

I read the current `AGENTS.md`, the repository `repo-structure`, `code-conventions`, `testing` and `engine-architecture` skills, then the full `notes/engine-rebuild/README.md` route. I traversed **all 26 top-level Markdown files, all seven `modules/*.md`, all 12 `research/*.md`, and every module/status group of `maturity.json`** listed in `tmp/handoffs/2026-11-01-engine-whole-plan-review/BASELINE.md` (46 records total). I checked every path and SHA-256 against that baseline: no file was missing or changed during my read. The 12 research files are rationale/prior audit evidence, not 12 additional current decisions. In particular, `WHOLE-ENGINE-REVIEW.md:3-5` labels its former no-blocker conclusion historical; `ARCHITECTURE-AUDIT.md:3-7` and `:148-169` govern the current open A01–A05 queue. `MATURITY.md:10-22` and the ledger distinguish high-level design from unbuilt runtime and unqualified platforms.

I traced four representative journeys: a browser board game's first rule and export (`FIRST-USE-WALKTHROUGHS.md:22-35`), an empty stylized game with original art and a direct rule (`FROM-SCRATCH-WALKTHROUGHS.md:38-63`), an imported room/toon character with reimport and target preview (`FIRST-USE-WALKTHROUGHS.md:100-123`), and a physically demanding two-view world with streaming, saves, quality transitions and mobile interruption (`CONSTRUCTION-PLAN.md:126-134`). I also traced the *next* change after shipping: adopting another SDK release while preserving source, extension and save behavior. The first three findings concern the creator path; they do not reopen A01–A05 or demand a general editor, scripting VM, marketplace, networking or every major-engine feature.

## Ranked findings

### C1 — P1: name a thin rendered/exported game milestone before the broad integration reference scene

**Failure example.** A new creator wants a turn-based overhead board game: a scene, camera, selectable pieces, one push rule, visible feedback, and a browser development export. The product text says small games select few capabilities, game rules register directly, and a rules-first/headless route exists (`ENGINE-EXPERIENCE.md:9-11`, `:56-69`, `:86-100`). The U01 walkthrough explicitly omits rigid physics, navigation, water, weather, streaming and skeletal animation (`FIRST-USE-WALKTHROUGHS.md:22-35`). Yet the ordered construction table names I3 as character motion/animation **plus** renderer, audio/UI and an environmental provider after D2's complete render/character/environment seams, and I4 follows I3 (`CONSTRUCTION-PLAN.md:40-53`). The only named public starter and one-target export gates are then assigned to I3 and a relevant I4 slice (`CONSTRUCTION-PLAN.md:108-124`; `FIRST-USE-WALKTHROUGHS.md:155-165`). A team could complete an impressive integrated character/environment scene while still lacking a specifically gated route that lets the board author ship the small game first.

**Boundary of the claim.** I1 already promises the smallest game-owned extension and a headless profile (`CONSTRUCTION-PLAN.md:32-38`, `:45`); the reference scene is explicitly an integration workload, not every game's required features (`CONSTRUCTION-PLAN.md:101-106`). T1/T2 also say not to delay a simple starter for unrelated environmental adapters (`modules/TOOLS-DELIVERY.md:87-94`). This is a **milestone and acceptance ambiguity**, not proof that runtime profiles force character, audio or environment features into every game.

**Smallest correction / owner / gate.** Under F1/F2, T1/T2 and P1/V2–V4, add one named early rendered-game slice to `CONSTRUCTION-PLAN`: direct game rule, action mapping, simple scene/view, optional unlit/basic material, inspection/restart, a real one-target development export and absent-capability/package-cost check. Reuse I1/I2 mechanisms and A01–A03 closure where the slice actually depends on them; do not invent a second engine or skip shader readiness for selected materials. Qualify it on a clean recipient machine with the U01 board or Z01 empty-game fixture **before** claiming the first public starter. Retain the two-region skinned/environment scene as the separate I3 whole-engine integration gate. This makes “small selection” observable without weakening the demanding path.

### C2 — P2: define an SDK-release upgrade path for an existing game

**Failure example.** A shipped stylized game pins SDK release N, uses a custom material pass and a small game-owned rule, and has player saves. Release N+1 changes the public material/registration API and the asset schema. The plan promises release-matched SDK examples and no silent rewrite of game-owned code (`ENGINE-EXPERIENCE.md:38-54`; `AI-DEVELOPMENT.md:182-187`), while schema and save migrations are deliberately distinct (`modules/TOOLS-DELIVERY.md:184`; `CONTRACTS.md:199-223`). It does not yet specify the creator-visible decision: remain pinned to N or attempt N+1; what upgrade command/report identifies breaking game code, extension bindings, authored/cooked content and save compatibility together; how to test on a copy; and what restores the prior working build if upgrade validation fails. Schema migration alone cannot compile a changed game API or prove a provider's semantics survived. An AI agent with version-matched skills can still make a plausible edit against the wrong release if the project/update boundary is not explicit.

**Smallest correction / owner / gate.** T2/F3/F4/F2 and the public SDK owners should write a finite release-support and upgrade contract: project lock identifies engine/tool/skill/API versions; an upgrade preflight reports source, schema, provider, target-product and save impacts; migration is explicit and preserves prior source/build roots; manual game-code fixes are named rather than auto-guessed. Test one ordinary game plus one public extension and a retained save across two SDK releases, including an aborted upgrade and rollback. Gate this before the **first breaking SDK release or promoted external game**, not before the first single-release starter. This is separate from A02's external *same-project* multi-file change-set recovery and A01's edit/play isolation; it uses those mechanisms after they are defined.

### C3 — P2 acceptance clarification: the minimum workbench should prove spatial composition

**Failure example.** An artist imports a room, then needs to place a lamp, rotate/scale a doorway and make a second prop instance before adjusting its lighting. The plan says artists can author appearance and newcomers can add scene objects (`ENGINE-EXPERIENCE.md:32-35`, `:81-84`), and its empty-game walkthrough explicitly needs transform/scale and camera framing (`FROM-SCRATCH-WALKTHROUGHS.md:38-46`). But the repeated *minimum visual workbench* list names frame/select, camera/light/material fields, source/play distinction and undo, without an explicit place/transform/duplicate-to-prefab action (`ENGINE-EXPERIENCE.md:162-166`; `modules/TOOLS-DELIVERY.md:80-85`). The later T1 scene/prefab editor has multi-selection and field metadata (`modules/TOOLS-DELIVERY.md:182`), so these actions may be intended; the gap is that the artist-usability acceptance test could pass with a good inspector but no comfortable scene-composition path. The U07 room and U08 character reimport journeys already require visual adjustment and stable authored overrides (`FIRST-USE-WALKTHROUGHS.md:100-123`).

**Smallest correction / owner / gate.** T1/W1/F3/F4 should add a short acceptance trace to the minimum workbench: import a prop; place/rotate/scale and duplicate or instance it in an authored scene; preview from the actual game camera; undo; reimport; verify instance transforms and game-owned material overrides survive; then build the target. Use existing typed operations and source records, with no new editor database or full modeling suite. Gate this before advertising the I3 visual/art workflow, and keep game behavior code as a programmer handoff (`modules/TOOLS-DELIVERY.md:61-65`). This is a bounded workflow proof, not a new architecture family.

## What the plan already handles well

- The creator vocabulary is small: project, scene and target, with one effective setup and direct game code for ordinary rules (`ENGINE-EXPERIENCE.md:13-24`, `:43-54`, `:136-148`). The D0 direction is static setup plus optional packages, with no universal provider search or live gameplay removal by default (`CONSTRUCTION-PLAN.md:30-38`). This is the right defense against descriptor bureaucracy; D1 must prove it with a compiling tiny rule.
- Art styles and cameras are treated as source/material/light/display choices with target-specific supported passes, not a magic toggle (`ENGINE-EXPERIENCE.md:155-177`). The no-sky/cloud-shadow distinction, two-view state and provider-off cost have explicit owners. Realistic, toon and painterly examples are proposed as *separate supported paths*, not universally certified results (`FIRST-USE-WALKTHROUGHS.md:100-138`).
- Ownership is unusually clear for an early architecture. W1/P3/E1/V3/P7/F4/T1 do not all own the same state; authoring, active runtime and saves have separate meanings. Required products publish together and failures retain a known-good active revision (`CONTRACTS.md:84-109`, `:199-227`; `modules/TOOLS-DELIVERY.md:176-184`). A01/A02 remain genuine open mechanism work, so the examples are still proposals.
- Audio, UI and accessibility are present as qualified contracts, not invisible polish: audio events follow committed state, UI has semantic input/focus/text obligations, and mobile/browser lifecycle and target delivery are separate claims (`modules/AUDIO-UI.md:9-35`, `:59-110`; `modules/PLATFORM-RUNTIME.md:76-103`). Headless and no-audio game paths are allowed; I would not add a universal audio/UI requirement to the small-game fixture.
- AI contributor and SDK routes are intentionally distinct, with game skills shipping only against real versioned APIs, bounded queries and exact evidence (`AI-DEVELOPMENT.md:12-21`, `:61-81`, `:182-214`). The skill set should remain short; scripts and public API indexes carry the mechanical detail.

## Readiness and decision

The whole plan is **coherent enough to commission D0–D2 and a thin starter slice**, with strong reasoning about authority, optionality, recovery and target-specific claims. It is **not ready to promise a generally usable SDK, artist workflow, browser/mobile export or high visual quality**: the ledger defaults all 29 modules to `not_started_for_target`, functional `not_run`, visual `not_reviewed` and each platform `not_run` (`maturity.json` defaults; `MATURITY.md:10-22`). A01–A05 remain the current shared-contract blockers for their stated dependencies (`ARCHITECTURE-AUDIT.md:32-40`, `:148-169`); my C1–C3 are additional creator-facing sequencing/acceptance gaps. Networking, pure 2D, MMO, full renderer replacement, a full GUI editor and every specialist model remain optional/out of scope (`ARCHITECTURE-AUDIT.md:130-133`; `FIRST-USE-WALKTHROUGHS.md:150-153`).

The next review should judge actual public code and authoring operations on the small fixture, then the demanding two-view scene, then a second SDK release. Passing document links, ledger hashes or an isolated demo should not be promoted as that evidence.
