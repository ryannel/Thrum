# Bevy, Fyrox, Flax and Wicked capability audit

Reviewed 1 November 2026. This is a source-backed challenge to the **custom** 3D engine brief, not a proposal to host on another engine or a claim of implementation parity. The target remains Mac/PC, browser and iOS/Android, with multiple camera styles, scalable visual quality and AI-friendly development. Pure 2D and MMO are excluded; ordinary networking remains open. The comparison is against `notes/engine-rebuild/ARCHITECTURE-BRIEF.md`, the seven `modules/` designs, `AI-DEVELOPMENT.md`, `COMPOSITION.md`, `FIRST-USE-WALKTHROUGHS.md` and A01–A05. All findings are design/discovery obligations, not runtime qualification.

## Six focused dispositions

1. **Animation creation and diagnosis — too implicit; add a narrow T1/P4/T2 authoring contract.** P4 and F4 already specify clips, graphs, root motion, skeletal compatibility and runtime diagnostics; T1's generic inspector does not yet say how a creator binds a new skeleton, previews a transition/root path at game scale, edits an event or diagnoses a bad retarget/IK result. Fyrox's animation editor and [Flax's graph/debug tool inventory](https://docs.flaxengine.com/manual/animation/index.html) show the productive workflow to test, without requiring their graph UI. Specify a minimum timeline/graph-state preview and inspectable pose/root/event trace through the shared T1 operations, with headless equivalents for agents. An optional visual graph editor can follow. **Owner:** P4/F4/T1/T2. **Qualification:** one changed clip/skeleton and one transition checked in editor/CLI and cooked Mac/browser/mobile targets; tools alone do not prove character quality.

2. **Terrain and vegetation authoring — too implicit; add a creator route, not a mandatory terrain algorithm.** W2/E1 define terrain geometry, surfaces, procedural recipes, vegetation and streaming, but the first-use workbench promises only generic field editing. [Fyrox's feature inventory](https://fyrox-book.github.io/introduction/introduction) includes multilayer terrain; [Flax highlights](https://flaxengine.com/features/) lists terrain, foliage and streaming; [Wicked](https://github.com/turanszkij/WickedEngine/blob/master/features.txt) lists procedural terrain and splines. For the already-supported third-person exterior profile, state how an artist/agent creates a small landscape from import or a recipe, assigns surface regions, places vegetation, previews render/collision/nav products and revises a seam across a streamed cell. Heightfield sculpting, spline roads, biome painting and large-world tools are optional providers until a game needs them. **Owner:** W2/E1/F4/P3/P5/V2/T1. **Qualification:** one editable two-region outdoor fixture and target-specific cook/stream review; no inferred large-world promise.

3. **Imported material compatibility — already covered in principle, but record an explicit support table in the content contract.** W2/F4 already validate glTF extensions and V3 already requires declared material/shadow/reflection path support. [Wicked's feature list](https://github.com/turanszkij/WickedEngine/blob/master/features.txt) names individual glTF material extensions, which exposes the practical question: what survives import, what is baked, what needs a selected renderer/provider, and what must fail or use an authored fallback? Add a per-target table for the supported glTF baseline and selected extensions, with import preview and a material/pass/shadow compatibility diagnosis linked to A03 shader demand. Avoid claiming blanket “glTF support” or importing every extension. **Owner:** F4/V3/V1/T1/T2. **Qualification:** a small extension-bearing reference asset on each advertised render profile. This is a specification clarification, not a new material system.

4. **Dynamic asset reachability — too implicit; close the cook/export escape hatch.** F4 and T2 define dependency closure and manifest publication, but there is no explicit rule for assets requested by a game through computed paths or late game policy. Fyrox's [1.0 export CLI](https://fyrox.rs/blog/post/fyrox-game-engine-1-0-0/) explicitly warns that its used-asset scan misses files loaded directly outside its resource manager. Require either stable logical IDs declared in game/package manifests or a discoverable asset-family declaration for dynamic loads; export should reject an undeclared required lookup and report the referring code/content identity. This extends existing F4/T2 closure and A03-style demand validation, not a second registry. **Owner:** F4/P6/T2/F2. **Qualification:** a cooked build with a runtime-selected asset and a failing undeclared selection on browser/mobile as well as desktop.

5. **Code and asset iteration promises — split by change type and platform; retain A01/A02/J04.** [Bevy](https://bevy.org/) advertises immediate reload for scene/texture/mesh assets, [Fyrox documents](https://fyrox-book.github.io/resources/hot_reloading.html) reimport identity hazards, and [Flax's feature page](https://flaxengine.com/features/) advertises editor C#/C++ hot reload while its [Web documentation](https://docs.flaxengine.com/manual/platforms/web.html) lacks C#. The current brief correctly avoids promising arbitrary binary reload, but “live editing” remains easy to overread. Put a change matrix in T1/T2: property edit, imported asset replacement, shader/material change, game-code rebuild, schema migration, feature/profile switch; for each give edit-world/play-world behavior, restart requirement, preserved state, failure rollback and availability on Mac/PC/browser/mobile developer builds. A01/A02 must settle authority and source pinning before claims of seamless play/edit. **Owner:** F1/F3/F4/P7/T1/T2; **qualification:** change/restart/retry fixtures in actual development builds, distinct from shipped runtime capability.

6. **Controller/mobile haptics — missing owner; optional scope addition.** [Wicked's feature list](https://github.com/turanszkij/WickedEngine/blob/master/features.txt) includes controller vibration/LED feedback. P1 maps inputs, while A1 explicitly says haptics are a separate consumer of a cause, but no module owns output. If a selected game uses haptics, give F1/P1 (or a small presentation adapter) a bounded cue/output contract with device availability, intensity limits, interruption/cancellation and player opt-out; consume P6 event identity once, independent of audio being on. Do not require haptics for all games or make it authoritative state. **Qualification:** representative controller and iOS/Android devices; browser vibration/gamepad actuation availability is device/browser-dependent and cannot be assumed from Wicked's native support.

## Do not inflate the mandatory engine

- Keep saves/replay, multi-camera, localization/text shaping/accessibility, rendering/physics/nav, debug attribution, asset reimport and platform qualification in their **existing** owners. They are already described in substantial detail in P7/P2/U1/T2/F4 and the module designs; the survey provides comparison cases, not missing modules.
- Do not require Flax-style visual scripting, CSG, online services, baked GI, 64-bit world coordinates, or Wicked's VRM/Gaussian-splat support solely because a feature page lists them. P6 graph/script hooks, W2 geometry providers and V3/V4 optional techniques suffice until a usage profile requires a concrete capability.
- Do not turn Fyrox's small/medium-world statement, Flax's browser limitations or Wicked's missing browser/Android entries into claims about our target engine's feasibility. They are reasons to keep explicit profile/feature gates and real device qualification. A01–A05 remain open architectural findings.
