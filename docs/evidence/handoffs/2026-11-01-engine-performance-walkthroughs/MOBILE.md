# Paper performance walkthrough: mobile tactics simulation

1 November 2026. **Paper scenario only.** No engine path, benchmark, mobile build, device result, or optimization campaign is claimed here. This applies the proposed [AI performance campaign](../../../design/AI-PERFORMANCE.md) to the [play systems](../../../design/modules/PLAY-SYSTEMS.md), [platform runtime](../../../design/modules/PLATFORM-RUNTIME.md), and [shared contracts](../../../design/CONTRACTS.md). The game is an illustrative future SDK client, not Broadsides gameplay. It tests whether agents could improve a whole engine path while preserving tactics play; it is not a proposal to add tactics AI to the current game.

## Commission to pin before execution

**User outcome:** a 3D overhead tactics game remains responsive through mass orders, moving obstacles, collisions, camera pans and sustained device heat. The cost objective is lower sustained simulation/navigation/collision time, memory pressure and thermal degradation **at the same gameplay scale and semantic quality**. A separate capacity objective could raise agent count at fixed cost, but must be reported as such. The objective is not to make a synthetic path query fast while delaying commands or skipping physical ticks.

**Illustrative workload, all unmeasured:** 384 active agents in two adjacent loaded cells, including 96 currently moving through a narrow crossing; 64 dynamic crates/doors/bodies; static cover and ramps; 24 simultaneous player-selected agents given a formation move command; enemy reactions and projectile/sensor contacts; a slowly moving blocking gate; one overhead camera panning/zooming while a small inset view is occasionally active. A 30-minute trace alternates quiet formation travel, crossing congestion, a 60-agent mass order, moving-obstacle invalidation, short combat bursts, two cell activations/retirements and 20 minutes of ordinary mixed play. A held-out trace changes formations, obstacle timing, order destinations, map topology and crowd densities (including near-empty and over-capacity cases). Pin the common authored workload, selected input/seed and camera traces, required outputs and acceptance contract. Record the baseline's and each candidate's distinct source, binary, shader and cooked-product hashes, including products actually loaded. A nav-layout or render-only cook optimization may legitimately change product bytes while retaining the required collision/nav meaning and visible cues. This scale is a stress proposal, not a supported product promise.

**Provisional target envelope, to be replaced by D0 device measurements:** native iOS/Android sustained 30 displayed fps (33.3 ms period); the platform note's illustrative CPU critical-path guide is 7 ms per presented frame and its engine-owned logical memory guide is 1 GiB. The game's fixed world step `h` must be selected from gameplay/physics requirements before this campaign. **If** that game selects `h = 1/60 s`, about two ticks fall per 30 Hz image; P3/P5/P6 then cannot each claim the whole 7 ms. Under that conditional example, reserve **at most 4 ms combined** for their two-tick critical path under the 7 ms guide, leaving 3 ms for input, animation, commit, extraction and host work. A different chosen `h` requires a revised tick-count and critical-path allocation. This is a planning allocation, not a measured feasibility claim. Candidate qualification would predeclare p95/p99 frame intervals and input-to-visible-response limits after choosing minimum devices; a suggested provisional limit is next admitted world tick for order acceptance, a visible order acknowledgment within one presented frame when active, and 100 ms p95 for a feasible route in the authored stress case. Route latency must be measured with age and backlog, not inferred from a lower CPU mean. No numerical thermal or physical resident-memory claim is possible before device choice. Measure physical footprint separately from the logical admission bound.

**Semantics gate:** F1 owns the selected fixed `h` and never lengthens it to save cost. Every admitted tick runs mandatory P3 contact/CCD and P6 event work. P5 supplies desired motion only; P3 returns achieved motion to P4 and W1 commits it once. A command may acknowledge promptly while a route is pending, but agents hold or follow an explicitly safe local policy and report pending state; they do not move through unknown or unloaded space. Queries name `Q_n`/`Q_(n+1)` and world, cell, tile, obstacle and content generations. A stale async path is rejected and rate-limited for repath. Sensor/contact IDs and saved authoritative state remain consistent across replay, stream changes and suspend. Define game-specific tolerances for collision penetration, route feasibility, formation deviation and moving-obstacle response **before** running candidates; no speedup can trade these away silently.

**Target scope:** one named iPhone/iPad class and one named Android class with OS, GPU/backend, compiler flags, resolution, thermal/power state and app build fixed at D0. Both must receive sustained and lifecycle qualification before a mobile claim. The exact devices are still unknown. Headless and desktop runs are useful semantic screens but cannot qualify phone performance. A lower-memory or 60 fps variant may be commissioned later as a distinct target. Do not demand the complete desktop/browser/API matrix to accept this scoped mobile gain; do verify portable semantics and record other targets as unqualified rather than imply benefit there.

## Cost and dependency argument

At tick `n`, P6/P5 decisions read committed `S_n` and P3's `Q_n`; they emit bounded intents. P4 and movement policy produce one request, P3 resolves contacts and displacement, then P4/P6 reconcile and W1 commits `S_(n+1)`. Navigation tile/obstacle changes become visible at the pre-tick barrier only after W2/F4 have complete matching collision and nav products. P2/V2 and audio consume the committed state/events. This dependency path, repeated twice per 30 Hz image **only under the illustrative 60 Hz world-step choice**, sets the simulation portion of display latency. Parallel search jobs can overlap other work, but they still compete for cores, bandwidth, allocator capacity and publication slots; elapsed stage sums and frame critical path are different measurements.

Let `A` be agents, `R` route requests per second, `N_i/E_i` graph nodes/edges visited by request `i`, `C` broad-phase candidate pairs, `K` constraints, `I` iterations and `S` substeps. A rough work model is `P5 = O(A * local_guidance + Σ_i (N_i+E_i) log N_i)` and `P3 = O(S * (C + I*K + B)) + casts`. It does not predict milliseconds: corridor topology, crowded cache behavior, cast shape cost, worker contention and memory traffic matter. Under the example's two ticks/image, an added `0.5 ms` per authoritative tick can add up to `1 ms` on the serial image path; saving `1 ms` in an async search that never gates motion may save power/queue age but not a visible frame millisecond. Likewise an agent-array shrink can reduce logical bytes while increasing query copies or cache miss traffic. Candidate reports need operation counts, queue age/completion, allocator bytes and the end-to-end critical path.

Three plausible, coupled hypotheses are worth testing analytically before implementation:

1. **Navigation search and invalidation:** share immutable tile/topology data, use stable corridor IDs, batch requests with common destination where valid, and incrementally repair only affected routes. This can reduce `Σ N_i` and duplicate reads. It also adds reverse-dependency metadata, invalidation work and possible memory residency. A cached corridor is valid only for the exact relevant tile/obstacle generations; a moving gate can invalidate it before use. Put per-request node, age and memory quotas in F1/P5 admission rather than letting mass orders create unbounded pending searches.
2. **Collision/query representation:** group static cell colliders and agent-class filters in a query-friendly P3 structure, reuse complete immutable `Q_n` pages for many casts, and consider SoA/batched shape query traversal where provider APIs permit. A broad-phase rebuild reduction can be valuable, but the solver still owns dynamic pairs, contact transitions and swept checks. A compact index must not turn an unavailable cell into empty space. A query page lives until every reader releases its lease, including async P5 work.
3. **Schedule and data flow:** publish generation-stamped result batches only at the pre-tick barrier; partition jobs by stable request ID with a bounded byte/count queue; avoid per-agent allocation and repeated conversions between nav and physics coordinates. Lower allocation can improve sustained tails and thermal load. F1 remains the one clock/job authority; moving a job off the main thread is useful only if total contention and admission improve.

The first experiments should estimate bytes and work from the authored map: tile and obstacle indexes, path corridor capacity, query snapshot copies, per-agent state, pending jobs, and cell replacement overlap. For example, `M_peak = M_live + M_pending_decode + M_replacement + M_transient + M_reserve` with shared allocations counted once; a proposed new 20 MiB route cache must fit this **peak**, including old/new cell products and leased old `Q_n` pages. The 1 GiB planning guide is for the whole engine, not a P5 entitlement. The actual budget is chosen by the coordinator after accounting for renderer, audio, content and OS behavior.

## Four-agent paper campaign

| Role | Separate authority and work | Handoff/evidence |
| --- | --- | --- |
| Coordinator | Owns whole-scene objective, baseline, F1 clock and shared query/snapshot contracts, device lease, work/memory allocation and accepted integration branch. Pins the commission/evaluator version. | Cost prediction and affected P3/P4/P5/P6/W1/W2/F4 consumers before assigning edits; integrates one candidate at a time. |
| Builder A | Owns a P5 route/search candidate in an isolated source/build area. May change path algorithm, compact representation and request batching inside the existing `Q_n`/generation contract. | Reports node visits, request age, memory/leases, overflow behavior and semantic tests; raises a coordinated change request before altering P3 query data or F1 scheduling. |
| Builder B | Owns a P3 collision/query candidate in another isolated area, including broad-phase representation, batched casts or stable snapshot publication. | Reports casts, candidate pairs, solver/contact invariants, query age, copy traffic, peak bytes and fallback; does not redefine P5 route freshness alone. |
| Evaluator | Owns versioned fixtures, reference/oracle, thresholds, measurement harness and result collection outside builders' editable areas. Reviews build/load identities and independently rebuilds finalists. | Cheap correctness screens, coupled scene, held-out cases, then exclusive device runs; files adverse and inconclusive results as well as wins. |

This is feasible parallel reasoning and source work, **not four concurrent phone benchmarks**. One measurement lease serializes actual device timing, competing CPU builds, disk I/O and GPU work on the contended machine. A separate evaluator agent in a shared writable tree is review help, not an integrity boundary: use permission/isolation of candidate workspaces, pinned evaluator inputs and independently launched builds. If a reference or threshold is wrong, version it and rerun baseline plus candidates. No candidate may change a score threshold or fixture and then call itself successful.

The campaign proceeds through: (1) D0 target/device and matched baseline with A/A noise runs; (2) independent analytical cost predictions and cheap compile/schema/reference/replay tests; (3) isolated component timing for attribution; (4) one-builder-at-a-time assembly into the full scene; (5) combined revision plus ablations if the gains conflict; (6) fresh held-out and sustained device qualification. Record source, compiler, cooked-product and **actually loaded** binary IDs for every run. Interleave baseline/candidate blocks to expose thermal drift. Treat each run block as an observation; thousands of correlated frames are not independent trials. Bound observer overhead and capture diagnostics separately from final timing. No actual run is authorized or recorded by this paper walkthrough.

## Failure and integration decisions

**Rejected local win:** Builder A's search microbenchmark becomes 3× faster by reusing corridors across four ticks or silently discarding lower-priority route requests. In the moving-gate trace, those corridors have the wrong obstacle generation; agents either enter blocked geometry or pause too late. Even if the cast catches the obstacle, the order-to-feasible-route tail and pending queue rise. Reject this as a same-experience cost reduction. A game-approved approximate route policy could be a separately named provider with bounded freshness and safe local behavior; it cannot borrow the baseline score.

**Independent wins collide:** A's shared corridor cache retains P3's `Q_n` page while B's double-buffered query pages prepare `Q_(n+1)`. Each isolated change reduces its own stage cost, but together three generations stay live during cell replacement, exceeding mobile peak admission; copy traffic may also erase the CPU gain. The coordinator must reconcile the common lease/invalidation contract with P3, P5, W2/F4 and F1. Options include smaller cache shards, compact generation-only route dependencies, a strict lease horizon with safe path invalidation, or declining one candidate. Never reclaim a page merely because cancellation was requested. Integrate sequentially and measure the combined scene; do not multiply 3× and 1.4× local ratios into an engine speedup.

**Stopped work is visible:** When route demand exceeds admitted capacity, F1/P5 bound count and bytes, expose pending/failed-with-retry status, prioritize player-issued and nearby danger queries under a documented fairness rule, and preserve a safe immediate movement/hold response. Mandatory contacts and world ticks cannot be dropped. If even mandatory ticks cannot keep up, F1 enters its explicit local `Overloaded` state rather than quietly slowing physical time. The campaign fails its responsiveness goal if overload is common in the required trace, even if average CPU time falls.

**Variant and fallback:** A phone-specific compact SIMD route provider is allowed only if feature dispatch, alignment/limit assumptions and bytecode/product identity are declared. It falls back to the qualified portable route provider on unsupported devices or a failed capability check. A lower-memory provider must meet the same path/query semantics or state a separately approved quality reduction. Profile or device restoration uses F2's transaction: reserve replacement peak, prepare, switch at a tick boundary, invalidate paths/query pages whose generations changed, and retire old leases after readers finish. On iOS/Android suspend, F1 closes new GPU submission and job publication; no background wall interval becomes catch-up ticks. On resume, revalidate device/profile/cell generations, reconstruct presentation products and discard old-generation async routes. A switch to an inset view does not step the world twice. Test both fallback selection and switching/restore on the actual qualified devices; compiler support or desktop timings alone do not qualify them.

**Promotion rule:** A candidate is eligible only after exact event/identity obligations, declared numerical tolerances, route freshness/latency, collision stability, lifecycle/save and fallback checks pass. Then compare repeated paired full-product p50/p95/p99 tick and displayed intervals, missed deadlines, input-to-visible delay, path age/completions, peak and retained memory, 30-minute power/thermal state and transition stalls. Keep the verified non-dominated mobile implementation and a concrete revert/dispatch path; reject a speedup smaller than predeclared run-to-run noise or one paid for by unacceptable tails, heat, memory or gameplay drift. Stop at the commission's compute/hardware budget, verified target, diminishing expected gain, inadequate measurement or a semantic dispute. Report unqualified targets plainly.

## Design gaps this walk exposes

- P3/P5 name generation and query age, but a mass-order game needs a **game-level maximum order-to-route age**, pending acknowledgment and safe local behavior. Set these per game without making one global engine latency promise.
- The platform note budgets whole-frame CPU and logical memory, while P3/P5 have no coordinated stress-scene allocation. A coordinator must reserve their combined two-tick critical path and peak query/path leases before parallel optimization.
- The ownership of shared `Q_n` pages and cancellation/reclamation is stated in C02/C05, but a concrete cross-P3/P5 route-cache lease horizon, cell-replacement overlap and repath storm policy still need a schema and worst-case cap.
- The existing AI performance design lists rendering and streaming as first campaigns. This mobile play-systems case is an equally credible future candidate **once** a representative executable path and target devices exist; it does not imply it should precede a better-supported bottleneck.
- Minimum iOS/Android devices, baseline, actual thermal and memory bounds, solver/provider choice and game-specific motion tolerances are unresolved. The paper cost model narrows the proof; it cannot close any of these with a claimed benchmark result.
