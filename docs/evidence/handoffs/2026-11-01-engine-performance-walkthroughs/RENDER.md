# Paper walkthrough: forest visibility, shadows and shared resources

Every number in the example commission below is an **illustrative, invented planning input**, not an observed baseline, selected budget, threshold, or result. Candidate decisions and evaluator outcomes below are hypothetical branches used to test the design. ## Commission and fixed obligations

The fictional game is a dense forest and shore scene with wind-driven trees, a moving third-person camera, a zoomable orthographic map view, a low Sun, two shadow cascades, visible water and fog, and streamed region boundaries. This is a **fixed-experience cost-reduction** commission: retain the same gameplay and accepted appearance, and reduce the complete product's cost on one named Mac configuration. It is not permission to reduce the simulation rate, output resolution, tree population, shadow cue, or gameplay obstacle set. Exact target hardware and real scene counts would be selected in D0; the following only makes the paper exercise concrete.

The evaluator pins a production-optimized baseline, source/content/profile and build inputs, compiler settings, observer overhead, device/OS/backend, cold and warm protocols, A/A noise control, paired interleaved A/B blocks, and independent held-out traces. Candidate branches can change their own code and cooked products. They cannot edit fixtures, references, clocks, thresholds or the evaluator. T2 independently verifies launcher artifact identity and actually loaded shaders/products, rather than trusting a candidate's self-report. A final scene score includes simulation/animation, extraction, CPU submission, V1 graph execution, GPU completion, present cadence, input-to-display latency, loading/compile stalls, allocation peaks and queue age. A p95 GPU win alone cannot confer whole-engine acceptance.

## Cost model and hypothesis split

Let `N` be resident plants, `V` visible plants per view, `D` changed transforms/deformation bounds, `C_s` candidate shadow casters, `P_a` masked foliage fragments, and `Q` views/shadow projections. A flat scan costs approximately `O(QN)` visibility checks and can produce repeated instance/upload work. A hierarchical, versioned index might approach `O(D log N + Q log N + ΣV + ΣC_s)` for favorable spatial coherence, but pathological overlap or frequent whole-canopy deformation can drive it back toward `O(QN)` and add memory. Shadow raster work still depends on caster geometry and masked overdraw, roughly `Σ(shadow-visible triangles + P_a)`; culling CPU time alone may be a small fraction of the GPU critical path. A shared immutable instance buffer can remove duplicate per-view copies, yet per-view visible lists, shadows and history remain distinct. The lower bound is the required visible and influential work; no algorithm should promise to remove it.

The coordinator first needs an actual baseline attribution. **For the hypothetical trace only**, suppose V2 per-view extraction and V3 shadow preparation are plausible bottlenecks and the GPU shadow/foliage passes dominate. That assumption selects two different hypotheses, not a claim about current code:

1. **H1, V2 visibility and instance representation.** Build one region-aware, versioned hierarchy from W2/F4 plant records and conservative current/previous wind-deformation bounds. Share immutable instance geometry/material data across main, map, reflection and shadow views; produce independent per-view compact index lists with projected-error LOD and a conservative caster query derived from visible receivers and light support. Keep a CPU fallback. Prediction: fewer instance scans, duplicate uploads and shadow submissions where `V,C_s ≪ N`; potential extra tree maintenance, compaction, index buffers and synchronization when wind/stream churn is high. The candidate must report exactly which instances were rejected and prove none could affect required coverage or receivers.
2. **H2, V3 shadow scheduling and V1 resource sharing.** Use static trunk/canopy components and explicit dirty regions to reuse only valid shadow tiles or layers; share stable shadow atlas allocation and geometry leases across views while keeping per-light/view visibility and update age explicit. Prediction: fewer shadow draws and atlas clears when light/casters/receivers remain valid; cost can worsen under low Sun, wind deformation, moving receivers or atlas fragmentation. A cached shadow is valid only for the same light projection, contributing caster geometry and coverage, receiver support, content/device epoch and accepted maximum age. C07's history sample, V3's shadow sample time and V4's image history are separate records.

The two hypotheses interact. H1's compact lists could make H2's dirty-tile build cheaper, or H2 might pin H1's old instance buffer and raise peak residency. Their isolated savings cannot be multiplied. The coordinator owns the combined memory ledger and schedules sequential integration and an ablation if the combination regresses.

## Ownership and actual handoffs the campaign must force

The coordinator sends a versioned contract-change proposal before either candidate changes a shared payload. This is an **example message shape**, not an existing command or schema:

> `Proposal forest-visibility/1`: V2 requests cooked per-plant stable ID, source/product revision, region/activation epoch, current and prior deformation envelope, material coverage class and optional distinct shadow proxy/error bound. W2/F4 own source identity, activation and product readiness; E1 owns wind/deformation samples and validity interval; P4 owns skeletal samples if a plant is animated there. V2 owns derived index, per-view visible sets and RenderPacket leases. V3 owns shadow contribution, age and invalidation; V1 owns buffer/atlas allocation, pass edges and fence retirement; V4 consumes coverage/motion/invalidation. P3/P5 retain independent authoritative collision/nav. Please either accept the semantics and invalidation cases or identify a missing producer/consumer before implementation.

The response must settle source/consumer obligations, not merely acknowledge receipt. W2/F4 would supply stable placement/proxy dependencies and transactional stream generation; E1 would define whether deformation bounds are conservative over an interval or force a query rebuild, and how prior wind state can be evaluated at each retained history time. V2 would reject stale epochs and publish per-view caster/coverage evidence; V3 would specify which cached shadow entries can survive each changed input; V1 would account once for aliased allocations and fence-protected old/new overlap. P3/P5 would confirm that render LOD and hierarchy never own obstacle identity or nav reachability. V4 would require reactive/velocity or invalidity when LOD or foliage topology changes. F2 would validate the selected profile and any live fallback. T2 would convert these obligations into evaluator-visible identities/counters. A disagreement about bounds or shadow-age meaning returns to the architecture coordinator under C07/C12; the agents cannot silently invent different contracts.

At four available agent slots, run coordinator + H1 agent + H2 agent + independent evaluator/reviewer. The evaluator agent designs and owns checks and candidate record review outside the candidate-edit area. The *trust boundary* is the protected evaluator/build inputs and execution identity, not the mere fact that a different agent reads them. The two candidates reason/build in isolated source/build directories, but only the evaluator holds the contended Mac measurement lease. Once the H1/H2 agents publish candidates or stop, reuse their slots for owner review and integration; keep the coordinator as the single whole-scene arbiter. Append candidate ancestry, failures and changed dependencies to campaign history. No side agent can change the commission's constraints or promote itself.

## Hypothetical staged search and a rejected win

1. **Cheap screening.** T2 validates source/schema, target/profile closure, cooked dependencies, shader demand, lease/lifetime rules, deterministic fixture replay and independent reference cases. A slow CPU visibility oracle enumerates source bounds and all light/receiver intersections for small and adversarial scenes. Seeded cases include plant at a frustum edge, offscreen caster, large bent crown, region-border duplicate, origin rebase, zero plants and maximum admitted instances. Exact IDs/sets are checked where possible; declared geometric error uses a spatial and pixel bound. The fixture asserts shadow-caster completeness, not identical draw counts. Invalid cases stop before GPU time.
2. **Tempting local result.** In the paper branch, H2 reports a faster shadow-update microbenchmark by retaining a whole cascade until the camera or Sun changes. The evaluator rejects it **even if that isolated timing is lower**: E1 wind can move foliage into a new silhouette while camera/Sun are stationary, and a moving receiver or newly admitted region changes required shadow visibility. A fixed camera is not a proof of valid cache contents. The evaluator preserves the failed record and asks for changed validity, not a new acceptance camera.
3. **Changed candidate.** H2 splits static trunk geometry from wind-deforming foliage, keys cache entries by light projection/receiver footprint, region/content/device epoch and an E1 deformation-version or conservative temporal envelope, and schedules only valid reuse. Dynamic foliage is refreshed within an explicitly accepted age/coverage bound; if its worst-case dirty area is too large, use the ordinary shadow path. H1 publishes a conservative caster query that includes offscreen influencers and returns its invalidation provenance. This is a substantial algorithm/representation change with a fallback, not a blind threshold tweak. If the revised bounds cannot be proved or accepted in motion, H2 is dropped and H1 may still proceed.
4. **Focused then coupled measurement.** The evaluator measures H1 and revised H2 separately on the disclosed main trace, then integrates H1, then H2 into the H1 revision. Each step checks the full graph and peak `M_live + M_pending_decode + M_upload_staging + M_replacement_overlap + M_transient + M_reserve`, counting shared allocations once. A joined result that allocates duplicate per-view lists, delays GPU fences, or stalls streaming is rejected regardless of local timings. If a regression appears, an H1-only/H2-only/joined ablation distinguishes interaction from noise; no one adds speedup percentages.

The paper candidate remains **unverified**. A real run may show H1's hierarchy maintenance costs more than it saves, H2's wind invalidation erases cache benefit, or both are irrelevant next to masked fragment cost. In those cases the correct outcome is to retain the baseline, change the hypothesis or stop at the commissioned limit.

## Final integrated qualification, not benchmark promotion

The evaluator independently rebuilds the integrated finalist and baseline from pinned source, toolchain, profile, cooked manifest and shader demand, then verifies loaded artifacts. It first proves W1/P3/P5 state, event IDs and physical elapsed time are unchanged for the same fixed-tick trace. It checks V2 visibility/caster completeness against an independent slow oracle on bounded fixtures, shadow age/coverage/LOD error envelopes, and C02/C05/C06 release after stream-out and device loss. It separately reviews moving-image sequences at native output for leaf shimmer, silhouette loss, contact shadows, disocclusion, camera cuts, orthographic zoom, wind gust and region changes. Human appearance acceptance is required for changed cues. Diagnostic captures are taken outside final timing runs.

The performance run then uses repeated interleaved baseline/candidate blocks with A/A control, warmup, a sustained scene, cold shader/product startup, and streaming/profile/device transitions. Report independent block distributions (p50/p95/p99/max and deadline misses), GPU critical path, CPU stages, present/input latency, queue age/completion, compilation/loading stalls, measured physical and estimated/logical memory, and thermal/power context. A timestamp feature or counter unavailable on that backend is marked unavailable; a driver wait is not automatically attributed to the function where the wait occurred. The result is **qualified on the named Mac configuration only** if all semantic, visual, lifecycle and regression gates pass and the measured effect clears the predeclared practical/noise threshold. The hypothetical ≤8 ms target and whole-frame guardrails are additional gates; meeting one does not excuse failing another.

The reserved **held-out contrast** is an interior-to-forest route with rapid wind and Sun direction changes, thin foreground branches, an offscreen caster entering a map camera, a region unload/reload, and a second view that skips frames. The evaluator does not expose its exact seeds/route to candidate agents during search. It asks whether the hierarchy and cache remain correct and useful when `D` and `C_s` approach `N`; it also measures the fallback's cost. If held-out semantics/appearance fail, reject or fix and use a fresh final set after adaptation. If cost gain disappears without regression, the claim narrows to the first workload rather than becoming a general forest or Mac claim. If the finalist passes both, it still requires separately named Windows, browser and mobile paths before cross-platform promotion. A target-specific Mac variant needs explicit F2 dispatch, A03 shader/product closure, finite binary/compile/residency budgets and a portable fallback. A desktop result cannot be averaged with a mobile failure.

**Recommendation:** use this as the first ambitious renderer campaign only after a real baseline and D0 fixture show visibility/shadow/shared-resource work is consequential. The current design allows a broad algorithmic search with clear authorities, but needs executable evaluator, exact provider bounds, shared lifetime accounting and A03 closure before any automatic promotion. Report a Mac-specific verified gain, an inconclusive result, or a retained baseline honestly; do not infer whole-engine improvement from the rejected shadow microbenchmark or from isolated H1/H2 scores.
