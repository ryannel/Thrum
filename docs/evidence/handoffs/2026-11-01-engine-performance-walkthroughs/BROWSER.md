# Paper dogfood: browser first play and streaming under contention

**Status:** paper scenario, 1 November 2026. Every target, trace, measurement and outcome below is **illustrative invented data**, not a selected engine budget, running tool, measured device result or proof. This walkthrough tests whether the [AI performance proposal](../../../design/AI-PERFORMANCE.md) can coordinate F1, F2, F4, W1/W2, V1/V2, P1/P3/P5/P7 and T2 through a complete web product. It follows [C02/C05/C12](../../../design/CONTRACTS.md), [platform/runtime](../../../design/modules/PLATFORM-RUNTIME.md), [world/content](../../../design/modules/WORLD-CONTENT.md) and [tools/delivery](../../../design/modules/TOOLS-DELIVERY.md). The [performance method](../../../../.agents/skills/plan-module/references/performance.md) requires end-to-end requalification. No engine, harness, device run or automated campaign is created here.

## Commission and readiness

The creator exports a bounded third-person woodland/harbor web demo. The player lands in a small starting clearing, moves immediately, selects a lantern, then crosses into a neighboring shore region. Both regions contain visible scenery, collision, navigation, audio cues and an animated character; a second distant camera is part of the held-out route. The developer changes a shared lantern material and its collision proxy, cooks the affected closure and republishes. The same logical scene, input trace, gameplay rules, visual cue floor, viewport and output format are pinned across candidates. Any product hashes that change legitimately are recorded, not required to match the baseline.

**Illustrative target only:** a named *hypothetical* Web-A desktop browser/WebGPU profile at 1280×720, DPR 1, single-thread baseline, with a declared fast-to-slow connection trace and a separate cache-cold run. Planning gates for this example: first *playable* state within 5 s of navigation on the declared connection; no active input-to-visible-action sample above 150 ms; no active frame interval above 50 ms during the crossing; logical peak under 512 MiB including staging and replacement overlap. A required blocked-loading state is reported separately from active-frame success; it cannot be hidden by omitting its duration. These numbers illustrate how a commission would be specified. They neither override the platform note's unmeasured envelope nor qualify any browser or device. The real campaign must first choose hardware, browser/version, connection distribution, art/scene scale, perceptual criteria and meaningful thresholds.

The objective is **cost reduction at fixed experience**: improve first playable time and crossing responsiveness without changing render output resolution, collision/nav meaning, input effects, world clock, selected visual cues or offline policy. A smaller artifact that delays interaction is not a win. A quality-reduced or larger-content variant would be a separately labeled fixed-cost experience claim. Cook latency after the shared prefab edit is a developer responsiveness metric, with correctness and deployability gates; it is not interchangeable with runtime startup.

The evaluator defines readiness as all boot-required bytes verified and loaded, profile and demanded pipelines ready, starting-region W1/P3/P5 authority committed at a pre-tick barrier, a presentable view, and P1 action routing able to produce the expected world and displayed response. Audio unlock is exercised after a user gesture and reported separately rather than blocking page readiness. T2 records navigation-to-ready, first action-to-visible result, active callback/frame tails, time in explicit loading, required-region ready age, fetch/decode/upload/shader queue lengths and ages, completed/pending/cancelled work, logical peak components and any available measured browser memory. It distinguishes estimated GPU bytes from physical residency. Cook trace records changed dependency closure, all product hashes, clean/incremental wall time and manifest publication; fast incremental cooking cannot omit a dependent collider or shader variant.

## People, slots and immutable evidence

One coordinator pins the commission and accepted baseline, owns the whole-scene budget and obtains F1/F4/W2/V1/P1/P3/P5/T2 owner review for contract changes. Hypothesis agent H1 owns content packaging/compression and cooker changes. H2 owns bounded fetch/decode/upload scheduling, startup closure and region lookahead. An independent evaluator owns fixtures, semantic oracles, thresholds, timing method and result store. These four roles fill the four allowed concurrent slots in the **paper staffing model**; no fifth agent is implied. In practice H1/H2 may reason or build while the evaluator holds the sole Web-A measurement lease. At selection the coordinator integrates sequentially, then H1/H2 stand down and the evaluator uses the freed capacity for held-out and clean-build checks. Separate agent identity in one writable tree is review, not an integrity boundary; evaluator inputs and run collection need a separately pinned read-only/versioned area in any actual implementation.

Milestones and handoffs are deliberately concrete:

| Milestone | Required output before next step |
| --- | --- |
| M0 commission | Frozen authored source/scene, input and connection traces, expected events/visual cues, boot and on-demand closure, target/profile, measurement protocol, resource/stop limits, baseline and evaluator revision. |
| M1 candidate screening | Each hypothesis supplies a cost model, owner/consumer impact, isolated source/build directory, changed product/dependency manifest, compile/schema/cook integrity, replay and readiness checks. Invalid or stale-product builds stop here. |
| M2 focused and coupled runs | Evaluator runs exclusive same-binary A/A noise controls, then paired baseline/candidate blocks in alternating order. Diagnose fetch, decode, shader, upload, activation and input critical paths; carry adverse transitions and failures forward. |
| M3 integration | Coordinator stages one candidate at a time, re-cooks the full affected closure, verifies startup and crossing together, and ablates a changed component if the combined result regresses. Retain the last known-good manifest/build. |
| M4 qualification | Independent clean rebuild, fresh reserved scene/route and connection trace, cache-cold and invalidated-cache runs, offline policy, memory pressure, lost-device/visibility restoration and sustained interaction. Report target scope, uncertainty and unresolved gates. |

The shared record is a versioned commission ID plus candidate ancestry, source revision/dirty state, toolchain and compiler lock, evaluator/fixture revision, target browser/device/backend/limits, profile and view/DPR, authored source IDs, dependency-hashed cooked product IDs, web package/manifest hash, demanded/actually loaded shader and binary IDs, active runtime manifest/region generations, run block ID, raw bounded trace and evaluator verdict. T1's edit correlation ID links edit → cook → activation → capture; it is not the product hash or an idempotency key. The evaluator checks launch artifact and actually loaded IDs, not only the candidate's self-report. A retry of a failed cook keeps the previous manifest active; `accepted/pending` is never recorded as completed activation.

## Walk and competing hypotheses

1. **Cold first visit.** The web page receives a frozen manifest pointer. F4 fetches the boot closure, checks hashes and reserves compressed, decoded, upload and transient bytes before admission. F1 runs the browser's single-thread cooperative baseline; W2 prepares the starting region, including the saved overlay and required collision/nav/gameplay products, then commits them together at a pre-tick barrier. F2 cannot advertise a profile whose A03 shader demand is stripped or unprepared. The first action trace is only eligible once the lantern selection and movement affect the committed world and displayed view. A pretty first frame with missing collider or inert input fails.
2. **H1 proposes a smaller web package.** A denser compressed mesh/texture bundle and a larger shared dictionary reduce transfer bytes and improve the isolated download trace; the cooker also caches more intermediates. In the invented comparison its network segment is shorter, but the browser's single thread performs a long decode before mandatory shader/upload and region activation. The action misses the latency gate and the compressed-plus-decoded-plus-upload overlap exceeds the illustrative logical peak. A cached warm visit disguises the failure. **Reject H1's decoder/download micro-win**: byte savings and incremental cook time alone cannot promote it. Retain its useful package analysis, including dependency hashes and decode expansion, as evidence.
3. **H2 proposes admission and ordering changes.** Derive a boot closure from the first playable region and its actual input, collider, nav, render and shader consumers; put the next-region products behind it. Bound fetch/decode/upload queues by count *and reserved bytes*, use cooperative decode chunks only where the chosen format supports independent chunks, reserve GPU upload time and stage bytes, and prioritize visible/soon-needed work with aging. The coordinator reviews F4 product and W2 activation contracts before accepting a new content layout or fallback. H2 cannot count deferred work as removed: T2 must show completed product counts, queue age, first crossing state and later catch-up.
4. **Connection drops during approach.** W2 requests the shore from the union of camera, body, nav and audio relevance. Its lookahead condition is `d_prepare ≥ v_max τ_ready + d_stop + r_body + margin`; an unbounded network tail means no finite prefetch distance guarantees readiness. If required collision/nav is late or peak admission fails, W2 closes traversal and shows explicit loading at a safe boundary while the world follows the specified local pause policy. It never draws a traversable proxy over absent ground. Optional scenery may appear later under a declared placeholder policy. Input responsiveness while the start region remains active is still measured, and the wait duration is part of the outcome.
5. **Developer edit and republish.** The shared lantern material/collider edit changes the complete active dependency closure. F4 cooks new products under tool/profile/source hashes; T2 reports clean and incremental cook paths and whether the shader-demand closure remains valid. W2/P7 stage authoritative dependencies, recheck active-set generation and publish manifest plus required representations together. A late old fetch/decode completion cannot publish after a changed product or host epoch. Browser cache may supply old bytes only when their hash matches the pinned old product; a cache hit is no authority to mix revisions. Rollback is a new safe manifest/desired-revision transition, not mutation of the sole good artifact.

**Revised integrated candidate I1 (paper choice):** keep H1's *dependency analysis*, use an independently decodable boot product layout and H2's bounded priority/reservation policy, and retain the ordinary portable decoder for the cold path. H1's dense bundle may remain an optional, separately qualified warm/offline variant only if its added binary, cook, memory and first-action costs meet the same gates. I1 is a proposed combined design, not a measured winner. Its predicted advantage is shorter critical-path *required* work and reduced staging overlap; its risk is extra requests/manifest overhead and delayed shore readiness. The paired integrated run, rather than either isolated result, decides.

## Evaluator decision, claim and stopping rule

The independent evaluator first rejects missing input/event outcomes, changed collision/nav or save behavior, stale or mixed manifest generations, omitted shader products, visual/motion cue failures, an unbounded queue, and pressure that silently drops admitted world ticks. It compares baseline and I1 by independent run blocks with A/A drift, cold and invalidated caches, interleaved order and the same authored trace. A frame is not an independent sample of uncertainty. Diagnostic captures are separate from final timing. Reserved qualification varies route, camera, region order, compression ratio, connection change point and interaction timing; repeated exposure of its scores invalidates its held-out status. A secondary target (another actual browser/OS/backend or mobile web view) must be measured before any cross-browser claim. A synthetic slowdown is only a scheduling stressor, not a low-end device result.

The **only permissible paper disposition now** is “I1 is a candidate for Web-A; performance and visual acceptance unqualified.” If a future real Web-A run passes the selected gates, the claim is limited to its named device/browser/backend, viewport/profile, content revision, connection/cache protocol and duration. It cannot say “the browser engine is faster” or multiply H1/H2 local savings. Report startup and cook separately, p50/p95/p99 plus maxima and deadline misses where sample counts support them, blocked-loading duration, action latency, active/pending completion counts, logical/estimated/measured memory scopes and all regressions or inconclusive comparisons. No WebGPU timestamp or browser resident-memory number is invented where the target cannot expose one.

For this **illustrative campaign only**, the coordinator would cap search at two candidate families plus one revised integration, a fixed small number of matched evaluation blocks chosen *before* the run, one target-device measurement lease, and a declared wall/compute/storage allowance. The actual quantities remain D0 commission decisions, not invented authorization for hardware spend. Stop earlier for failed semantics, invalid artifact identity, pressure with no safe fallback or an unresolved appearance decision; stop at the allowance even if the numeric target is missed. Retain the best verified complete product and compact raw evidence, rejected candidate reasons and selected rebuild inputs; release disposable builds under the repository storage lifecycle. A result can close the paper reasoning task while runtime qualification and source changes remain deferred.

## Gaps this walk exposes

- **First-play contract:** the design distinguishes startup closure, on-demand content and residency, but D1 has not selected a machine-readable *first playable* dependency/readiness definition that covers action routing, required shaders and authoritative starting-region products. A splash/first frame cannot stand in for this gate.
- **Network-tail gameplay rule:** W2's lookahead depends on a qualified upper-tail `τ_ready`, which a changing or offline connection may not bound. The game must choose the safe stop/loading behavior, timeout/retry and what happens to action latency while blocked; F1/F4/W2 cannot infer those policies from a frame budget.
- **Web publication/cache coherence:** immutable product hashes and manifest swaps are specified, but the web package/service-worker rollout and mixed old/new cache handling need an exact browser handoff protocol before invalidated-cache and update claims are executable.
- **Shader demand A03:** the finite boot and transition variant closure, readiness/fallback and actually loaded shader identity remain open across F2/F4/V1/V3/T2. A compressed content win is unsafe until that closure is proved.
- **Cook/edit authority A02:** an external multi-file source update and a pending T1 edit need a coherent source change-set boundary before incremental cook timing can be trusted as a valid developer loop. A01 play-session isolation matters if the edit is tested against a running preview.
- **Budget and measurement:** actual browser/device matrix, perceptual floor, cook responsiveness target, network distribution, pressure signal, timestamp and physical-memory observability are unselected or unmeasured. Logical admission cannot be mislabeled OS memory qualification. The exact byte/time caps and safe activation chunking are D1/D2 parameters, not solved by this story.

This is a worked counterexample and proposed protocol under the current design, not closure of those missing mechanisms or a performance result.
