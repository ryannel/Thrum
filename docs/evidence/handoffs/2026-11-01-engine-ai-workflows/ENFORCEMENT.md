# AI-first engine enforcement handoff

1 November 2026. Design analysis for the proposed custom Rust engine and games built with it. The engine and its Rust checks do not exist yet. This note proposes a small, diagnostic-first gate set; it does not change current repository policy or implement a linter. Read with `notes/engine-rebuild/ENGINE-EXPERIENCE.md`, `modules/TOOLS-DELIVERY.md`, `CONTRACTS.md` and `ARCHITECTURE-AUDIT.md`. A01–A05 remain open, so their affected interfaces must not be frozen by a check invented here.

## What the current repository actually verifies

The shipped TypeScript/Vite game is a useful precedent, not the Rust engine's architecture. `package.json` runs three TypeScript checks, ESLint, baseline guard, WGSL static/Naga checks, Prettier, a value-import cycle guard, Knip and the fast tests in `npm run check`; `check:full` adds WGSL compilation, gated GPU probes and slow tests. `npm test` uses `.agents/scripts/test-changed.mjs` to select fast tests from a static import graph against files changed from `origin/main`; its source/import matching does not cover every shader, data, generated or configuration relationship. A selected set is useful feedback, not proof that every affected behavior ran. These commands apply to the current tree only.

`eslint.config.js` and `.agents/lint/` enforce layer import directions, public/lab/testing surfaces, forbidden dependencies, typed imports, limited sim ownership by adapters, conservative module-state rules, complexity/size bounds, naming, casts, GPU boundaries and selected WGSL rules. `cycle-guard.mjs` rejects value cycles in `game/src`, while type-only cycles are allowed; labs retain a recorded cycle baseline. `eslint-suppressions.json` holds existing violations and `lint-baseline-guard.mjs` prevents per-file/per-rule debt from growing or moving without a recognized rename. Scripts receive recommended lint rules without type information. These are exact current mechanisms, not proof of a future Rust check.

The existing conventions also show where blanket translation would mislead: `render/audio/ui` may call pure sim helpers but may not construct or step sim objects; `local/adapters-do-not-own-sim` uses type information but recognizes a finite set of constructors and stepping method names, not every semantic mutation. Mutable `TUNE` tables have an explicit exception; pure-layer readonly checks are shallow and admit other escape paths; `local/surfaces` is a declared-port rule, not a full proof of runtime authority; the cycle guard ignores type-only imports. TypeScript's 400-line/80-line limits, five-parameter limit, file naming, no casts and no magic numbers are local readability decisions. Do not import them verbatim into Rust, where modules, traits, generated code, `unsafe`, numeric kernels and borrow-checker behavior differ. The engine should retain their underlying goals: small inspectable units, explicit authority, public boundaries and reviewable exceptions. Rule configuration and suppressions are policy changes for review, never an agent's shortcut to make a failure green.

## Minimum proposed gates, in implementation order

All commands in this table are **proposed, not implemented**. Their eventual names are illustrative. An agent's first failure should identify the object or system, selected target/profile, relevant source span or stable ID, and the shortest cause chain; structured JSON carries the same diagnostic and revision for tools. Emit an applicable error at the earliest stage, while preserving valid incomplete draft source.

| Priority / owner / stage | Proposed enforceable rule and command | What it proves; limit |
| --- | --- | --- |
| 1. Rust compiler plus F1/F3, D1 then I1 | `engine check code`: compile selected game and engine crates, including supported target configurations; expose narrow public APIs for authoritative world mutation, clocks, saves, products and GPU handles. Make ordinary game rules use explicit system registration and typed input/output. | Type/visibility/trait checks reject many invalid calls; a separate resolved-setup gate detects missing registrations. The compiler cannot prove that a system's behavior is deterministic, that a declared access set is truthful, or that external code has no side effects. An internal `unsafe` or privileged adapter is a reviewed boundary with a reason and owner, not a blanket ban. |
| 2. F1/F2/F3 plus T2, D1 then I1 | `engine check setup --target <name>`: resolve the **effective** setup from explicit game registration, named defaults, selected build inclusion, target/profile and authored content. Validate missing/conflicting providers, required capability/quantity/units, unsupported target combinations, save readers and build/load/live transition scope. Print `why included` and provenance. | Finds an unsatisfied or contradictory selected plan. A declaration graph alone is insufficient: a capability may be registered yet not active, or a content object may demand a provider not selected. Do not require novice authors to maintain redundant hand-edited manifests or infer registration from hidden folder scanning. No automatic cheaper physical substitution. A01/A03/A04/A05 will refine selected constraints. |
| 3. F1/W1/F3, D1 then I1 | `engine check schedule`: derive the **effective** tick/phase/access graph from registered systems and selected profiles; reject an actual cycle, ambiguous authoritative writer, missing before/after constraint, undeclared resource/component access where instrumentation or an API can observe it, and a producer consumed before its publication boundary. Report the minimal cycle or producer/consumer path. | A declared schedule is a promise; a resolved schedule and controlled access API can check whether the engine *could* run it coherently. Static code search cannot prove all effects of arbitrary Rust calls, native libraries, callbacks or dynamic dispatch. Use runtime assertions/instrumentation in dev builds and targeted behavior tests to close that gap. A system with legitimate multiple phases declares them explicitly. Avoid broad `no cycle` rules over type relationships or a single total order that destroys parallelism. |
| 4. F3/F4/T2 with F2, W1/W2 and V1/V3 consumers, D1–D2 then I2 | `engine check content --target <name>`: validate structural schemas, stable IDs/units, references, asset package dependencies, source-to-cooked closure, migration support and finite required shader/material/pass/geometry variants for selected content and supported visual tiers. Stage an immutable manifest only after all required products pass. | Schema validation catches shape/version issues; cross-record semantic validation catches missing/incompatible references; effective product closure catches omissions that a declared asset list misses. It cannot certify appearance or runtime device support. Draft source can save before target readiness. A03's shader-demand representation and A02's coherent external source snapshot must be chosen before this gate's exact inputs are frozen. The existing `factory/ASSET-STORAGE.md` remains canonical for current assets; new engine records are adapters/projections, not an unrequested migration. |
| 5. P7/F1/W1/T2, I1 then I2 | `engine test replay --scenario <name>`: run a fixed-step headless scenario twice from a pinned source/setup/content snapshot, seed, initial state, inputs and captured external results; compare authoritative state hashes at declared checkpoints and exercise save/restore and stale-result rejection. | Establishes determinism only inside a stated envelope for that scenario and target implementation. A static ban on wall clocks or random calls is useful in authoritative crates but cannot prove deterministic math, parallel reduction order, stable serialization, platform floating-point equivalence or all external effects. Conversely, a hash match once is not a universal guarantee. Keep render captures and presentation timing separate from authoritative replay. |

The first four gates should be fast and local enough for an edit loop; T2 records exact inputs and gate results for a pinned candidate. Targeted test selection should use declared dependency/schema/content closure, not only source imports, and conservatively run a wider suite when that closure is unknown or the checker changes. A build/package gate consumes those results and then proves target package load, required offline assets, restore and selected smoke behavior. Release qualification additionally needs named device/backend performance and human-approved appearance. A green `check` cannot promote the maturity ledger's `visualEvidence` or `platformEvidence` fields.

## Static rules that are worth the maintenance cost

Add a narrow architecture lint or source/metadata validator **only where compiler/API design does not express the boundary**. Start with: (1) authoritative modules cannot import/use platform wall-clock, nondeterministic RNG or GPU facilities except through named adapters; (2) engine internals cannot be imported from game crates when a public port exists; (3) the declared system access/schedule metadata and selected setup use registered stable IDs, not hidden discovery; and (4) selected content and provider graphs have no dangling hard edge. Rule (1) should resolve symbols through the Rust compiler or an equivalent semantic index; token/regex matching would miss aliases and flag names in comments. Rule (2) needs a curated crate/module dependency policy and explicit test/tool exceptions. Rules (3) and (4) belong to schema and graph validation, not an AST rule.

Do not start with blanket `unsafe`/numeric-literal/clone/trait-size/line-count prohibitions. They produce false positives in SIMD, FFI, generated bindings, shader/layout kernels, codecs, tests and compatibility adapters, and can hide genuine ownership errors in exception lists. Prefer a small allow-list of boundary crates/functions with a local rationale and tests. `cargo fmt`, compiler warnings and a selectively configured Rust linter can support readability, but no current Rust workspace or configuration exists here. Proposed command names must remain labeled proposed until implemented.

Distinguish three graphs in every diagnostic: **declared** source/feature/schema metadata, **resolved** active plan for the selected target/profile/content and **observed** work/products/accesses during a run. The declared graph can be structurally valid while the effective graph has a missing provider or shader; a valid effective graph can still overrun memory or produce wrong pixels. Preserve provenance through all three rather than reporting “the graph is valid.” A dependency checker can be complete over the declared subset while only partially observing dynamically selected code; disclose that limit.

## AI-first workflow contract and proof boundaries

Make each gate callable by the human CLI, workbench and local agent API over the same snapshot and schema. An agent can query bounded schema, setup, object, access graph, dependency closure, pending jobs and evidence by stable ID; submit a typed edit with expected revision and idempotency key; receive a semantic diff and structured failure; then re-query after conflict. This follows T1's proposed operation surface and avoids a separate agent-only source truth. Source files stay canonical, and external multi-file changes require explicit coherent sync under A02. Play is an isolated, pinned session under A01; code/schema changes rebuild and restart. Agent work never quietly applies runtime state back to source or assumes a watcher proves a checkout complete.

Use targeted proof rather than overclaiming lint: compiler/API tests for access controls; graph fixtures for provider conflicts, declared/effective divergence, schedule cycles and clear cause chains; transaction tests for stale revision, idempotency and partial source/cook failure; a headless replay scenario; target package smoke; visual captures with human review; and device performance traces with stated thresholds. The engine architecture programme places analysis and cross-owner contract closure before experiments. These tests check a selected design; they do not choose missing A01–A05 mechanisms by trial.

**Immediate design handoff:** D1 should specify the exact typed registration, schedule/access declaration and source snapshot that the first four checks consume. F2/F3/F4/T1/T2 should agree on a single effective-plan/provenance diagnostic schema. A03 must close shader demand with V1/V3, and A01/A02 must close source/play isolation and coherent file admission before implementation. Keep any newly authored enforcement rule next to its owning checker, with one positive and one rejected fixture and a documented exception path. Do not expand the rule set until its error message helps an agent repair a real supported workflow.
