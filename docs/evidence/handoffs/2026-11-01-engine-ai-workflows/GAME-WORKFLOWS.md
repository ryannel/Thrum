# Game-development workflows for an AI-first engine

1 November 2026. Paper workflow review of [developer experience](../../../design/ENGINE-EXPERIENCE.md), [empty-project walkthroughs](../../../design/FROM-SCRATCH-WALKTHROUGHS.md), and [tools/delivery design](../../../design/modules/TOOLS-DELIVERY.md). This is a proposal for an unbuilt custom engine. It specifies observable outcomes, not implemented commands or public syntax. A01–A05 remain open.

## Principle

An AI assistant should be able to use the same source, editor operations, build checks, play sessions, and evidence that a human uses. The core need is a legible, deterministic development loop: discover what a project accepts, make a reviewable change, launch exactly that source revision, inspect what happened, and report the limits of the result. A model runtime, inference server, embedded chat, agent-only mutation route, or MCP transport is not required. A local CLI with structured output is the first useful adapter; an authenticated local API or MCP wrapper can expose the same commands and queries later.

Direct code edits remain normal for game rules, algorithms, and provider implementations. Structured scene/asset operations are useful where F3 owns schema, stable IDs, revisions and validation. The agent must not write transient play state into source or bypass the owner of world, content, physics, GPU or save state. The visible workbench and headless client must share authority and diagnostics.

## Workflow 1: from empty project to one working action

**Creator request:** “Make a small overhead game: clicking a seed collects it, increments a count, opens a gate, and shows feedback. Start with an empty project.”

1. The client asks for target prerequisites and project capabilities. The result identifies engine/toolchain lock, actual installed target support, supported example/version match, and missing prerequisites. It chooses one target; installing mobile SDKs is not a prerequisite for a browser preview.
2. It creates ordinary project source: effective setup, an entry world and game view, seed and gate data, an input action, and a registered rule that owns the count/gate state. The optional guide and direct path produce the same files and registration. The UI camera, grid, and inspection light remain tool helpers unless explicitly authored as game content. A draft can be saved even when it is not runnable.
3. The client queries schema/help for each structured field and effective default. For rule code it uses normal source editing and language tooling. Before play, a readiness query scoped to the selected target reports entry, view, required products and provider dependencies. It distinguishes source syntax/schema validity from target-ready play. No hidden scene search or implicit physical model supplies missing registration.
4. It builds and launches an isolated play process pinned to the accepted source, provider/profile lock and content hashes. A launch result names session, source revision, target and active build. If new code fails to compile, the old session remains explicitly identified as old; it cannot be presented as testing the change.
5. A recorded input sequence clicks the seed. The client checks the authoritative count and gate state, action focus/consumption, matched rule execution, and visible feedback. It records a screenshot or short clip from the game camera and a trace/state sample at the same tick/frame, then reports functional and visual evidence separately. A human can inspect the same path in the editor.

**Failure the tools must explain:** A click can be consumed by workbench focus, miss the target, match no object data, reach an inactive/unregistered rule, or be rejected by game logic. The diagnostic must connect declared action and system to the accepted plan, active schedule, matching objects, state/events, source location and session revision. The engine can reveal the rejection event but cannot invent the game's “already collected” reason if game code did not supply it.

**Minimum proof:** Create from genuinely empty source, run a click replay headlessly for state assertions, render one view for review, restart from the same pinned inputs and get the same authoritative result within the declared deterministic envelope. An empty scene and rules-first headless game have different readiness requirements; neither route needs a camera before its chosen run mode does.

## Workflow 2: diagnose a visually or behaviorally broken game

**Creator request:** “The boat looks underwater and steers through a dock after I changed its material and water setting. Find what is actually wrong.”

1. Capture the failing view and a short input replay with source/build revision, target/backend/device, active provider plan, camera/exposure, content hashes, world tick and frame. Label whether the capture is actual target rendering or a proxy. A recent source edit is not assumed to be active in a running session.
2. Inspect the boat by stable authored ID and current runtime identity: source transform and imported pivot/scale, active pose, collider/body state, material/product provenance, camera visibility, light/display inputs, water query provider and draw provider. Query bounded dependency slices, not a whole-scene dump. Compare a neutral asset view with the game view to separate import/material defects from scene lighting and medium integration.
3. Replay the steering input and query action routing, rule/system execution, physics contacts and resolved body motion at the relevant ticks. Correlate a frame trace with the clip. If no collision was authored, say so; if a stale collider product was active, identify its source/product generation; if steering changed only the renderer, identify the authority violation. A visual mismatch does not automatically imply a simulation failure.
4. Propose the smallest source or typed scene edit, with expected revision and a semantic impact preview. The preview names affected assets, physics/nav products, providers, views/histories, staging memory and whether restart is required. Run a target readiness check and one repro replay after activation. Return before/after state assertions, view captures, actual active revision and any unresolved visual judgment.

**Failure the tools must explain:** A tool may accept a desired edit while cook or activation fails. The report must separate desired, active and checkpoint revisions and provide the failed dependency path. An old valid view remains live, but is not called “fixed.” A stale worker result or cached web bundle must be identifiable by content/build hash. If the target cannot render the selected material/pass, report the unsupported combination and explicit choices, not a silent fallback that changes physics or quality.

**Minimum proof:** Reproduce a defect before changing it; one test at the lowest useful layer for an authoritative state bug, plus a named target capture when appearance is part of the claim. A screenshot alone does not prove contact or steering; headless state alone does not establish that the boat looks right. Human visual acceptance is a separate recorded decision.

## Workflow 3: change an engine provider used by a game

**Developer request:** “Replace the water-surface query model for this scene; keep buoyancy, wake drawing, camera and replay working.”

1. Discover the public provider contract, version/capability matrix, consumers, owner and target support. The relevant tool output lists units, time/sample conventions, validity domain, authority, determinism, quality limits, demanded content/shaders, and fixture requirements. This is a source/code change with a rebuild/restart unless the design explicitly supports a narrower data-only transition.
2. Before editing, obtain a bounded consumer impact graph: hull/body buoyancy, motion feedback, wake generation, water presentation, gameplay rules, save/replay, asset products and target profiles that consume the old provider. Query the current plan and its provenance. A visible water draw is not automatically a physical surface query. If a river joins the sea, A04's domain-edge flux/level/query ownership must be decided before claiming a compatible provider; if atmosphere/media overlap changes, A05 remains a separate contract.
3. Edit the provider implementation and registration in ordinary source, update typed schema/profile declarations where needed, and run compile, lint, contract and small consumer fixtures. Validate hard requirements before cooking. A missing provider or two authorities for the same quantity fail with a dependency path and source link. Declared and effective access can be checked at registration and instrumented boundaries; this does not prove arbitrary user code has no interior mutation or side effect. Do not automatically replace a gameplay model with a cheaper visual tier.
4. Prepare products for all affected active consumers under exact source/tool/profile hashes. A plan/dry run shows intended semantic diff, dependency closure, target shader demand/readiness (A03), peak old/new overlap, invalidations and expected restart. Only an admissible complete plan may activate. On failure the prior active plan remains, with staged failure and old/new revisions visible; retries and cancellation refer to a durable operation ID and generation so stale results cannot publish.
5. Run a pinned scenario: deterministic input/replay state, water query samples, body motion, drawn wake and two views at the selected targets. Compare captures with the named baseline and record trace/timing separately. If a code restart is needed, reopen an explicitly retained private test save only under the declared migration policy; it never becomes player or authored source by accident.

**Minimum proof:** A reference consumer fixture and one integrated scene distinguish “provider compiles” from “game still works.” A desktop capture does not qualify browser or mobile. A new provider API is not ready until its consumers and profile/build owners agree on units, authority, lifetime, content, replay and failure semantics.

## Tool contracts these workflows require

| Surface | Minimum observable contract | Existing design / unresolved detail |
| --- | --- | --- |
| Discovery | Machine-readable schemas/help with stable type and field IDs, units, defaults, ownership, allowed operations, effective value provenance, target capability/extension requirements and version compatibility. Human docs link to the same public API. | F2/F3/T1 direction exists. Exact source syntax and help format remain D1. |
| Scoped checks | A check request selects source revision, target and claim (source validation, headless rule behavior, content/provider readiness, rendered capture or package). Its result repeats exact inputs and reports pass, fail, skipped or unavailable with reasons and evidence links; it never turns a skipped platform check into a pass. | T2 gate direction exists. Public check selection/output format and target adapters remain detailed work. |
| Bounded inspection | Filter by stable ID, action, rule, asset, provider, frame or operation; include snapshot/revision, pagination/cursor, source location and causal links. Query accepted/desired/active/checkpoint states separately. | T1/T2 direction exists. Session-scoped source/state identity is A01/A02. |
| Reviewable changes | Typed edits with schema/semantic validation, expected revision, idempotency key, actor/scope, dry-run diff, dependency/cost impact and explicit commit result. Direct code writes need a coherent external change-set sync; do not treat watcher quiet time as a transaction. | T1 transaction design exists. A02 file admission, conflict and recovery must be resolved before API freeze. |
| Async work | Build/cook/play/capture return operation or job IDs, accepted/pending/completed/failed/cancelled state, progress stage, revision and target. Reconnect can query outcome. Cancellation invalidates late publications; retry is unambiguous within a durable epoch, then explicitly expires. | T1/T2 and C10 sketch this. Exact process and operation lifecycle needs A01/A02 closure. |
| Play and replay | Explicit launch/stop of isolated process; pinned code/source, schema, provider lock, products, seed, initial state and input/operation tick order. Private test-save namespace and intentional apply-back with source diff. Query authoritative world state independent of rendered frame. | ENGINE-EXPERIENCE direction; A01 session lifetime, side effects, restore and apply-back remain open. |
| Visual/motion evidence | Actual target screenshot/short clip with camera, tick/frame, exposure/gamut, profile and hash; input replay, world-state samples and correlated trace. Headless assertions, visual review, device performance and release claims remain separate. | T2 has scenario/capture direction. Target implementation and human visual acceptance are unqualified. |
| Diagnostics | Object/action first, then structured cause chain, owner, source, active revision and repair options. Distinguish source, content, provider, build, device and game-authored rejection. Report estimates as estimates. | Present in T1/T2 recommendation; needs end-to-end producer/consumer instrumentation. |

The same contract may have a human workbench, a JSON CLI and a local API adapter. The transport is not an architecture decision. All three must call the same validated operation/query authority. Agent access should be disabled in shipped games unless an explicit developer build enables it.

## Smallest credible build order

1. **Freeze source/session identity first (A01/A02):** coherent file change-set admission and recovery; accepted versus runnable revision; isolated pinned play process, stop, private test save and selected apply-back. Without this, a tool can falsely claim it tested its latest code.
2. **Provide typed discovery and revisioned edit/inspection for one scene:** stable IDs, units/default provenance, bounded queries, dry-run impact, async cook/activation status and stale-revision conflict. Use the same authority in a simple UI and JSON CLI; a full editor is unnecessary.
3. **Complete the first interaction path:** target preflight, empty project, action/rule registration and a headless rule fixture first. Then add one game-camera capture for the rendered path. Instrument declaration → plan → world construction → active execution, including zero matched objects and focus consumption.
4. **Add one provider change path:** one reference fixture and one integrated consumer scene; provider closure/error explanation, A03 finite shader demand, cook generation checks, restart, replay, trace and capture. Close A04/A05 only for model combinations actually advertised.
5. **Qualify named targets incrementally:** build/packaging provenance, clean checkout and offline/load checks where claimed, target captures and device measurements. Report each unqualified target honestly; release publication is a separate action.

This sequence gives an AI agent useful work after steps 1–3 without requiring every engine module, model, platform, visual editor or inference service. The stop condition for an AI workflow claim is a repeatable source-to-active-to-evidence path with a human-readable failure path. Paper scenarios alone do not establish implementation, usability, appearance, performance or platform qualification.
