# AI-first engine and game contribution: skills and setup review

1 November 2026. Design-stage recommendation only. The custom host and SDK do not exist yet. Rust is the current shared-runtime/tools recommendation, with Mac, PC, browser and mobile targets; exact toolchain, public syntax and support matrix remain D1/I1 work. A01–A05 remain open, so this plan must not freeze their interfaces or claim a working agent workflow.

## Decision

Make the engine's ordinary source, public APIs and typed tool operations useful to both people and agents. Add a narrow skill for **routine engine changes** and one for **building games with the SDK** when their real commands exist. Add a shared **runtime diagnosis** skill only after a working inspect/replay surface gives it a distinct recurring job. Keep architecture and new-module work in the existing `engine-architecture` and `engine-module-design` skills. Put invariants in schemas, compiler checks, tests and CLI diagnostics; use skills to route judgment and evidence collection. Do not create a skill per engine module or a mandatory stack of skills for every edit.

The [developer experience](../../../design/ENGINE-EXPERIENCE.md) already recommends ordinary source, one inspectable setup, a prerequisite check, version-matched examples, and the same editor/CLI/agent operations. [System design](../../../design/SYSTEM-DESIGN.md#ai-oriented-structure-and-development-surface) assigns query/operation contracts and bounded diagnostics. [Tools/delivery](../../../design/modules/TOOLS-DELIVERY.md#t1-one-operation-and-query-surface) details revision preconditions, stable IDs, transactional activation and provenance. Skills should teach contributors to use those interfaces, never invent an agent-only authority or ask a model to infer hidden engine state.

## Routing and context layers

1. **Root/core instructions:** retain short durable facts: where the custom engine and game projects live once chosen; project skill precedence; preserve unrelated work and worktrees; source-of-truth links; how to choose the first relevant task route. Remove the blanket three-skill read after scoped instructions are available. Do not embed the 29-responsibility map, all contracts, a universal test matrix or per-module tips in root context.
2. **Scoped `AGENTS.md` in the future implementation checkout:** one for engine-owned code, one for SDK game/examples, and narrower files only when a real boundary warrants them. State owner, import direction, public surface, local commands, where evidence goes and escalation triggers. The new implementation's path is not yet selected; do not apply these to existing `game/` merely because its name matches. Existing Broadsides TypeScript keeps its current rules.
3. **Task skills (on demand):** `engine-architecture` for whole system; `engine-module-design` for new/substantially redesigned module; proposed `engine-contribute` for an implementation change within an accepted design; proposed `game-authoring` for a game using public SDK surfaces; proposed `runtime-diagnosis` for an observed failure requiring inspect/replay across engine or game. Only load one primary task skill, then the relevant reference page or contract section. Architecture owner can request both when a task genuinely spans design and implementation.
4. **Machine-readable truth:** schemas/API metadata, dependency closure, build plan, diagnostic queries, sample-project manifests, evidence records and pinned release lock. The skill tells an agent which query or check to run, while tools determine validity.

### Proposed skill contracts

| Skill | Trigger and boundary | Useful output/stop condition | Supporting references to load only when needed |
| --- | --- | --- | --- |
| `engine-contribute` | Implement or repair a bounded engine behavior, tool command, public API or integration inside a selected design. A semantic owner, clock, schema or cross-family contract change routes to the architecture owner and relevant module review before dependent code is accepted. | Small owned change with exact API/contract version, affected producers and consumers, applicable scoped checks, one behavioral proof or repro, evidence and unresolved limits. Do not claim visual/platform qualification from headless tests. | One-page contribution quickstart; public API/contract lookup; scoped check matrix; operation/query and evidence reference. No copy of all engine contracts. |
| `game-authoring` | Create or change a game, example or extension on the engine SDK; includes empty-project, guided, direct and headless-first paths. A new engine capability or unsuitable public seam routes to `engine-module-design` or architecture review rather than private imports. | Ordinary inspectable project source; one effective setup; runnable named target or a precise readiness failure; interaction/state/feedback proof where requested; source revision and target/profile captured. Sample content can be deleted without leaving a special project mode. | Version-matched quickstart, task recipes (interaction, art, save, external code), public API index, target prereq guide, troubleshooting/query reference. Load the task page, not the whole SDK. |
| `runtime-diagnosis` (conditional) | An observed game or engine failure needs targeted state/trace inspection, replay, or source-to-runtime provenance. Use only when inspect/replay commands work. A structural diagnosis can route onward to architecture or module redesign. | Reproducible failure identity, causal trace across owners, smallest responsible contract/model, corrected outcome and honest remaining uncertainty. | One inspect/replay command map, scenario format, diagnostic interpretation and evidence fields. No duplicated module-specific troubleshooting encyclopedia. |

The skill descriptions should be discriminating: “Use when changing an accepted engine implementation or its public integration,” “Use when creating or changing a game with the engine SDK,” and, only when operational, “Use when tracing a reproducible runtime failure through engine/game state and provenance.” Their first screen should name input, expected outcome and route changes. Existing `engine-architecture`/`engine-module-design` descriptions already separate whole engine from substantial module design. No separate “AI orchestration” or per-provider skill is justified yet. These proposed names are design labels, not installed skills.

## Minimum contribution setup

Build this as an SDK product, not a pile of prompt files. D1/I1 should choose and ship a pinned engine/toolchain release manifest containing compiler, content/schema tools, public API revision, target triples, feature/profile definitions and supported device/browser range. A prerequisite command checks only the requested target and explains the next missing dependency; an engine-contributor can use a smaller engine/tool bundle, while a game author installs the SDK/game bundle and only the selected target's platform tools. Mobile signing and store credentials are separate optional steps.

Provide one clean-checkout path for each role. Engine contributor: clone selected source revision, verify toolchain and generated/API products, run a headless smoke path, edit one public contract or implementation, run owned checks and a consumer example, then produce an evidence record. Game author: create an empty project or expand a small editable sample into ordinary files, inspect effective setup and dependency plan, add one action/rule/feedback loop, run on a named target, query failures by object/action/revision, then package a development export. The exact commands and syntax must come from D1's implemented CLI, not this document's invented examples.

Every release should pair docs, API reference and examples with the same immutable SDK revision. CI should compile the documented snippets or execute examples against that revision, verify API links/anchors, check starter lockfiles and target claims, and run a clean-cache rebuild. Unsupported targets or unavailable shader/content products should fail with the missing requirement and consumer, not produce a plausible but misleading sample. Samples need an actual interaction and a route to source. A bootstrap copy must not silently rewrite game-owned code on engine upgrade.

## Tool-enforced behavior versus skill judgment

| Put in tools/checks | Leave to skills and review |
| --- | --- |
| Schema versions, units, field ownership, stable IDs, required products and profile compatibility; explicit public imports/registration; operation preconditions, idempotency, revision/epoch and dependency validation. | Identify the smallest relevant owner and consumer set; choose whether a change is routine, module redesign or architecture; assess whether a new abstraction improves actual games. |
| Reproducible headless scenario descriptor with pinned seed, tick/input stream, code/schema/content/profile lock and captured external results; known nondeterminism declared. | Select a scenario that tests the consequential behavior; distinguish semantic proof from rendered appearance and device evidence. |
| Compiler/lint/import guards, schema generation and drift checks, focused tests, examples that compile, clean-checkout setup, package/build closure, queryable source-to-runtime provenance. | Interpret diagnostics, correct the model or contract, and explain limitations. Avoid tests that merely inspect source text or mirror implementation. |
| Query APIs for effective setup, producer/consumer dependencies, active versus desired revision, pending operations, resource/plan status and bounded traces. | Ask targeted queries and hand off a compact causal account rather than dumping full logs into context. |

The engine's deterministic envelope has to be defined per authority: fixed authoritative ticks and explicit event ordering for headless semantics; asynchronous render/audio, driver timing and visual captures get reproducibility metadata and separate acceptance. The agent should never describe a passing unit test as Mac/mobile/browser qualification.

## Parallel work and handoff

Use an isolated worktree or clean checkout per task only after checking disk and owner status. Assign one owner for each shared contract. Parallel agents can own independent modules or games, but a cross-boundary change begins with a compact contract proposal: ID/revision, semantic change, producers/consumers, migration/compatibility, tests and proof scope. The architecture owner resolves it and notifies affected owners before dependent branches build on it. Do not let each branch create its own authority, schema or overlapping version of a public surface. Integrate reviewed slices sequentially. Preserve unrelated working changes and other agents' worktrees.

The handoff is a small machine/linkable record: task and owned paths; base/head revisions and dirty state; public API/schema/toolchain/profile locks; changed contract IDs and affected consumers; exact checks and scenario/capture commands with results; evidence location/hash; assumptions, unresolved gaps and requested review. State whether the result is design, built, functionally checked, visually accepted or platform qualified using the maturity ledger's separate axes. No missing artifact counts as passed evidence.

## Behavioral validation before adoption

Run independent fresh-agent tasks with the task brief and relevant skill only, using a real pinned SDK/checkout. Score the artifact and decision trail, not whether the agent repeats wording. Keep baseline and skill-assisted runs comparable; record route choice, context loaded, files/commands used, failures and task completion.

1. **Engine routine repair:** A fixed-tick behavior regression with a failing headless scenario. Success: a minimal repro/fix on the owned surface, consumer check, stable seed, truthful evidence. Failure: invokes whole-engine redesign or changes a second authority.
2. **Cross-boundary change:** An asset/schema edit affects runtime and render or save. Success: notices producer/consumer closure, sends a contract delta, checks revision/activation behavior, avoids private cross-imports. Failure: a local pass while a consumer is stale.
3. **Empty game:** Start from no sample on a named supported target, create one interaction and inspect a failed click. Success: ordinary source and one setup, working action/state/feedback, diagnostic reason tied to source revision. Failure: hidden template mode or invented API.
4. **External extension:** Add a narrow physics/material/library integration. Success: uses the smallest real public boundary, conformance check and target support statement; ordinary helper remains ordinary code. Failure: builds a generic plugin descriptor or claims unsupported save/model compatibility.
5. **Clean handoff:** Another agent opens the exact revision without warm caches and produces a development export. Success: pinned inputs and tool versions, prerequisite messages, build products and launch steps. Failure: depends on private local files, an absent SDK, or cross-target claims from one run.

Negative routing probes matter too: a TypeScript Broadsides bug should still use the existing `code-conventions`/`testing` route; a whole-engine authority dispute uses `engine-architecture`; a new water model uses `engine-module-design`. Refresh tests when public APIs change. A skill whose only measured effect is naming or syntax compliance has not established value.

## Sequence

1. In D0/D1, close A01/A02 before freezing source/session identity and contribution commands; define A03 demand readiness before executable render samples. Keep A04/A05 open in affected model docs until their owner reviews close them.
2. During I1/I2, implement the minimal query/operation, prereq and headless/first-interaction paths, then write the contribution and game skills against actual commands and release-matched documentation. Add `runtime-diagnosis` when inspect/replay supports the behavioral trials. Scope future `AGENTS.md` to the chosen new implementation/game paths and shorten root routing only after those paths exist. Broadsides' foundation queue and TS/Vite rules remain with the existing game/labs tree.
3. Run the behavioral trials above and clean-checkout trials on named supported targets. Record failures as product, doc, check or skill problems; repair the responsible layer and rerun only the affected trial. Promote no maturity axis without its own evidence.
