# Empty-project circumstances: three adversarial paper journeys

1 November 2026. These are paper walkthroughs of the proposed custom Rust-hosted engine, not executed SDK paths, observed users, measured latency, or certified exports. They start with an empty project: no entry scene, camera, light, material, object, controller, action, input binding, save schema, imported asset, or example rule is presumed to exist. They pressure-test the recommended developer model in [ENGINE-EXPERIENCE](../../../design/ENGINE-EXPERIENCE.md) and the earlier starter-based [first-use review](../../../design/FIRST-USE-WALKTHROUGHS.md). The target remains Mac/PC, browser, and mobile apps; the custom host is proposed, not built. A01–A05 in the [architecture audit](../../../design/ARCHITECTURE-AUDIT.md) remain open.

The first-timer here can edit code and files but has never used this engine. The veteran can write Rust/game code and deliberately chooses an empty project to avoid inherited game policy. In both cases, *source* means versioned game-owned files and editable asset masters; cooked textures, shaders, platform packages, and play state are derived or separately retained products. A clean checkout must be able to rebuild those products for its declared target, subject to named tools and licenses. A playable export is a separate product that its nondeveloper recipient uses without an authoring SDK. A well-formed empty draft must be saveable as source even when it has no runnable entry; source/schema/operation checks still apply. Play and build readiness then check their chosen target and required graph, without forcing every platform's prerequisites on the first edit. No commands or APIs below are executable claims.

## C01 — Solo creator's small offline mobile workshop

**Need and initial choices.** A first-timer wants one room, a tappable workbench, a recipe counter, a little characterful art, and a local save. The first target is an offline native phone build. Before touching a scene, the creator must select the mobile target/host combination and learn whether this computer has the relevant Rust toolchain, native SDK, device/deployment path, and content cooker. A desktop preview is useful, but it does not validate touch, suspend, storage, or device rendering. “Offline” has two distinct promises: the installed game can start and play without a network, while a developer's first build may need dependencies and SDKs downloaded. The tool must say which is supported; it must not quietly require a server at game startup. Optional remote art is inappropriate as required first-scene content.

**From zero to the first own interaction.** The creator can save the empty source draft. To play, the creator needs a project entry, a room or empty scene, one visible workbench (a documented built-in primitive is acceptable only if actually supplied), a camera that frames it, a material and light/display setup that makes it visible, and a touch action routed to a game rule. A tap should increment a game-owned completed-recipe count and update a legible UI label or other feedback. If input picking requires collision or a hit shape, that requirement must be named and authored; the visible mesh alone does not prove it can be tapped. If the project has no entry scene/camera/light/action, play readiness should identify that missing link at the action or scene where possible while leaving the valid draft intact. An implicit scene, automatic camera, or default binding can help only if its source and effective value are inspectable. The simple rule should not force physics, character animation, outdoor lighting, networking, or an extension package.

**Persistence and art arrive in deliberate order.** Once the tap works, the creator decides what survives restart: count and any pending recipe are player state, while workbench placement and recipe definitions are source. Define the durable schema and checkpoint/suspend policy before claiming offline saves. A private play save can exercise restore but must be labelled separately from a real install's save slot. The artist replaces the primitive with a licensed master asset, imports it, inspects units/orientation/material and hit shape, and retains the master and import settings in source; cooked mobile variants are reproducible products. The creator may adjust camera, palette, light, UI scale, safe-area placement, and touch size for this game. This is an art and interaction task, not a demand for every mobile UI feature in the engine's minimum example. A license or provenance record matters when the selected art is redistributed; an empty project cannot assume the starter's sample art is licensed for this game.

**First handoff and failure.** On a clean development checkout, the engine/tool version and source dependencies must resolve; the content cook and mobile package must regenerate without borrowing ignored local caches or the creator's private save. A nondeveloper recipient installs the finished package without the engine SDK, opens it without a network, taps the bench, leaves/restarts, and sees the committed recipe count. If a required font, texture, shader variant, or storage adapter exists only in the developer's warm cache, the export fails before the recipient receives it. If a recipe/schema edit later makes the test save unreadable, keep the old save and identify the version mismatch; migrate only through an explicit supported path or start a new private test save. On device interruption during a save, the last complete checkpoint must remain recognizable, with failure reported rather than an invented success. These are qualification scenarios, not claims the design already meets them.

**What this exposes beyond a starter.** U03/S02 start with touch actions and a room already assembled. Empty-project use must explain the first dependency chain from project entry to tappable object and feedback, then the boundary between editable source, local test save, player save, and offline package. The earliest hard choice is save semantics, not visual fidelity. Owners: F1/F2 for setup and action diagnostics, F3/F4/W1/T1 for scene/import/source, P7/T2 for saves and target package, A01/A02 for play/source isolation, A03 for required mobile shader closure. I3 can qualify one complete interaction; the relevant I4 mobile slice qualifies offline start, lifecycle, and export on named devices. No general offline development distribution or store submission workflow is implied.

## C02 — Artist and programmer build a polished browser portfolio demo

**Need and initial choices.** A veteran programmer and a first-time engine artist want one short, deliberately framed scene: walk to a lantern, switch it on, and reveal a small composition. The portfolio recipient opens a browser link on a named supported browser/device class. The team chooses browser as the first target, defines the content entry and approximate download/startup budget as an assumption to measure later, and pins the engine/tool release together. They must know whether browser output and the selected material/lighting path are supported before authoring a look around them. A desktop renderer preview cannot certify browser shaders or appearance.

**From zero to the first own interaction.** With no starter, the programmer must create an entry scene, camera and controller or a simpler click/tap action, the lantern's hit/collision shape, a game-owned on/off state, an input binding, a rule that changes the state, and visible/audio feedback derived from it. If walkable control is chosen, body motion and camera follow need named owners; a camera that happens to show the asset does not imply a controller. The artist imports a self-owned lantern and small environment, inspects scale, orientation, textures, material slots and light anchors, then frames the scene through the actual browser target. Imported lights/cameras are accepted source data only if deliberately selected, and the art workbench edits the same versioned scene that the programmer's code reads. The lantern may light the scene without a visible sky or an atmosphere module. The artist should see which light, surface and display settings contribute to the result.

**Two-person edit and style pass.** The programmer changes the toggle rule while the artist adjusts placement, materials, exposure, shadow response, and a palette. These are different edits to the same source project; neither editor operations nor file writes may silently replay over the other person's newer revision. External checkout/import must be admitted as one coherent change set, with an inspectable pending change and an explicit accepted revision. A live play session remains pinned to its old revision until rebuilt/restarted. Reimporting a revised lantern mesh must preserve authored overrides where stable node correspondence exists; an ambiguous renamed slot or moved light anchor is a conflict to repair, not a reason to drop the artist's work. A polished style may require new geometry, painted textures and supported material/pass combinations. A “painterly” or “toon” switch is not a substitute for those choices.

**Recipient, clean build, and failure.** The portfolio package should include only the entry scene's required cooked content and compatible browser shaders, with the authored masters and license/provenance retained in the project source or its recorded durable store. A clean development clone needs the pinned toolchain and accessible source assets, not the team's import cache. The nondeveloper recipient follows the link without an engine SDK, waits for the named download, and completes the lantern action. The output must identify the accepted source revision and target so an old CDN/browser cached build is not mistaken for the new change. If the chosen skinned shadow, outline, transparency or lantern material pass is unsupported in that browser tier, validation names material, pass and target; the team chooses a supported look or narrows the target. It cannot silently show an unlit asset or claim the desktop capture represents the browser. A broken reference after reimport leaves the prior complete build identifiable and preserves source for repair.

**What this exposes beyond a starter.** U07–U09 begin with an imported room or working character and defer multi-person source admission. This empty-project case makes the smallest shared authoring surface and target-aware preview necessary for an artist before “artist usability” is claimed, while keeping the programmer's rule ordinary code. It also connects source licensing and asset masters to a recipient's cold browser build; sample content being available in a template does not answer whether a portfolio team can redistribute it. Owners: F3/F4/W1/T1 for import, mappings and shared source; V2–V4 for light/material/display semantics; T2 for browser delivery; A02 for concurrent external edits and A03 for shader demand/readiness. I2 owns stable import/conflict operations, I3 a minimum visual workbench and full interaction, and the browser I4 slice qualifies the recipient path. No collaborative cloud service, full modeling editor, or universal style system follows.

## C03 — Strategy team proves rules headlessly, then adds presentation

**Need and initial choices.** A veteran team starts a turn-based strategy/simulation game with many simple units. Its first deliverable is a repeatable rules run in CI before anyone has authored a map mesh or renderer setup. The game may later show an overhead battlefield on desktop and a browser excerpt. The headless profile must be a real supported composition of the same world/rules authority, not a rendering failure mode. The team must choose a clock/turn model, input command format, seed handling if random, game-owned state and durable identity, and whether saves/checkpoints are in initial scope. It should not have to choose lights, shaders, GPU features, physics bodies, skeletal animation, or a visible camera to register a move rule.

**From zero to the first own interaction.** The team's first scene can be a data-authored board/topology or initial world record with two units and an obstacle; “playable” here means an external command orders a unit to move, the rule accepts or rejects it, the world advances at the declared step/turn, and an inspectable state/result changes. A command interface and deterministic runner need an explicit public path even without UI or a render window. If the engine's scene admission always demands a camera or render product, this is an architectural leak: either a headless entry has its own minimal valid requirements or the initial headless promise is false. Navigation can begin as ordinary game code over the board graph; a navigation service is warranted only when its shared contract/cost helps. A lost or stale path result after an obstacle edit must not mutate an unrelated later world generation. The unit position has one game/world authority; visual transforms later read that position.

**Presentation and source evolution.** Once the rules run, the artist adds a map/units, an overhead camera, selection/picking, material/light/display choices, and action feedback. The team maps rendered objects to the durable unit identities; cosmetic animation and quality tiers must not pick winners or alter the authoritative turn order. A close view could justify more geometry/animation; it does not turn all simple units into rigid bodies. A headless CI run and a desktop visual play session pin the same accepted source revision and rule version. Derived cook products differ, while the command semantics and saved rule state stay game-owned. If the team later adds a rule field, a retained private save or fixture must declare migration/compatibility rather than deserialize by accident.

**Clone, export, and failure.** A clean CI checkout with only source, pinned dependencies and declared tools must run the headless rule fixture without a GPU, licensed sample art, warmed shader cache or desktop window. The desktop/browser builds then add only the corresponding presentation products and target prerequisites. A nondeveloper reviewer can run an exported visual build and issue the same order; a test log alone is not a playable demo. If headless registration secretly imports a renderer or device initialization, CI fails for a reason the architecture should prevent. If the browser excerpt cannot fit the full simulation or content, the team must explicitly choose a bounded scenario or distinct rules variant, with its changed semantics named; lowering shadows cannot silently reduce unit count or alter orders. If an asset is absent, headless rules may still run, while a visual build with required content must fail clearly. Claims about thousands of units or browser performance require later measured workloads, not this trace.

**What this exposes beyond a starter.** S07 describes headless use after units and topology exist. Empty-project use asks whether the *first* meaningful change can be a rule with zero rendering resources, and whether later presentation attaches to the same identities without forcing an asset-first architecture. Owners: F1/F2/W1 for composition, command/rule and identity; P5 only if navigation becomes a service; F4/V1–V4/T2 for later visual products; P7 for optional durable saves; A01/A02 for revision/session boundaries and A03 for eventual browser shaders. I1 should qualify the GPU-free rule path; I3/target I4 slices add the visual recipient and export. This does not establish a mandatory general simulation server, network mode, or massive-agent performance target.

**Verification status.** This document adds no implemented project, runnable test, device evidence, public API, performance number or user acceptance.
