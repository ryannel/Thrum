# From-scratch veteran journeys — bounded paper dogfood

1 November 2026. Three empty-project traces for experienced creators. They test the proposed custom Rust host and [developer experience](../../../design/ENGINE-EXPERIENCE.md), [composition rules](../../../design/COMPOSITION.md), [first-use review](../../../design/FIRST-USE-WALKTHROUGHS.md) and [system design](../../../design/SYSTEM-DESIGN.md). They are design probes, not executable instructions, observed usability, or proof of target support. No starter scene, camera, controller, light, asset, provider, editor, command name or public API syntax is presumed. A01–A05 in the [audit](../../../design/ARCHITECTURE-AUDIT.md) remain open. Mac/PC, browser and mobile are ambitions; every export below requires its own qualified target and prerequisites. Existing code is a reconciliation candidate, not the engine being dogfooded.

The guided minimal 3D setup, direct empty setup and headless-first setup are possible authoring/documentation routes over the *same* project source, game registration, validation, runtime and target build path; they are not persistent modes or privileged templates. An editor navigation camera, grid, selection light or diagnostic mesh is a tool overlay and does not silently become a camera, light or asset in the exported scene. Conversely, a game scene without an authored runtime camera/light must surface that omission through validation or a clearly named visible default, never rely on what the editor happened to show.

## V1 — An experienced Unity/Unreal game developer builds a third-person key-and-door scene

**Situation and first decision.** A developer who has shipped a third-person game wants a tight exploration prototype on a desktop target. They know how to assemble actors/prefabs, bind input and cameras, and press Play in their former editor. They choose an *empty* project to see the engine's actual primitives. Before adding content, they name one desktop target, inspect toolchain availability and engine release, and choose whether the game needs rendering, input, UI, collision/character motion, and audio. Weather, water, streaming, inventory, save and network are absent. They must choose a compatible controller/body model and one motion owner, rather than assuming a generic `CharacterController` appears by creating a mesh. A visual recipe can supply inspectable defaults for camera, light, material and display; it cannot covertly install behavior or certify the result as artistically good.

**Source to execution.** The creator makes a room scene with floor, a door, a collectible key and a visible player placeholder. They set units, camera framing, a deliberately simple light, collision shapes and object identities in authored source. The imported room mesh is appearance data until collision is explicitly supplied/accepted. The player composition declares its visual, collider/body, camera-follow target and game-owned `has_key`/door state (names illustrative, not API syntax). In the one effective game setup they register the game schema and two systems/handlers with actual reads/writes and phase/order: semantic move/interact actions become intents; the selected locomotion/physics owner resolves movement; an interaction rule checks range and key possession and commits door state. The door mesh/animation and collision opening observe the same accepted door state at their respective barriers. Direct registration places this work *inside* the declared schedule and authority; it does not give game code permission to write a solved body transform, mutate committed world data from a callback, or submit GPU work outside V1. A local helper calculating interaction range remains ordinary code and needs no separate registration, plugin descriptor or provider.

**First vertical interaction.** Registration is only a declaration. The engine must resolve the selected services, validate schema and system access/order, validate scene and target product requirements, cook the required assets/shaders, pin an accepted revision, construct the world, then activate systems at their declared boundaries. If the developer registers a rule but forgets the key component on every object, inspection should show that the system has zero matching entities; if a feature is disabled, show that it never activated. Run the accepted revision: move to the key, collect it, approach the door, open it, walk through. Also try the door first. The engine can show that input was received/consumed, which system ran, which state writes/events occurred and which did not; it cannot infer the semantic reason `missing key` from arbitrary game code unless the rule emits a structured rejection or the developer has declared an inspectable condition. A useful starter example should author that reason and link it to the door and source rule. Inspect game-owned key and door state, physics body result, visual pose, source revision and running session. A moved door mesh with a closed collision shape is a diagnostic failure, not a successful interaction. Stop play and confirm unsaved key possession is discarded; authored placements survive. A retained private test save is introduced only if the developer elects to test persistence. Changing the rule or schema makes a new accepted revision and requires rebuild/restart; an older valid process must be labelled with its older revision. A changed lamp position may use a declared safe data preview; restart remains the baseline.

**Style, failure, delivery.** Replace placeholders with authored art and inspect imported scale, orientation, materials, skeleton/animation and collision mappings. Reimport must preserve game-owned overrides or report ambiguous node correspondence before accepting the affected collider/attachment. The developer tries a toon outline pass; if the selected target lacks a material/pass variant, validation names the object, material, pass and target and leaves the last valid build identifiable. The developer can explicitly choose a supported fallback or narrow the target. Export the one named, supported desktop profile from a pinned accepted source/product set and check the running package, not just the editor preview. Browser/mobile packaging remains separate work with separate prerequisites and device evidence.

**Vocabulary bridge and friction.** `Prefab`/`Blueprint` maps to authored recipe plus component schemas and required capabilities, not an opaque actor class. `Scene` maps to authored content with checked dependencies, not a place where executable components acquire update order by being present. `MonoBehaviour`/actor tick maps to registered systems and declared access/order. `Play in Editor` maps to a disposable pinned play session; editor undo, game undo and player saves have different scopes. A material graph is not implied by a material extension. The dangerous assumption is that a veteran can drag a controller or post-process component onto an object and have a valid owner, schedule and shader demand silently appear. The useful affordance is a source-to-runtime inspector showing each object requirement, its supplying binding, its current owner and the revision that actually ran.

## V2 — An engine/rendering specialist builds a small boat game around their own wave model and painted water

**Situation and first decision.** A specialist has a Rust wave/surface-query library and a stylized water shader. They want a single controllable boat circling a buoy; no weather or global hydrology is required. From an empty project they choose one desktop target for the first working slice, a fixed game tick, input, world, a simple rigid body, camera and baseline rendering. They separately decide whether the wave library is merely a pure function called by a game-owned rule, a provider of physical surface queries used by buoyancy/contact, or only a render deformation. Those choices have different authority and evidence. Their surface model has to declare coordinates, units, time, supported domain, validity/error bounds and state/reset policy before it can be advertised as a physical provider. A render shader can draw water without satisfying a boat's query requirement.

**Source to execution.** The specialist authors an empty scene, then adds a boat hull/collider, buoy, camera, light and a flat water surface. They select the motion owner (P3 or a qualified alternative), declare input actions and register the steer/throttle game rule with access/order. They first make a vertical slice with a prescribed or constant query-capable surface: steer the boat, observe an accepted action, observe body motion and a wake/visual response. This isolates steering, body and camera before the custom water work. Bringing in the plain wave library as source code needs dependency/target compilation and a call inside an existing system; its internal numerical arrays and search/spectral nodes need no engine schemas. Once buoyancy consumes its surface queries, the specialist binds one narrowly scoped physical surface capability through the public provider contract. The provider supplies samples/forces or query outputs to P3 at the declared tick; it does not directly integrate the boat or overwrite P3's authoritative transform. If waves have durable state, replay/save policy is explicit. A typed provider registration declares service ownership, target support, products and lifecycle, rather than using a `plugin` word to skip shared admission.

**Rendering and style.** A water material or pass extension declares geometry/deformation inputs, light/media inputs, pass placement, shader variants, target requirements, resource lifetime and motion correspondence for history. It submits through the GPU graph and cannot own an independent device/queue. The painted look comes from authored palette, shape, material response, light, shadows and display, with the camera/exposure held during comparisons; a `stylized` flag cannot guarantee it. If the renderer uses a visually displaced surface while physical queries use different wave phase/time, the buoy and hull expose the mismatch. Any render-only exaggeration is labelled and bounded rather than fed back into body motion. Removing visible water drawing may be possible while retaining the query provider; removing the query provider while the boat requires it must fail with the boat named as consumer. No atmosphere/sky is presumed. If a sky image is later added, background, environment light, Sun attenuation and local media remain separate outputs.

**Failure, debugging, delivery.** Attempt to bind a visual-only surface under the boat: admission should say that the boat needs physical surface queries and identify the unsupported contract. Attempt to use a shader variant unavailable for the selected desktop tier: the message should identify the boat/water material, pass, feature, target and missing product while preserving the prior valid play revision. Inspect one surface sample with source/provider ID, tick and units; one P3 force/motion result; the extracted water geometry; shader product readiness; and GPU frame/pass diagnostics. Change numerical code, accept a coherent source revision, rebuild/restart and check the old session is not labelled current. Export one qualified desktop profile with its finite shader-product closure. A browser profile must separately test Wasm/toolchain, shader limits, content size and device behavior; merely compiling the Rust library on desktop proves nothing about it. If a second river domain is added, A04 requires an explicit visual/prescribed/conservative interface; this first slice makes no seamless river-to-sea claim. If volumetric fog overlaps atmosphere, A05 remains a design dependency before an exact joint integration claim.

**Vocabulary bridge and friction.** `Plugin` may mean a source crate, a game system collection, a provider adapter, or a distributable versioned package; only the last needs package metadata by default. `Renderer replacement` is much broader than adding one material/pass; the latter is the demonstrated scope. `Physics plugin` cannot supply a second transform authority or assume private solver state migrates to another provider. The hidden burden is that a specialist may need the narrow contracts for queries, time, transform authority, shader demand and history *before* there is a working example. A tiny reference boat plus a conformance fixture for the exact advertised query/render targets would make the path testable, while A03–A05 prevent publishing this as an already supported recipe.

## V3 — A small-studio lead builds a stylized delivery loop around existing art and build tools

**Situation and first decision.** A two-to-five-person studio already uses Blender, texture tools, scripted asset exports and CI. They want a compact overhead cooperative-feeling single-player courier game: drive a cart through a town, collect one parcel, deliver it. (No network requirement is inferred from team size.) From an empty project, the lead selects a desktop target for the first playable export, names a browser target as a later independent qualification, and budgets content size and visual tiers without pretending one target's success certifies the other. They choose world/content, input, orthographic or tilted camera, rendering, simple collision/kinematic movement, semantic UI and audio if desired. They explicitly omit ocean, weather, skeletal animation, navigation, advanced physics and editor-only scaffolding unless a chosen asset or rule actually needs them. A named style recipe may initialize visible values, but its expansion and omissions must be inspectable.

**Source to execution.** The studio creates a scene with ground, cart, depot, parcel and delivery marker, supplying camera and light itself. Their importer converts an interchange file into versioned runtime products with a report of units/orientation, material slots, textures, unsupported data and stable source-node mapping. The editable masters and importer settings remain separate from game-owned placement, collider and material overrides. The lead registers a cart-control rule, parcel pickup/delivery rule and game-owned parcel status; input actions enter the fixed tick, collision/picking checks the candidate, accepted state emits visual/UI/audio feedback. The cart model has no requirement to use a rigid-body solver if the declared movement/collision path suffices. An external pathfinding or economy library, if later added, is ordinary code called by the game rule; engine-managed background jobs, storage and effects still cross their public lifecycle boundaries. No parallel set of manifests should be needed merely to expose parcel state to save/inspection; necessary schema declaration should be co-located or mechanically derived and inspectable.

**Daily iteration and source/tool boundary.** One artist reexports the cart mesh while a programmer edits the pickup rule and the lead edits the scene. The source files are canonical; the editor, CLI and agent are clients of the same typed operations, with direct file edits admitted as one coherent revision. A file watcher may flag a pending change but cannot infer that a multi-file export or branch checkout is complete. The team deliberately admits the complete source change, validates schema/content/dependencies, cooks versioned products and starts a play session pinned to that accepted revision. A failed import or compile leaves the old valid build identifiable and must not mix its cart with the new rule. Reimport maps known nodes; a renamed axle/collider attachment becomes a repairable conflict rather than guessing. Tool operations record their base revision, support undo and preserve conflicting edits for review; their recovery log is not a second project database. Multiple noncooperating writers still require team coordination, because the design claims no magical file locking or security sandbox.

**Debugging and export.** The first delivery should show the parcel attaching to the cart, parcel status changing, the marker updating, and a success sound/UI cue from the accepted state. Test a rejection by trying delivery without a parcel. Diagnostics can trace marker/action to the rule, show that the rule ran without a state change and identify the current source/session; the specific `no parcel` explanation must be authored as a rule outcome, not guessed by the inspector. Test a target failure by selecting a browser tier with an unsupported material/pass or oversized required asset: report the responsible object/product and exact target, offer an explicit alternative, retain the accepted desktop build. A private test save, if introduced for progress, has its own schema/restore compatibility and cannot be copied into authored scene data. Stop/restart after code/schema edits; safe data preview is optional and declared. Export the desktop package from a pinned revision and check on a named device. Browser export gets separate toolchain, content/shader closure, startup/download and device checks; mobile store packaging/signing is a later explicit path, not a side effect of choosing a profile. CI uses the same validation/cook/build/inspection operations as the local workbench, but command names and exact packaging interfaces remain D1/T2 decisions.

**Vocabulary bridge and friction.** Their `asset database` corresponds to source masters/import settings plus the engine's hashed product graph and stable node mapping; an interchange file is not automatically a playable scene. Their `prefab variants` correspond to source recipes plus game-owned overrides; reimport must not erase those overrides. Their `build pipeline` corresponds to source admission, cook, target lock, package and device qualification as separate states. The hidden assumption is that an experienced studio will accept a tool that is technically scriptable but cannot visually inspect scale, materials, lighting, overrides and source/play status. The minimum workbench must show the selected target's actual renderer or a labelled proxy, support camera/light/material editing with units and undo, and expose the same operations available to scripts. It need not replace Blender or become a full DCC tool.

**Limit.** This paper pass does not select exact API syntax, commands, SDK distribution, ECS library, physical solver, shader language, asset format, target devices or a release date. It proposes no new runtime branch for veterans: a novice starter and these empty-project paths use the same project source, registration, validation and play/build semantics. The next useful evidence is an implemented empty-project slice alongside a starter, then observed cold/warm edit-to-play and export on named hosts/devices, including one realistic failure and recovery.
