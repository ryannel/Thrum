# Empty-project newcomer journeys

1 November 2026. Paper walkthroughs of the proposed custom-host engine, starting from an empty project directory and an intention, with **no copied scene, sample rule, preplaced camera, or working interaction**. They are analytical traces, not observed users, runnable instructions, measured iteration times, or evidence that any target or workbench is implemented. Rust is the current implementation recommendation/candidate; Bevy is not the host. Exact source syntax, first supported host/device, and A01–A05 mechanisms remain open. The journeys use the [developer experience](../../../design/ENGINE-EXPERIENCE.md), [first-use review](../../../design/FIRST-USE-WALKTHROUGHS.md), [construction plan](../../../design/CONSTRUCTION-PLAN.md), and [audit](../../../design/ARCHITECTURE-AUDIT.md) as recommendations and obligations, not working features.

An empty project is a valid authored draft, not yet a runnable game. It becomes runnable only after its selected target has the necessary entry scene, view/camera and required content; an interaction adds its own input/rule/state needs. The host, graphics backend and task scheduler remain engine responsibilities, not blank-project chores. A guided minimal addition may write ordinary, inspectable project source through the same operations that an expert uses directly. Guides, grid, navigation camera, headlight and neutral preview are authoring-app aids unless deliberately accepted into the game source.

## N01 — Basic coder, new game developer: overhead browser garden

**Intention and constraints.** A person who can edit basic code wants a small, colorful overhead game: move a cursor or character, collect three seeds, and open a gate. They choose a browser demo to share by link. They do not yet know game loops, authoritative state, input actions, camera projection, or possibly Rust. That last gap needs a named language/toolchain prerequisite; it cannot be silently counted as engine learning. No starter scene or example rule exists in their project.

1. **Create and preflight.** Select a named browser/WebGPU target and check the actual supported host, compiler, content tools and browser/device requirements before authoring. Project creation must yield an inspectable source root and one effective setup; it need not invent a game scene. A browser ambition is not proof that this target is qualified. The blank authoring view may show only editor guides; it must say that no runnable game entry exists yet.
2. **Make first visible content.** Create a scene, choose an overhead camera and frame a self-authored floor and seed object. Pick an explicit minimal light/display choice and one material. Grid, axis, selection highlight and neutral preview light may belong to the authoring app; they are not shipped scene objects or evidence that the game has a light. A play preview should identify which authored camera and illumination it uses. If there is no camera or renderable entry content, say so rather than silently borrowing an invisible sample.
3. **Make first interaction.** Bind keyboard/pointer input to a named game action. Establish player/cursor position or selected cell as game-owned state. A seed pickup rule validates reach/selection, commits the seed count, removes or marks the seed, and drives a visible gate change. Input, rule, state and feedback must be traceable; the render mesh must not be the sole record of collection. They need a short task path that introduces registration/access/order only where the rule actually needs it, with effective defaults inspectable.
4. **Make it theirs.** Replace primitives with a hand-authored garden tile/seed asset or small imported model, then choose a color palette and shadow/material response at gameplay distance. This requires ordinary content import and mappings, not a style toggle or complete environment stack. A no-sky choice still needs explicit background, light and any attenuation choices. They should be able to remove the seed mechanic without editing unrelated provider declarations.
5. **Diagnose a realistic failure.** They remove a required input binding or object field while adding a second seed. Validation should identify the action/object, missing binding/field, source, active accepted revision and proposed repair. If a material pass is unsupported by the named browser target, report that target/material/pass separately. The previous valid session may keep running, but must be labeled as the old revision; rejected source never appears active.
6. **Save, play, share.** Admit one coherent source snapshot; play in a private session, stop, and distinguish discarded unsaved pickup progress from an optional retained private test save. A build/export pins the accepted revision and cooked products. A shareable browser result additionally needs a qualified browser/device path and hosting handoff; a local desktop preview does not establish either. This trace claims no link or export exists today.

**What the template-first path concealed.** U01 began with a camera, picking, board topology, input, named action, rule, feedback and target support already selected. Empty creation must expose their minimum dependency order. It must not imply that a novice can write Rust instantly or that a visible editor grid is a game scene.

## N02 — Experienced programmer, new to 3D: native desktop spatial puzzle

**Intention and constraints.** A general programmer wants a compact native Mac/PC puzzle: rotate a mirror to send a beam to a door. They are comfortable with code and build systems but unfamiliar with 3D transforms, camera perspective, scale, coordinate frames, picking, and which representation owns collision. The visual target is restrained, graphic 3D rather than realism. Start with empty files; no prewired third-person controller or physics scene.

1. **Create and preflight.** Choose one named native desktop target and check host/compiler/graphics prerequisites. The initial project source must declare a game entry and selected capabilities. The effective setup should explain that this puzzle needs rendering, input/picking and a game rule, but need not require rigid-body dynamics, navigation, sky, water, skeletal animation, or a packaged extension. Mac and PC delivery must be qualified separately where their GPU, packaging or inputs differ.
2. **Make first visible content.** Author a scene with a camera, mirror, emitter, receiver and door, using consistent units and transforms. Define the camera framing and an explicit light/material/display baseline; the editor's neutral asset preview is a separate diagnostic view. The engine should show world/local axes, scale and object identity so a programmer can diagnose why an object is behind the camera or too small. Geometry imported from a model is reviewed for orientation/scale; its mesh does not automatically supply colliders or behavior.
3. **Make first interaction.** Bind a click/drag or key action to select and rotate the mirror. Picking resolves the authored object; a game-owned orientation/rotation action validates the change. A pure beam/path computation can remain ordinary game code. The receiver rule commits door state; render/animation follows that state. Ray visuals cannot be treated as the authoritative puzzle result, and a moved door mesh cannot alone establish traversability. No physics provider is needed unless the game chooses physical contact/collision.
4. **Make it theirs.** Import the programmer's simple mechanical model and map its pivot/material slots to the existing mirror identity; inspect close and game camera views. Adjust graphic color and light response through authored content. If reimport changes the pivot or node name, show the mapping conflict and preserve game-authored rotation/material overrides until repaired.
5. **Diagnose a realistic failure.** A mirror rotates in the editor but a play run keeps the old angle, or the door looks open but blocks a path. The inspector must distinguish authored transform, running state, last accepted source and collision state; it should point to the owner/consumer mismatch. For a changed source file during play, reject unsafe implicit activation and offer a coherent admit/rebuild/restart path. An interrupted multi-file edit must not be replayed over a different revision.
6. **Save, play, share.** Save project source, validate a snapshot, play and inspect one accepted/rejected mirror action, then stop. Apply back only a selected authored mirror placement with revision checks, not the played door-open state. Package the selected native target from pinned products, with its actual device/package evidence. A second desktop target is a separate qualification, not inferred from the first.

**What the template-first path concealed.** U02 and U07 already supplied camera, character or room scale, movement/picking, collision, import mappings and an agreed light recipe. For this user, the blank path's core difficulty is 3D spatial meaning and state ownership, not basic syntax. A default camera or invisible test light that makes the scene appear correct in-editor must be identified as authoring assistance unless serialized into game source.

## N03 — Artist/designer with limited code: painterly mobile diorama

**Intention and constraints.** An artist wants a small touch-first native mobile scene: tap a painted lantern in a garden to reveal a path and hear a short sound. Their strength is models, texture, composition and pacing; they can make minor source edits but cannot be assumed to implement a game rule in Rust. The app-store ambition makes touch, screen aspect, device memory, suspend/resume and signing real target concerns. The first pass begins with an empty project, not a character template or prebuilt art scene.

1. **Create and preflight.** Choose one named mobile target only if supported; otherwise identify the exact unsupported prerequisite and keep the project source intact. Project creation must expose a scene entry, target and asset import route through the same canonical files/operations used by code and tools. Desktop pointer emulation can aid iteration but cannot certify native touch or packaging.
2. **Make first visible content.** Import one authored lantern and ground/foliage asset, review scale/orientation, material slots, textures and unsupported data, then place them with a camera, explicit lighting and display choices. The workbench may display a grid, selection gizmo, neutral light, proxy preview and bounds; those are app overlays/helpers. The game view must show the authored camera and actual selected target path, or label any proxy/fidelity gap. Import alone does not create a playable scene, collision or tap behavior.
3. **Make first interaction.** Define a touch target and tap action, then a rule that records a game-owned lantern/path state and produces visual/audio feedback. The minimum visual workbench currently proposed only edits/selects/previews camera, light and material properties; it does **not** establish visual rule authoring. This artist therefore needs either a release-supported, inspectable interaction operation/recipe whose generated source is ordinary game code, or a programmer collaborator for this rule. Claiming a fully no-code game here would exceed the design. Even with a collaborator, the artist must be able to inspect which object/action changes the path and test it without editing engine internals.
4. **Make it theirs.** Reimport a revised painted lantern/foliage master, keep stable node/material references and game-owned overrides, then tune painterly response across camera distance and the named mobile material/pass support. Style depends on geometry, texture, light, shadow and display; a single style switch cannot guarantee it. The artist may choose no visible sky without losing intentionally selected light. A neutral asset view distinguishes bad import from scene lighting.
5. **Diagnose a realistic failure.** A renamed lantern node makes the tap target/collider ambiguous after reimport, or a required outline/transparent material pass is unsupported on the mobile target. Diagnostics should name the affected authored object, mapping or material/pass, the running accepted revision and a repair choice; they must not retarget the interaction, discard overrides, or silently drop the effect. A generic build failure leaves this user unable to proceed.
6. **Save, play, share.** Admit the accepted scene/asset/rule source revision, launch an isolated private play session, and test touch plus suspend/resume on an actual named device when the target exists. Preserve optional private test saves separately from authored placement. Build/package the pinned source/products; store signing/submission is a separate supported step. Until the workbench, interaction path, target device and packaging are qualified, this is a design trace, not an artist-ready or store-ready workflow.

**What the template-first path concealed.** U08/U09 began with an existing character or board interaction and did not require the artist to create a rule. The proposed minimum workbench addresses import and visual edits, not independent game logic. The blank path needs an honest handoff to code or a genuinely supported narrow authoring operation; a generated sample that cannot be removed is not a solution.

## Material findings for existing owners

| Finding from the three empty paths | Consequence and existing owner |
| --- | --- |
| “Create project” currently begins the recommendation but has no traced empty source-to-first-pixel path. A visible editor overlay can mask the absence of camera, light or game content. | D0/D1 and T1/W1/F3 specify the canonical empty project, scene/entry creation and effective setup; I2/I3 prove a first authored object and actual game camera/light. Keep editor guides and neutral preview explicitly separate from shipped scene source. |
| First interaction requires an input/action → rule → authoritative state → feedback chain that starters supply in advance. | F2/F3/W1, input/UI and I3 expose one small direct path with traceable registration/access and useful rejection; no general graph/plugin framework follows from this finding. Qualify a blank-scene path separately from the existing starter gate. |
| Artist-ready, no-code and AI-assisted are different claims. Current minimum workbench can support visual authorship but not an independently authored game rule. | T1/F2/I3 either scope a narrow inspectable interaction authoring operation under ordinary source semantics or document the programmer handoff. Do not advertise no-code completion based on CLI or visual selection alone. AI uses the same source/operation/diagnostic path. |
| The first accepted revision and actual target must be visible before and after first play; an old valid run can otherwise appear to include failed blank-project edits. | A01/A02, T1/T2, F4/P7 and I4 retain pinned source/product/session identities, recovery and target-specific preflight/export. The workbench cannot promise safe concurrent writes or automatic apply-back while those mechanisms remain open. |
| Three choices need not share a forced scene recipe: overhead browser garden, native spatial puzzle and painterly mobile diorama use different cameras, light/materials, inputs and delivery constraints. | D0/F2/F4/V2–V4/T1/T2 maintain named, inspectable defaults/recipes with explicit semantic choices and supported material/pass/target products. A03 matters at build time; A05 only if the chosen atmosphere/media overlap requires it. A04 is irrelevant to these three scenes. |

**Qualification boundary.** After the relevant D0–D2 contracts, I1–I3 implementation and one I4 target slice, run a clean empty-directory trial in addition to the existing starter trial: record every created source object, prerequisite, undocumented step, accepted/rejected revision, workbench-only visual, target product and user-edited file. Human usability, native device behavior, actual edit-to-play latency and visual quality require later observation. These paper journeys close none of A01–A05.
