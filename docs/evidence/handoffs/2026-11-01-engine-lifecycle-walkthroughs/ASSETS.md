# Asset lifecycle: paper walkthroughs and friction

1 November 2026. This is a paper dogfood of [the lifecycle proposal](../../../design/STORAGE-LIFECYCLE.md) against [the current asset contract](../../../ASSET-LIFECYCLE.md), not an executed promotion, restore, or cleanup. No assets were changed. The examples name files to make the decisions testable; they do not prescribe new folders for every asset.

## 1. A first generated prop, with one irreplaceable original

**Situation.** A newcomer asks for a dock lantern. An image reference and two paid model generations are made. Candidate B looks better at game camera distance. The service can regenerate something similar, but cannot return B's exact original after its download expires.

1. **Start the run.** The artist or agent checks free space and the output area's size, estimates the peak for two downloads, Blender import, texture unpacking, two exports and review captures, and writes a short run note under `tmp/handoffs/`: owner, question, input/reference, generation staging path, expected peak, and the selection checkpoint. Generation goes to one owned `tmp/generations/<run>/`, not `game/public` and not a new whole checkout. A first sample is inspected before ordering a sweep.
2. **Choose.** Review A and B at the actual camera and close range. Record “B selected; A rejected because silhouette is unreadable,” with one compact comparison image or a link to its evidence. If visual selection is pending, keep only A and B for that named decision. The agent must not label B “approved” from format validity alone.
3. **Adopt B.** Create `factory/props/dock-lantern/` only once selected. Move or copy **the exact B original bytes**, any separately delivered textures, the editable Blender master, the reference needed to explain the choice, a build recipe and provider/task/license/credit facts into that package. Hash the selected original and master. A prompt and task ID accompany the original; they do not replace it. Use a short README and `asset.json` for current source, status, retention, and links. Add one production-index row. For this one-file prop, no ship-style profile tree, dependency graph or exhaustive hashes of every screenshot are necessary.
4. **Protect the source.** Check ignore and LFS attributes on those exact files. Commit/upload or place them in a recorded durable store; actually restore the exact original/master to a clean location and compare hashes before saying remote recovery was verified. If the network is offline, adoption can remain local and marked `not-verified`; no cleanup of the sole original and no remotely recoverable handoff claim. An LFS pointer or service receipt is insufficient.
5. **Cook and try the game.** Export one game-ready GLB into fresh staging, validate the format and the real loader/camera, record size and pivot/material expectations, and ask for visual acceptance of **that export identity**. Only then promote the selected payload and minimal loader metadata to `game/public/models/props/dock-lantern/` and wire the consumer. `exported`, `consumer-tested`, `visually-accepted`, and `integrated` are separate claims. Rebuild from retained source with caches empty before calling the package reproducible.
6. **Close the run.** Inspect only this run's paths and remove rejected full downloads, redundant exports and bulk captures after the selected chain and evidence are safe. If a review choice remains open, record its owner and next review trigger. Keep the original B, master and required inputs even if they are large. Report retained bytes and actual free space if disk reclamation was the objective; a same-disk move does not free it.

**Crash/offline test.** If Blender crashes before selection, both candidates remain owned staging, and the run note explains why. If it crashes after B's original was moved but before backup verification, recovery is local only; resume by checking file hashes and recording the missing upload. If the paid service disappears, the selected original still supports cooking. The run is not closed while B exists solely in ignored scratch.

**What the current tree can do.** The `tmp`/factory/runtime separation, production index, package record, Git LFS rules, Meshy generation script, asset-specific builders/viewers and scoped tests exist. The `bilberry` package demonstrates retaining a paid original while dropping an unselected runtime variant. There is no generic select/adopt/publish command, automatic remote restore proof, or disk reservation tool. The `traveller-lantern/asset.json` shows a danger: a small prop can accumulate a long ledger of every entrypoint and screenshot hash. The current contract calls for a *small current* record; put trial detail in one linked review note, not a growing registry.

## 2. Art and rig revision while the previous game remains playable

**Situation.** A rigged ship is already in a playable release. The artist changes a sail mesh and bone names. A new close profile exports, but the reduced profile fails halfway through cooking. Another developer is playing the previous release.

1. **Keep the live closure intact.** Identify the old release manifest and every file it needs, including old rig bindings. Retain that closure under the release/rollback policy. A branch name, old hash, or retained master is not a substitute for the bytes the previous game loads. Reserve space for old + new files, temporary unpacking and captures before starting; otherwise narrow the revision or defer it.
2. **Revise source once.** Make the art and rig change in the canonical `factory/ships/<id>/` master and recipe. Record the old source identity, new source identity, changed bone/socket/material semantics, and affected consumers. Do not copy the entire ship workbench into `-v2` or a new full worktree for each attempt. Check whether animation clips, collision, attachment points, close/reduced exports and save-bound IDs need adaptation; independent quality profiles must preserve gameplay/rig semantics intentionally.
3. **Stage complete products.** Cook close and reduced profiles plus their binding metadata into an owned staging root. Verify exact hashes, manifest references, decoder, consumer loading, animation/masks, attachments and representative native views. The failed reduced cook leaves staging incomplete and **cannot switch the game** to the new revision. Fix/retry the affected product from the same retained source and compatible staging root. A crash leaves the old release active and the incomplete staging path recorded for its owner to inspect, never inferred disposable from age.
4. **Publish only a coherent selection.** The export records the expected-current delivery identity it was based on. Immediately before promotion, compare that identity with the actual current selection; if another agent has published since the build began, reject the stale switch and reconcile/revalidate. First make the new payload closure durable; then change the game's selected manifest/release reference at one controlled publication point. A reader already using the old manifest must still get old bytes. New readers get only the new manifest and matching new bytes. Record the exact promoted manifest and its validation. If an old save or rollback can still request the old rig revision, keep the old closure until the support policy ends or a migration is proved. A failed game integration is rolled back by selecting the prior release, not by rewriting source history.
5. **Finish source and cleanup.** Retain the new editable master and exact necessary source ancestry. Once the new release is accepted and rollback/support no longer protects the old product, remove only verified redundant cooked copies and this job's staging/captures. Do not remove an old master merely because its cooked product is no longer served. Record the next review trigger for old supported bytes.

**A real limitation today.** Broadsides' builders can stage and verify specific packages, but the repository has no generic atomic multi-file publication, manifest-pointer protocol, reader lease or release-root registry. Vite copies everything under `game/public` into a build. Replacing files at stable URLs while a dev server or browser is reading them cannot promise an uninterrupted old game; one manifest may fetch a mixture. The immediate safe procedure is to leave the currently served release untouched, validate in an isolated preview/staging consumer, build/deploy a coherent new release, and retain the old deployable release for rollback. Avoid promising simultaneous hot asset switching in the current dev server. The proposed F4/T1/T2 mechanism should later prove the manifest-switch and reader/collector race; a same-volume rename alone does not make several browser requests atomic.

## 3. One reusable fitting, two games and two device profiles

**Situation.** A cannon is used by a naval game and a harbour game. Each wants a close mesh and a small-device mesh; each paints it differently. The cannon's geometry changes once, then an artist adjusts only the naval paint.

1. **Select one source owner.** Keep one metre-native cannon family master and mounting frames in its canonical source package. Give the consuming ships/games placement and support recipes, not copied editable cannon masters. Store the paint family separately when it is actually shared; a game-private skin can remain with that game's package. Record source identity and licensed reuse scope.
2. **Build four requested products, not four source trees.** Each game's delivery declares its selected profile, texture/skin and exact cannon source revision. A profile changes geometric or texture cost; it does not silently change weapon state, socket names or collision. Cooked products may be shared only when their complete source, tool, target, format and profile keys match. Different platform compression or semantic bindings require distinct products even when the mesh looks the same. Measure actual download, decoded memory and draw cost before retaining another tier.
3. **Change narrowly.** A cannon geometry edit invalidates the dependent products and their consumer checks; a naval paint-only edit invalidates the naval surface products, not the harbour geometry or physics. Keep a compact dependency record at the relevant package/delivery boundary so the agent can explain what recooked. Do not copy a whole LFS library into each worker checkout just to change one skin.
4. **Release and restore.** Each game selects only its required runtime closure. A clean checkout with empty caches restores the canonical source and builds the selected profiles; if either game has an older supported release, retain that release's cooked closure independently. Losing an immutable cook cache costs time, never the ability to rebuild. If a shared remote store is offline, a game with a complete published closure remains playable; a new cook waits for its required source or uses an already verified local copy.

**Boundary to decide, not assume.** `factory/props/naval-cannon/` is canonical *within Broadsides*. Two independent repositories need an explicit source owner and versioned distribution contract (package, submodule, artifact store or another chosen method); a relative `factory/` path cannot serve both. The engine proposal should not require a universal cross-game asset registry for this case. The smallest useful support is stable source identity, exact dependencies at build/delivery, and a package owner. Cache sharing can wait until repeated builds prove it saves enough time and disk.

## Findings to fold into the plan and skills

| Friction found | Precise change |
| --- | --- |
| The sequence “review candidate → adopted source” sounds mandatory for every trial and may create package churn. | A trial stays in one owned bounded `tmp` run until selection. Create or update a durable factory package only when an exact source is adopted, or when a commissioned workbench is already durable. One-file props get a short record and one GLB. |
| “Exact dependency hashes” can turn `asset.json` into a screenshot and export inventory. | Keep `asset.json` current and small: stable ID, owner/status, source/rebuild/review links, selected identity, retention and recovery state. Put payload hashes in the delivery manifest and trial detail in a linked note. Hash only required source inputs and declared dependencies; let Git history carry previous revisions. |
| “Verify remote recovery” is sound but can block local iteration when offline and become a ritual assertion. | Allow local adoption with explicit `not-verified`; protect the only local original. Require an actual clean restore before *remote handoff/cleanup claims*, not before every preview export. Record the precise restore target and compared hash. |
| “Publish coherent manifest” lacks a current browser procedure. | For Broadsides now, stage and validate, then publish a new whole release while the previous release stays served. For a future hot path, specify immutable URL/closure and atomic selection, plus reader/collector coordination, and prove interrupted publication before advertising it. |
| Two agents can each validate a complete replacement and the slower one can silently replace newer work. | Each promotion carries an expected-current delivery identity and fails if the selected delivery changed. Reconcile source and consumer changes before retrying; an old export is not automatically safe because its own hashes pass. |
| Rollback/support and Vite's copied `public` can keep every old package in new downloads. | Treat supported old releases as separate retained deployable closures; keep new `game/public` limited to the *current* game's declared roots. Do not store every old revision beside current assets merely to offer rollback. The release tool must explain included bytes, including dynamic/locale roots. |
| Reservations, leases and GC could dominate a novice's first asset. | Keep manual owner, peak-space estimate and inspected cleanup for bulk runs. Implement inventory/admission before automation. Never ask a novice to write lease metadata or operate a collector. Suspect sleep/crash leases remain owner-reviewed until the future protocol is proved. |
| Reusing a family across independent games is underspecified. | State the source owner's repository/store and versioned distribution choice per family. Keep consumer recipes and runtime products local to each game. Defer shared immutable cache architecture until one cross-game case needs it. |

**Minimal skill support.** Add a compact “start/select/adopt/export/close” checklist to `repo-structure` or its storage reference, linked from asset-specific creation skills. It should ask for owner, exact selected original, source backup state, one current package record, staging/consumer proof, and owned cleanup trigger. Add one warning to the asset creation/Blender handoff: prompts do not replace generated originals, and `game/public` is the selected deployable payload. Add an example of a *simple* prop `asset.json` next to the complex ship example; do not require a new skill, wizard, global schema migration or per-file run ledger. An optional future helper can report hashes, LFS/ignore state and package closure, but its absence should not block a small asset made with the documented steps.
