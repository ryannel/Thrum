## Scope and observable success

The reusable engine serves 3D top-down, isometric, third-person and first-person games, with modern desktop quality, scalable website demos, and iOS/Android app-store delivery. Pure 2D and MMO workloads are excluded. **V1 proof targets** are this M3 Max with its 120 Hz ProMotion display, the iPhone 18 Pro simulator (function only) and Chrome WebGPU on this Mac; desktop-high (NVIDIA, AMD, Intel), Android and physical iPhone follow V1 on rented hardware. **Working assumptions:** Mac and Windows are initial desktop releases; Linux is optional pending qualification; mobile means iOS/iPadOS and Android, initially ARM64 device builds. BASELINE-SPEC now selects reference OS/device/browser candidates and content scale; actual support remains unqualified. Future multiplayer is first-class; [N1](NETWORKING.md) selects authority/replica roles and bounded transport. Camera type does not set the renderer tier. A world advances once while several views and presentation providers may read it.

The foundation succeeds when one packaged content source and authoritative world can run a native desktop showcase, a browser demo at showcase quality and representative mobile builds; each handles focus, surface/device loss, resize, asset activation, memory pressure, and suspend/resume without duplicating world time or leaving GPU work active in the background. Headless simulation and cooking do not construct a window or GPU. A profile that disables a provider stops its avoidable jobs, uploads and allocations while retained consumers receive a named substitute.

## Selected architecture

**Selected design:** Rust core and custom application host; `winit` for event/window integration where supported; `wgpu` as the GPU executor, using its native-only features and one isolated raw-backend module per backend; thin platform adapters for web page/JS, iOS app shell and Android activity/packaging. Own composition, clock, state, jobs, asset residency and renderer policy. Each GPU family gets a frame recipe selected by the capability registry; platform-specific techniques sit behind providers that declare their feature and resource contract, with a portable fallback. Reuse mature format decoders, compression, physics, audio and text libraries after a target audit. Do not import another engine's app, ECS, render, asset or platform layers as concealed host facilities. A standalone algorithm from another engine may be evaluated if license/provenance, direct dependencies, maintenance and platform behavior are recorded.

This is an architectural inference, not a performance claim. The host must preserve a single world clock across multiple views, reject stale async completions after a state change, and run without any presentation device. A small owned coordinator with separately owned shell, GPU and content services satisfies those constraints directly; a reused scheduler would still operate under these owned contracts. The user selected a custom host, which does not exclude standalone scheduling/storage libraries; evaluate those without transferring host lifecycle ownership. Rust has maintained iOS, Android and WebAssembly targets; `winit` handles different callback lifecycles; `wgpu` covers Metal/Vulkan/DX12 and browser WebGPU, but its optional feature and limits model still constrains techniques. In particular, wgpu 30 documents ray-query and mesh-shader paths as experimental/native-only, so they are recipe-selected providers with portable fallbacks rather than the shared floor; the floor never caps what a recipe may use. [Rust iOS](https://doc.rust-lang.org/rustc/platform-support/apple-ios.html), [Rust Android](https://doc.rust-lang.org/rustc/platform-support/android.html), [winit lifecycle](https://docs.rs/winit/latest/winit/application/trait.ApplicationHandler.html), [wgpu features](https://docs.rs/wgpu/latest/wgpu/struct.Features.html).

| Alternative | Architectural benefit | Reasoned selection/rejection condition |
| --- | --- | --- |
| Rust + winit + wgpu (selected) | One language for world, tools and most renderer; portable API baseline; direct ownership of frame/lifetime policy | Its callback and feature model covers the required ownership graph. Replace a boundary only if a required contract is unrepresentable or a measured platform cost exceeds the allocated budget; do not replace the whole host for one provider. |
| Rust + raw Metal/Vulkan/DX12 GPU backends | Native API reach and platform-specific optimizations | Multiple backends multiply shader, resource and failure-state implementations while browser remains separate. Add a scoped native provider only if a mandatory technique has no portable representation or a quantified bandwidth/latency benefit pays that permanent cost. |
| C++ host plus platform SDKs | Mature game SDK access and native tooling/ecosystem | FFI shells are narrower than moving world/resource ownership to C++. Reconsider only if an indispensable native library or lifecycle path cannot be safely exposed through that boundary. |
| TypeScript/browser-first runtime with native wrappers | Fast web iteration and existing project familiarity | It makes browser delivery primary but leaves app-store/native pacing and asset lifecycles inside wrappers; choose it only if those native constraints are reduced by product scope. The current browser game is evidence of one game, not this reusable engine. |
| Other complete engine | Integrated authoring/runtime libraries | Would transfer lifecycle and ownership to another host, contrary to the intended custom-engine control unless authoring/runtime reuse is shown to dominate that cost. The custom-host decision remains in force. |

The custom host is **not** a promise to build every utility. Its irreducible owned contracts are the ones that keep state, time, resources and failure responses coherent. Libraries are replaceable only at real boundaries. `wgpu` is the selected baseline graphics abstraction, not an escape from WebGPU limits or a guarantee of uniform backend features.

### G3b world and presentation lifecycle — selected, partial implementation

`ClockedWorld` owns authoritative time and rules. Native `WorldLane` schedules that owner on a resident thread;
`thrum-render::FrameHost` owns bounded frame slots, completion and submitted history. Platform adapters own the
window/surface and display-link callbacks. Presentation loss never implies an authority pause: explicit local-game
policy chooses pause, while a headless or multiplayer authority may continue. Rendering cannot create a second clock.

Explicit native pause/resume uses one ordered lifecycle request slot, separate from replaceable continuous controls.
A designated controller receives typed Busy while a request is queued, draining, or has an unconsumed reply; accepted
requests are never overwritten. The worker delegates to its clock owner. Pause preserves the existing `TickClock`
cutoff at the last admission sample, clears fractional time and drains already accepted ticks through ordinary capped
updates before acknowledging. It does not first admit unsampled elapsed time. Resume uses the worker's monotonic
origin after draining, excluding paused wall time; repeated Pause/active Resume are idempotent without resetting an
active clock. The immutable reply carries operation, snapshot identity, timeline and matching clock sample even if
later updates replace the shared observation. Zero-tick acknowledgements wake the observer. Stopped/faulted tasks
report failure; a failed tick is never acknowledged as completed. Paused publication recovery remains bounded.

Mac P is an explicit game action, ignores key repeat and retains desired state across an outstanding transition.
It uses the asynchronous native controller; inline browser pause/drain/resume remains synchronous. Mode misuse must
return an error rather than reach an inline-only world through a threaded handle. Surface loss/occlusion alone does
not issue a lifecycle request. Camera/presentation may continue while the chosen world is paused. Pause does not
change world epoch/timeline or reset submitted transform history by itself.

Mobile adapters retain separate surface, foreground and local-play policy. Release a surface before suspend returns,
reject old-generation input/completions and recreate only surface-dependent resources on resume. A local single-player
game may choose background pause; a client cannot pause remote authority. Keep winit the sole Android event consumer
and distinguish Activity pause from surface destruction. Typed input preserves accepted discrete actions; cancellation,
focus/surface loss and recreation clear gestures so an old release cannot become a new action. The iOS worker/late
acquisition migration and simulator lifecycle sequence remain G3b work; Android qualification follows V1. Simulator
checks prove function, never device speed. Historical [I1 core](../../evidence/i1-headless/MOBILE-CORE-PORTABILITY.md)
and [shell](../../evidence/i1-headless/MOBILE-APP-SHELL.md) records describe retired prototypes, not V1 qualification.

Native developer play uses a separate player process by default with pinned SourceRevision/BuildRevision/profile,
fresh SessionId/WorldEpoch and private save authority. Browser/mobile hosts use isolated world instances and workers
where supported; this is not a security sandbox. F1 cancellation drains owned leases; old-session completions cannot
publish into a restarted run. Shared MatchId and wire identity are N1 concepts, not local session handles. Memory observation and pressure response cover every world/view/prediction instance; per-world counters alone cannot describe aggregate process use.

W1 owns the selected component columns; F1 owns the explicit dependency/access schedule. Standalone, authoritative server,
replica and prediction roles have distinct permitted stages. No framework scheduler or storage backend changes those
roles. Source/code changes create a new pinned run; active network matches retain their gameplay build.

## Capability and support matrix

Separate **capability**, **provider**, **quality budget** and **validated configuration**. A device/API is supported only after running the representative scene, not because a crate compiles. The capability registry resolves one of four frame recipes: Apple tile, Android tile, desktop high (NVIDIA, AMD, Intel) or portable. Native recipes are designed first and use their hardware fully; portable (raster and compute within WebGPU limits, GPU culling, cooked compressed assets) runs on every device as reference and fallback. Ray tracing, mesh shading, vendor reconstruction and ML are recipe providers promoted by measured win. WebGL2 is extra scope, not a silent fallback.

## Derived execution model and invariants

**Single simulation authority.** The host owns a monotonic tick index `n` per authoritative world/session and a configurable fixed duration `h` (selected default `h = 1/60 s`, subject to game physics/animation requirements). Every simulation system reads state `S_n` and tick-stamped intents, then commits `S_(n+1)` in an explicitly ordered dependency graph. Animation, physics and game policy must agree which system owns solved motion; the platform scheduler does not choose that policy. Render, audio and editor views consume a committed snapshot tagged `n`; they never step the world. A view can interpolate from the two latest committed snapshots by a bounded fraction, but interpolation does not become authoritative state. This is necessary because two cameras or a delayed present must not advance the world twice or read a partially updated body.

**Known producer before consumer.** Order per tick is pre-tick publication of prepared simulation-affecting region/content changes → input sampling → game intent → physics/animation/agent systems in their specified dependency order → event and world-state commit. Order per presented frame is committed snapshot → presentation-only resource publication barrier → per-view extraction → GPU submission → presentation. Collision/nav/gameplay changes cannot be attached after the snapshot as if they were merely rendering uploads. Async decode and shader jobs can run between barriers, but their completion order cannot change simulation results. Simulation-affecting publications are keyed to a requested tick and stable ID, then committed in canonical order; if a required product is not ready, region activation waits or uses an explicitly authored substitute. A worker cannot mutate live state. This avoids scheduling-dependent world state without requiring the renderer to be deterministic.

**Clock separation.** Maintain monotonic platform time, world tick time, presentation deadline time and audio-device time as separate quantities with explicit conversion at event emission. A display callback is permission to present, not a simulation clock source. On a 30 Hz display with a 60 Hz world step, ordinary cadence is two ticks per presented frame; a 120 Hz display may present twice between world ticks. A hidden/background interval is a state transition with an explicit game policy: default local single-player policy pauses world time, records the pause, resets the accumulator on resume, and does not simulate the hidden wall duration. A remote server continues independently of a suspended client; that client reconnects/resynchronizes under N1. A listen server suspended by its host must announce unavailability/disconnect peers, not pretend it kept ticking. During active overload, the host first reduces optional presentation work and may skip a presentation to retire queued ticks; it never silently discards ticks or lengthens `h`. Proposed safety ceilings are four ticks processed per callback and eight queued ticks; these are unqualified policy values, not proven throughput. Admitted ticks must also fit the callback CPU budget: k ≤ floor((B_cpu − C_other) / C_tick_bound), with a nonnegative result and measured/analytically bounded C_tick_bound; if no tick fits, the overload policy applies. At the eight-tick limit, local single-player enters an explicit `Overloaded` pause: stop accumulating world time and admitting gameplay intents, drain pending ticks, show the condition, then resume from a new wall-time origin. This is a visible failed-performance state, not an optimization. Sustained arrival of work faster than service cannot be made real time by any scheduler; online authority bounds optional work/peer queues under N1; if it cannot meet its tick service budget, it reports session overload and terminates/resynchronizes the affected session rather than silently changing dt or applying the local background-pause policy.

**Versioned lifetime.** Keep independent monotonic generations for host lifecycle, surface, GPU device and content product. A job/result/handle carries the generations relevant to it; publication requires equality with current generations and a live consumer lease. Resize changes the surface generation and view histories, not the world. Device loss changes the device generation and invalidates all GPU products, but not durable world state or cooked source identity. Content replacement changes its product generation and retires old representations only after leases and GPU fences release. This prevents late completions from resurrecting resources after suspend, replacement or profile-off.

**State machine invariants.** `Active` permits submission only with an active surface, valid device and resolved profile. `Overloaded` pauses local world time and gameplay intent admission but may present a low-cost status view while the surface is active. Entry to `Suspending` closes submission admission synchronously on the platform callback thread; already submitted work may finish, but no new GPU work is queued. Surface-dependent resources are released in dependency order, while CPU source/manifest state remains. `Suspended` has no surface lease and no presentation tasks. `Restoring` rebuilds in order: platform surface → adapter/device validation or recreation → provider graph → required GPU products → view histories; only then can it enter `Active`. A restore failure remains in a recoverable non-presenting state or reports a clear unsupported configuration. A save requested on suspend is best-effort because the OS may terminate the process; P7 must use periodic durable checkpoints rather than rely on one final callback. [Apple background Metal](https://developer.apple.com/documentation/Metal/preparing-your-metal-app-to-run-in-the-background), [winit lifecycle](https://docs.rs/winit/latest/winit/application/trait.ApplicationHandler.html), [wgpu recovery](https://docs.rs/wgpu/latest/wgpu/enum.CurrentSurfaceTexture.html).

## Work, cadence and memory models

**Snapshot lifetime (C02 reconciliation):** F1 owns W1 immutable read-model bundle leases, retention and explicit reader backpressure. A selected bounded profile may additionally use a shared byte reservation pool.
Consumers hold SnapshotLease plus relevant CPU/provider leases through extraction; no published page aliases mutable
solver/world arrays. V2 produces an owned RenderPacket before releasing the world lease; GPU packet retirement uses
submission fences separately. Optional stale unsubmitted views are cancelled/deferred and reset when retention is
exceeded, but pages are reclaimed only after actual reader release. Required readers backpressure publication or
enter the explicit overload state. Prior-view samples and save-state captures have their own retention policies and measured costs.
See [C02](../CONTRACTS.md#c02-time-and-committed-state--f1-coordinator-w1-world); optional byte-pool choices do not weaken immutability or last-reader release.

Let `D = 1 / target_fps` be the display period. Let `C` be main-thread critical work from input to submit, `G` GPU execution including transfer/compute/render dependencies, `P` platform present/compositor delay, and `J` admitted background work that contends for CPU, bandwidth or memory. For a pipelined steady state, frame throughput cannot beat `max(C, G, P)`; input-to-display latency also contains serial dependencies from sampling through submission and present. Thus an isolated fast renderer or a low mean `C` cannot prove cadence. The coordinator caps frames in flight at **two initially** to bound latency and transient attachment/upload overlap; this value is a design parameter that may be reduced on memory-constrained devices. It schedules against display deadlines and leaves reserve for variance rather than filling every estimated idle millisecond. Actual p95/p99 frame interval and missed deadlines validate the model.

Background queues have explicit maximum counts **and** byte reservations for I/O, decode, shader/pipeline preparation and GPU upload. Admission requires capacity for the job's worst-case staging bytes and a consumer lease; priority classes serve visible/soon-needed work before speculative work, with aging so low-priority work is not starved. Work arriving faster than service is backpressured at the producer: refuse/defer a region request, reduce lookahead or choose a declared lower-res product. It is never allowed to create an unbounded queue. Upload batches are charged against per-frame bytes and time; shader preparation cannot block the presentation critical path unless a missing mandatory pipeline intentionally blocks activation. Cancellation suppresses publication, while resource reclamation waits for the last reader and GPU fence.

For capacity planning, track logical categories `M_durable` (world and metadata), `M_cpu` (decoded resident products), `M_gpu` (GPU products), `M_transient` (render graph and frames in flight), `M_stage` (download/decode/upload scratch), and `M_replacement` (old and new content briefly coexisting). Estimate `M_peak = M_durable + M_cpu + M_gpu + M_transient + M_stage + M_replacement + reserve` for a transition and compare it with the profile planning target and observed device pressure. The general runtime does not impose a universal hard byte admission gate. `M_replacement` counts the extra overlapping copy, not the whole resource twice. GPU/CPU allocations may share physical memory on Apple devices, so this sum is a conservative *logical planning estimate*, not an OS resident-byte prediction; measure physical footprint separately. When a desired product threatens the device target or triggers pressure, evict unleased data, prepare in smaller chunks or select a documented lower-memory provider before making the region live. A profile switch accounts for old/new overlap and retires old resources only after the new graph is ready or explicitly enters a loading state. GPU loss reconstitutes from F4's retained source without duplicating world state.

The render graph must model attachment lifetimes and load/store dependencies. If a transient target is consumed only inside one render pass, it should not be retained beyond that pass; on tile GPUs, avoid unnecessary stores and reloads to external memory. If a later pass needs the data, count the store/read traffic and residency. This is a known bandwidth consequence of tile architecture, not a claim that wgpu can expose every Metal-only tile operation. [Apple tile architecture](https://developer.apple.com/documentation/metal/tailor-your-apps-for-apple-gpus-and-tile-based-deferred-rendering), [Metal memoryless storage](https://developer.apple.com/documentation/metal/mtlstoragemode/memoryless).

Background time does not automatically become catch-up sim time.

## Mobile and web constraints with architectural effect

- Apple silicon mobile GPUs use tile-based rendering; pass boundaries, attachment load/store and transient attachment residency can change power and bandwidth. The Apple tile recipe is the primary Apple path: the executor derives memoryless depth and intermediates, merges passes and avoids full-target round trips; Metal-only tile features (programmable blending, imageblocks, rasterization rate maps) are reached through the isolated escape hatch with measured wins. The portable graph also minimizes full-frame intermediate stores. The Android tile recipe applies the same discipline through Vulkan transient attachments. [Apple TBDR](https://developer.apple.com/documentation/metal/tailor-your-apps-for-apple-gpus-and-tile-based-deferred-rendering), [memoryless targets](https://developer.apple.com/documentation/metal/mtlstoragemode/memoryless).
- Sustained mobile performance is a separate target from a cool-device burst. Thermal state, refresh changes, CPU/GPU contention and Android pacing affect displayed cadence; the quality governor reads thermal state (Apple `ProcessInfo.thermalState`, Android ADPF thermal headroom and performance hints), applies hysteresis and preserves the world clock. Apple recommends testing frame-rate changes on actual devices; Android Swappy/ADPF integration with wgpu presentation is **unproven** and is an Android tile recipe task. [Apple ProMotion](https://developer.apple.com/documentation/QuartzCore/optimizing-iphone-and-ipad-apps-to-support-promotion-displays), [Android slow sessions](https://developer.android.com/games/optimize/vitals/slow-session).
- Android `winit` uses `android-activity` glue; `GameActivity` is a C/C++-oriented Jetpack adapter with lifecycle/input/text benefits. BASELINE-SPEC selects GameActivity through the matching winit re-export; qualify touch, controller, IME, accessibility handoff, background and packaging on the named device. Avoid combining incompatible entry-point glue. [winit Android](https://docs.rs/winit/latest/winit/platform/android/), [GameActivity](https://developer.android.com/games/agdk/game-activity).
- Browser presentation is callback driven; background tabs commonly pause animation callbacks. Treat visibility/page restoration as lifecycle events, cap elapsed catch-up, and restore audio only as permitted by browser policy. Threaded Wasm requires deployment headers and cross-origin resource cooperation; the baseline must run without it. [Page Visibility](https://developer.mozilla.org/en-US/docs/Web/API/Page_Visibility_API), [cross-origin isolation](https://developer.mozilla.org/en-US/docs/Web/Security/Practical_implementation_guides/CORP).
- Runtime payloads are addressed by logical manifest IDs and dependency hashes, not paths. Browser fetch/cache, desktop files, iOS bundle/background-asset mechanism and Android Play asset packs supply bytes asynchronously through one source interface. Android packs can be unavailable or invalidated after updates; Apple's on-demand resources are now documented as deprecated for a future iOS release, so the iOS delivery mechanism needs a current SDK review before selection. No store limit or policy is assumed here. [Play Asset Delivery](https://developer.android.com/guide/playcore/asset-delivery), [Apple resource limits/deprecation notice](https://developer.apple.com/help/app-store-connect/reference/app-uploads/on-demand-resources-size-limits/).
- Mobile memory limits are device-dependent. F4 must track CPU decoded bytes, GPU allocation estimates, transient targets, pending upload staging, and app-reported pressure separately. Eviction and a lower-memory profile must be possible before OS termination; actual thresholds are qualification data. [Apple memory guidance](https://developer.apple.com/documentation/xcode/reducing-your-app-s-memory-use).
- Network access is optional for play unless a game opts into network features; content fetch is a separate delivery dependency. Initial boot must declare which bytes are offline and which may be fetched. N1 and NETWORK-SPEC now fix multiplayer timing/authority and the initial bounded static-controller prediction contract.

## Historical whole-scene envelopes — retired admission targets

These earlier proposals are history under the [6 November owner decision](../decisions/PERFORMANCE-PHILOSOPHY-2026-11-06.md). Record measurements, investigate visible/comparable regressions and tune later; these numbers are neither admission gates nor certification claims. Count game logic, animation, physics, AI, streaming, UI, audio, rendering, browser/OS overhead and presentation together; instrument p50/p95/p99 frame intervals, sustained 20–30 minute sessions, peaks and stalls.

| Profile | Frame target and allocation | Residency/loading target | Adjustment/rejection rule |
| --- | --- | --- | --- |
| Native desktop high | 60 displayed fps / 16.7 ms; initial CPU critical path ≤5 ms, GPU ≤10 ms, ~1.7 ms reserve (overlap means sums are illustrative) | Target: ≤3 GiB engine-owned resident CPU+GPU estimate for sample scene; ≤1 s interactive shell, ≤5 s first representative scene on local SSD | Revise per minimum GPU and content; native enhancement must not regress p95/p99 or reliability beyond agreed limits. |
| Browser demo | 60 Hz at 1080p in Chrome on this Mac for V1 (G7); 30 fps / 33.3 ms floor on other qualified browsers; initial CPU ≤8 ms, GPU ≤16 ms at 30 fps with browser reserve | Target: ≤512 MiB live app memory estimate, ≤25 MiB compressed initial download, ≤5 s first interactive on qualified connection; async later content | Reject profile if it needs isolation, native-only features or uncontrolled shader/upload stalls unless explicitly published as restricted demo. |
| Mobile sustained | 30 fps / 33.3 ms baseline; 60 fps optional qualified tier; initial CPU ≤7 ms, GPU ≤16 ms at 30 fps, deliberate power/thermal headroom | Target: ≤1 GiB engine-owned resident estimate for initial scene; ≤40 MiB initial install content slice; other assets on-demand/offline policy explicit | Qualify device-specific memory/thermal envelope; use hysteresis and measured pacing, never silently slow sim to hit fps. |

The CPU/GPU allocations are *guides to prioritize work*, not additive proof because execution overlaps and platform compositor/driver costs vary. Initial admission policy reserves at most 10% of the profile's logical memory envelope for in-flight I/O/decode/upload staging. Optional preparation on the critical thread uses the [baseline recipe's 10% share of its CPU critical-path envelope](../BASELINE-SPEC.md#budget-allocation-and-failure-rules), further constrained by actual remaining frame-deadline slack; 10% of the full frame period is not an additional allowance. The actual cost of a mandatory activation is presented as loading rather than hidden inside a frame. These are proposed control limits, not observed safe thresholds. Measure rendered resolution/DPR, transient peaks, upload queues and shader compilation separately. Keep a quality floor defined by the same visible cues and gameplay semantics, not by matching identical pixels across APIs.

## Design completion and validation order

1. **Complete the design on paper**: specify the tick dependency DAG, solved-motion authority, provider dependencies, view snapshot schema, asset activation barrier, versioned GPU/content lifetimes and terminal failure policy with their neighboring module owners. The contracts and invariants above are recommended now; their detailed schemas and game-specific ownership still require joint design, not experimentation.
2. **Derive a workload and predicted cost envelope**: one authored/animated character, instanced environment, local lights/shadows, transparency, one environmental provider, streaming boundary, two camera styles, input/audio/UI and inspect/edit hook. Compute resource sizes, pass traffic, task rates, staging/replacement peaks and frame dependencies from authored content and selected providers. Freeze expected limits before running it.
3. **Validate substrate and clock predictions**: minimal custom Rust/winit/wgpu native and web shells plus headless tick driver. Check that two views read one tick, old-generation jobs never publish, a hidden interval adds zero local world ticks, and a saturated queue backpressures without memory growth. A failure identifies a violated contract or library incompatibility; revise the design before adding features.
4. **Validate platform-specific assumptions**: iOS function on the simulator for V1, then iOS/Android app shells on rented devices; rotate, background/foreground, surface/device loss, audio interruption, controller/touch/IME, offline content, memory pressure and sustained thermal state. The recommended core ownership is fixed; empirical work chooses the narrow Android activity bridge, iOS shell details, minimum device matrix and packaging mechanism.
5. **Validate renderer portability and residency predictions**: same quality cues on Metal/DX12(or Vulkan)/browser WebGPU/mobile Vulkan. Check predicted pass traffic, shader preparation and peak overlap. A raw-API provider is considered only for a specified mandatory operation that the portable API cannot represent or a measured benefit that exceeds its maintenance cost.
6. **Validate full transitions**: stream/retire a region, switch overhead/first-person views, omit visible clouds while retaining lighting inputs, save/reload and recover device. Verify that every lease/job/resource retired by profile-off disappears, all retained consumers have substitute inputs, and world state remains one authority. Select device support and numeric budgets from these qualifications.

**Unresolved design contracts:** the precise simulation dependency graph and solved-motion authority, world/asset schema, and provider-specific resource sizes must be designed with their neighboring modules. They are missing design detail, not questions to answer by benchmarking. **Unmeasured qualification:** device/browser/API coverage, wgpu implementation cost for the chosen renderer, mobile shell/packaging integration and numeric sustained budgets. The next-wave studies should derive predicted pass/resource costs and API representability first, then test those predictions on devices. A failed prediction revises the governing contract rather than prompting an unguided series of prototypes.

## Initial transition and networking scope

BASELINE-SPEC owns the R0/R2 boot and peak worksheet. Initial gameplay regions are preloaded or use explicit
stop/load, with old world/provider leases retired before replacement allocation; the staging share does not promise
room for a complete second live world. A later live streaming recipe needs scoped state/consumer commit and peak
admission. Thin native mobile lifecycle shells remain early work alongside the small game, not postponed until a
large editor exists. Native authoring exports browser builds; browser play/cache/save does not require a browser editor.

N1's concrete R4 full-group/result/cadence recipe in NETWORK-SPEC participates in the same F1 CPU/memory budget.
The server drains bounded queues and commits outcomes without waiting for a peer or its renderer. Local authority
uses the same actions/rules. Transport I/O never schedules or mutates the world itself.
