# Play systems — integrated operating design

**Initial implementation specification:** [PLAY-ENVIRONMENT-SPEC.md](../PLAY-ENVIRONMENT-SPEC.md) now selects the concrete baseline mechanisms,
limits and failure rules. This family document retains the wider responsibility; specification does not imply runtime qualification.

31 October 2026, reconciled with [architecture decisions](../ARCHITECTURE-DECISIONS.md) and [N1](NETWORKING.md) on 1 November. **Design status:** recommended high-level operating model; provider choices provisional, implementation unbuilt, functional/visual/platform evidence absent. This design follows the [brief](../ARCHITECTURE-BRIEF.md), [programme](../DESIGN-PROGRAMME.md), shared [contracts](../CONTRACTS.md) and [primary-source account](../research/PLAY-SOURCES.md). The custom host and 3D desktop, browser and mobile-store ambition are selected by the user; Rust, wgpu, Jolt, Rapier, Recast/Detour and ozz are candidates. No external engine runtime, pure-2D or MMO burden is assumed. Future multiplayer has a first-class server-authoritative contract; N1 is optional at runtime and unbuilt. This design does not infer target capability from the current browser game's implementation.

## Outcome, supported regimes and one state authority

One fixed-tick world supports overhead/isometric, third-person and first-person play. A character can be player- or AI-driven, cross loaded cells, interact with a dynamic object, switch to ragdoll and be observed from two cameras without a second simulation. Game packages choose control and rule policies; the engine supplies action mapping, camera and view services, physics/query adapters, skeletal and morph evaluation, nav facts, bounded execution and event identity. Flight/swim, vehicles, destructibles and force-driven characters can use distinct policy/providers; a ground navmesh and kinematic capsule are not misrepresented as universal solvers. Headless operation retains all authoritative play semantics and omits views/audio/GPU.

| ID | Observable obligation and owner | Required handoff/failure behavior |
| --- | --- | --- |
| P1 | Focus/context-ranked device events become timestamped, actor-directed actions; rebinding, accessibility and recording use the same action schema | UI/text focus consumes before game mapping. Missing device/focus emits no stuck action; releases/suspend synthesize cancellation. |
| P2 | Perspective/orthographic camera rigs, picking and multiple view descriptors | Per-view matrices, time, projection and cuts are explicit. Camera obstruction queries carry an epoch; stale results cannot move a camera. |
| P3 | Static/kinematic/dynamic body modes, contacts, joints, sensors, casts and resolved body pose/velocity | One solver/query adapter owns physical representation. Unavailable required collider blocks activation. Mode changes are committed transactions. |
| P4 | Clip graph, skeleton/morph pose, IK, attachments, root extraction, ragdoll mapping | Pre-physics root request applies once; post-physics solved root and correction drive pose. Prior deformation is evaluable at the retained history sample time or invalid. |
| P5 | Agent-class walkability, tile/link connectivity, paths, local guidance, perception facts | Tile/obstacle generations validate asynchronous paths. Guidance is intent, not a body transform. Incomplete boundary path stops/replans. |
| P6 | Typed interactions, bounded state/action execution, script/sequence scheduling and game rule packages | Pre-solve commands and post-solve reactions have different phases. Exactly-once event IDs and durable rule state are save/replay inputs. |

**Canonical authoritative state at tick `n`:** W1 owns identity, hierarchy, active cell membership, committed transform `T_n` and its body-authority mode tag; P3 owns the corresponding solver representation, mass/inertia, shape refs, velocity `v_n`, solver state and collision/query snapshot `Q_n`; P4 owns graph state, clip phase, skeletal/morph state and extracted root accumulator; P5 owns nav tile/connectivity/obstacle versions and agent path/decision state; P6 owns game rule state and pending commands. P2 camera state is a view/control state, not a body transform authority. Render V2 owns derived draw data. P7 persists only the durable portions by stable ID and schema revision. Stable ID, runtime slot/generation and product hash are separate (C01/C10). Every async result or event carries the relevant world, cell, content and producer epoch. No subsystem can write `T_n` as a side effect of drawing, animation playback or path following.

## Deriving the tick and frame schedule

The causality is `S_(n+1) = F(S_n, ordered actions_n, h)`, where `h` is one host-owned fixed step (proposed 1/60 s, not measured). The following phases are a dependency schedule, not an invitation to callbacks that mutate each other's internals:

1. **Barrier and intent:** F1/W2 commit only complete, version-matched region and profile transactions. P1 orders sampled actions by `(tick, actor stable ID, local sequence)` after UI/context consumption. P6 and P5 read `S_n` and immutable `Q_n`; AI decisions and game rules produce bounded, typed intents. Asynchronous paths may become available only at this barrier after generation checks.
2. **Movement request:** game movement policy converts intent and navigation guidance to a desired translation/rotation or forces for body mode. P4 evaluates the animation graph's locomotion phase and extracts root delta from a baked track exactly once. A policy selects/combines **one** desired displacement `d_req`; it must not add full code-driven velocity and full clip root displacement. Pre-step casts against `Q_n` may adjust it; their snapshot and any prediction of moving supports are explicit.
3. **Physical solve:** P3 integrates dynamic forces, moves kinematics, performs broad/narrow phase, CCD and constraints for `h`, with declared substeps/iterations. It returns `T_(n+1)`, `v_(n+1)`, actual character displacement `d_act`, support/contact data and canonical contact/sensor event candidates. Environmental force samples are taken at declared tick time and submitted once. A controller that pushes a dynamic body creates one identified impulse; no later contact callback repeats it.
4. **Reconcile and react:** P4 computes `r = d_req - d_act` in the same frame, then chooses bounded phase-rate/stride warp/foot correction and builds the skeletal pose relative to **solved** root `T_(n+1)`. P6 evaluates post-solve contacts/triggers and enqueues rule changes for the declared same commit or next tick; any reaction needing a second physics solve is a named intra-solver iteration, otherwise it takes effect at `n+1`. P5 consumes new obstacle facts for next-tick guidance. W1 atomically publishes state/events with tick, stable source and sequence IDs; P7 can checkpoint this boundary.
5. **Presentation:** F4/V2/A1 publish presentation-only products at a separate pre-extraction barrier, tagged to committed world/content revisions; this cannot change `Q_n` or gameplay state. P2 constructs each view from committed/interpolated state and an explicit camera policy. V2/P4 evaluate current skin, morph and bounds at `t_present`; for each temporal consumer, historical deformation is evaluated at **that consumer's retained `history_sample_time`** or declared invalid. Rendering and audio read the committed event/state once; neither steps gameplay. A1 schedules a contact sound from its authoritative event ID and tick, independent of visual culling; visual interpolation must not emit it again.

For linear momentum `p = mv` and force integration, the chosen rigid solver must preserve the meaning of impulses: `v⁺ = v⁻ + M⁻¹ Jᵀ λ`, `x_(n+1) ≈ x_n + h v⁺` for a semi-implicit step. Momentum is conserved only in closed dynamic body interactions up to numerical error; gravity, drag, motors, friction and kinematic characters inject/remove energy by declared policy. Solver iterations approximate contact complementarity `g ≥ 0, λ ≥ 0, gλ = 0`; stacking/fast contacts require a workload-dependent iteration/CCD policy. Capping maximum speed or silently teleporting through a streaming boundary is not a conservation-preserving substitute. A fixed `h` makes scheduling reproducible but neither stability nor cross-platform bit identity automatic. Use substep `h/k` when a specified speed/feature thickness or stiffness demands it; `k` is internal to P3, charged to the same world tick. A swept cast/CCD needs to cover `|v|h` plus shape and numerical margins. Discrete queries against `Q_n` can be one tick stale relative to a moving platform; P3 either predicts support motion from known velocity, solves it together, or reports the known latency. Rapier's controller and Jolt's virtual character document precisely this class of query/order issue ([sources](../research/PLAY-SOURCES.md)).

**Authority modes:** static colliders follow authored/W1 edits; position/velocity kinematics follow a single P3-corrected movement request; dynamics follow forces/impulses and constraints; animation-driven props must enter a kinematic mode, with authored animation translated into an input trajectory before solve. Animation never writes a dynamic body afterward. On ragdoll entry at tick boundary, P4 maps committed bone model transforms and velocities to P3 bodies, transfers authority to dynamics, retires or disables the capsule according to collision policy, and marks a pose discontinuity. On recovery, choose a stable support/root from the solved ragdoll, blend skeletal pose toward a selected get-up clip while collider clearance is validated, then switch to kinematic authority at a barrier. Attachments name parent joint and time; gameplay hitboxes must use committed tick pose, while render-only attachments may use presentation pose.

## P1 input and P2 camera control

P1 has a platform-event queue with monotonic time, device identity, focus/window and text/gesture context. A deterministic context stack maps raw key, pointer, controller and touch inputs to game actions with explicit consumption priority and dead zone/repeat policy. Analog value is dimensionless in a documented range; device-specific sampling/filters occur before the action record. A command admitted for tick `n` is replayed by value, not by rereading the device. Rebinding changes the map version; a replay retains its map or resolved actions. This does not imply input latency can be eliminated: the next admitted tick is the earliest world response, with additional displayed latency from interpolation and present queues. Accessibility assistance (hold/toggle, remap, sensitivity) is represented as explicit action-map policy; game rules still consume one action schema. UI focus, IME and safe-area layout remain U1/host responsibilities.

P2 receives actor intent, `T_n/T_(n+1)` and per-view rig state. A camera target can be `T_view = interpolate(T_n,T_(n+1), α)` while `α ∈ [0,1]`, or use latest committed pose for a lower-latency control option; the policy is recorded per view. Rig smoothing is a sampled filter such as `c' = c + (1-e^{-h_view/τ})(target-c)`, with reset on cut and no hidden world mutation. Use a shape/ray cast from target to desired camera pose against a stated query epoch for obstruction; collisions alone do not decide desired framing. First-person head motion and third-person shoulder motion come from a declared tick or presentation pose, avoiding a one-frame mismatch with hands/weapon. Late camera orientation from fresh pointer input is permitted as a **view-only** correction for latency; the same final view matrix must feed all depth, shadow-view, motion and reconstruction consumers for that image, and it cannot change gameplay aim retrospectively. A cut, projection switch, target teleport, origin rebase, stream representation change or incompatible FOV/viewport transition propagates history invalidation. Picking reports the view/matrix/scene epoch used; an editor/game command validates object generation before applying it. Secondary views share W1 state but retain separate rig state, histories and budgets.

## P3 physical representation, queries and environmental exchange

Recommend a mature host-independent rigid solver behind a small adapter that maps stable IDs to solver handles and exposes body-mode commands, casts, contacts, joints and saveable state. Jolt and Rapier are credible candidates; choose after pinned-version/license/FFI and native/Wasm/mobile audits, using the same workload and contract. Avian's documented dependency on an external engine ECS and absent built-in character controller make it a poor default for the selected custom host ([source comparison](../research/PLAY-SOURCES.md)). This does not require a universal engine wrapper around every physics API. Collision shapes are cooked F4 products with material/filter/mass metadata; render meshes may be more detailed but cannot silently define authoritative contact. A static cell's collider is versioned with W2 activation, and P3's query index is published at an explicit tick barrier. Query request/result names `Q_n` or `Q_(n+1)`, shape/filter, origin and content generations, maximum staleness and fallback. A pre-step control cast reads `Q_n`; a post-step aim/interaction query may read `Q_(n+1)` after solve. If a required target/collider vanished, result is `stale/unknown`, not an empty-space hit. Collision and sensor events are derived from solver transition state with pair IDs and substep ordering; post-step inspection alone can miss short CCD contacts, as Rapier's event documentation warns. Contact sound/impact/V5 effects consume one committed event identity.

Water/wind (C09) provide physical fields with units, support, unique domain authority and tick time. P3 asks E1's single water query router for a named capability at X[n]; it receives the selected domain/model/source revision and validity/error or a typed outside/ambiguous/stale/unsupported result. It never chooses a height by blending two domains or by render order. A buoyant body can receive `F_b ≈ -ρ g V_submerged` plus flow-relative drag `F_d ≈ -½ρ C_d A |v-u|(v-u)` at sampled points; exact pressure integration is an optional provider. These forces enter P3 once before integration, and the body returns identified disturbances/impulses to water at the specified next-tick boundary. This is an approximation with error from sample count, surface curvature and time lag. A hull spanning two domains needs an admitted crossing contract with bounded surface/force discontinuity; visual-only or missing conservative transfer cannot grant passage. W2's stream cells do not define physical water domains, and missing boundary/query products block activation or crossing rather than becoming dry space. A rendered wave cannot become a contact height unless E1 explicitly supplies that same physical representation/query. A weather-off profile may supply constant field values; no duplicate wind clock is created in P3.

In [N1](NETWORKING.md), only the server or standalone authority world commits P3 forces, E1 water flux/disturbances and P6 consequences. A client replica may display committed/interpolated state and different visual detail, but its render water cannot supply authoritative contact. A water-contacting body is **not predicted by default**. Opt-in prediction requires complete capture/restore of relevant P3 bodies and E1 domain state, boundary/forcing revisions, source phase, returned disturbances and once-only event policy; a seed or rewind of the boat alone does not close that dependency set. N1 bounds replay work and discards prediction for missing content/state or budget exhaustion, then resynchronizes from confirmed state. Correction changes speculative presentation only; it never overwrites the server world or P7 authority save. Body, water/underwater and effect/image histories invalidate where correspondence is lost. Gameplay content negotiation pins compatible collision and E1 physical model/domain/edge/source data; local water mesh, foam, optical and shader tiers may differ only within the declared contact/occupancy error.

## P4 animation and P5 navigation/agents

P4's cooked animation package records stable skeleton/joint IDs and hierarchy, bind/inverse-bind transforms, clip revision/duration/wrap, morph IDs, event markers, motion-extraction mask/reference/bake policy and curves in metres/radians. Incompatible clip/skeleton products block character activation unless a game explicitly accepts a bind-pose fallback with disabled gameplay-dependent markers. Ozz documents low-level sampling, blend, local-to-model, IK and root-track extraction, but not a high-level graph or renderer; it is a kernel candidate ([sources](../research/PLAY-SOURCES.md)). A graph uses explicit state, phase and transition weights. Normalize blend weights where applicable; additive layers name a reference pose, masking and order. Extract root delta over the whole phase interval including clip wrap; bake that motion out of the skeletal root so `T_solved` applies it once. Motion matching, retargeting and procedural cloth are optional providers, with the same root and history contracts. Two-bone IK may correct planted feet after `T_solved`; IK target queries carry a physics snapshot epoch. Foot lock may reduce sliding but cannot alter the body's solved root silently. Morph curves combine by authored rules/clamps, with facial/viseme input from an explicit source. Skeletal pose evaluation for draw may interpolate graph state only when it preserves event/root semantics; gameplay pose remains fixed tick. To produce truthful motion vectors, retain bounded graph/clip state or sampled palettes sufficient to reconstruct both `t_present` and each retained `history_sample_time`; if skipped-view history is older than retention, mark motion invalid and reset/reject locally. P4 supplies current/historical skinned bounds or a conservative envelope to V2, including ragdoll and morph changes. GPU skinning is a V2 provider choice, not animation authority.

P5 separates **path topology** from **local movement**. Cooked Recast-style tiles represent walkable surfaces for an agent class `(radius, height, max slope, step)` with explicit border portals and authored off-mesh links. W2 activates a tile only with mandatory collision and matching content revision; adjacency is valid when both neighbor tiles and link requirements are live. A path is a polygon/link corridor with tile generations, then a smoothed desired trajectory; steering chooses `v_des` under speed/acceleration limits and nearby-agent constraints, but P3 resolves the actual body motion. This avoids DetourCrowd or another crowd solver becoming a second transform authority. Nav rebuilds for dynamic obstacles are asynchronous and can lag physics; a moving crate is handled immediately by P3 local avoidance/casts, while a generation-stamped obstacle update revises the route later. High-frequency actors should use local steering/short-horizon avoidance rather than rebuilding tiles every tick. Path requests have CPU/node/latency quotas, stable request IDs and cancellation; stale paths are rejected and repath is rate-limited. At an unloaded frontier, the portal is closed before collider removal, and agents wait/replan; a game can explicitly stream ahead/pin neighbor cells. Flying/swimming agents need a different topology provider but retain the intent/body authority contract. Perception reads versioned world/physics queries with range/frequency budget and reports uncertainty when cells are unavailable; decisions do not treat missing content as visible empty space. A behavior tree, state machine or utility selector may produce intents, but species tactics are game policy, not P5 pathfinding.

## P6 interactions, rules, scripts and sequences

P6 defines typed `read facts → evaluate guard → emit command` operations with actor/target stable IDs, expected generation/revision, tick and correlation ID. Game packages own combat, inventory, quest and economy state and rules. A reusable hierarchical state/action executor provides ordered transitions, task lifetime/cancellation and bounded per-tick instruction/work quotas; Unreal StateTree is production evidence for this organizational pattern, not a runtime dependency ([source](../research/PLAY-SOURCES.md)). Scripts/graphs can run in the same restricted operation model; they cannot access solver internals or mutate W1 mid-step. A sequence schedules authored camera/animation/audio/game commands by world tick, with an explicit pause/skip/cancel policy. Cinematic control of a body is a body-mode/movement request, not direct render-transform animation. Interaction targeting may use P3 casts and P2 picking but validates identities and snapshot epochs at command admission. Events are an ordered committed ledger `(world epoch, tick, producer stable ID, local sequence, kind)` with durable or ephemeral class and consumer cursor. Exactly-once here means one emission per committed cause and deduplication by ID at downstream consumers; it does not promise a distributed exactly-once network protocol. Save/load preserves durable rule state and event cursors required to avoid duplicate reward/audio emission. Disabled game packages remove jobs/state/resources and reject operations needing them; no empty success response hides missing policy. For N1 sessions, clients send actor-directed intents through validated tick/sequence/ownership envelopes; P6 executes irreversible rules and side effects only in the server-authoritative world. Confirmed event IDs reconcile optional speculative cosmetic cues, whose replay cannot emit them again. Replication uses a purpose-specific committed projection, not a P3 solver pointer or V2 render packet; deterministic lockstep and universal rollback are not promised.

### N1 action and result boundary

P1 submits typed actor intent through N1; P6 validates against the committed authority state and returns the committed
or rejected outcome with its actual resolution tick and event origin. A packet acknowledgement cannot confirm an
inventory purchase, cue or rule effect. NETWORK-SPEC owns the exact bounded result/group schema and scheduling modes:
ordinary board/inventory actions use next-authority-tick semantics, timed controls declare their latency window.
Only the authority commits durable consequences. Any game offering cross-reconnect durable retries must atomically
publish its operation outcome with its P7 state before acknowledging that stronger guarantee.

W1 replicas admit lifecycle and required dependent state as one group; P3/P6 never inspect a half-spawned actor.
Optional static-controller prediction reconciles individual resolved inputs against the matching authority state,
not just an envelope receipt. The initial network game needs neither prediction nor water. E1 water-enabled recipes
pair body pose and query sample at the same tick, and keep fluid forces on the server. C13/NETWORK-SPEC own these
rules so the play modules do not invent a second result queue or transport API.

## Crossing a cell boundary and an authority change

At `n`, player input or P5 guidance asks the locomotion graph for a stride toward a neighboring cell. W2/F4 has cooked collider, nav tile and gameplay products, restored P7 delta and validated border portals; at the activation barrier it installs them as one transaction, then P3 may query the boundary. P4 extracts root delta, policy emits one request, P3 sweeps the capsule against the now-active geometry and returns achieved displacement/contact. A missing mandatory product leaves the portal and physical boundary closed; intent remains pending/stops under game policy, never crossing visual placeholder terrain. P4 adapts feet/phase from achieved motion; W1 commits final pose and membership transfer without respawning the character. A1/V5 receive the authoritative foot/contact/impact event once by ID. P2 follows the committed/interpolated root; V2 renders the current pose and uses historical bone/morph state at each view's retained history sample, or invalidates. An orthographic map view may skip images without changing the world or borrowing the main view history. A profile may hide distant animation but cannot change collision/nav semantics without game consent.

If a hit changes the character to ragdoll at `n+1`, P6 issues one mode-switch command. P4 transfers each relevant bone pose and velocity to P3 bodies before the solver step; the kinematic capsule is disabled/replaced at the barrier. P3 owns the new dynamic poses; P4 maps them back to skeleton for rendering, with explicit pose discontinuity and conservative bounds. Camera target policy may move from head to pelvis with a cut or damped transition declared to V4. Any current path is suspended; after recovery, clearance and support checks determine when a get-up animation may request kinematic motion. Unload cannot remove support colliders beneath active ragdoll bodies; W2 pins swept-support cells or explicitly blocks unload/motion. P7 saves mode and required body/rule state at committed boundaries. This chain is a design obligation even if the first proof uses one character, two cells and a few joints.

## Work, error and profile reductions

Let `B` be dynamic bodies, `C` candidate collision pairs, `K` contact constraints, `I` solver iterations, `S` substeps, `J` evaluated joints, `L` sampled clip layers, `M` active morph channels, `A` agents, `N` nav polygons visited per query and `V` retained views. Rough active work is `P3 ≈ O(S(C + I K + B))` plus casts; `P4 ≈ O(J L + J + M)` per character/tick, with extra prior-pose work per view only when temporal consumers require it; path search is `O((N+E) log N)` in visited corridor graph, amortized by bounded requests; perception is bounded by query count and range. These are scaling variables, not measured timings: broad-phase quality, cache behavior, narrow-phase shape cost, crowd density, GPU skin bandwidth, FFI and queue contention can dominate. The whole-frame critical path includes P1/P6 → P4 root → P3 solve → W1 commit → P2/V2 extraction, plus GPU/present. Nav tile builds and asset decode are asynchronous but activation waits on required products. If a solver/agent budget is exceeded, defer low-priority **decisions/path requests**, reduce cosmetic pose/view rates with honest history invalidation, or enter the host's explicit overloaded state; do not drop mandatory contact steps or secretly alter `h`.

Error accounts distinguish: physics penetration/contact residual from finite solver iterations; tunneling risk when displacement exceeds un-CCD-tested feature thickness; kinematic moving-support lag of at most the declared query age plus prediction error; nav path error from tile voxel/cell resolution and obstacle-update latency; animation foot drift `|d_req-d_act|` after bounded correction; camera follow delay from tick/interpolation/filter/present; visual motion error from missing historical deformation. Proposed tolerances are content/game-specific and must be set before qualification. A game needing precise platforming or projectile collision may raise CCD/substep/cast quality without forcing every game to pay that cost. Large worlds use F3/W1 coordinates and local solver origins; rebasing transforms representations at a barrier, never physical displacement or animation phase.

F2 separates capability, provider and quality. Physics-off is valid for a noninteractive viewer if no gameplay consumer requires collision; an active character cannot get a silent no-collision substitute. Nav-off accepts player-only or scripted movement but removes path tiles/queues and returns `unavailable` to path requests. Animation-off can use a static pose only when hitboxes/interactions do not depend on animated bones. Camera-off/headless removes view rigs/render work; input-off can still accept recorded/AI commands. Dynamic ragdolls, high-fidelity IK, crowd avoidance and temporal pose history are optional providers with declared savings and semantic limits. Live changes validate dependencies, reserve overlap, commit mode/representation transfer at a tick boundary, invalidate per-view histories, then retire old products after leases/fences. Lower render quality cannot silently change authoritative P3/P5 resolution. For desktop 60 fps and browser/mobile 30 fps planning envelopes, these modules must share the platform note's CPU critical-path and memory reserves; no standalone numeric allocation is certified until the integrated workload and target devices are fixed. Report p50/p95/p99 tick, path queue, upload and displayed latency, plus sustained mobile thermal behavior and feature-off residual work.

## Creator workflow refinements

The [capability survey](../CAPABILITY-SURVEY.md) makes P4/P6 outcomes explicit. T1/F4/P4 must let a creator bind and
preview imported skeletons/clips, transitions, root paths and event markers at game scale, and inspect pose/retarget/IK
failures. P6 sequences expose camera, animation, audio and effect bindings, timing and events through the same typed
tools; a timeline/graph UI remains optional. Inspection does not bypass P3 body authority or create another clock.
H01/H11 enter D1/D2 interfaces and the I3 creator path; they do not require every advanced animation provider.

H12 is an optional haptics extension: when selected, P1 owns player feedback cues/settings and F1 owns device output.
Consume committed P6 event identity once, independently of A1 audio. Bound intensity/duration and cancellation;
handle unavailable devices, focus/suspend and opt-out explicitly. It is presentation output, never authoritative
game state or a required feature for all profiles. Exact APIs and native/browser support need separate qualification.

**Initial design versus wider family:** PLAY-ENVIRONMENT-SPEC selects the Rapier adapter, motion/root bridge,
clip/IK and ground-navigation algorithms; BASELINE-SPEC selects reference devices, and NETWORK-SPEC selects the first
wire/action/result recipe. Their dependency/API/license checks and conformance remain unrun implementation work.
Each game still declares policy such as movement intent arbitration and hitbox sample timing; an unsupported choice
cannot be hidden in an engine default. Ragdoll/advanced platform motion and live cross-cell transfer beyond the named
initial scope require separate complete mappings/transfer recipes before admission. These are additional capabilities,
not reasons to delay the small action/render/save/network game or pretend trial-and-error supplies missing mechanics.

**Dependency-ordered qualification:** first freeze schemas, authority, tick order and provider audit; then a headless two-cell scenario checks action order, complete activation, root exactly once, moving-platform contact, ragdoll transition, save/replay and event deduplication with named rejection rules (double displacement, pass-through, stale path publication, lost support, repeated contact). Next add two views and audio, inspect prior deformation/history validity, camera latency and cuts. Finally run the same semantic scene on qualified native Mac/PC, browser and iOS/Android builds with profile-specific providers, measured critical paths, peak memory and sustained behavior. Those checks qualify explicit predictions; their absence is recorded as unbuilt/unmeasured rather than “passed.”
