# Clouds: ownership, transport rules and the retained optical reference

3 November 2026, revised 13 November. **Status: planned, no engine renderer yet.** The `CLOUDS` module's design is [docs/plans/CLOUDS/DESIGN.md](../../plans/CLOUDS/DESIGN.md), written from [its brief](../../plans/CLOUDS/BRIEF.md) under the [sea/cloud port decision](../decisions/SEA-AND-CLOUD-PORT.md); it replaces the implementation target this page used to carry. What stays here, and stays in force, are the ownership and transport rules selected from `codex/cloud-system-design` at `3b46c19` and the retained Python references. That branch remains separate; its cohort renderer and bulk experiments are not a runtime dependency. No cloud appearance or frame budget is qualified by this page.

## Ownership and consumers

E1/W1 owns deterministic weather causes, world time, wind and gameplay queries. F4 owns admitted cloud source assets; V3 owns optical coefficients and transport; V1 owns GPU resources/submission; V2 extracts committed source snapshots; V4 owns display/history. A source snapshot names its revision, epoch, time, support and interpretation. Optical samples name extinction/scattering in m⁻¹, phase parameters, validity and error. Valid zero cloud differs from unavailable data. GPU caches never become authoritative weather or save state.

Main view, reflected view, Sun attenuation/shadows, sky/IBL and optional headless semantic queries are separate consumers of the **same** source. Hiding visible clouds does not retire an offscreen shadow or reflection consumer; removing all optical consumers releases cloud GPU resources after readers finish. Headless wind/rain/visibility needs no GPU readback. A visual fallback may reduce cloud quality while preserving physical/gameplay weather facts and reporting its age/error.

## Transport and reference

Beer attenuation for a constant segment is `T = exp(-σ_t Δs)`. A source segment contributes `S = j(1-T)/σ_t`, with limit `j Δs` as `σ_t→0`. Compose front segment A and rear segment B as `(T_A T_B, S_A + T_A S_B)`. Overlapping air, fog and cloud require summed coefficients and one source-light evaluation; independent lit images cannot be blended into exact overlap. A near/far level substitutes for another representation of the same condensate; it never adds a duplicate density. V3 applies named air, cloud and geometry attenuation once to a source path. The Hillaire clear-air multiple-scattering approximation is labelled separately from cloud/fog scattering.

The retained independent Python references in [`scripts/reference/cloud/`](../../../scripts/reference/cloud/optical_reference.py) define float64 atmosphere transport, Beer segment cases and Rayleigh/Henyey–Greenstein phase parameters (`WEIGHTS`, `BRANCH_B`, `LIQUID_G`). They are comparison oracles, not runtime code or a selected cloud morphology. They require NumPy and are taken from branch commit `3b46c19`; their 23 unit tests passed locally with Python 3.14 and NumPy 2.4.6, without qualifying an engine render. The earlier per-cloud cohort measured about 13 ms GPU for one cloud on an M3 Max, so the implementation must use a shared weather/source representation and early cost screen rather than scale that implementation.

## Implementation target

[The module's design](../../plans/CLOUDS/DESIGN.md) selects it: a deterministic weather field with a CPU evaluator, 2D weather fields with a vertical profile and shared 3D noise, one summed Sun-path optical-depth product for self-shadow and ground shade, a layer traced at part of the render extent and reconstructed over frames, placed voxel volumes that stand for cells of the field, and a shadow-only profile. The earlier candidates on this page (a 2.5D or panorama mobile tier among them) are not selected; a phone tier is designed when a phone is a target. Dimensions, step counts and quality are chosen from measurements in that module's milestones, and maturity is promoted only from its recorded GPU time and visual evidence.
