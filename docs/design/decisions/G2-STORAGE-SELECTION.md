# G2 decision: registered game components over private hecs storage

4 November 2026. **Selected for G2 implementation, subject to integrated profiling.** C01/C02 keep one authoritative world, checked public handles, stable identities, a fixed world tick and immutable publication. The ECS entity remains private. Game component types and rules move out of `thrum-core`; the engine owns registration, storage, scheduling, access enforcement and publication. The render and network consumers use committed read models, never a borrowed mutable ECS world.

## Decision and cost account

Use hecs 0.11.2 through prepared storage-order queries for dense systems. Keep the existing fixed-capacity stable-ID/slot/generation index outside hecs; it is the public identity boundary and sparse lookup. Register game component types and system access keys at setup, compile dependency waves once, and expose only scoped typed query borrows during a system invocation. Runtime access enforcement must reject an undeclared or conflicting borrow before any authoritative mutation. Stage writes until validation succeeds, then commit once and update per-component change ticks. Serial and Rayon executors must process the same compiled schedule and produce equal committed outcomes. Capture/restore records registered components and stable identity for prediction replay; a hecs entity number is never serialized.

The [matched release comparison](../../evidence/v1-workload/G2-STORAGE-COMPARISON-2026-11-04.md) uses separate mover/static archetypes, 15% movers, 1% static edits and 1%/s static churn. Hecs's storage-order tick is 2.416–2.499 µs at 10k and 26.74–27.62 µs at 100k. A fixed two-archetype SoA is 1.645 µs and 19.08–19.24 µs. The custom advantage is 0.77–0.85 µs per 10k tick and 7.5–8.5 µs per 100k tick, about 0.05/0.5 ms of CPU time per elapsed second at 60 Hz. These are isolated kernels, not a whole-game speed comparison. The custom candidate still needs arbitrary component registration, transitions, safe access, replay and target support; its present timing is a lower bound on that implementation. Existing hecs integration already preserves checked identity and runs on the Wasm serial target. Those costs and the small absolute kernel gap select hecs for the first complete generic game path.

Avoid an unconditional O(all entities) worklist or per-tick boxed dispatch for every system. Dense movers use prepared storage traversal; sparse edits use checked stable-slot lookup. Track changed components in preallocated tick lists and publish into G1's leased immutable pages without whole-static copying. The first generic implementation must measure allocations, hot-loop time, publication bytes and end-to-end game tick at 10k; repeat at 100k before declaring the backend qualified. Reopen the choice if integrated storage traversal or hecs structural churn becomes a material frame/tick cost, if registered game types require copying every static record, or if the serial/Rayon/replay contract cannot be met without unsafe or duplicate authorities. A future custom SoA must then implement the same public semantics and compare as a complete backend, not only this fixed-column lower bound.
