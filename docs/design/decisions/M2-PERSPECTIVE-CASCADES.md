# M2 perspective camera and cascaded Sun shadows

4 November 2026. **Selected V1 direction; perspective and two-cascade diagnostics run, full renderer/device qualification open.** This continues the running 10k scene under [C06–C08](../CONTRACTS.md) and [RENDER-SPEC](../RENDER-SPEC.md). Prior exposure to Thrum's orthographic diagnostic informs the reconciliation below; this is not a blind design study.

## Required interaction and owners

One V2 view packet supplies a right-handed, Y-up camera looking along −Z, finite near/far, unjittered current/prior matrices and a stable view identity. V1 prepares GPU resources and pass order; V3 derives light lists and Sun visibility from the one scene light registry; V4 consumes scene radiance. W1's fixed-step simulation never waits for a shadow map or derives gameplay visibility from it. A camera move, cut, resize, source change or device generation change invalidates the relevant prepared view/history. A game can disable Sun shadows and retire their maps and draw lists while keeping direct Sun lighting, and a headless game pays no GPU cost.

The current synthetic path uses identity orthographic projection, a fixed view ray toward −Z and cluster indices derived directly from world XY/Z. Its 10k objects sit at nearly one depth. Appending a depth map here would not prove cascades, projection, caster coverage or shadow stability. M2 first makes the running scene consume a perspective view packet and projection-aware local-light bins. A near/far receiver pair and an off-camera caster then prove two cascade selections, visible occlusion and caster inclusion before scaling back to the 10k moving scene.

Use the already-cached, pinned `glam 0.33.12` for matrix/vector construction in the view producer; it supports the project's Rust 1.99.1 and targets, with no new runtime dependency chain in its minimal profile. Its [WebGPU/DirectX right-handed projection](https://docs.rs/glam/latest/glam/camera/rh/proj/directx/index.html) supplies the [0,1] clip convention. A checked finite reverse-Z transform maps near→1 and far→0; no deprecated infinite projection is substituted. CPU tests round-trip camera points/rays and verify rejection of degenerate input before packing the existing 160-byte `ViewRecord`. The renderer consumes matrices and origin-relative data; it does not create another camera authority.

## Shadow representation and cost

The first V1 profile uses two 1024² D32 Sun maps (8 MiB logical depth storage), one per perspective depth interval. A practical split blends uniform and logarithmic depths at an authored weight; split depths and light matrices travel together in one prepared view packet. For each interval, fit a rotation-stable sphere around its eight frustum corners, project the receiver footprint into light space and snap its XY center to whole shadow texels. Include caster bounds outside the camera frustum when they can project onto the receiver footprint. The same shared instance table feeds shadow and forward; compact per-cascade u32 visible-slot lists avoid duplicating full instance records. Rebuild those lists from changed poses or view/light changes with reused CPU storage, then measure whether M3 GPU culling should take over.

One depth-only pipeline per reachable material/geometry role writes reverse-Z with clear 0/greater depth test. The forward pass samples each map with four comparison taps and a bias expressed in world/light-space units, converted through the actual projection. Cascade transition uses a short overlap blend to hide split seams; it cannot silently omit a required Sun shadow. This follows the frustum partition, fit and sampling sequence in [Microsoft's CSM guidance](https://learn.microsoft.com/en-us/windows/desktop/DxTechArts/cascaded-shadow-maps), with [texel-snapped projection](https://github.com/microsoft/DirectX-SDK-Samples/blob/main/C%2B%2B/Direct3D11/CascadedShadowMaps11/CascadedShadowsManager.cpp) for stable camera movement. Those sources motivate the method, not a Thrum performance claim.

The two-map choice revises RENDER-SPEC's earlier single 2048² map worksheet: two 1024² D32 maps need 8 MiB of depth texels versus 16 MiB for the single map, but two passes/list products have different CPU/GPU costs. The first 640×360 scene already spends roughly 0.13 ms in its forward pass on M3 Max; this is not spare shadow budget. Measure shadow pass GPU times, list rebuild/upload, full host pacing, peak logical resources and named mobile/browser limits. If 1024² near-cascade edges are visibly inadequate at intended distance, raise the selected quality tier with a measured budget rather than claiming the initial tier sufficient.
