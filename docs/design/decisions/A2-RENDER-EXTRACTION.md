# A2 decision: render extraction from committed simulation

4 November 2026. **Selected for the first V1 bridge; leased visual read-model now integrated, worker execution remains open.** W1 owns gameplay pose and stable identity. V2 owns copied presentation columns and GPU resources. A render visit reads a complete committed W1 tick and never writes back. The first consumer is the `v1-scene` 10k-entity offscreen diagnostic; this does not claim a general game runtime or a complete multi-consumer C02 read-model bundle.

## Representation and lifecycle

Use two preallocated structure-of-arrays CPU frames. Each row holds stable identity, current and previous origin-relative f32 position, visual revision and history-valid bit. A randomized fast hash map indexes the prior frame by stable identity. The extractor clears and reuses the staging frame, visits the immutable source once, then swaps only after the visit returns. A previous sample is valid only for adjacent ticks in the same world epoch with the same stable identity and visual revision. The frame exposes both current and previous view origins; a consumer must use the matching origin and ignore invalid prior entries. A skipped tick, restart or visual change resets history for the affected row. Iteration order carries no identity meaning.

Presentation over-capacity, duplicate identity or unrepresentable view-relative position drops that sample and increments a reported counter. It cannot fail or stall the authoritative tick. The [next slice](../../evidence/render/A2-VISUAL-LEASE-2026-11-04.md) adds three preallocated W1 visual pages containing only stable IDs, world-space positions and visual selectors. A page is copied from a complete tick, then shared through an immutable `Arc` lease; its pool slot cannot be rewritten while any lease remains. The running host releases the lease immediately after V2 copies its render columns. A full pool sheds an optional view after the world has advanced, with a counter. This first consumer page is not yet a worker-owned extraction or an owned `RenderPacket` with GPU staging/resource leases.

## Cost and proof

At 10k visible entities, each extraction visits 10k rows, hashes at most 10k stable IDs twice (current insertion and prior lookup), and copies aligned columns into reused storage. Two 10k frames avoid per-frame Vec growth; the maps retain capacity across churn. The alternative of four full `ComponentEntity` copies measured 222.8 µs median in A1 and carries health/ownership/velocity that rendering does not use. A2's measured isolated extraction and assembled scene are in [the first slice](../../evidence/render/A2-SIM-RENDER-2026-11-04.md). Reuse of foldhash 0.2.0 is registered in architecture policy; no custom hash table is added.

The first live-update diagnostic retains one fixed-size prepared GPU instance table. Its producer passes sorted, distinct changed slots; V2 validates and packs only those records into reused staging, coalesces adjacent slots into at most 64 queue writes, and falls back to one full-table write when changes are scattered or cover more than half the table. Malformed presentation records retain their last valid GPU value and increment a counter. The producer submits each frame before preparing the next, so the same buffer is not rewritten between two unsubmitted views. At 10k instances, the prepared CPU packed baseline and staging each reserve 1.92 MB, plus 40 KB of slot scratch; this is a diagnostic cost, not a final multi-view memory policy. [The Metal result](../../evidence/render/A2-LIVE-UPLOAD-2026-11-04.md) verifies image changes but not sustained pacing.

The first [serial frame-host diagnostic](../../evidence/render/V1-FRAME-HOST-2026-11-04.md) now drives that update every due tick through the shared fixed clock and both GPU passes on Metal. It holds one prepared table and blocks on each render and timestamp completion; this keeps GPU buffer lifetime simple while measuring the assembled path, but adds a second command submission and readback wait per frame. A 100-sample Divan comparison found 115 benchmark-thread Rust allocations per frame with timestamps and 60 without, including synchronous wgpu calls. The variation across two 600-frame paced runs keeps the Mac frame budget open.

The visual page uses three fixed-capacity SoA columns, 48 logical payload bytes per retained visual row; three 10k pages reserve about 1.44 MB before allocator and driver overhead. Its 10k capture measured 32.52 µs median on M3 Max, and the assembled Metal host test passes. This adds a CPU copy to the serial diagnostic; its measured assembled-frame samples are too variable for a speed comparison. It is a lifetime boundary for workers, not a claimed speedup. Next: execute extraction from a held page on the F1 worker graph, produce an owned render packet, and overlap with a subsequent world tick without reading mutable W1 columns. Measure worker wakeup, CPU phases, GPU passes, memory and skipped views on named targets. Network extraction uses change ticks and the separate A5 schema codec; render columns are not wire state.
