# M2 clustered forward lighting

4 November 2026. **Provisional selection for the running V1 diagnostic**, under [C06–C08](../CONTRACTS.md) and the [render specification](../RENDER-SPEC.md). This record commissions a real local-light interaction in the existing 10k-instance renderer; it does not claim a general camera, dynamic light registry, shadow or cooked-product implementation.

## Workload and ownership

The V1 scene has 10,000 instances and initially four unshadowed local lights plus the directional Sun. V3 derives a per-view light packet from one scene registry; V1 owns prepared GPU buffers, graph declarations and submission. The current synthetic fixture may author its four lights directly, but that fixture is not a second game light authority. Light count is runtime data, not a pipeline variant. The renderer still consumes the A2 presentation frame without stepping the world.

At 640×360 with a 32×18×16 screen/depth grid, there are 9,216 clusters. A 2×u32 offset/count table costs 72 KiB, plus 32 bytes per source and four bytes per cluster-light reference. At the declared 32-light per-cluster desktop capacity, worst-case references are 1.125 MiB; the actual compact index buffer is sized to assigned references. Binning cost is proportional to the projected sphere spans, not to all scene instances. A fragment loops only over its cluster's local lights, then evaluates the independent directional source. This pays table lookup overhead for four lights, so the assembled GPU pass must be compared with the directional baseline. A fixed 32-entry table per cluster would transfer the worst-case size on every change; compact CSR avoids that waste. Cluster layout and light payload are immutable while the diagnostic camera/lights are held, so they are prepared once rather than rebuilt per frame.

For the first orthographic fixture, world XY maps to clip XY and depth lies in [0,1]. Binning intersects a light sphere with the conservative cluster AABB; the shader uses the same grid mapping from interpolated world position. The local BRDF uses the existing metallic-roughness closure with a per-fragment direction, inverse-square irradiance and a smooth finite-radius cutoff. Preparation validates finite positions, positive radius and nonnegative intensity. A pathological cluster over capacity keeps the highest estimated contribution with deterministic tie-breaking, increments dropped-reference telemetry and remains renderable; it cannot index past the GPU buffer. Authored source validity still rejects invalid data before readiness. No silent light truncation is permitted.

## Alternatives, limits and proof

Brute-force four-light shading is simpler but scales linearly with every visible fragment and all lights. A GPU compute assignment pass may win when many lights/cameras move each frame, but adds dispatch, synchronization, staging and overflow management before that workload exists. The compact CPU-built table is selected for the fixed V1 fixture; dynamic update cost decides whether a later GPU builder replaces it. The [clustered shading paper](https://diglib7.eg.org/items/6342d4d6-5220-4376-a5c6-a153058f4a3c/full) motivates 3D light lists over 2D tiles, but its published scene timings are not a Thrum device result.

First proof: four nonoverlapping and overlapping sources must change pixels only in their influence volumes; a zero-local-light scene must retain the directional result; capacity stress must report dropped references with valid indices. Graph validation must account for every light/list read. Capture the running 10k scene and compare GPU forward-pass and whole-host distributions on the same Metal device. Then extend the view packet to perspective/resize and live lights before calling this a reusable clustered renderer. Cascaded shadows remain the next M2 interaction and are not implied by local-light success.
