# V1 bounded frame host

6 November 2026. **G3b selected boundary; qualification open.** [C02](../CONTRACTS.md#c02-time-and-committed-state--f1-coordinator-w1-world), [C06](../CONTRACTS.md#c06-gpu-execution-and-lifetime--v1) and [C07](../CONTRACTS.md#c07-render-scene-views-and-temporal-data--v2-with-p4v3v4) govern. The running macOS window has a display link, a render actor and an authoritative world thread. The optional A3 extraction lane was removed because no game or fixed frame benchmark used it. The browser keeps serial extraction.

The platform owns the display link, surface generation and acquired drawable. The game owns rules, schema, scene mapping and controls. The engine frame runtime must own the fixed-step clock, generic game driver, two GPU slots, extraction handoff and completion order; the current `FrameHost` still lives in the game and is G3b work. A committed page is the only world-to-render input. One native render actor reads it, extracts rows, updates camera/lights/shadows and encodes. The world thread advances from observed monotonic time independently of display callbacks. A target timestamp only sets bounded interpolation alpha and never advances authority. A busy GPU ring sheds an optional view, counts it and keeps committed ticks.

The render actor owns surface configuration and encodes the scene before requesting a drawable. The platform advances a checked surface generation on resize, occlusion and close; work invalidated during acquisition is discarded. Resize waits for old GPU uses, while explicit close detaches a blocked actor. The world thread never waits for presentation. Replay, visual replacement, resize and device change reset history. Scene submission before acquisition and device-loss recovery remain open. Short live-window runs now present successfully; [current evidence](../../evidence/render/V1-BOUNDED-FRAMES-2026-11-04.md) separates drawable wait from frame work. Browser execution remains serial; discrete actions preserve order while continuous axes may coalesce.

Qualify on the M3 Max built-in 120 Hz display: ten-minute present-interval p99 within 1 ms, complete 10k/1080p render-frame CPU p95 at most 0.3 ms with zero per-frame allocations on every frame thread, input-to-photon timestamps, and surface/background/device-loss recovery. The iPhone 18 Pro simulator proves configuration and lifecycle only. Use paired interleaved runs under competing load; the actual active display is required for present timing. Move `FrameHost` behind a game-agnostic engine API only after the running display-link path and late-acquire ownership are stable.
