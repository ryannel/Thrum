# V1 cooked constant light and visual replacement

4 November 2026. **Selected bounded construction path; first native A/B diagnostic implemented, full hot reload open.** This binds the existing `constant-light-v1` source profile to the running V1 scene under [C02, C04–C06 and C08](../CONTRACTS.md), the [render light units](../RENDER-SPEC.md#4-scene-colour-and-light-quantities) and the [environment design](../modules/ENVIRONMENT.md). It does not select a new world authority or a general live gameplay edit path. The first accepted visual replacement changes constant Sun colour/direction/intensity, ambient and terminal background while the authoritative simulation and game code keep their identities.

## Producer, artifact and consumer

F3 owns an accepted exact-byte root. F4 receives its live `PinnedSource`, reads the project's selected `core.scene@2`, its `thrum.environment.authored@1` edge and that record's `thrum.light.identity@1` edge, and refuses a missing, duplicate, undeclared or mismatched identity. The light identity has no independent transform or intensity. The cook uses the already checked numeric source parsers, keeps the accepted root only as provenance, and keys its target-independent immutable product by cooker revision plus the four exact direct-input hashes (project, scene, environment, light). An unrelated admitted source edit can reuse the product. A deterministic artifact carries the product key and numeric payload with a separately verified content hash; cache bytes never acquire source authority by themselves.

The V1 renderer consumes one product generation at a time. The Sun direction, raw perpendicular RGB illuminance in lux, isotropic ambient RGB irradiance in lux and independent background radiance in cd/m² retain the [R0/V3](../RENDER-SPEC.md#4-scene-colour-and-light-quantities) meaning. The synthetic renderer has a separate photometric preparation input: it retains the product's units, uses the same Sun direction for direct shading and shadow matrices, adds Lambert ambient, pre-exposes scene and background radiance, and counts finite presentation channel clamps. Diagnostic lighting remains a fixture input. Zero Sun omits shadow resources and passes. Sun angular radius remains in the product but fixed PCF does not yet express disk or penumbra size; radius-only edits are not visually qualified. No arbitrary lux-to-diagnostic multiplier is a product format.

A source edit first becomes a new accepted root. F4 cooks and checks the selected visual closure, then V1 can prepare a detached scene copy and new GPU targets on its existing device/queue while the old view remains usable. A host-owned candidate publishes only after its older packets complete; it uploads current instance rows before the atomic swap. A successful target replacement now invalidates the extractor's prior-pose history, including a same-tick capture; the next extraction starts a fresh view history even if the product bytes happen to match. The serial diagnostic exposes preparation as a separate API; it does not yet schedule a background worker or live file watcher. The world tick never performs source read or pipeline compilation. A failed edit, cook or preparation leaves the previous ready visual revision and world untouched. Visible failure diagnostics, full temporal-image history handling, and gameplay edit classification remain open under C05.

## Cost and first proof

Source reads and SHA-256 work occur once per accepted change, never per tick. The constant-light product is a few hundred bytes; shader-facing f32 values are checked and rounded once at preparation. The first 10k/1.5k-mover diagnostic has three roughly 34.5 MiB logical offscreen target sets; pending old/new preparation may temporarily retain both. The actual driver residency and preparation latency must be measured, not inferred from those logical bytes. No extra per-frame source decode, hash or CPU allocation is permitted. A cooked visual revision must be inspectable with its exact source root, product hash, GPU generation and frame tick.

The first native test cooks two admitted roots, publishes A and B through the running 10k host, sees a same-tick pixel difference for changed Sun colour, and checks continued ticks and frame revision. An unrelated admitted file reuses the product key; a missing scene edge and corrupt artifact refuse. A third zero-Sun root omits shadow passes and reports clean GPU timing. The remaining proof must change Sun direction and check shadow direction, hold A's submission deterministically across B preparation, exercise GPU-preparation failure and prior-view retention, measure cook/preparation latency and replacement peak, and run sustained costs on named Metal. Chrome and iPhone runtime remain separate gates.
