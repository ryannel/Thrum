# G2 design: one registered simulation for the running game

4–5 November 2026. **Qualified in the running game; see [evidence](../../evidence/v1-workload/G2-GAME-RUNTIME-2026-11-04.md).** C01/C02 remain binding: stable identity differs from physical slot and backend entity, one fixed tick commits once, failed authority work changes no committed state, and consumers receive immutable leased endpoints. [Storage selection](G2-STORAGE-SELECTION.md) chooses private hecs 0.11.2 with storage-order prepared queries. G1's current page is a migration endpoint, not a reason to keep fixture fields in the engine.

## Ownership and public composition

`thrum-core` owns `World`, dense slot/generation mapping, hecs storage, setup registration, schedule compilation, tick transaction, change lists, publication leases and restore. A game owns all component Rust types, system callbacks, input actions and rules, replicated fields and their stable schema/quantization IDs. The V1 game declares distinct moving and static bundles; a mover has position and velocity, while a static has position without velocity. Its four controlled actors retain velocity capability even while idle, although their stable IDs lie outside the initial 1,500 moving IDs. The engine never names position, health, visual, ownership or a V1 action in production API or tests. Games register components and systems at setup before the first tick; removal/replacement of a registered component or system starts a new run until a migration contract exists. A second game can compile against public APIs without importing the example.

Component registration binds `TypeId` to a stable game schema ID and per-type operations needed for validation, snapshot capture and restore. `TypeId` remains process-local; schema IDs are explicit game data for saves and G6 wire use. A system registration binds a stage, stable `SystemId`, dependency IDs, typed query, permitted typed edit targets and callback. The engine derives query accesses and edit-target writes at registration, checks each component is registered, and compiles their union into the schedule. A writer can emit only registered target types in that union; structural spawn/despawn and external resources require explicit capabilities. This prevents a command writer from bypassing a compiled conflict edge. The current `Schedule` graph compiles conflict-free waves; the executor invokes the actual registered callbacks, once per due tick. Game callbacks receive a scoped query and typed command writer, never the raw hecs world or an unchecked entity ID. Sparse lookup uses a checked `Handle`. Query iteration follows hecs storage order; public results resolve through engine slots.

## Tick, publication and replay

The input gate checks generic `InputFrame<GameAction>` identity, sequence, count and axes; game validation checks its action payload. Accepted frames remain pending until a tick commits. Each callback reads the committed state and writes to a reusable per-system typed edit buffer. Stage dependencies may read prior staged values only through the engine's candidate view; the engine must not publish or apply a partial candidate. Validate all outputs, identity edits, finite values where the game declares that rule, and structural conflicts before applying. Apply in a stable slot/system order, update per-component change ticks, seal one G1 page, consume inputs and advance the clock exactly once. Failed preparation retains the same due tick and admitted frames. Publication pressure is checked before input admission. The game declares which registered components enter the read-model bundle; render and future replication consume that same `SnapshotId`, dirty slots and structural journal. They never query a second authoritative world.

Prediction stores owned input frames and a rolling capture of registered authoritative components, slot generations, stable IDs and relevant game resource state. Restore reconstitutes the same identities and system state at a specified tick, then replays through the same serial schedule. The capture also records relevant per-archetype traversal order and game callback/resource state; backend hecs IDs do not enter it. Per-entity independent systems may use fast storage order. Order-sensitive selection, accumulation and event emission use a canonical stable-slot traversal/reduction or a recorded order, so a changed hecs layout cannot change replay. Parallel execution uses Rayon for conflict-free waves with private edit buffers; merge order equals the serial executor. Every callback produces the same output for the same input and world tick; nondeterministic results must be recorded. A serial-versus-parallel equality test compares full committed state, event order, dirty sets and snapshot IDs, including churn, rejected input and restore/replay from a capture after swap-removal churn. Device floating-point identity across platforms is a separate qualification, not inferred from one-machine equality.

## Cost and migration gates

At 10k/1.5k moving, the isolated hecs kernel is 2.42–2.50 µs per tick versus 1.65 µs for fixed SoA; at 100k/15k, 26.74–27.62 versus 19.08–19.24 µs. The total game tick and page cost is larger, so avoid per-entity boxed calls, full-static copies, per-tick allocation and random lookup for dense motion. Registry and graph work allocate at setup; typed edit buffers grow to high water and reuse; structural changes remain bounded by configuration. Measure 10k and 100k game ticks, allocation assertions, publication bytes, restore/replay cost and serial/parallel crossover. A parallel executor can be slower at 10k and should choose serial there by measured policy, while remaining result-equivalent.

Migrate the **existing** V1 authority: first introduce registered storage and callback dispatch within its tick; then move V1 types, action validation, motion/control rules and schedule declarations into `examples/v1-game`; then replace the fixed page columns with registered read-model capture. Adapt its current window/Chrome/iOS consumers and projection outbox in the same slice, retaining one running game and no new fixture binary. Remove the old fixed `Simulation`, `ComponentEntity`, `SimAction` and core fixture schedule after the game uses the generic path. Tests in core use minimal independent components. G2 is complete only when the one game draws committed generic state and passes the serial/Rayon, replay, authority-failure, 10k/100k and `./dev check` gates. G3 then moves `FrameHost` to the renderer.
