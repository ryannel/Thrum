# E1 product-store physical layout — provisional comparison

3 November 2026. This is a bounded storage decision for the fixed 160-byte E1 product, 80-byte manifest and 204-byte source binding in the [governing identity candidate](E1-CONSTANT-LIGHT-PERSISTENT-IDENTITY-2026-11-03.md). It does not select storage for general F4 assets or establish a ready build. C05 assigns product authority to F4; C10 requires product/source/reader retention and atomic selection at the authority that owns each root.

## Comparison and provisional direction

| Layout | Closure publication | Reuse and cost risk |
| --- | --- | --- |
| Three immutable named files | Three install/sync/reopen sequences plus partial-closure restart rules; no-replace hard links need a qualified root and directory envelope. | Shares a blob and manifest across source-only rebindings, but the per-object filesystem work is disproportionate to 444 logical bytes until measured otherwise. |
| One packed binding-named file | One install sequence and simple all-or-none packed closure. | Duplicates 240 blob/manifest bytes on each source-only rebind; does not demonstrate shared physical product ownership and is a poor default for future larger products. |
| Separate SQLite product CAS | One transaction installs missing blob/manifest/binding rows and a keyed product publication outcome. WAL/checkpoint work and page amplification replace per-file syncs. | Direct sharing, one closure authority and an ordinary exact-key lookup. Needs its own root, writer, WAL backpressure, uncertain-COMMIT recovery and physical accounting. |

**Preferred first proof candidate: a separate SQLite E1 product CAS with no GC.** This is a work-count/design judgment, not a latency result or a final selection. [SQLite's WAL design](https://www.sqlite.org/wal.html) permits readers and one writer to overlap, but a long read transaction can prevent a complete checkpoint; the reader lease should own verified fixed-size bytes and a product-owner reference after closing its short SQL read. WAL transactions across separate attached databases are not one atomic cross-database selection. `FULL` synchronization and checkpoint policy need a tested native envelope, not a claim inferred from a successful process-kill test. Compare warm source-only rebind, changed product and cache hit including checkpoint tails against the file and packed candidates before selecting a broader layout.

For `N` exact-source bindings to one product, separately shared logical objects contain `240 + 204N` bytes while packed closures contain `444N`. Neither expression predicts page, WAL, directory or allocation cost. Cold database initialization may dominate the first E1 object; file installs may dominate many rebindings. Measure both.

## Candidate authority and transaction

The product database must live in a private F4 root **outside the editable source tree and F3's `.engine` scan tree**, on a verified intended filesystem domain. The current F3 stage-budget scanner excludes only `source.sqlite` and its WAL at the `.engine` top level; placing `product.sqlite` there would mischarge retained product rows/WAL as managed staging. The current T2 host separately accounts only materialized F4 input, not a product root. Product main, WAL, SHM/control files, outstanding growth and checkpoint debt require an explicit distinct owner/class in composed same-volume accounting. Logical 444-byte closure size is not a physical allocation allowance.

One possible strict schema is `blob(blob_hash PRIMARY KEY, bytes)`, `product(product_revision PRIMARY KEY, blob_hash REFERENCES blob, canonical_manifest)`, `binding(binding_revision PRIMARY KEY, product_revision REFERENCES product, canonical_binding)`, and `publication_outcome(operation_id PRIMARY KEY, request_hash, binding_revision REFERENCES binding)`, with exact BLOB type/length checks and foreign keys enabled. Store metadata fixes format, incarnation and operational source-store binding. There is no mutable `CookKey` index, public update/delete, or row repair. SQL constraints are supplemental: the caller still checks canonical grammars, every digest association, exact expected context and freshly recooked 160 bytes against the same accepted pin. Bound row lengths before allocating returned BLOBs, including corrupt rows. A conflicting existing key refuses unless **all** expected bytes and associations match; `INSERT OR REPLACE` cannot implement immutable identity.

The first transaction holds one F3 accepted pin and its project-store owner, expected source/context, product ownership, and a private writer. Before `BEGIN IMMEDIATE`, it has already copied/verified four selected files, recooked expected bytes, checked fixture or trusted class/target context as appropriate, and secured a composed incremental storage claim. Insert missing rows; on conflict compare exact existing rows; commit closure and operation outcome together. A lost response resolves by the operation ID and request hash after fresh exclusive recovery, then verifies the full bound closure. A final-COMMIT I/O uncertainty quarantines writes and automatic checkpoint/close cleanup until recovery can establish committed versus absent outcome. Missing outcome leaves the previous build selection untouched. Existing immutable A rows and reader-owned copies remain while B publishes.

This is a **product closure transaction only**. It cannot atomically check F3's moving accepted root or install F4/T2's ready selector across stores. The wider ready owner must conditionally check request epoch, source generation, selected prior build and complete product/tool closure at its own commit, acquiring durable source/product ownership before releasing publication leases. An obsolete request may leave an **unselected historical exact-source association** in a no-GC store; that row is not a current-source assertion, ready binding, or activation grant. This bounded policy removes an impossible cross-store stale-binding precheck while preserving stale-result refusal at the ready selector. A fixture-class private store proof may exercise row/recovery mechanics but cannot issue a production reusable binding while T2's verified executing-cooker class and player target lock do not exist.

## Required rejection and measurement

Prove exact-key corruption refusal, self-consistent wrong product against recook, same product/blob under repeated source-only bindings, A reader while B commits/checkpoints, two cooperating openers, failed outcome insert, process kill and native `ENOSPC` around row write/commit/checkpoint, lost success response, restart outcome resolution and uncertain final commit quarantine. Include simultaneous F3 main/WAL, T2 materialization/compiler and F4 product claims on the same opened filesystem identity. Retained rows, WAL and freelist are occupied storage; only incremental future growth is additionally claimed, without double-counting already retained allocation. Unknown growth defers work rather than inventing an arbitrary count or space reserve. Power-loss qualification remains a separate gate.

The [pinned-cook cost probe](../../evidence/i2a/E1-PINNED-COOK-PERF-2026-11-03.md) measures source authentication and recook, **not** any of these store layouts. No product-store latency, physical peak or ready-build performance claim follows from it.
