# Core-engine architecture challenger audit

1 November 2026. Independent derivation was preserved first in [`tmp/handoffs/2026-11-01-engine-audit/core-independent.md`](../../evidence/handoffs/2026-11-01-engine-audit/core-independent.md), before inspecting this design package. This is a **decision audit**, not an implementation, benchmark, exhaustive engine comparison or certification. The custom host is a user choice. The target is a reusable 3D engine for overhead/isometric/third/first-person games on Mac, PC, browser demos and native mobile stores; AI-assisted development does not imply an in-game LLM. Ordinary networking is undecided. Existing code is not the target by default.

## Most consequential result

The package has good cross-system invariants: stable identity differs from runtime handles and content hashes; one authority controls each body; required region products activate before world queries; views read committed state; and presentation/physical effects can be selected separately. The **open architectural choices** are narrower and more concrete than an alleged missing feature list:

1. D0 has not compared a validated static composition root with the candidate plugin registry, though some later text assumes the latter.
2. W1 already permits standalone storage libraries as a D1 choice. Its current comparison does not yet evaluate using an existing **complete ECS only for W1**, while leaving physics, navigation, render and assets specialized.
3. F1/COMPOSITION need a schedule model that covers specialized-store accesses and multiple update cadences without relying on ECS component access declarations alone.
4. The renderer design needs to state what *replaceable renderer* actually means: graphics backend, rendering pipeline, transport/material family, or whole renderer. The proposed V1/V3/V4 authorities already make some options expensive or unavailable.

These are decision-quality follow-ups and boundary clarifications for D0/D1/D2, not a claim that D1 deferral itself is an architectural blocker. A concrete candidate design is valuable, but the existence of a coherent candidate is not a comparison with strong alternatives. The prior [composition review](COMPOSITION-REVIEW.md) checked internal lifecycle/consistency and says so; it did not select the package model against simpler choices.

## F1 — Composition mechanism lacks its strongest simpler comparator

**Classification:** weak justification and a selection-status conflict, not a newly discovered feature gap. **Prior claim:** [COMPOSITION](../COMPOSITION.md#the-developer-model) lines 8–13 explicitly reopens selection, yet lines 28–55 say games are built from a small kernel plus engine/game feature plugins; lines 75–110 specify descriptors, registration, provider locks, access declarations and activation; [CONSTRUCTION-PLAN](../CONSTRUCTION-PACKAGES.md#ordered-work-packages) lines 26–31 correctly reserves selection for D0. [TOOLS-SOURCES](TOOLS-SOURCES.md#derived-selection-and-alternatives) line 19 argues against scattered booleans, which is a weak comparator: a finite typed application recipe with a validator and explicit extension hooks also avoids scattered booleans.

**Competing approaches and inspected primary scope:** [Bevy's plugin guide](https://bevy.org/learn/quick-start/getting-started/plugins/) shows App registration, grouped defaults/minimal selections and optional renderer registration; it supports a plugin approach, not an obligation for this engine. [O3DE Gems](https://www.docs.o3de.org/docs/user-guide/gems/) package code/assets, while its [component reference](https://www.docs.o3de.org/docs/user-guide/components/reference/) shows that component availability and dependencies are coupled to Gems. [Unreal's Gameplay Framework](https://dev.epicgames.com/documentation/en-us/unreal-engine/gameplay-framework-in-unreal-engine) uses actors, components and scoped subsystems as the ordinary game structure; this is evidence that a framework can expose substantial composition without making each game rule a plugin. These pages do not establish comparative runtime cost. A strong local alternative is **statically linked feature modules plus a typed, validated game recipe** selecting capabilities/providers at build/load, with narrow game registration hooks and no universal plugin descriptor or live disable protocol. A hybrid can reserve true packages for externally distributed/optional subsystems.

**Why it matters / concrete scenario:** a small first-person game adds `Health`, `DamageIntent` and one damage system. The candidate requires a Combat package descriptor, schema/version compatibility, registration, provider/operation lifecycle and disable semantics even if the game never switches Combat off at runtime. A static recipe plus typed system registration may meet E01/E02/E12 with fewer contracts, while still rejecting absent Health schemas and producing an inspectable lock. Conversely, an engine intended to accept independent third-party gameplay packages across many games may justify the full registry. No representative package count, change cadence, ABI/distribution requirement or explicit cost model selects between them yet.

**Recommended resolution / owners:** D0 should compare (a) validated static recipe, (b) static modules with package-level optionality, and (c) the current plugin registry on the two [COMPOSITION recipes](../COMPOSITION.md#two-games-one-engine) plus Combat, using dependency explanation, third-party extension, omitted binary/runtime work, compatibility/migration burden and AI inspection as criteria. Select separately what needs package installation, provider selection, gameplay system registration and live switching. F2/T1/F3, F1, W1/P6/P7 and V1 are affected. Keep the candidate text marked as such until selected; do not infer that user approval of flexibility selected Bevy-like packaging.

## F2 — W1 storage choice omits the existing-ECS-only-for-W1 alternative

**Classification:** decision-quality follow-up, not a missing reuse policy or invalid D1 deferral. **Prior claim:** [WORLD-CONTENT](../modules/WORLD-CONTENT.md#selected-representations-and-authority) lines 23–27 recommends a small entity registry with archetype tables, sparse sets, schema reflection, generation-checked IDs and specialized external stores. It explicitly allows owned **or standalone** table/sparse primitives at D1. Its alternatives at lines 94–100 reject “one archetype ECS for every subsystem,” which is not the closest competitor. [CONSTRUCTION-PLAN](../CONSTRUCTION-PACKAGES.md#decisions-before-construction) line 13 preserves the library choice. [PLATFORM-RUNTIME](../modules/PLATFORM-RUNTIME.md#candidate-architecture) line 13 excludes Bevy ECS as a *concealed host facility*, which need not exclude a bounded standalone ECS dependency used only inside W1. Its line 15 says an application-framework scheduler is “excluded by the user decision.” That overstates the user decision: it excludes Bevy **as host**, not use of a standalone scheduling library behind an owned F1 contract. A library that silently owns the loop/world lifecycle would still violate the selected custom-host boundary.

**Competing approaches and inspected primary scope:** the [Bevy ECS crate README](https://github.com/bevyengine/bevy/blob/main/crates/bevy_ecs/README.md) shows direct `World` and `Schedule` usage outside the Bevy App/renderer host. Its [storage docs](https://docs.rs/bevy_ecs/latest/bevy_ecs/storage/index.html) and [StorageType](https://docs.rs/bevy_ecs/latest/bevy_ecs/component/enum.StorageType.html) identify table/sparse behavior and protected low-level storage APIs. [Unity Entities baking](https://docs.unity.cn/Packages/com.unity.entities%401.0/manual/baking-overview.html) shows an authoring representation converted to runtime entities; [structural-change guidance](https://docs.unity.cn/Packages/com.unity.entities%401.0/manual/components-add-to-entity.html) shows why deferred entity commands matter. [Godot's scene/server split](https://docs.godotengine.org/en/stable/engine_details/architecture/godot_architecture_diagram.html) and [server bypass](https://docs.godotengine.org/en/4.6/tutorials/performance/using_servers.html) show another hybrid: friendly scene objects over specialized services. None proves one storage implementation is fastest for this workload.

**Why it matters / concrete scenario:** W1 must load a prefab with dynamic optional components, inspect it by schema, stream it, make game systems query it, issue structural commands, save durable state, and extract a leased snapshot while P3 keeps a private body table. An existing ECS can supply entity generation, queries, change tracking and borrow-conflict machinery; adapters still own stable IDs, transactions, persistence and specialized stores. Owning the tables may reduce dependency coupling and give exact layout/serialization control, but also requires implementing these mature mechanisms and maintaining them across platforms. The currently cited “one ECS for every subsystem” would be wrong for the P3/V2 stores; it does not refute the bounded option.

**Recommended resolution / owners:** Before D1 freezes W1 APIs, compare an existing ECS library confined to W1, a custom W1 registry, and scene-object/component storage with targeted dense arrays. Compare a standalone schedule library under F1 as a separate option. Inspect exact crate versions/dependencies/licensing and the fit of component schema IDs, deterministic command order, immutable snapshot extraction, generational identity, multi-world scoping, wasm/mobile size, hot reload and specialized-store handle mapping. Decide the *public* W1/F1 contracts separately from library internals so a library can be rejected without changing game semantics. F3/W1/F1/P6/P7/T1 and V2 are affected. This is not a request to adopt the Bevy host.

## F3 — Declared ECS access is not yet a complete CPU execution model

**Classification:** missing architectural choice at the W1/specialized-store boundary; exact executor algorithm is a genuine D1 detail. **Prior claim:** [COMPOSITION](../COMPOSITION.md#declaration-validation-and-activation) lines 99–104 says systems declare component/resource reads/writes and that conflicting access prevents concurrency. [CONTRACTS C02/C03](../CONTRACTS.md#c02-time-and-committed-state--f1-coordinator-w1-world) lines 23–28 and 54–67 establish one fixed authoritative tick, pre-tick publication, a body/animation feedback order and no implicit callback loop. [PLATFORM-RUNTIME](../modules/PLATFORM-RUNTIME.md#derived-execution-model-and-invariants) lines 43–49 describes an ordered graph, but W1, P3, P4, P5, E1 and game rules use several specialized stores and asynchronous results. The access declaration's scope and scheduling granularity for these stores are not established.

**Competing approaches and inspected primary scope:** [Bevy ECS](https://bevy.org/learn/quick-start/getting-started/ecs/) uses system data access to run independent work in parallel and explicit chaining where order matters. [Unity Entities system groups](https://docs.unity.cn/Packages/com.unity.entities%401.0/manual/concepts-systems.html) separate initialization/simulation/presentation and support nested groups; [Unity fixed-step time](https://docs.unity.cn/Packages/com.unity.entities%401.0/manual/systems-time.html) permits a fixed group to run multiple times per frame. [Unreal tick groups/prerequisites](https://dev.epicgames.com/documentation/en-us/unreal-engine/actor-ticking-in-unreal-engine) establish phase barriers around physics and explicit dependencies; [Godot SceneTree](https://docs.godotengine.org/en/latest/tutorials/scripting/scene_tree.html) uses deterministic tree/lifecycle order with frame and fixed callbacks. These are different choices of granularity and predictability, not evidence that all work should use one ECS scheduler.

**Why it matters / concrete scenario:** P5 plans a route using an immutable obstacle snapshot while P3 solves contacts, P4 builds a pose from achieved motion, E1 updates a surface field, and a game damage system mutates Health. Marking each subsystem as one coarse write resource serializes much of the tick; exposing internal slices to the scheduler risks bypassing P3/E1 ownership. A 30 Hz mobile view may still need 60 Hz body steps, lower-rate navigation and environmental updates, and per-view frame work. “One world clock” can support those cadences, but the documents do not state when held/stale outputs are admissible, how phase ordering relates to access conflicts, or how asynchronous completions publish without nondeterministic ordering.

**Recommended resolution / owners:** D0/D1 should select an explicit **semantic phase DAG and access scope**: which work is fixed-tick authority, multi-rate derived/authoritative work, presentation-frame work and asynchronous preparation; which specialized stores expose read snapshots versus mutating jobs; barriers for command application, physics, animation, environment, events and snapshot publication. A scheduler may then use declared component/resource access *within* phases where it is truthful. Specify rate multiples, sample age/hold/interpolation and catch-up behavior for representative P3/P4/P5/E1/game work before executor selection. F1/W1/P3/P4/P5/E1/P6/V2 are affected. A dependency graph is justified; one generic runtime system-access abstraction is not yet.

## F4 — Renderer replacement boundary and shading policy need an explicit selection

**Classification:** missing choice about promised extension level, with a weakly justified default for all game styles. **Prior claim:** [COMPOSITION](../COMPOSITION.md) lines 15–24 explicitly says whole-renderer replacement requires its own justification and compatibility contract. Yet [RENDERING](../modules/RENDERING.md#proposed-operating-model-and-decisions) lines 19–27 selects V1/V2/V3/V4/V5 authority and a clustered-forward, energy-accounted material/transport baseline; [CONTRACTS C06–C08](../CONTRACTS.md#c06-gpu-execution-and-lifetime--v1) requires one GPU executor, V3 transport/light/material composition and V4 display. Those are strong choices for the baseline, but they are also constraints on what a third-party renderer can replace. The notes do not say whether renderer substitution is an actual product requirement or merely an observed Bevy precedent.

**Competing approaches and inspected primary scope:** [Bevy plugins](https://bevy.org/learn/quick-start/getting-started/plugins/) show the built-in renderer can be omitted as an App plugin. [Unity's active render pipeline](https://docs.unity3d.com/6000.1/Documentation/Manual/srp-setting-render-pipeline-asset.html) allows built-in, URP, HDRP or custom SRP, and explicitly warns that assets/code must be compatible when pipelines change; its [RenderPipeline entry point](https://docs.unity3d.com/kr/current/ScriptReference/Rendering.RenderPipeline.Render.html) exposes a full custom render loop. [O3DE Atom RPI](https://www.docs.o3de.org/docs/atom-guide/dev-guide/rpi/rpi/) supports passes/features over an [RHI](https://docs.o3de.org/docs/atom-guide/dev-guide/rhi/rhi/) that handles platform APIs; [frame rendering](https://www.docs.o3de.org/docs/atom-guide/dev-guide/frame-rendering/) shows component-to-feature-processor transfer. [Godot RenderingServer](https://docs.godotengine.org/en/4.4/classes/class_renderingserver.html) permits lower-level scene bypass, which is different again. These sources support several distinct seams; none demonstrates cost-free full replacement.

**Why it matters / concrete scenario:** a game wants a painterly/illustrative renderer with a non-GGX material response, different light accumulation and deliberate media compositing, while another game uses physically based clustered forward. A V3 material/shadow provider might support that style if its contract admits a distinct closure; otherwise the game must fork V3 or the whole renderer. If it replaces the whole renderer, it still needs W1/V2 identity, views, GPU lifetime, content products, device loss and diagnostics. Calling both paths “renderer plugins” hides the material and authoring compatibility work. A deferred/hybrid path with the *same* material/light contract is narrower than a custom pipeline.

**Recommended resolution / owners:** D0/D2 should define three separate promises: (a) optional renderer/headless mode, (b) replaceable graphics API backend or render feature/provider, and (c) independent render pipeline/material-transport family. Select (c) only for a supported game/style use case and budget its asset/schema, extraction, history, display and tool compatibility. If the engine promises only (a)/(b), state that clearly and keep V3's baseline; if it promises (c), find the stable scene/view/device contract below V3 and test a structurally different pipeline on paper. V1–V4, F4/F2/T1, E1, P4 and world extraction are affected. This audit does not ask for a generic all-renderer abstraction before a use case exists.

## Safe deferrals and scoped cross-checks

| Decision | Classification and assessment | Consequence for construction |
| --- | --- | --- |
| Exact ECS crate and low-level table layout | Genuine later detail **after** the W1 boundary comparison in finding F2. The current identity, save and derived-store contracts give a useful constraint set; using a library must not silently import a second host. | D1 pins a version/dependency closure and checks contract fit before W1 implementation. |
| Ordinary co-op/networking | Optional/out of current scope, safely deferred at the protocol/replication level. C01 stable IDs, C02 tick-stamped commands, P6 event IDs and P7 persistence make later design possible; they do **not** prove rollback, prediction, authority or cross-platform determinism. | Do not label the current local-overload pause or replay system “network ready.” Revisit authority and scheduling together when a networked game is selected. [Unreal actor replication](https://dev.epicgames.com/documentation/en-us/unreal-engine/actors-in-unreal-engine) and [Unity multi-world bootstrap](https://docs.unity.cn/Packages/com.unity.entities%401.0/manual/systems-icustombootstrap.html) illustrate different costs, not current requirements. |
| Authored scene vs runtime state | The package already chooses a defensible hybrid: typed editable scenes/overrides and cook DAG feed runtime W1/specialized products. This is not a missing decision. Unity's [baking overview](https://docs.unity.cn/Packages/com.unity.entities%401.0/manual/baking-overview.html) establishes the performance/authoring tradeoff; Godot's [scene instancing](https://docs.godotengine.org/en/latest/getting_started/step_by_step/nodes_and_scenes.html) is the direct-runtime alternative. | Exact format, editor preview and apply-back semantics remain important. A separate delivery audit owns the edit/play session finding; its resolution must preserve world-scoped IDs, epochs, provider instances and scheduler state. |
| One authoritative world | Correct **per game session/view set**, but not yet a decision that the host process is globally single-world. The delivery audit owns edit/play preview semantics. [Unreal PIE](https://dev.epicgames.com/documentation/unreal-engine/play-in-editor-multiplayer-options-in-unreal-engine?lang=en-US) and [Unity multiple Worlds](https://docs.unity.cn/Packages/com.unity.entities%401.0/manual/systems-icustombootstrap.html) show useful isolated concurrent instances. | F1/W1/F2/P7/T1 should scope handles, clocks, schemas/provider instances and diagnostics by world/session rather than accidental globals. This does not add multiplayer. |
| Baseline graphics technique | The clustered-forward argument derives a plausible portable starting point from light overlap and bandwidth, with explicit deferred/tile challenger. Technique qualification remains D2/I3. | Do not confuse the baseline technique's reasoned recommendation with proof of visual quality/performance on named devices. |

## Review scope and stop condition

Inspected `ARCHITECTURE-BRIEF`, `SYSTEM-DESIGN`, `COMPOSITION`, C01–C12, `CONSTRUCTION-PLAN`, `MATURITY`, the platform/world/play/render/tools module notes, `COMPOSITION-REVIEW`, and the relevant primary-source ledgers. Compared the selected/candidate boundaries against the official Bevy, Unity, Unreal, Godot and O3DE pages linked above, at the stated page/section scope. Did not inspect engine source beyond the cited Bevy ECS crate README/API or run a target implementation. No finding depends on a speculative need for pure 2D, MMO, runtime LLM, arbitrary native hot-loaded plugins or a visible sky. This report stops at decisions that can materially change D1/D2 interfaces; it makes no blanket claim that the remaining architecture is optimal or implementation-ready.
