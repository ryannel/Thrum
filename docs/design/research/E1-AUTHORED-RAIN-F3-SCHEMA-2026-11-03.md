# Proposed E1 authored-rain F3 schema and closure proof

3 November 2026. **Frozen proposal and isolated executable proof, awaiting C09/F3/F4 owner adoption.** No production parser, canonical contract, Build Plan or maturity entry was changed. Today's SDK still refuses authored schema 2 and these new companions. This does not establish accepted source, an F4 product, forcing/deposition, a game runtime or renderer readiness.

This refines the [selected bounded source](../modules/ENVIRONMENT.md#selected-bounded-authored-source-and-light-handoff), [next F3 extension](../FOUNDATION-SPEC.md#first-engine-owned-environment-records--selected-next-f3-extension), [C08](../CONTRACTS.md#c08-light-materials-and-transport--v3-with-e1-and-v4), [C09](../CONTRACTS.md#c09-environmental-fields-and-physical-exchange--e1-with-p3), and the [paper fixture](ENVIRONMENT-IMPLEMENTOR-DOGFOOD-2026-11-02.md#proposed-f3-source-records). The [build queue](../../BUILD-PLAN.md#parallel-render-and-environment-module-preparation) keeps source admission, products and consumer proofs distinct.

**The storm cannot satisfy R0's complete required Sun + ambient + background closure as written.** It provides raw Sun facts, but no ambient-irradiance or background-radiance field. It is not a `ConstantLightProductV1` input and does not define a complete render closure; optical air, terminal sky and prepared render-product bindings are absent. No black background, ambient fill, sky, fog or schema-1 snapshot is fabricated. An R0 consumer needing those quantities must refuse this binding until an explicitly adopted separate-provider/profile composition supplies them without overlapping authority. A headless rain proof does not require a visible background.

## Five decisions requiring adoption before production dispatch

1. **Keep the versions distinct.** Authored schema 1 remains `constant-light-v1`, with its existing `1e-9` source normalization tolerance and unchanged meaning hash/parser. Proposed schema 2 admits only `authored-vertical-rain-v1` and preserves the dogfood's `1e-6` tolerance for initial direction, axis and colour. This proposal pins schema-2 source length to `sqrt(((x*x)+(y*y))+(z*z))` and colour luminance to `((0.2126*r)+(0.7152*g))+(0.0722*b)` in ordered binary64 without contraction. Cooked normalization is a separate F4 gate. C09/F3/F4 must adopt this deliberate difference; sharing schema 1's private tolerance constant would silently change schema 2.
2. **Pin the phase anchor and validity.** The first profile requires a 60 Hz F1 world clock; [C02](../CONTRACTS.md) allows other configured clocks, so F2 must explicitly refuse every non-60-Hz binding rather than silently rescale rates or continue dividing by 60. It uses initial phase at tick 0 and `valid_ticks=[0,N]`, `1<=N<=216000`. Inclusive endpoint validity admits an interval only if both endpoints fit. A rate starts at 0; later starts are strictly increasing and less than N. Initial phase offsets may be negative and finite; all reached weather phases need explicit track coverage. This excludes an ambiguous nonzero validity-start/phase-anchor interpretation. A different F1 clock needs an explicitly compatible profile binding, not a second private clock.
3. **Pin absence and capability semantics.** `air` is optional but never null. With air present, `unsupported` is exactly the six dogfood tokens; without it, add exactly `air`. All are unique and order independent. Positive capabilities are Sun, wind, cloud optical depth, precipitation and air iff present. Neither missing ambient/background nor absent air becomes zero. The limitation vocabulary is profile specific: schema 1's `thermal` and schema 2's `thermal_irradiance` must not be compared as an unversioned global feature set. C09/F2/F3 must adopt the typed capability mapping and absent-air spelling.
4. **Keep the first pond/resource envelope narrow.** Receiver types are fixture-only. Admit at most one referenced fixed-footprint pond, with exactly a 4×4 closed reflective grid; require a fully wet admitted stage interval below its wall crest. If a recipe references it, every authored solid-flux knot is zero, even if a nonzero knot would be unreachable or multiplied by zero. Count its 16 product-local receiving cells toward the 1024-element limit. These are conservative first-fixture restrictions, not a general water or snow model. C09/W2/water/F3/F4 must adopt them and the listed resource caps.
5. **Do not invent the missing fog or datum grammar.** The paper mentions optional fog and a scene datum record, but supplies neither a complete source schema nor a typed reference for them. This first grammar has no `fog` field and always declares `optical_air`/`terminal_sky` unsupported. Its coordinates are literal C01 world metres with absolute world Y, not height above terrain or a geospatial datum. No new scene key or phantom record is introduced. Adding such content later requires an explicitly versioned/provider contract before admission.

These are proposed source decisions, not discretionary production defaults. The proof demonstrates that one coherent choice is implementable; it does not authorize selecting it in the SDK.

## Exact source grammar

Every new record has exactly `{id,type,schema,fields}` plus optional top-level `documentation` text. `id` and every known UUID field use the existing lowercase RFC-4122-form policy: 36 characters, displayed hyphen layout, version nibble 1–8 and variant 10xx. Labels and documentation are at most 4096 decoded UTF-8 bytes and cannot be null. Human labels never resolve references. JSON numbers in quantity fields decode to finite f64; ticks, dimensions, numerators, denominators and schema tags are integers, not fractional-number or string coercions. Signed zero is accepted in source. The prototype's source predicates use ordered binary64 except exact rational phase coverage.

A record is at most 16 MiB, 1,000,000 value nodes including containers, and 64 container levels including the envelope. Object keys are not value nodes. Reject duplicate decoded keys, invalid Unicode, nonfinite numbers, unknown types/versions/profiles and unknown known-object fields. In particular, `"a"` and `"\u0061"` are the same key. Arrays have limits checked before deserializing/retaining an extra typed element; the bounded syntax pass may already have scanned that value.

The Sun object has exactly `light_ref`, `initial_toward_source_unit:f64[3]`, `rotation_axis_unit:f64[3]`, `period_phase_seconds:positive f64`, `peak_perpendicular_illuminance_lux:nonnegative f64`, `intensity_envelope="positive-world-y-squared"`, `unit_luminance_linear_rec709:nonnegative f64[3]`, `angular_radius_rad:nonnegative f64`, `direction_model="geometric-straight"`, and `applied_attenuation=[]`. `light_ref` requires a schema-1 light identity. Initial direction and axis are nonzero within the schema-2 length tolerance; colour satisfies the listed Y tolerance. Illuminance is raw perpendicular photometric lux, not cloud-attenuated light or thermal W/m². No competing direction/intensity exists in the identity record. The source says how to evaluate the Sun under day phase; F3 does not run that evaluator.

The wind object has exactly `reference_height_m:f64`, `vertical_multiplier:array[2..8]` of `[world_y_m,nonnegative multiplier]`, and `weather_phase_vector_knots_mps:array[2..256]` of `[phase_seconds,f64[3]]`. Heights are strictly increasing within 0..1000 m and within world height support; reference height lies in this domain. Velocity Y is exactly zero numerically. Interpolate vectors and height multipliers linearly, not wrapped bearings. Wind height means **absolute world Y**. A request below the wind-height domain is outside that quantity's support, even if it is inside another quantity's source box.

The cloud object has exactly `plane_height_m:f64`, `map_origin_xz_m:f64[2]`, `spacing_xz_m:positive f64[2]`, `periodic_node_dimensions:u32[2]` with each dimension 1..64, `vertical_tau_nodes_x_fastest:array[0..4096]` with exactly Nx×Nz values in [0,8], `advection_wind_height_m:f64` within wind support, and `low_sun_policy="authored-fade-to-clear-0.2-to-0.1"`. The plane lies within world height support. Grid node (0,0) is at the map origin; the periodic extent is Nx×dx by Nz×dz, with positive finite periods. It stores vertical optical depth, not already evaluated transmittance or density. Its receiver domain additionally requires Y below the plane. The periodic tile does not widen world query support. Advection integrates the declared wind in **world time**, including when a held nonzero wind is selected by frozen weather phase. The selected low-Sun authored clear/fade policy remains tagged, not atmospheric truth.

The precipitation object has exactly `origin_xz_m:f64[2]`, `cell_size_xz_m:positive f64[2]`, `dimensions:u32[2]` with each 1..128, `cell_multiplier_x_fastest:array[0..16384]` of nonnegative values with exactly Nx×Nz elements, two tracks named `weather_phase_liquid_flux_knots_kg_m2_s` and `weather_phase_solid_flux_knots_kg_m2_s`, `exposure_ref`, and `input_reservoir_ref`. Each flux track contains 2..256 `[phase_seconds,nonnegative f64]` pairs. The finite rain rectangle lies within world X/Z support. Each cell's multiplier scales a **cell-mean horizontal** water-equivalent flux in kg/(m²·world s). Its footprint is static and does not advect with the cloud tile. Outside the rain rectangle is `OutsideSupport`, not implicit zero precipitation.

Across wind, liquid and solid **temporal** tracks there are at most 256 knots; wind-height knots and rate segments have their own separate limits. All temporal coordinates are finite and strictly increasing. Require first track coordinate <= the initial weather phase and last >= the maximum reached weather phase. No single-knot hold or out-of-track clamp is introduced; a constant track uses two equal values at distinct covered phase coordinates.

The optional air object has exactly `temperature_k` in [273.15,313.15], positive `local_absolute_pressure_pa`, `vapour_gas_mass_fraction` in [0,1), and `saturation_law="nws-liquid-magnus-bounded-v1"`. These are constant independent gas facts, not a hydrostatic atmosphere. q excludes condensed phases. Relative humidity/dew point are diagnostics, not extra source fields. The bounded liquid saturation fit, RH admissibility and `NoFiniteDewPoint` at q=0 remain F4/F2 preparation/query gates. Warm gas and separately authored solid flux are not claimed physically consistent.

Opaque fields are allowed only directly under `fields`, with literal ASCII prefix `x.thrum.environment.` and a decoded key <=4096 UTF-8 bytes. Permit at most 16 keys; each untouched raw JSON value <=16 KiB; total raw value bytes <=256 KiB; at most **4096 value nodes across all opaque values**; each value's container depth <=16; any decoded string/key <=4096 UTF-8 bytes. Preserve exact internal raw value bytes, including number spelling and escapes. Enclosing object order/whitespace may change. Nested duplicate keys refuse. These values have no runtime control, reference, quantity or required-resource meaning. Known-object extension keys and non-prefixed unknown fields refuse.

### Exact phase coverage without rounding a gap closed

For an interval of Δticks under rate num/den, accumulate integer weight `Δticks*num*(64/den)`. Over the whole validity, `phase_end = initial_seconds + weight/3840`. With the admitted limits, weight <=3,317,760,000. The comparison treats each decoded finite f64 as its exact binary rational and checks the rational sum against decoded track endpoints; it does not repeatedly add tick durations or round the sum down before checking coverage.

The native proof scales finite binary64 values by `3840*2^1074` and uses a signed fixed 2176-bit stack representation. The largest operand needs at most 2110 bits. Python independently uses `Fraction`. Their 856 comparisons include adjacent representable values, negative offsets, subnormals and ±f64 maximum. For example, initial=f64::MAX plus a positive phase advance is not covered by a track ending at the same f64 maximum, even though naive f64 addition rounds that advance away. This is a specialized source predicate, not a new runtime time authority or a mandated public bigint API.

## Executable proof, cost and limits

The retained Rust program uses bounded syntax traversal and fixed typed Serde decoding, not a generic JSON Value tree. It separately checks source predicates and global closure. Its large source is boxed rather than inflating every record enum slot from 264 to 832 bytes. It avoids temporary temporal-coordinate vectors during coverage checks. The experiment uses a whole-record syntax pass, borrowed header pass and typed pass; production should reuse the existing bounded header to avoid this extra walk. The Python oracle deliberately uses a separate bounded lexical guard, duplicate-aware standard JSON decoder, shape/meaning checks and exact Fraction arithmetic. It is a reference oracle, not a production representation proposal.

Results: **3 native debug + 3 release unit tests passed; 104 adversarial cases agreed (15 positive variants, 89 refusals); 856 phase comparisons agreed.** The adversarial matrix covers duplicate/escaped aliases, wrong type/version/profile, global and embedded UUID conflicts, valid-target nonreciprocal cycles, unknown/absent/null fields, phase/rate/track failures, grid/receiver/pond limits, opaque raw bytes/count/aggregate nodes/depth/UTF-8 limits and global byte/node/depth refusals with malformed tails. It includes actual 65536/65537-edge graphs. A typed opaque-neighbor test retains exact value spelling; it is not a production editor or staged-root preservation test. Independent audit found two oracle categories not covered by the original matrix: integer-token finiteness/typed f64 normalization, including a shifted-X case at 2^53, and optional-label allowances on project/history records. The reference now rejects nonfinite integer tokens, decodes known quantity operands to f64 before comparison, keeps integer fields strict, and uses type-specific label sets. Added negative huge-integer/project/history vectors and a positive large-integer quantity-spelling counterexample agree with the unchanged native parser. No disagreement remains in the expanded matrix. During bring-up the Python oracle incorrectly passed a float tick endpoint to Fraction; retaining integer ticks fixed the oracle exception without weakening expected acceptance. The unchanged production schema-1 parser's 11 `environment_json` tests also passed.

## Implementor ownership and sequence

After owner adoption, use bounded sequential changes with these file boundaries:

1. **Immutable meanings first.** Pin the adopted new definition bytes in a private SDK rain/fixture table. Leave schema 1's bytes, parser, hash and constant-light F4 path unchanged. Suggested new private files: `crates/thrum-source/src/authored_rain_json.rs` and `environment_fixture_json.rs`; expose neither a general numeric game schema language nor speculative public runtime APIs. `lib.rs` adds private modules only. Do not add a crate or change production dependency features merely because the prototype uses derives.
2. **Typed source parser next.** Implement all strict objects/limits and exact phase/support predicates, reusing existing bounded UUID/text/header helpers where appropriate. Add the positive fixture and independent/adversarial vectors. Unknown rain versions/profiles must refuse before fallback. Prove exact opaque retention and a real neighboring edit separately.
3. **Complete F3 closure.** Extend `registry_stage.rs` fixed dispatch by checked type/version; add declared embedded-ID summaries, required typed edges, reciprocal predicates, fixture caps and manifest identities. Preserve existing game descriptors, schema-1 scenes, schema-2 type-level environment binding and unselected-content behavior. Exercise real staged candidates with mixed game/engine records, every collision class, edge caps and rejection preserving prior stage. Existing `project_v2_json.rs` membership grammar need not widen.
4. **Immutable source handoff separately.** Reuse the source-store/lease owner; do not build a second store or read mutable checkout bytes during cook. Rain must pass the actual provisional/admitted path with exact source revision, retry/reopen/corruption and old-reader behavior before claiming that interaction. 5. **F4 and consumers after that.** Adopt source/grid and shared fixture geometry products, then exposure; pin all definition/cooker/evaluator/dependency identities. Do not introduce an exposure→source-product hash dependency cycle. F2 validates retained P3/water/surface/vegetation/audio/V3 consumers and substitutions.
