## Derived selection and alternatives

The default is a typed command/query core shared by UI, CLI and local API, backed by F3/W1/P7/F4 rather than a universal editor object database. A custom large visual scripting graph is **not** required for the confirmed AI-oriented development goal; Decima's presentation shows it served its production needs, but here it would add runtime semantics, migrations and debugging cost before a game demonstrates need. A direct mutable remote ECS API is also insufficient because stable authored IDs, cook latency, undo and multi-record activation require transactional rules. The initial F2 recommendation compared a finite provider constraint resolver with scattered feature booleans. The 1 November [decision audit](../ARCHITECTURE-AUDIT.md) found that comparison too weak; the subsequent [scenario walkthroughs](../SCENARIO-WALKTHROUGHS.md) support explicit static game setup with dependency validation and finite named target tiers as the simpler baseline. General provider search is no longer recommended by default. This is our scenario-derived choice, not a claim that the sources prescribe it. Full arbitrary live toggling remains outside the baseline; build, load and specifically supported live changes have different costs and state effects.

Remaining empirical qualification concerns dependency validation cost at the selected project size, cook invalidation fan-out on representative content, UI responsiveness with live game preview, clean-build hash agreement, trace overhead, native SDK packaging and named-device performance. These tests check stated mechanisms and bounds; they do not choose missing schema or transaction rules by experimentation.
