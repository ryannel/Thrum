# Play systems — source inspection and decision evidence

31 October 2026. Primary vendor/project documentation and project source inspected for the [play design](../modules/PLAY-SYSTEMS.md). These sources support library capabilities and limits; the engine coupling, equations, update order and fallback policy are our synthesis. No library, language binding, target device or binary revision is selected or qualified. Links to moving `main` documentation must be pinned to a revision before code adoption. This is a design review, not evidence of a built system.

## Decision ledger

| Decision | Status and reasoning | What could change it |
| --- | --- | --- |
| P3 uses one host-owned physics adapter boundary around a mature solver, with separate query epoch and body-mode contract | **Recommended.** Collision/constraint solvers are large validated numerical systems; building one anew adds risk without serving the engine's distinctive composition goal. Jolt and Rapier remain competing candidates. | A specified target, license/binding audit or representative coupling workload demonstrates a material incompatibility. Numeric performance is qualification, not architecture discovery. |
| Character default is a query-resolved kinematic capsule with explicit dynamic-body interaction policy; fully dynamic locomotion is a distinct profile | **Provisional.** It gives stable authored control and root-motion reconciliation for top-down and third-person games. It is not energy conserving and can require deliberate push impulses. A dynamic option fits simulation-led games and ragdolls. | Game requirements demand continuous force-driven player control, or moving-platform/contact behavior cannot meet defined error tolerance. |
| Ground navigation cooks agent-class tiled walkability and commits versioned tiles with W2; Detour is a candidate provider | **Recommended.** Cooked tiles bound startup and incremental changes. Local avoidance is velocity guidance, never a second transform authority. | A supported game needs flight/swim/voxel traversal as its primary topology; add a different provider under the same intent contract, not pretend a navmesh solves it. |
| Animation samples/blends clips and extracts root displacement before physics; P4 owns graph and skeletal pose; ozz is a kernel candidate | **Recommended.** Offline extraction removes locomotion from the skeleton so applying the solved root once is tractable. | An animation provider proves equivalent root accounting, historical pose reconstruction and platform fit with lower integration cost. |
| P6 uses typed, bounded action/state operations and game-owned rule packages | **Recommended.** Keeps scripting inspectable and replayable, while combat, quests and economy remain selected game policy. | A concrete game requires a richer VM; it must still preserve tick-order, quotas, typed operations and durable state. |

## Specific unmeasured qualifications

Pin library revisions and licenses; verify custom-host native/Wasm/mobile builds, alignment and ownership across FFI if used. Measure P3 query and solver time with moving platforms, contact churn, stacked props and ragdoll; P4 clip/IK/skin cost and pose-history retention for skipped views; P5 tile build, border validity, obstacle latency and path queue tails. Measure integrated p95/p99 and sustained mobile power with the exact cross-boundary scene. A successful isolated demo does not certify the combined schedule.
