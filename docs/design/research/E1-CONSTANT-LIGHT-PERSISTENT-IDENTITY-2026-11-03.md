# E1 constant-light persistent identity and publication — candidate

3 November 2026. This is an implementor-facing proposal refining the [selected E1 product/binding](../modules/ENVIRONMENT.md#selected-first-f4-constant-light-product-and-binding) and [C05 source/product boundary](../CONTRACTS.md#c05-assets-streaming-and-retirement--f4-with-w2-v1-and-p7). The pure 160-byte codec and four-record accepted-pin cook exist. This note does not implement a cache, authorize a ready build or promote source/runtime/device maturity. Its byte grammar, cook class and publication transaction need producer/consumer review before selection.

## Distinct identities and their owners

| Identity | Meaning | Owner and reuse |
| --- | --- | --- |
| `SourceRevision` | Exact complete accepted source tree, including selected labels/opaque fields and unrelated files. | F3 accepted store; never inferred from a checkout or product. |
| `CookKey` | Selected E1 known meaning under one product recipe and execution class. | F4, derived from four verified selected records and F3 built-in meanings; stable across formatting, label, opaque, path and unrelated-file edits. |
| `BlobHash` | SHA-256 of the exact 160 product bytes. | F4 codec; checked on every load. |
| `ProductRevision` | SHA-256 of a canonical manifest binding `CookKey` to `BlobHash`. | F4 product store; content identity, not source authority. |
| `BindingRevision` | SHA-256 of a canonical exact-source binding to `ProductRevision`. | F4 build assembly; a component of a wider `BuildRevision`, never a runnable build by itself. |

Every operation uses one selected `PinnedSource` from the intended project store. Keep its owner binding and pin alive through all selected reads, expected payload calculation, cache verification and binding installation. A returned `PinnedConstantLight` contains provenance but owns **no** pin. The caller must not take its root alone as a durable lease or use a new current root to complete an old cook. Open an operation-scoped publication lease tied to the source pin; once the three content names are calculated, register them with the product store **before** any cache lookup or write. Registration and collection synchronize under one store authority, so the prospective blob, product manifest and binding remain protected even while absent. The lease spans install, reopen, return and wider-build assembly; a ready-build transaction atomically acquires durable closure ownership before releasing it. An unready abandoned publication can be cleaned only after its lease is released. A stale asynchronous result is allowed to become an immutable product, but never a ready selection for an obsolete request.

## Canonical semantic recipe

Hash the exact following binary stream with SHA-256. Multi-byte integers are little-endian. There are no implicit Rust struct bytes, JSON serialization, native strings or map iteration order:

1. ASCII domain bytes `thrum.e1.constant-light.cook-key.v1\0`.
2. `u16` recipe version `1`, `u16` product format `1`, `u16` cooker revision `1`, `u16` normalizer revision `1`, `u16` evaluator revision `1`.
3. `u8` fixed driver code `1` for `incoming-environment-sun`; `u32` unsupported mask exactly `0x7f`.
4. Environment UUID then light UUID, each 16 octets in canonical displayed-hex order without hyphens. Both are checked by F3 and again by the codec.
5. Environment built-in definition hash then light built-in definition hash, each 32 octets, from the **same F3 descriptor lookup** used in admission. F4 must not maintain copied hash constants. For the current F3 descriptor sources, these are `8f3d060dcd716a40ebfeddcdae58cc7285d281b6bba24fa9a38ebf2000ab5cfb` and `9376fbe1d51794e5cae447c41ae0d02a71cd3f652830c9b650375144ac97b166`, respectively; the implementation checks the lookup, not these explanatory hex strings.
6. A 32-octet `CookClass` digest bound to the actual cooker execution/target class. Its descriptor grammar and trusted source are **not yet selected**; an arbitrary caller string or a guessed host target is insufficient for durable cross-process reuse. A local ephemeral class may exercise the encoder but may not publish a reusable product.
7. Fourteen raw decoded binary64 values in this order: toward-source direction XYZ, unit-luminance colour RGB, perpendicular illuminance, angular radius, ambient RGB, background RGB. Encode each as little-endian IEEE-754 bits after replacing either zero sign with positive zero. All other finite bits, including subnormals, remain unchanged. The source parser's tolerance and domain checks precede this encoding; the key does not hash normalized output instead of authored known values.

The current recipe stream is 10 fixed integer bytes plus one driver byte, four mask bytes, 32 UUID bytes, 64 definition-hash bytes, 32 class bytes and 112 numeric bytes, after the domain. The length is fixed for version 1. A future extra field, descriptor, normalization rule or codegen class changes the recipe version/class and invalidates reuse. Scene ID and scene definition hash are absent here: rebinding the same environment/light known meaning may reuse the product, while the exact build binding changes.

`CookClass` must distinguish compiler/toolchain binary closure, target triple/features, floating-point codegen settings and the cooker/normalizer/evaluator implementation. T2's trusted builder should supply a canonical class descriptor digest from its verified build closure. Until that exists, correctness does not depend on the class being a complete attestation because cache lookup must recook the expected 160 bytes from the verified pin before accepting the cached association. The class still needs a concrete versioned grammar before a durable key is exposed; no permanent cache API should accept an opaque unreviewed class digest.

## Fixed manifests

The product manifest is exactly **80 bytes**:

| Offset | Bytes | Field |
| ---: | ---: | --- |
| 0 | 8 | ASCII `THRE1PM` then zero |
| 8 | 2 | Manifest version `1`, little-endian |
| 10 | 2 | Product format `1`, little-endian |
| 12 | 4 | Product byte length `160`, little-endian |
| 16 | 32 | `CookKey` |
| 48 | 32 | `BlobHash` |

`ProductRevision = SHA-256("thrum.e1.constant-light.product-revision.v1\0" || manifest[0..80])`. An authoring-time cache association check requires exact manifest length/header/version/format, the requested `CookKey`, exactly 160 payload bytes, `BlobHash` match and strict `ConstantLightProductV1::from_bytes`. It also **recooks the expected payload from the verified raw input** and compares all 160 bytes and the resulting canonical manifest. Checking only a self-consistent cache manifest plus blob would accept a replacement of both with a different but valid light. For this tiny product, recook is constant work; the cache primarily avoids rewriting and allows immutable sharing, not numeric normalization cost. Runtime loading from a trusted, pinned ready build instead verifies its bound manifest/bytes/lease chain; it does not reopen F3 source or recook.

The exact-source binding is exactly **204 bytes**:

| Offset | Bytes | Field |
| ---: | ---: | --- |
| 0 | 8 | ASCII `THRE1BD` then zero |
| 8 | 2 | Binding version `1`, little-endian |
| 10 | 2 | Reserved flags `0` |
| 12 | 32 | Accepted `SourceRevision` |
| 44 | 16 each | Project, entry scene, environment, light UUIDs, in that order |
| 108 | 32 | Entry-scene F3 built-in definition hash |
| 140 | 32 | Canonical semantic profile/target lock digest; its descriptor and provider/target closure must be selected before publication |
| 172 | 32 | `ProductRevision` |

`BindingRevision = SHA-256("thrum.e1.constant-light.binding-revision.v1\0" || binding[0..204])`. The current scene@2 definition hash from the F3 descriptor lookup is `75c09153b459c576f89ad3328dc6e3bac82379368cd7e3ac9317f058a2ea8aa7` for review only. A future scene@3 binding uses its actual F3 descriptor and changes this exact-source binding even if the E1 payload is byte-identical. The binding's `SourceRevision` covers exact selected paths, file bytes and every other admitted file; do not duplicate file hashes inside `CookKey` or mistake the product manifest for source authority. A wider build manifest must still bind required render, code, toolchain, delivery and other products before readiness.

An authoring-time binding load accepts an **expected context**, not a digest alone: intended project-store owner and pinned accepted root; selected project/scene/environment/light UUIDs; F3 scene definition; and the build's trusted profile/target lock. It checks exact 204-byte length, magic, version, zero flags and all expected fields, recomputes `BindingRevision` and verifies that the filename equals it. It then reopens the named product manifest and 160-byte blob, checks their filename/revision/hash chain and compares the association with the freshly recooked expectation from the same verified pin. A runtime consumer instead follows a pinned ready-build manifest's already trusted binding and verifies its immutable transitive byte/hash chain; it neither consults current source nor recooks. A missing binding, missing referenced product or missing blob is an incomplete product closure, distinct from a present corrupt object and from source decode failure.

## Publication and failure order

1. Pin the requested accepted root from the intended project store and open an operation-scoped publication lease tied to it. Verify four complete copies and F3 typed closure, then calculate the canonical semantic recipe, expected payload, `BlobHash`, manifest and exact-source binding under that same source pin. Register all three calculated names with the store's collector authority before lookup or installation. Refuse unsupported profile/target or missing trusted class/lock **before** installing a durable binding.
2. If a cache entry exists, reopen and verify its byte names and bytes, then compare it with the freshly recomputed expected payload and canonical manifest. A missing entry is a cache miss. A present entry with invalid bytes is `CorruptProduct` and refuses this attempt; immutable-name collision is never repaired by overwrite or silently treated as a miss. The previous ready result remains held.
3. Install immutable content-addressed `blobs/<BlobHash>`, `products/<ProductRevision>` and `bindings/<BindingRevision>` using owned temporary files, exact write/sync, atomic no-replace installation, parent-directory sync and reopen verification. Existing names must match exactly; a collision or partial old file refuses. Install the binding **last**. Publication-lease names protect newly installed entries even before a binding is present. Crash-left temporary or unreferenced immutable entries are collectable only after recovery proves no live publication/ready/reader lease owns them.
4. Return the immutable binding with the publication lease, not as a bare digest. The wider ready-build publisher enters one conditional transaction that checks the intended project store owner, accepted source generation, request epoch, cancellation state, expected prior selector and all required product/tool closures **at the commit point**. It atomically acquires durable source/product closure ownership and commits the new ready selector before releasing the publication lease. A competing source advance, newer request, cancellation or selector change refuses this commit; an old asynchronous completion cannot win after a new request. Before the transaction commits, recovery preserves the prior selector. After commit, recovery selects the new complete build even if the success response was lost; resolve uncertainty by durable operation identity. Reader leases retain an old build independently through either outcome. Test every named cut point and concurrent collector boundary, not just ordinary error returns.

Use direct lookup by freshly computed expected `ProductRevision`; this first slice has **no mutable `CookKey` index**. Two concurrent writers of the same expected object either find the same exact bytes or one wins a no-replace install and the other reopens/verifies the winner. A different valid product can share a blob only through its matching `BlobHash`; each product manifest is checked independently. A stale or cancelled worker may finish an immutable product under its live publication lease, but it may not install an exact-source binding after its request has been invalidated. Treat source copy/decode/product refusal, unsupported class/profile, missing cache object, present corrupt object, and native I/O/space failure as separate stages; a selected source error precedes cache inspection because expected semantics are computed first. A present corrupt immutable name refuses rather than being silently overwritten or recast as a miss. Short writes, `ENOSPC` and permission errors leave old selection intact and retryable work distinct from invalid authored source.

The first native store implementation must choose a concrete **private root and file envelope** before claiming this publication algorithm. Candidate: same-volume task-owned native directories, fixed lowercase hexadecimal SHA-256 filenames, regular files only, no symlink traversal, one store-owner lock, temporary files created in the destination directory, and `hard_link(temp, absent_destination)` as the atomic no-replace operation followed by temp unlink and directory sync. The hard-link operation requires a verified same-filesystem regular temp and is distinct from Rust `rename`, which can replace a destination. Reopen by checked directory handle/name and reject symlinks, nonregular files, changed inode/length or mismatching bytes. Directory creation and ownership, cross-process locking, retained reader handles and T2 per-volume space accounting still need an owning native-store design. In an initial **no-collector** proof profile, product files are never deleted while a store is open; even that profile needs explicit cleanup/recovery of its own temporary names and measured disk growth. A collecting profile needs the publication/ready/reader lease registry above. Neither profile may promise power-loss durability from process-kill tests alone; sync failures produce uncertain installation resolved by reopening exact names under the store owner. Power-loss qualification is a separate gate.

The logical payload/manifest/binding total is **444 bytes**, excluding names, filesystem metadata, index entries, temporary copies and old/new overlap. Hashing and normalization are constant count after four bounded verified source copies; storage sync and pin acquisition likely dominate. Measure complete cook/cache-hit/rebind paths and peak residency with A/B overlap on the named host before selecting a latency or memory claim. No arbitrary reserve or source-count limit follows from the 444-byte accounting.

## Proof matrix before selection

- Independent byte and SHA goldens for the canonical recipe, key, manifest, binding and all three digest domains. Strict manifest/binding decoders refuse bad magic/version/length, and the binding decoder also refuses nonzero flags. Expected-context and transitive-association checks reject swapped same-width digest or UUID fields; a context-free decoder cannot infer their intended order. Existing payload-codec tests own numeric zero and UUID byte-domain refusals; a hash is not a round-trippable recipe.
- A/B accepted pins while the checkout and current root advance; formatting, label, opaque and unrelated edits preserve `CookKey`/payload but change exact binding; value, UUID, definition, recipe and execution-class changes invalidate the key.
- A valid but **wrong self-consistent blob and product manifest** under the requested key must fail the pure expected-association check against recooked bytes. Direct store lookup by expected `ProductRevision` may refuse this mutation earlier at filename/revision verification; test both stages without requiring one error order when the earlier check already fails. Corrupt, truncated, missing and cross-wired blob/manifest/binding refuse; prior ready result stays readable.
- Process kill at each owned temporary write, each sync/install/reopen and either side of ready-selector commit; recover old before commit and new complete selection after it, including lost-response lookup by operation identity. Concurrent collection at install/reopen/lease transfer never deletes protected source or product bytes; retained readers keep old products.
- Advance the accepted root, cancel the request and start a newer request in barriers between preparation and conditional publication; each stale attempt must refuse atomically and preserve the current selected build.
- Race identical writers and preexisting matching/corrupt names; share a blob between distinct valid product manifests; inject short writes, full/permission faults and disappearance attempts at every object. Check the no-collector proof envelope or collecting lease envelope selected for that implementation.
- Measured full selected-source read/decode, recook/cache-hit, rebind, old/new peak and T2 concurrent work. No device or visual qualification follows from these CPU tests.

The read-only F3 built-in definition lookup is now implemented. Next implement a **pure, nonpublishing identity layer** with typed digest wrappers and canonical recipe/manifest/binding encoders plus strict decoders and independent goldens. Its test-only class and lock digests prove byte grammar only; they never authorize a durable cache or ready build. A durable content-addressed store must wait for a selected native root/no-GC or collector envelope, typed `CookClass` and profile/target-lock descriptors, and a lease-bearing API that takes/retains the same pin rather than publishing a detached `PinnedConstantLight`. The wider ready-build selector/transaction belongs to F4/T2's complete build design, not this 444-byte E1 object. Keep this candidate separate from the current headless `SceneProductRevision` grammar and its test-only candidate output; neither establishes these E1 associations.
