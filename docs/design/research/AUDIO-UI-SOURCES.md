# Audio and UI source study

Inspected 31 October 2026 for [A1/U1](../modules/AUDIO-UI.md). These are primary specifications, platform documentation and upstream library documentation. Source statements below describe the cited implementation or API; the engine design is a deduction, not a claim that a library supplies the complete module. Current library/platform versions and device behavior remain to be pinned before implementation.

| Source and inspected section | Relevant evidence and limit |
| --- | --- |
| [miniaudio programming manual](https://miniaud.io/docs/manual/), §§1, 2.6, 4, 5, 6, 7, 15 | The low-level device callback and higher-level engine/node graph are separate; resource manager supports async decode and streaming, but its stream refill may post a job from the audio thread and the manual warns about strict lock-free use. Spatial sounds have listeners, inverse/linear/exponential attenuation and doppler; default selection is closest listener, which is **not** the policy selected for a multiview game. Native backends include WASAPI, Core Audio and AAudio/OpenSL ES; web support is documented through Emscripten and has distinct AudioWorklet build requirements. This documents candidate reach, not successful Rust-host, iOS/Android app-shell or browser integration. |
| [CPAL upstream README](https://github.com/RustAudio/cpal/blob/master/README.md), supported functionality/platforms/features | CPAL supplies low-level device streams, not an authored mixer. Its current table lists Windows WASAPI, macOS/iOS CoreAudio, Android AAudio and Web Audio for Wasm. The optional Wasm AudioWorklet path requires atomics, `SharedArrayBuffer` and cross-origin headers. Thus it cannot be the unrestricted browser baseline without deployment constraints. Upstream support table is not tested engine coverage. |
| [Kira upstream README](https://github.com/tesselode/kira), platform support | Useful higher-level game-audio model, but upstream says it is mainly tested on desktop and its Wasm path lacks streaming and file-loaded static sounds. A common cross-platform streaming baseline cannot rely on that claim alone. |
| [Web Audio `currentTime`](https://developer.mozilla.org/en-US/docs/Web/API/BaseAudioContext/currentTime), [buffer scheduling](https://developer.mozilla.org/en-US/docs/Web/API/AudioBufferSourceNode/start), [AudioWorklet](https://developer.mozilla.org/en-US/docs/Web/API/AudioWorklet), [autoplay](https://developer.mozilla.org/en-US/docs/Web/API/Web_Audio_API/Best_practices) | Audio context time is an independent clock and stops while suspended; scheduled buffer starts use that clock, and a source node starts once. Browser policy can require creation/resume inside a user gesture. AudioWorklet runs custom processing away from the main thread, but is not a blanket guarantee for a Wasm backend or deployment. Browser buffering/output latency must be qualified on actual browsers. |
| [Android low latency audio](https://developer.android.com/games/sdk/oboe/low-latency-audio), [audio focus](https://developer.android.com/media/optimize/audio-focus) | Android recommends callbacks with no allocation, I/O, mutex waits or heavy one-time work; buffer underruns are observable. Low latency mode/exclusive access are requests, not guaranteed outcomes. Audio focus/ducking varies by Android version. Oboe is an alternative native adapter, not evidence that a Rust/CPAL or miniaudio path automatically has equivalent latency. |
| [Apple interruptions](https://developer.apple.com/documentation/AVFAudio/handling-audio-interruptions), [route changes](https://developer.apple.com/documentation/AVFAudio/responding-to-audio-route-changes) | iOS interruption notifications indicate begin/end and whether resume is appropriate; route removal can require pausing for privacy. Route changes may alter stream format/buffer duration. The app shell must forward these events; mixer internals alone do not implement OS policy. |
| [HarfBuzz getting started](https://harfbuzz.github.io/getting-started.html), [buffer properties](https://harfbuzz.github.io/setting-buffer-properties.html), [clusters](https://harfbuzz.github.io/working-with-harfbuzz-clusters.html) | Shaping turns Unicode input into glyph IDs/positions under font, script, language and direction; clusters link output back to source. This is one stage of text layout, not bidi resolution, line breaking, editing, fallback selection, glyph rasterization or accessibility. |
| [Unicode UAX #29](https://www.unicode.org/reports/tr29/), [UAX #14](https://www.unicode.org/reports/tr14/), [UAX #9](https://www.unicode.org/reports/tr9/) | Current Unicode annexes specify grapheme/word segmentation, line-break opportunities and bidi ordering. Their current pages show Unicode 18 revisions in September 2026. Pin Unicode data version in cooked text tooling/tests; byte offsets and glyph indices do not substitute for grapheme cursor positions. |
| [WAI-ARIA keyboard interface](https://www.w3.org/WAI/ARIA/apg/practices/keyboard-interface/), [modal dialog pattern](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/) | Composite widgets require explicit keyboard/focus behavior; modal dialogs constrain and restore focus. These are browser accessibility authoring patterns, not a native-platform adapter. |
| [AccessKit overview](https://accesskit.dev/), [architecture](https://accesskit.dev/how-it-works/) | AccessKit exposes an accessibility tree for custom-rendered UIs and its current overview lists macOS, Unix and Windows adapters. The overview does **not** establish iOS, Android or web adapter coverage for this engine. Native mobile and browser bridges require separate audit/implementation. |
| [CSS safe-area environment variables](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/env) | Browser safe-area insets are supplied by the page layout environment. Engine U1 should receive them through the web shell, with native shells supplying equivalent viewport insets. |

## Evidence status and competing approaches

The selected **semantic** design uses P6 committed causes, A1 logical voices and an audio-device clock; U1 owns one semantic tree feeding visual layout and accessibility. It is design synthesis. Candidate implementation substrates remain provisional. Native miniaudio offers a mature sounding graph/resource vocabulary but requires C/Rust FFI and a callback audit. CPAL gives direct Rust output but requires owning more mix/stream machinery. Kira's published Wasm limits make it unsuitable as the sole baseline. Browser Web Audio's native graph avoids mandatory shared-memory deployment, though native/browser DSP parity then needs explicit qualification. None of these source pages proves end-to-end Mac/PC/iOS/Android/WebGPU browser support, latency, audio quality or accessibility compliance.
