# Creation-to-delivery architecture audit

1 November 2026. Independent comparison against selected major-engine creation workflows. This audits **decisions**, not implementation quality. The [pre-inspection checklist](../../evidence/handoffs/2026-11-01-engine-audit/delivery-independent.md) was written from the user brief and primary engine documentation before reading the engine-rebuild design. The governing design examined here was the working tree on 1 November; its pages were not runtime-tested. The findings below are proposed corrections for the coordinator and affected owners, not unilateral changes to C01–C12.

## Scope and method

The brief is a reusable custom 3D host for overhead/isometric/first/third-person games on Mac, Windows PC, browser demos and native iOS/Android stores. Selectable capabilities matter, including light and cloud attenuation without a visible sky. Bevy is a source of ideas rather than a required host or a mandate for universal plugins. AI is a development client, not a runtime LLM. Pure 2D and MMO scale are excluded; ordinary networking is undecided. An integrated GUI editor, scripting VM, hot binary reload, remote collaboration service and WebGL fallback are **options**, not inferred requirements.

I inspected [SYSTEM-DESIGN](../SYSTEM-DESIGN.md), [CONTRACTS](../CONTRACTS.md), [COMPOSITION](../COMPOSITION.md), the [brief](../ARCHITECTURE-BRIEF.md), [construction plan](../CONSTRUCTION-PACKAGES.md), [maturity](../MATURITY.md), the platform, world/content, rendering and tools/delivery module designs, and their relevant prior reviews/source ledgers. I compared creation, play, edit, cook, package and device diagnosis paths with official documentation for Unreal, Unity, Godot, O3DE, Bevy and PlayCanvas. These are **sampled documented mechanisms**; I did not survey every engine, run their editors, inspect their full source trees or measure their workflows or this proposed engine. Their different solutions expose questions; they do not select ours by popularity.

## Findings

### CD1 — The edit/play session authority is undefined

**Classification:** missing decision at a shared boundary; high consequence before D1/I2. **Prior claim/location:** [TOOLS-DELIVERY, ownership and T1](../modules/TOOLS-DELIVERY.md#observable-capabilities-and-ownership) says T1 does not fork a second world, and its [T1 operation model](../modules/TOOLS-DELIVERY.md#t1-one-operation-and-query-surface) publishes edits as durable desired source then active runtime revision through W1/W2/P7. The inspector promises preview using runtime providers. [C02](../CONTRACTS.md#c02-time-and-committed-state--f1-coordinator-w1-world) defines one authoritative running world and [C10](../CONTRACTS.md#c10-persistence-reproducibility-and-authored-operations--p7f3t1) defines recovery. None defines a developer **play session** against an editable scene: when it begins/stops, which mutations are temporary gameplay state, how a paused inspection relates to authored records, and how an intentional simulation result becomes an authoring edit.

**Concrete scenario:** a developer moves a rigid body in the scene, presses Play, collides with it, then stops. P3 has changed the body pose; P6 may spawn/despawn entities; P7 may checkpoint. If play used the same W1/P7 authority, stopping could leave the source scene or save overlay changed by gameplay, or an editor undo could act on a gameplay mutation. If play uses a separate world, its IDs, product leases, edits made during play, captures and apply-back path must be scoped. C02's immutable **read snapshots** protect rendering but do not by themselves isolate a simulation session or protect authoring from gameplay writes.

**Alternatives and prior art:** (a) create a separate play world from a pinned authored/content revision, discard its gameplay deltas on stop, and apply selected differences through ordinary T1 operations; (b) run in the editor world with an explicit reversible checkpoint/rollback and strict side-effect policy; (c) use a separate process/player with a synchronized edit channel. [Unreal's Play/Simulate documentation](https://dev.epicgames.com/documentation/unreal-engine/ineditor-testing-play-and-simulate-in-unreal-engine) describes a duplicated level and selective Keep Simulation Changes. [Unity's source-asset modification guide](https://docs.unity.com/en-us/engine/6000.5/manual/assets-and-media/modifying-source-assets-through-scripting) distinguishes temporary instance changes from permanent source-asset changes. These support the need for a boundary; they do not prove duplication is best for this host. A headless test runner plus external scene editor could satisfy the requirement without an integrated PIE UI.

**Resolution/owners:** before D1 fixes identity and operation APIs, choose the baseline developer play-session semantics, session ID/world epoch, source revision pin, save isolation, side-effect policy and stop/apply-back behavior. State whether "T1 does not fork a second world" means only that T1 has no competing *authoritative authored* world; it should not accidentally prohibit an isolated play instance. Trace editor edit → play → gameplay mutation → stop → optional selected apply-back → cook/commit/undo, including a crash and two views. Owners: T1, W1, P7, F1, F3/F4, with P3/P6 and T2 consumers.

### CD2 — The gameplay code edit loop has no chosen baseline

**Classification:** missing decision / weak justification, not a demand for hot reload or scripting. **Prior claim/location:** [COMPOSITION, removal table](../COMPOSITION.md#components-scenes-and-feature-removal) explicitly does not promise unloading/reloading native machine code and makes compiled plugins process-lifetime; [TOOLS-DELIVERY](../modules/TOOLS-DELIVERY.md) says a general scripting language is not required; [construction I1–I3](../CONSTRUCTION-PACKAGES.md#ordered-work-packages) builds the host, content and play path. These are sensible exclusions, but no baseline says how a game developer changes a rule or component system and gets back to play, how editor state survives code changes, or when a code/schema change requires a clean restart/migration rather than data-only live activation.

**Concrete scenario:** a game author changes a Rust `Combat` system's damage rule or component schema while the editor is open with a play session and an unsaved scene edit. Asset hot replacement and F2 live profile selection do not load changed executable code. If the build replaces the editor process, T1's desired journal, active scene, preview and diagnostics need a handoff/restart rule. If code is patched in place, schedule registrations, schema versions, system state and live worlds need migration/quiescence. Either path is workable, but the difference changes the F1/F2/F3/T1/T2 lifecycle contract and productive iteration cost.

**Alternatives and prior art:** (a) deliberately choose rebuild/restart of the play process with fast incremental compilation and restoration from pinned source/scene revision, while the editor/CLI remains available; (b) allow restricted code reload only at a stopped-world boundary; (c) add an interpreted or separately compiled gameplay layer for selected rules, with its own schema/version boundary. [Unity's code reload guide](https://docs.unity.com/en-us/engine/6000.5/manual/scripting/compilation-and-code-reload) documents code and scene lifecycle tradeoffs. [Unreal Live Coding](https://dev.epicgames.com/documentation/en-us/unreal-engine/using-live-coding-to-recompile-unreal-engine-applications-at-runtime) shows one hot patch path; [O3DE script-only projects](https://www.docs.o3de.org/docs/user-guide/build/script-only-projects/) show a different no-compile authoring tradeoff. None implies this engine needs their mechanism.

**Resolution/owners:** D0 should select the **minimum supported code iteration contract** using a representative game-rule edit, with expected restart/rebuild boundary and state/schema handling. D1 can detail it. Keep executable reload and scripting optional unless a measured iteration requirement justifies them. Distinguish code edits from T1 data edits, F4 asset recook and F2 live feature switches in user-visible status and T2 evidence. Owners: F1/F2/F3, P6, T1/T2 and game code packaging.

### CD3 — Shader and material variant closure is deferred across the wrong seam

**Classification:** missing cross-module decision; shader language, compiler and exact cache layout are legitimate D2 detail. **Prior claim/location:** [RENDERING, backend and material path](../modules/RENDERING.md#proposed-operating-model-and-decisions) leaves shader translation open while selecting semantic material/lighting contracts; its automation section offers shader warmup. [CONSTRUCTION-PLAN](../CONSTRUCTION-PACKAGES.md#decisions-before-construction) puts "shader variants" under rendering detail. [F4 content contract](../CONTRACTS.md#c05-assets-streaming-and-retirement--f4-with-w2-v1-and-p7) keys target/API/quality cooked products; [COMPOSITION](../COMPOSITION.md#packaging-and-dependencies) permits features to be absent from a build and live presentation transitions. No shared rule says which material × provider × pass × geometry × platform combinations must exist in a package, how a target build proves closure, or what happens when a live-selected variant is absent or still compiling.

**Concrete scenario:** the browser demo excludes visible cloud rendering and advanced shadow code at build time, but supports a live quality switch between two retained shadow tiers. A material and its masked shadow variant work in the editor's native preview. The web package strips a variant judged unused by the initial scene; after the switch or a streamed prefab activation, V1 requests it. F2 saw a valid provider plan, F4 admitted the material, yet V1 cannot render that pass or stalls to compile it during play. A generic "warm up shaders" command cannot determine the required closure unless F2/F4/V3/V1 agree on variants and allowed dynamic specialization.

**Alternatives and prior art:** (a) finite cooked variant closure for every supported target profile and declared live transition, with strict failure on a missing required variant; (b) smaller cooked baseline plus bounded runtime specialization/compilation and an explicit temporary fallback/loading policy; (c) dynamic branches for selected dimensions, trading runtime work for fewer variants. [Unity's shader variant guide](https://docs.unity.com/en-us/engine/6000.5/manual/materials-and-shaders/shaders/shader-troubleshooting/shader-reducing/shader-variants/shader-variant-stripping) documents profile-specific stripping and the risk of removing a runtime-required variant. [O3DE's shader build pipeline](https://www.docs.o3de.org/docs/atom-guide/dev-guide/shaders/shader-build-pipeline/) makes shader variants cooked assets. [Unreal shader development](https://dev.epicgames.com/documentation/unreal-engine/shader-development-in-unreal-engine) describes source-hashed shader caching and cooked material shaders. These are production precedents, not measured costs for this engine.

**Resolution/owners:** before I2/I3 depend on asset admission and profile switching, add a cross-module **variant availability contract**: declaration of variant dimensions and pass requirements; build-profile closure and stripping rule; cache/product identity; supported runtime specialization/fallback; strict diagnostic when content or a transition lacks a required variant; and measured compile/stall/size evidence. D2 may choose WGSL/native source, translation and compilation strategy, but D1's F4/product/profile contract must reserve the dependency and failure semantics. Owners: F2, F4, V1/V3, T1/T2 and platform adapters.

### CD4 — File-based project changes and the durable operation journal lack a reconciliation point

**Classification:** missing source-authority decision, not a request for a collaboration server or a particular text format. **Prior claim/location:** [WORLD-CONTENT, import](../modules/WORLD-CONTENT.md#import-cook-and-runtime-residency) says the source package owns editable masters, import settings and stable IDs. [T1](../modules/TOOLS-DELIVERY.md#t1-one-operation-and-query-surface) gives editor/CLI/agent edits a durable desired revision and operation journal, while allowing direct file editing for source control through a watcher that submits an equivalent revision transaction. [C10](../CONTRACTS.md#c10-persistence-reproducibility-and-authored-operations--p7f3t1) defines the RecoveryRoot, and T2 records a source commit/dirty state. Exact serialization is rightly deferred, but the canonical **project source authority and change-set boundary** between filesystem/source control and T1's journal is not specified.

**Concrete scenario:** an editor has accepted a pending prefab edit at desired revision `R+1`. A developer checks out a Git branch containing coordinated changes to that prefab, its imported mesh metadata and a scene reference, possibly with an asset rename. The watcher observes file writes one by one. If each becomes a T1 operation, intermediate states may fail validation or trigger recooks and active publication before the checkout is complete. If the journal remains authoritative, a restart may reconstruct `R+1` over the checked-out files; if files are authoritative, the accepted operation may disappear or its idempotency result cease matching the source. A clean build after restart must name one coherent source snapshot, not an arbitrary mix of journal and filesystem revisions.

**Alternatives and prior art:** (a) versioned source files as the durable project authority, with T1 journal as a transaction/change log and atomic workspace snapshot import on external changes; (b) durable project database/journal as authority with explicit export/import to source control; (c) hybrid manifests that atomically select versioned source records while individual DCC masters remain files. [Unity asset metadata](https://docs.unity.com/en-us/engine/6000.6/manual/assets-and-media/import-assets/asset-metadata) demonstrates stable IDs/import settings alongside source files and the failure when metadata is lost; [Unity version-control guidance](https://docs.unity.com/en-us/engine/6000.5/manual/get-started/project-configuration/version-control/versioncontrolintegration) treats source plus metadata as the versioned set. [O3DE project configuration](https://www.docs.o3de.org/docs/user-guide/project-config/) exposes project configuration through both file editing and CLI. These sources expose merge/import constraints; they do not prove any serialization choice for this project.

**Resolution/owners:** D1 must choose the source of truth and define a whole-project or dependency-closed external change-set admission boundary, stable-ID/rename behavior, dirty editor versus checkout conflict response, and recovery after restart. T2 build provenance should identify the exact accepted project-source snapshot and unresolved external changes; the F4 cook should not activate a partial checkout. The specific text/binary file format, VCS product and merge UI can remain later details. Owners: T1, F3/F4, P7, W1/W2 and T2.

## Ordered correction

CD1, CD2 and CD4 should be resolved together at D0/D1's creation/runtime boundary: define a project-source snapshot, a play-session world/authority, and a code-change/restart rule. CD3 is a D1–D2 shared design input for F2/F4/V1/V3/T2 before the first complete cooked/rendered content path. Then run the construction plan's reference scene through edit → play → stop/apply-back → external source change → cook → web/mobile package with a declared shader/profile switch. The paper trace should show stable IDs, revisions, world epochs, exact product/variant closure, rollback/restart behavior and failure diagnostics; device experiments then test stated latency, size and performance predictions.
